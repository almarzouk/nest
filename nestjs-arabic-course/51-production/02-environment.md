# Environment Variables

## الهدف من هذا الدرس

قراءة الإعداد من بيئة التشغيل مع تحقق عند الإقلاع، وإبقاء الأسرار خارج Git وخارج صورة Docker.

## المشكلة التي يحلها

عنوان قاعدة مكتوب في المصدر يصل إلى المستودع. ملف `.env` منسوخ إلى الصورة يتجمد مع الإصدار الخطأ. غياب `DATABASE_URL` الذي يُكتشف عند أول طلب يفتح المنفذ ثم يسقط. التحقق عند الإقلاع يرفض العملية قبل `listen`.

## الفكرة ببساطة

`ConfigModule.forRoot` يحمّل البيئة ويمكن أن يقرأ `.env` في التطوير فقط. في الإنتاج المنصة تحقن المتغيرات ولا تعتمد على ملف داخل الصورة. دالة `validate` ترمي إن غاب متغير أو فسد رقم. `getOrThrow` عند الاستعمال يمنع سلسلة فارغة صامتة.

## التعريف التقني

```ts
import { Module } from '@nestjs/common';
import { ConfigModule } from '@nestjs/config';

@Module({
  imports: [
    ConfigModule.forRoot({
      isGlobal: true,
      ignoreEnvFile: process.env.NODE_ENV === 'production',
      validate: (env: Record<string, unknown>) => {
        if (!env.DATABASE_URL || typeof env.DATABASE_URL !== 'string') {
          throw new Error('DATABASE_URL مطلوب');
        }
        return env;
      },
    }),
  ],
})
export class AppModule {}
```

`ignoreEnvFile` في الإنتاج يمنع ملفًا قديمًا داخل مجلد العمل من تغطية متغيرات المنصة. في التطوير اترك القراءة من `.env` غير المتتبع.

لا تطبع `config.get('DATABASE_URL')` في سجل.info. إن احتجت تشخيصًا فاطبع المضيف فقط بعد التحليل لا كلمة السر.

`.env.example` يسرد المفاتيح بلا قيم سرية حتى يعرف الفريق الأسماء. القيم الحقيقية في مدير أسرار أو في بيئة Compose المحلية غير المرفوعة.

`forRoot` مرة في الجذر كما في فصل الوحدات الديناميكية. الميزات تحقن `ConfigService`.

أرقام المنافذ: حوّل `PORT` بـ `Number` وتحقق من المجال. سلسلة `"3000"` تعمل مع `listen` أحيانًا وتفشل في حساب آخر.

## Mental Model

```text
تطوير: .env غير متتبع
إنتاج: بيئة المنصة، ignoreEnvFile
إقلاع: validate ترمي قبل listen
الكود: getOrThrow لا افتراض صامت لسر
```

## أبسط مثال

```ts
const port = Number(process.env.PORT ?? 3000);
await app.listen(port, '0.0.0.0');
```

مع التحقق أن `PORT` إن وُجد فهو رقم. `DATABASE_URL` بلا افتراض `localhost` في الإنتاج. الافتراض المحلي يختبئ في `.env` التطويري فقط.

## شرح المثال

المنصة تضع `PORT` أحيانًا. تجاهله يجعل النشر على منفذ لا يراه الوكيل. `0.0.0.0` مع Docker كما سبق. التحقق المركزي في `validate` أفضل من عشر `getOrThrow` بلا رسالة موحّدة، و `getOrThrow` يبقى عند المزود الذي لا يُبنى إن فشل التحقق أصلًا.

## ماذا يحدث داخليًا؟

1. عملية Node ترث البيئة من systemd أو Docker أو المنصة.
2. `forRoot` يقرأها وقد يدمج ملفًا في التطوير.
3. `validate` ترمي فيوقف الإقلاع.
4. `ConfigService` يوزع القيم على المصانع و `forRootAsync`.
5. تغيير السر في المنصة يحتاج إعادة تشغيل أو آلية تحديث لا قراءة ملف داخل الصورة القديمة.
6. سجل البناء في CI لا يطبع الأسرار في الأمر `echo`.

## مثال عملي

مفاتيح دنيا: `DATABASE_URL` و `REDIS_URL` و `PORT`. في Compose الأسماء `postgres` و `redis`. على المنصة عناوين مُدارة. نفس المفاتيح. `.env.example` يوثقها. اختبار الوحدة يمرر `useValue` للإعداد ولا يقرأ ملفك الشخصي.

## أخطاء شائعة

- سر في `forRoot({ url: 'postgres://user:pass@...' })` داخل Git.
- `.env` في `COPY` الصورة.
- `ignoreEnvFile` مطفأ في الإنتاج فيغلب ملف قديم.
- طباعة البيئة كاملة عند الإقلاع.
- افتراض `localhost` إن غاب المتغير.

## متى نستخدمه؟

لكل عنوان وسر ومهلة تختلف بين الأجهزة.

## متى لا نستخدمه؟

لا تضع علم ميزة يتغير كل طلب في البيئة. ذلك إعداد يُنشر أو قاعدة. البيئة تُقرأ عند الإقلاع.

## مقارنة

| المصدر | التطوير | الإنتاج |
| --- | --- | --- |
| `.env` | نعم، غير متتبع | لا يُعتمد عليه |
| بيئة العملية | ممكن | المصدر |
| قيمة في المصدر | ثوابت غير سرية | لا أسرار |

## أسئلة مراجعة

- أين تعيش قيمة الإنتاج؟
- ماذا لا يُطبع في السجل؟
- متى `getOrThrow`؟

## الخلاصة

المتغيرات من بيئة التشغيل، تُتحقق عند الإقلاع، ولا تدخل الصورة ولا Git. التطوير يقرأ `.env` محليًا، والإنتاج يتجاهل ذلك الملف.

## ماذا بعد؟

Logging في الإنتاج: ماذا يُكتب بعد أن منعت طباعة الأسرار.
