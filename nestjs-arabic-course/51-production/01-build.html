Build

الهدف من هذا الدرس

إنتاج مجلد dist من TypeScript وتشغيله بـ node، وهو ما تشغّله الصورة والعملية في الإنتاج لا وضع المراقبة.

المشكلة التي يحلها

start:dev يبقي المترجم والمراقب ويعيد التشغيل عند الحفظ. على الخادم لا يوجد حفظ، والعملية الزائدة تستهلك ذاكرة وتخفي خطأ التجميع حتى الطلب. البناء خطوة منفصلة تفشل CI قبل النشر إن كان النوع خاطئًا.

الفكرة ببساطة

npm run build يشغّل nest build الذي يستعمل tsc حسب nest-cli.json و tsconfig.build.json. الناتج dist/main.js. التشغيل node dist/main.js أو سكربت start:prod. لا تشغّل ts-node في الإنتاج.

التعريف التقني

في قالب Nest:

npm run build
node dist/main.js

package.json النموذجي:

{
  "scripts": {
    "build": "nest build",
    "start:prod": "node dist/main.js"
  }
}

tsconfig.build.json يستبعد الاختبارات حتى لا تُترجم إلى dist. المسارات في المخرجات تحترم إعداد الوحدة. هذه الدورة تستعمل استيراد ESM بامتداد .js في المصدر، والمخرج يجب أن يطابق ما تشغّله Node. إن كان المشروع commonjs فالمخرج require. لا تخلط شكل الاستيراد في dist مع شكل تشغيلك.

Prisma: prisma generate قبل البناء حتى توجد الأنواع. migrate deploy ليس جزءًا من nest build.

المصدر والخرائط: خريطة المصدر تساعد السجلات وقد تكشف البنية. لا تنشر src إن اكتفيت بـ dist. لا تنشر .env.

CI يشغّل npm ci ثم npm run build ثم الاختبارات ثم يبني الصورة من الناتج أو يبني داخل Docker كما سبق. فشل build يوقف الخط.

Mental Model

src/*.ts -> nest build -> dist/*.js -> node dist/main.js
start:dev يبقى على جهازك

أبسط مثال

npm ci
npx prisma generate
npm run build
node dist/main.js

على جهاز الإنتاج أو في مرحلة Docker. المتغير PORT من البيئة. إن خرج الأمر فورًا فاقرأ الخطأ في الطرفية قبل أن تعيد start:dev.

شرح المثال

npm ci من القفل يعطي نفس الشجرة التي بناها CI. generate يكتب العميل. build يكتب dist. node يشغّل الملف الذي صار نقطة الدخول. راقب أن main في التشغيل هو dist/main.js لا src/main.ts.

ماذا يحدث داخليًا؟

  1. nest build يقرأ الإعداد ويشغّل المترجم.
  2. ملفات الاختبار المستبعدة لا تظهر في dist.
  3. Node يحمّل dist/main.js ويشغّل bootstrap.
  4. لا مراقب ملفات ولا إعادة تشغيل عند استثناء غير ممسوك إلا إذا أضفت مدير عملية.
  5. تغيير TypeScript بلا بناء يترك الخادم على النسخة القديمة.
  6. الصورة التي نسخت dist فقط تشغّل هذه الخطوة الأخيرة.

مثال عملي

أضف في CI:

npm ci
npm run build
npm test

ثم ابنِ الصورة التي تعيد البناء داخلها أو تنسخ dist من العامل. لا تعتمد على مجلد dist مرفوع في Git. الناتج يُولد. أضف dist إلى .gitignore إن لم يكن كذلك، واستثنه من صورة التطوير فقط عبر البناء داخل Docker.

أخطاء شائعة

  • start:dev في وحدة systemd أو في CMD.
  • نسيان prisma generate في CI النظيف.
  • تشغيل dist قديم بعد سحب المصدر.
  • رفع node_modules من جهازك إلى الخادم.
  • استيراد .ts في المخرج.

متى نستخدمه؟

في كل نشر وكل صورة إنتاج.

متى لا نستخدمه؟

أثناء تحرير الدرس على الجهاز حيث المراقبة أسرع. لا تبنِ لكل حفظ يدويًا إن كان start:dev يعمل محليًا.

مقارنة

الأمر المترجم يعيد التشغيل الإنتاج
start:dev نعم نعم لا
build ثم node dist/main.js وقت البناء لا نعم
start:debug نعم مع مفتش لا

تمارين

تمرين سهل

ما الملف الذي تشغّله Node بعد البناء الناجح؟

الحل

dist/main.js.

تمرين متوسط

لماذا يفشل CI النظيف إن نسيت prisma generate قبل build؟

الحل

لأن الأنواع والعميل غير موجودين في شجرة نظيفة، والتجميع يستوردهما.

تمرين متقدم

لماذا لا يُرفع dist في Git بدل خطوة البناء؟

الحل

الناتج يُولد من المصدر والقفل. رفعه يفرّق عن المصدر ويخفي أن البناء لم يعد قابلًا للتكرار.

أسئلة مراجعة

  • أي سكربت يكتب dist؟
  • ماذا يُستبعد من بناء الإنتاج عادة؟
  • أين تبقى start:dev؟

الخلاصة

الإنتاج npm run build ثم node dist/main.js. البناء يفشل قبل النشر إن تعطل النوع، والمراقبة تبقى على جهاز التطوير.

ماذا بعد؟

Environment Variables: من أين تُقرأ الأسرار بعد أن صار التشغيل بلا ملف تطوير.
