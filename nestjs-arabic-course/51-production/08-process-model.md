# نموذج العملية

## الهدف من هذا الدرس

فهم أن نسخة Nest حلقة أحداث واحدة، وأن التوسع الطبيعي نسخ متعددة بلا حالة في الذاكرة، لا خيوط لكل طلب.

## المشكلة التي يحلها

تشغيل `cluster` أو PM2 بعدد الأنوية يُظن أنه يضاعف الصحة بينما الجلسة في مصفوفة داخل العملية. الطلب التالي يصل إلى نسخة أخرى فلا يرى الجلسة. عمل ثقيل متزامن يسد الحلقة في كل النسخ إن نسخته كما هو. النموذج الصحيح: عملية واحدة خفيفة لكل نسخة، حالة مشتركة في Redis أو القاعدة، وتوسع بعدد الحاويات.

## الفكرة ببساطة

Node يشغّل JavaScript على خيط واحد مع حلقة أحداث. طلب ينتظر Prisma لا يسد الحلقة إن كان الانتظار إدخالًا وإخراجًا. حساب طويل متزامن يسدها. نسخة ثانية من الحاوية خلف Nginx `upstream` أو المنصة تضاعف القدرة على الانتظار المتوازي. الصق الجلسة إن بقيت في الذاكرة، أو انقلها إلى مخزن مشترك فتستغني عن الالتصاق.

## التعريف التقني

نسخة واحدة في الحاوية أمر `node dist/main.js`. المنصة تشغّل ثلاث حاويات من نفس الصورة. الوكيل يوزع. لا حالة طلب على حقل Singleton إلا إذا كانت لكل النسخ عبر Redis.

`Scope.REQUEST` لا يحل التعدد. هو يكرر الشجرة داخل النسخة ويزيد الكلفة التي قستها في فصل النطاقات.

وحدة `cluster` في Node أو وضع cluster في PM2 تشغّل عدة عمليات على آلة واحدة. ذلك مفيد عندما تملك آلة كبيرة ولا منصة حاويات. كل عامل عملية لها حلقتها. شارك الحالة خارجها. في Kubernetes فضّل نسخة حاوية على إدارة cluster داخل الحاوية حتى لا تتداخل إدارة العمليات.

عمل CPU ثقيل: عملية منفصلة أو طابور، لا طلب HTTP ينتظر الحلقة. سد الحلقة يفشل فحوصات الحياة إن كانت بطيئة.

الالتصاق (sticky) لازم لـ WebSocket في ذاكرة العملية أو لجلسة الذاكرة. بوابة WebSocket مع محول Redis تغني عن الالتصاق للبث بين النسخ.

## Mental Model

```text
نسخة = حلقة واحدة
I/O ينتظر بلا قفل الخيط
CPU متزامن يسد النسخة
التوسع = نسخ بلا حالة محلية
الجلسة في Redis لا في مصفوفة
```

## أبسط مثال

```nginx
upstream shop {
  server api1:3000;
  server api2:3000;
}
```

`proxy_pass http://shop;` بلا `ip_hash` إن كانت الجلسة في Redis. مع جلسة ذاكرة أضف الالتصاق واعلم أن سقوط النسخة يضيع جلساتها.

## شرح المثال

الطلب يذهب إلى إحدى النسختين. `PrismaService` في كل نسخة مجمع نحو نفس `postgres`. لا مجمع مشترك في الذاكرة بين النسختين. راقب عدد الاتصالات: نسختان ضرب حجم المجمع قد تتجاوز حد Postgres.

## ماذا يحدث داخليًا؟

1. كل حاوية عملية Node.
2. الوكيل يختار واحدة لكل اتصال حسب سياسته.
3. الانتظار على الشبكة يحرر الحلقة لطلب آخر في نفس النسخة.
4. حلقة `while` ثقيلة تؤخر الصحة والسجلات في تلك النسخة فقط.
5. إعادة النشر تستبدل النسخ تدريجيًا مع الإيقاف اللطيف.
6. حالة على الحقل تُفقد عند الاستبدال إن لم تكن في القاعدة.

## مثال عملي

ثلاث نسخ خلف المنصة، `trust proxy` ما زال 1 إن كانت قفزة واحدة أمامها. Redis للكاش والجلسة. لا `cluster` داخل الصورة. حد مجمع Prisma مضبوط حتى 3 × الحجم أقل من `max_connections`. عمل توليد PDF يذهب إلى طابور لا إلى `POST` المتزامن.

## أخطاء شائعة

- جلسة مصفوفة مع نسختين بلا التصاق.
- `cluster` داخل كل حاوية فيتضاعف العدد بلا قصد.
- طلب CPU يسد فحوصات الحياة.
- مجمع قاعدة غير محسوب مع عدد النسخ.
- `Scope.REQUEST` كخطة توسع.

## متى نستخدمه؟

عند زيادة الحمل: أضف نسخة بلا حالة، أو أخرج العمل الثقيل من الحلقة.

## متى لا نستخدمه؟

لا تضف نسخًا قبل قياس أن الحلقة مشغولة بالانتظار لا باستعلام بلا فهرس. الفهرس أرخص من نسخة رابعة أحيانًا.

## مقارنة

| الأسلوب | الحالة | متى |
| --- | --- | --- |
| نسخة واحدة | في العملية | حمل يناسب حلقة |
| نسخ متعددة | Redis أو القاعدة | توسع أفقي |
| cluster على الآلة | نفس شرط الحالة | بلا منسق حاويات |
| التصاق | ذاكرة محلية | جلسة أو مقبس بلا محول مشترك |

## أسئلة مراجعة

- ماذا تضاعف النسخة الثانية؟
- أين تضع الجلسة؟
- لماذا الحلقة المسدودة تسقط الصحة؟

## الخلاصة

كل نسخة حلقة واحدة تتوسع بالانتظار لا بالحساب الثقيل. شغّل نسخًا بلا حالة مشتركة في الذاكرة، واحسب اتصالات القاعدة، ولا تستخدم نطاق الطلب كخطة توسع.

## ماذا بعد؟

أمثلة بناء وبيئة ووكيل، ثم فحوصات الصحة التي يسحب بها الوكيل النسخة المريضة.
