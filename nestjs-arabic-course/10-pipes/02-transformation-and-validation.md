# Transformation و Validation

## الهدف من هذا الدرس

تمييز وظيفتي الأنبوب: تحويل شكل القيمة، أو الحكم عليها ثم تمريرها أو رفضها.

## المشكلة التي يحلها

خلط الوظيفتين في صنف واحد بلا اسم يجعل الفشل غامضًا: هل `NaN` نتيجة تحويل أم رفض؟ الصفحة تفصل الحالتين حتى تختار الأنبوب باسمه.

## الفكرة ببساطة

أنبوب التحويل يرجع قيمة من نوع آخر، مثل نص إلى عدد صحيح. أنبوب التحقق يرجع القيمة نفسها إن صلحت، ويرمي إن فسدت. أنبوب واحد قد يفعل الاثنين، والأوضح أن يكون الاسم صادقًا مع الأثر الأساسي.

## التعريف التقني

من صفحة Pipes:

- Transformation: تحويل المدخل إلى الشكل المطلوب، والمثال الشائع من نص إلى عدد.
- Validation: تقييم المدخل. إن كان صالحًا يمر كما هو، وإلا يُرمى استثناء.

في الحالتين يعمل الأنبوب على المعاملات المتجهة إلى المعالج، قبل الاستدعاء. الاستثناء من أنبوب تحقق يمنع تنفيذ الدالة. هذا سبب توصية الصفحة بأن يكون التحقق من بيانات الخارج على حدود النظام هنا.

`ParseIntPipe` المدمج تحويل وفحص معًا: إما عدد صحيح أو `400`. درسه التفصيلي لاحق. هنا القاعدة: إن رجعت قيمة جديدة فأنت حوّلت. إن رميت فأنت رفضت. إرجاع القيمة بلا تغيير بعد فحص ناجح هو تحقق خالص.

## Mental Model

```text
تحويل:   "18"  →  18
تحقق:    "INV-18" إن طابق النمط → "INV-18"
         "18" إن خالف النمط → BadRequestException
```

الخدمة في الحالة الأولى تستلم عددًا. في الثانية تستلم النص نفسه أو لا تُستدعى.

## أبسط مثال

```ts
import {
  BadRequestException,
  Injectable,
  type PipeTransform,
} from '@nestjs/common';

@Injectable()
export class InvoiceCodePipe implements PipeTransform<string, string> {
  transform(value: string): string {
    if (!/^INV-\d+$/.test(value)) {
      throw new BadRequestException('Invoice code must look like INV-18');
    }
    return value;
  }
}
```

هذا تحقق: النجاح يعيد النص نفسه.

```ts
@Injectable()
export class CentsPipe implements PipeTransform<string, number> {
  transform(value: string): number {
    const cents = Number(value);
    if (!Number.isInteger(cents)) {
      throw new BadRequestException('cents must be an integer');
    }
    return cents;
  }
}
```

هذا تحويل مع رفض عند الفشل: النص `"2500"` يصبح العدد `2500`.

## شرح المثال

- `InvoiceCodePipe` لا يبني كائنًا جديدًا. القاعدة شكل الرمز.
- `CentsPipe` يغيّر نوع القيمة التي يراها المعالج. الخدمة تجمع قروشًا كأعداد لا كنصوص.
- الرمي في الاثنين `BadRequestException`، والرمز الافتراضي `400`.
- لا قاعدة بيانات في أي منهما. جلب فاتورة بالرمز أنبوب تحويل من نوع آخر، مسموح، لكنه يخفي استعلامًا داخل المعامل. أبقِ الجلب في الخدمة حتى يبقى الأنبوب حدًا رخيصًا.

## ماذا يحدث داخليًا؟

`transform` تُستدعى بالقيمة الخام. ناتجها يستبدل المعامل قبل الدالة. الصفحة تقول ذلك صراحة عن حالة التحويل: ما يرجع من `transform` يحل محل القيمة السابقة.

في التحقق الخالص، الإرجاع هو القيمة الأصلية بعد الحكم. الإطار لا يفرّق بين النوعين بواجهة ثانية. الفرق في ما تفعله داخل الدالة.

إن حوّلت ثم فحصت في الصنف نفسه، فشل الفحص يرمي والقيمة المحوّلة لا تصل. نجاحه يمرر القيمة الجديدة. `ParseIntPipe` المدمج يعمل بهذا الشكل، ولذلك يُذكر في الصفحتين معًا.

الأنبوب لا يغيّر معاملات أخرى. `CentsPipe` على `amount` لا يلمس `code`.

## مثال عملي

`POST /invoices` فيه حقل استعلام `cents=2500` ومسار لاحق `GET /invoices/INV-18`.

- `CentsPipe` على الاستعلام يجعل الخدمة تستلم `2500` لا `"2500"`.
- `InvoiceCodePipe` على المسار يرفض `GET /invoices/drop` قبل الخدمة.
- Middleware التتبع يعمل في الحالتين ولا يعرف الفرق. الحارس إن وجد يعمل قبلهما ولا يحوّل `cents`.

## أخطاء شائعة

- تسمية صنف `ValidateCentsPipe` بينما يرجع عددًا. الاسم يقول تحققًا والأثر تحويل. سمِّه بما يرجع أو بما يرفض.
- إرجاع `null` عند الفشل بدل الرمي. المعالج يعمل بقيمة فارغة ويظن أن الطلب سليم.
- فحص الدور داخل أنبوب التحويل. السماح للحارس.
- تحويل كيان كامل من قاعدة البيانات داخل الأنبوب ثم نسيان أن الفشل الشبكي يصبح خطأ معامل.

## متى نستخدمه؟

التحويل حين يكون نوع المعامل في الدالة غير نوع السلك، والنص إلى عدد أشهر مثال. التحقق حين تكون القاعدة «القيمة إما مقبولة كما هي أو مرفوضة».

## متى لا نستخدمه؟

لتغيير جسم الرد، أو لختم الطلب، أو لقاعدة تحتاج عدة حقول من طبقات مختلفة مع قرار صلاحية. عدة حقول في DTO ستجتمع في `ValidationPipe` لاحقًا، ما زالت أنبوبًا، لكن موضوعها كائن لا نص مسار واحد.

## مقارنة

| | تحويل | تحقق |
| --- | --- | --- |
| عند النجاح | قيمة جديدة غالبًا | القيمة نفسها |
| عند الفشل | استثناء إن كان التحويل مستحيلًا | استثناء |
| مثال هذا الدرس | `CentsPipe` | `InvoiceCodePipe` |
| مدمج لاحق | `ParseIntPipe` | `ValidationPipe` |

## تمارين

### تمرين سهل

أنبوب يرجع `value.trim()`. هل هذا تحويل أم تحقق خالص؟

<details>
<summary>الحل</summary>

تحويل. النص الذي يصل إلى المعالج غير النص الخام إن وُجدت مسافات. لا يوجد رمي.

</details>

### تمرين متوسط

تريد رفض `cents` السالب وتمرير الموجب كعدد. أي أثرين يجتمعان في `transform`؟

<details>
<summary>الحل</summary>

تحويل من نص إلى عدد، ثم تحقق: إن كان سالبًا ارمِ `BadRequestException`، وإن كان موجبًا أرجع العدد.

</details>

### تمرين متقدم

زميل أعاد كائن الفاتورة من قاعدة البيانات داخل الأنبوب حتى «تصل الدالة جاهزة». ما الحد الذي كسره بالنسبة إلى خدمة الفواتير؟

<details>
<summary>الحل</summary>

الأنبوب صار طبقة جلب لا حدًا على القيمة. فشل القاعدة وشكل الاستعلام واختبار المعالج كلها تعلّقت بمعامل. الإبقاء على الرمز كنص مفحوص، والجلب داخل `InvoicesService`، يبقي كل مسؤولية في طبقتها.

</details>

## أسئلة مراجعة

- ماذا يرجع أنبوب التحقق عند النجاح؟
- ماذا يفعل أنبوب التحويل بالقيمة السابقة؟
- لماذا يمنع الرمي تشغيل المتحكم؟
- أي الوظيفتين يغلب على `InvoiceCodePipe`؟

## الخلاصة

التحويل يستبدل القيمة. التحقق يمررها أو يرمي. الواجهة واحدة، والاسم والأثر يجب أن يتفقا. الحدود الرخيصة على معامل واحد تعيش هنا، والجلب في الخدمة.

## ماذا بعد؟

الدرس التالي يعرض الأنابيب المدمجة في `@nestjs/common` حتى لا تكتب `CentsPipe` إن كان `ParseIntPipe` يكفي.
