Idempotency

الهدف من هذا الدرس

تصميم POST /books في رف بحيث إعادة نفس الطلب من العميل لا تنشئ كتابين، باستخدام مفتاح يرسله العميل ويخزّن الخادم نتيجته.

المشكلة التي يحلها

الجوال أرسل إنشاء كتاب وانقطع الرد. أعاد الإرسال. القاعدة فيها صفان بنفس العنوان. الرمز 201 في المرتين صحيح شكليًا وخاطئ تجاريًا. التحقق من «عنوان مكرر» لا يكفي لأن العنوان نفسه قد يكون مقصودًا لكتابين.

الفكرة ببساطة

العميل يولّد مفتاحًا لكل محاولة إنشاء ويضعه في Idempotency-Key. الخادم ينفذ مرة واحدة لكل مفتاح ضمن نطاق المستخدم، ويحفظ الوضع والجسم. الإعادة ترى نفس النتيجة. هذا عقد تصميم. الحزمة @nestjs/idempotency في فصل الاعتمادية تنفذه لاحقًا بـ @Idempotent()؛ هنا نثبت معنى المفتاح.

التعريف التقني

المفتاح خاص بعملية واحدة لا بكل المستخدم إلى الأبد. نفس المفتاح مع جسم مختلف خطأ عقد (409) لا تنفيذ ثانٍ. نفس المفتاح مع نفس المعنى يعيد الرد المخزن، بما فيه 201 الأول، ولا ينشئ صفًا. المفتاح يسافر في الترويسة لا في الجسم حتى تبقى إعادة المحاولة نسخة طبق الأصل. نطاق المفتاح يتضمن هوية العميل حتى لا يعيد مفتاح شخص نتيجة شخص آخر. GET و PUT بمعرّف ثابت و DELETE لمعرّف ثابت تحمل تكرارًا آمنًا من معنى HTTP؛ POST الإنشاء هو الذي يحتاج المفتاح لأنه كل نداء قد يعني فردًا جديدًا.

Mental Model

المحاولة 1: مفتاح K → إنشاء b1 → خزّن 201
المحاولة 2: مفتاح K → أعد 201 و b1
مفتاح K وجسم مختلف → 409

أبسط مثال

export interface StoredReply {
  status: number;
  body: unknown;
}

export class CreateBookLedger {
  private readonly replies = new Map<string, StoredReply>();

  replay(userId: string, key: string) {
    return this.replies.get(`${userId}:${key}`);
  }

  save(userId: string, key: string, reply: StoredReply) {
    this.replies.set(`${userId}:${key}`, reply);
  }
}

شرح المثال

  • المفتاح المركب userId + key هو النطاق.
  • replay يعيد الرد كما حُفظ، لا يعيد تشغيل create.
  • الذاكرة هنا للشرح. الإنتاج مخزن يبقى بعد إعادة تشغيل العملية، وإلا ضاع الحماية.

ماذا يحدث داخليًا؟

  1. العميل يولّد UUID للمحاولة ويثبته عبر إعادات هذه المحاولة فقط.
  2. الخادم يبحث عن الرد. إن وجده يكتبه كما هو، مع 201 إن كان الأول إنشاءً.
  3. إن لم يجده، ينشئ الكتاب ويحفظ الرد ثم يرسله.
  4. طلبان متزامنان بنفس المفتاح يحتاجان قفلًا أو قيدًا فريدًا على المفتاح حتى لا يمر كلاهما من «غير موجود».
  5. جسم مختلف لنفس المفتاح يرفض. التنفيذ الثاني بمعنى آخر يكسر وعد الإعادة.

مثال عملي

import { Body, Controller, Headers, HttpCode, Post } from '@nestjs/common';
import { CreateBookLedger } from './create-book.ledger.js';

@Controller('books')
export class BooksCreateController {
  constructor(private readonly ledger: CreateBookLedger) {}

  @Post()
  @HttpCode(201)
  create(
    @Headers('idempotency-key') key: string,
    @Body() body: { title: string },
  ) {
    const userId = 'u1';
    const prior = this.ledger.replay(userId, key);
    if (prior) return prior.body;
    const book = { id: 'b1', title: body.title };
    this.ledger.save(userId, key, { status: 201, body: book });
    return book;
  }
}

المثال يختصر القفل ومقارنة الجسم. العقد الكامل: بلا ترويسة على هذا المسار → 400 لأن الإعادة غير آمنة، ومفتاح معاد بجسم مختلف → 409. @HttpCode(201) يبقى للنداء الأول؛ الإعادة يجب أن تعيد 201 أيضًا لا 200، لأن العميل يقرأ الرمز. إن صعب إرجاع الرمز المخزن من return فقط، اكتب الوضع صراحة من السجل. صفحة Idempotency keys لاحقًا تفعل ذلك داخل المعترض.

أخطاء شائعة

  • اشتقاق المفتاح من العنوان فقط، فيمتنع كتابان مقصودان بنفس الاسم.
  • تخزين المفتاح بلا هوية المستخدم.
  • تنفيذ الإنشاء ثم حفظ المفتاح بعد إرسال الرد، فيضيع الحفظ عند الانقطاع وتُنشأ نسخة عند الإعادة.
  • اعتبار Idempotency-Key بديلًا عن قيد ISBN. القيد قاعدة كتالوج، والمفتاح قاعدة نقل.

متى نستخدمه؟

على POST الذي ينشئ أثرًا لا يُستنتج من المعرّف في المسار: إنشاء كتاب، إنشاء طلب، خصم رصيد.

متى لا نستخدمه؟

على GET. وعلى PUT /books/b1 عندما الاستبدال الكامل لنفس المعرّف أصلًا يعيد نفس الحالة. ولا كمفتاح تفرضه أنت من عنوان IP.

مقارنة

النداء التكرار بلا مفتاح مع المفتاح
GET /books آمن غير لازم
PUT /books/b1 بنفس الجسم يستقر على نفس الفرد غالبًا غير لازم
POST /books كتاب جديد كل مرة نفس الكتاب

تمارين

تمرين سهل

الجوال أعاد POST /books بنفس Idempotency-Key بعد 201. كم صفًا جديدًا يُسمح به؟

الحل

صفر. الرد الثاني هو الرد المخزن للأول، بما فيه id الأصلي.

تمرين متوسط

نفس المفتاح وصل مع title مختلف. ما الرمز، ولماذا لا ننفذ العنوان الجديد؟

الحل
  1. المفتاح يعد بنتيجة واحدة. تنفيذ الجسم الثاني يعني أن إحدى الإعادات كانت ستنجح بمعنى غير الذي خزنه العميل.

تمرين متقدم

طلبان بنفس المفتاح وصلا معًا قبل أي حفظ. ماذا يمنع كتابين؟

الحل

قيد فريد على (userId, key) أو قفل حول «اقرأ ثم أنشئ». الفحص في الذاكرة بلا ذرية يمر من الفرعين معًا. الخاسر يرى الصف الفائز ويعيد نفس الرد.

أسئلة مراجعة

  • من يولّد المفتاح: العميل أم الخادم؟
  • لماذا لا يكفي تشابه العنوان؟
  • ماذا يُعاد في الإعادة الناجحة: تنفيذ جديد أم الرد المخزن؟
  • أي طلبات HTTP لا تحتاج المفتاح عادة؟

الخلاصة

Idempotency-Key يربط محاولات إنشاء واحدة بنتيجة واحدة داخل نطاق المستخدم. الإعادة تعيد نفس 201 ونفس id. جسم مختلف لنفس المفتاح تعارض.

ماذا بعد؟

القائمة التي نجح إنشاؤها تحتاج عقد صفحة: ماذا يعني page وما شكل الفراغ. الدرس التالي pagination كعقد لا كمعامل حر.
