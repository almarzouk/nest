# الإصدار داخل التصميم

## الهدف من هذا الدرس

كتابة الإصدار كجزء من عقد رف المكتوب للعميل: ماذا يثبت بين النسختين، ماذا يتغير في كتاب السعر، وكيف يُعلَن الإيقاف، بعد أن صارت الآلية معروفة في فصل Versioning.

## المشكلة التي يحلها

الفريق فعّل `VersioningType.URI` ونشر `/v2/books` بجسم مختلف بلا جدول فروقات. تطبيق الجوال ما زال على v1، والتوثيق يعرض v2 فقط. عميل ثالث يخلط 201 وشكل الخطأ بين النسختين لأنه ظن أن الإصدار يغيّر «كل شيء».

## الفكرة ببساطة

وثيقة العقد لكل نسخة تقول: المسارات، الرموز، شكل القائمة، شكل الخطأ، وشكل الكتاب. النسخة الجديدة تنسخ القديمة ثم تسجّل سطر الكسر فقط. ما لم يُذكر في السطر يبقى. الإيقاف تاريخ ومقياس نداءات لا حذف صامت.

## التعريف التقني

الآلية من `enableVersioning` تختار الدالة. التصميم يختار الفرق. في رف، v1 فيها `price` عددًا بالسنت و v2 فيها `price.amount` و `price.currency`. الرموز لا تتغير بين النسختين: القائمة الفارغة 200 والفرد الغائب 404 والإنشاء 201. شكل الخطأ نفسه (`statusCode`, `code`, `message`) حتى لا تتفرع الواجهة. إن اضطررت لكسر الشكل، فهذا سطر صريح في ملاحظات النسخة لا أثر جانبي. `defaultVersion` قرار توافقي مؤقت يُكتب في العقد («غياب النسخة يعني v1 حتى تاريخ») لا إعداد ينساه المشغّل.

## Mental Model

```text
عقد مشترك: أسماء /books، 200 للقائمة الفارغة، 201 للإنشاء، شكل الخطأ
عقد v1: price عدد
عقد v2: price كائن
الإيقاف: بعد ما تصل نداءات v1 إلى العتبة المتفق عليها
```

## أبسط مثال

```text
GET /v1/books/b1 → { id, title, price: 2500 }
GET /v2/books/b1 → { id, title, price: { amount: 2500, currency: "SAR" } }
كلاهما 404 بنفس code: book_not_found إن غاب b1
```

## شرح المثال

- الكسر الوحيد نوع `price`.
- `code` مستقر حتى يبرمج العميل ضد الخطأ وهو يهاجر.
- لا حقول v2 تظهر بصمت داخل v1.

## ماذا يحدث داخليًا؟

1. وثيقة OpenAPI تُنشر لكل نسخة أو بعلامة الإصدار التي اخترتموها (مسار أو ترويسة أو `Accept`).
2. المتحكم يستدعي `toV1` أو `toV2` على نفس النموذج.
3. اختبار عقد يقارن المفاتيح. إضافة مفتاح في v1 الحالية قد تكسر عميلًا صارمًا؛ إن كان العقد يسمح بالإضافة فذلك مكتوب.
4. مقياس العداد على كل نسخة.
5. حذف v1 يتم عندما يقول المقياس ذلك، ويُحذف التمثيل من الوثيقة في نفس التغيير.

## مثال عملي

سطور ملاحظات النسخة التي تُراجع مع الـ PR:

```text
v2
- price: number → { amount: number, currency: string }
- يبقى: 201 عند POST /books، 200 مع data: [] للقائمة، Idempotency-Key على الإنشاء
- شكل الخطأ لم يتغير
- v1 مدعومة إلى أن تنخفض نداءاتها تحت العتبة أسبوعين
```

`POST /v2/books` ما زال 201 مع جسم v2 لا جسم v1. المفتاح يمنع التكرار داخل النسخة التي ناداها العميل. إعادة المحاولة يجب أن تضرب نفس النسخة، لأن الجسم المخزن شكل عقد تلك النسخة.

## أخطاء شائعة

- اعتبار رقم الإصدار غلافًا للدالة مع تغيير الرموز «لأننا هنا».
- توثيق v2 فقط.
- `defaultVersion` في الإنتاج بلا جملة في العقد، فيبقى الجوال على القديم إلى الأبد من غير أن يعرف.
- تخزين رد Idempotency من v1 وإعادته لطلب v2 بنفس المفتاح.

## متى نستخدمه؟

عند كل كسر اتفقتم أنه يستحق نسخة في درس «لماذا الإصدارات». الوثيقة تُحدَّث في نفس التغيير الذي يضيف المتحكم.

## متى لا نستخدمه؟

لا تفتح v2 لتغيير جملة `message` إن كان العميل يبرمج على `code`. ولا توثّق إصدارًا لكل بيئة (اختبار/إنتاج). البيئة ليست عقدًا.

## مقارنة

| البند | يتغير بين v1 و v2 في رف | يبقى |
| --- | --- | --- |
| `price` | نعم | |
| قائمة فارغة | | 200 و `data: []` |
| إنشاء | | 201 |
| مفاتيح الخطأ | | `statusCode`, `code`, `message` |
| اسم المجموعة | | `books` |

## تمارين

### تمرين سهل

هل انتقال `price` إلى كائن يبرر تغيير 201 إلى 200 في v2؟

<details>
<summary>الحل</summary>

لا. الإنشاء ما زال إنشاءً. سطر الكسر هو شكل السعر فقط. تغيير الرمز كسر إضافي بلا سبب في هذا التصميم.

</details>

### تمرين متوسط

العميل أعاد `Idempotency-Key` نفسه على `/v2/books` بعد ما أنشأ على `/v1/books`. ماذا يجب أن يحدث؟

<details>
<summary>الحل</summary>

النسختان عقدان. المفتاح يُخزَّن ضمن النسخة (أو يعاد التنفيذ على v2 كأنه مفتاح جديد إن لم يُرَ هناك). لا يُعاد جسم v1 لطلب v2. نطاق المفتاح يتضمن النسخة.

</details>

### تمرين متقدم

اكتب شرط حذف v1 قابلًا للمراجعة.

<details>
<summary>الحل</summary>

بعد أسبوعين متتاليين نداءات v1 تحت العتبة المتفق عليها، يُحذف متحكم v1 و `toV1` من الوثيقة، ويصبح طلب `/v1/books` 404. قبل ذلك تبقى v1 بخمسة الرموز وشكل الخطأ حتى لو تغيّر `price` في v2.

</details>

## أسئلة مراجعة

- ماذا يثبَّت في العقد المشترك بين النسختين؟
- أين يُكتب سطر الكسر؟
- لماذا `defaultVersion` جملة عقد لا إعداد صامت؟
- هل شكل الخطأ يتغير تلقائيًا مع رقم النسخة؟

## الخلاصة

الإصدار في التصميم جدول فروقات صغير فوق عقد مشترك: رموز، قائمة، خطأ، وأسماء. في رف يتغير شكل `price` ويبقى 200 للقائمة الفارغة و 201 للإنشاء. حذف النسخة قرار مقياس لا أثر جانبي لنشر.

## ماذا بعد؟

عقد HTTP مكتوب. الفصل التالي يحمي واجهة GraphQL عندما يطلب العميل شجرة كتب أغلى مما تحتمل العملية.
