Rate Limiting و @nestjs/throttler

الهدف من هذا الدرس

وضع سقف لعدد الطلبات على الدخول وقراءة القوائم عبر @nestjs/throttler حتى يبطؤ التخمين والضغط.

المشكلة التي يحلها

POST /auth/sign-in بلا سقف يسمح بتجربة كلمات المرور بسرعة. GET /posts المفتوح يمكن أن يُطلب آلاف المرات في ثانية. الحظر داخل الخدمة بعد نجاح المصادقة لا يحمي مسار الدخول أصلًا.

الفكرة ببساطة

ThrottlerModule.forRoot يعرّف نافذة زمنية ttl بالملي ثانية وحدًا limit. ThrottlerGuard يعدّ الطلبات لكل متتبع، غالبًا عنوان الشبكة. عند تجاوز الحد يرجع رفضًا. مسار أضيق مثل الدخول يأخذ حدًا أقل بـ @Throttle. مسار صحة يمكن استثناؤه بـ @SkipThrottle.

التعريف التقني

npm i --save @nestjs/throttler

import { Module } from "@nestjs/common";
import { APP_GUARD } from "@nestjs/core";
import { ThrottlerGuard, ThrottlerModule } from "@nestjs/throttler";

@Module({
  imports: [
    ThrottlerModule.forRoot({
      throttlers: [{ ttl: 60_000, limit: 100 }],
    }),
  ],
  providers: [{ provide: APP_GUARD, useClass: ThrottlerGuard }],
})
export class AppModule {}

ttl بالملي ثانية منذ الإصدار 5. المساعد seconds(60) من الحزمة أوضح من الرقم الخام. عدة نوافذ: مصفوفة فيها name مثل short و long.

@Throttle({ default: { limit: 5, ttl: 60_000 } })
@Post("sign-in")
signIn() {}

المفتاح default إن لم تسمِّ المجموعة. @SkipThrottle() على مسار الصحة. خلف وكيل اضبط trust proxy وإلا فكل الزوار يُحسبون عنوان الوكيل أو يُحسب عنوان خاطئ. الصفحة تعرض ThrottlerBehindProxyGuard الذي يقرأ req.ips.

المخزن في الذاكرة لا يُجمع بين النسخ. الإنتاج متعدد النسخ يحتاج مخزنًا مشتركًا مثل Redis من مزودات المجتمع التي تذكرها الصفحة، ما دام ينفّذ ThrottlerStorage.

forRootAsync يقرأ الحد من ConfigService. هذا forRootAsync حقيقي ثانٍ بعد معاينة قاعدة البيانات.

الحارس العام للـ throttler مستقل عن حارس المصادقة. ضعه بحيث يعدّ حتى الطلبات المرفوضة بـ 401، وإلا فالتخمين لا يُحسب.

أبسط مثال

import { Controller, Post } from "@nestjs/common";
import { Throttle } from "@nestjs/throttler";

@Controller("auth")
export class AuthController {
  @Throttle({ default: { limit: 5, ttl: 60_000 } })
  @Post("sign-in")
  signIn() {
    return { ok: true };
  }
}

شرح المثال

خمسة محاولات في الدقيقة لهذا المسار، بينما الحد العام قد يكون أوسع للقراءة. العداد هنا ما زال على العنوان لا على البريد. مهاجم يبدّل العناوين يتخطى سقفًا ساذجًا، لذلك السقف يبطئ ولا يستبدل قفل الحساب أو تكلفة scrypt. اجمع الاثنين.

لا تضع الحد 5 على GET /posts العام إن كان الموقع يحمّل الصفحة بعدة طلبات مشروعة، ولا تضع 1000 على الدخول.

ماذا يحدث داخليًا؟

الحارس يزيد مفتاح التخزين لكل طلب ضمن ttl. عند بلوغ limit يرمي استثناء الحد، غالبًا 429 في هذا الإصدار من الحزمة، مع رؤوس X-RateLimit-* إن لم تعطّل setHeaders. انتهاء النافذة يعيد العد. النسخ بلا مخزن مشترك لكل واحدة عدادها، فيتضاعف الحد الفعلي بعدد العمليات.

خلف trust proxy غير المضبوط قد يزوّر العميل X-Forwarded-For إن وثقت بكل وكيل. اضبط الثقة على الحلقة أو على وكيل معروف كما في الصفحة.

مثال عملي

اختبار يرسل ست محاولات دخول خاطئة من عنوان واحد ويتوقع رفض السادسة حتى لو كانت الكلمة صحيحة، ضمن النافذة. هذا يمنع إخفاء التخمين داخل 401 فقط. مسار GET /health عليه @SkipThrottle حتى لا يسقط فحص المنصة. في الإنتاج مفتاح Redis واحد لكل النسخ.

أخطاء شائعة

  • ttl: 60 بعد الإصدار 5 معتقدًا أنها دقيقة، وهي 60 مللي ثانية.
  • حد الدخول نفسه حد تنزيل القوائم.
  • ذاكرة محلية مع عشر نسخ.
  • trust proxy مفتوح لكل عنوان.
  • اعتبار السقف بديلًا عن تجزئة بطيئة.

متى نستخدمه؟

على الدخول والتسجيل وأي مسار رخيص على المهاجم ومكلف عليك.

متى لا نستخدمه؟

كحماية وحيدة لكلمة المرور. ولا على حركة داخلية موثوقة بين خدمات بلا تمييز المتتبع، حتى لا تحظر نفسك.

الخلاصة

@nestjs/throttler يعدّ الطلبات في نافذة ويمنع التجاوز. ضيّق الدخول، وشارك المخزن بين النسخ، وأبقِ التجزئة المكلفة.

ماذا بعد؟

CSRF طلب المتصفح المزوّر من موقع آخر.
