# Mail

## الهدف من هذا الدرس

إرسال تأكيد نشر كتاب في رف عبر `@nestjs/mail` بعد التزام الصف، مع نقل يُستبدل في الاختبار.

## المشكلة التي يحلها

HTML يُلصق اسم الكتاب بلا تهريب فيكسر الرسالة أو يحقن وسمًا. أو فشل SMTP يلغي طلبًا التُزم أصلًا. أو الاختبار يتأكد أن دالةً وهمية استُدعيت ولا يرى الرابط في المتن.

## الفكرة ببساطة

`MailModule` عام ويوفّر `Mailer`. صنف الرسالة يطبّق `Mailable` ويعيد الموضوع واسم القالب والسياق. المحرك المدمج يهرّب القيم. التطوير يكتب `.eml` بـ `FileMailTransport`. الاختبار يستبدل `MailTransport` بـ `InMemoryMailTransport`. الإنتاج SMTP أو Resend أو غيره عبر متغير بيئة. الإرسال بعد الالتزام يمر بصندوق الصادر حتى تُعاد المحاولة؛ فشل البريد لا يعيد المشروع إلى `draft`.

## التعريف التقني

`npm i @nestjs/mail`. الحزمة بلا اعتماديات خارج Nest. `MailModule.forRoot({ transport, templates, from })`. `FileTemplateEngine` يقرأ HTML من مجلد، ويلفّه في `layout`، و `cache` يعمل في الإنتاج فقط حتى يظهر تعديل القالب في التطوير بلا إعادة بناء للمنطق. أضيفوا `mail/templates/**/*` إلى `assets` لأن `tsc` لا ينسخ HTML. `{{ }}` قيمة مُهرَّبة و `{{{ body }}}` في التخطيط لمكان المتن المُصيَّر. `#each` يكرر صفوفًا. `Mailable<T>.render` يعيد `subject` و `template` و `context`. `Mailer` يرسل. نقل ناقص أو `from` غير صالح يوقف الإقلاع. `MailEvents` يبلّغ ما نُجح وما فشل. في الاختبار `overrideProvider(MailTransport)`.

## Mental Model

```text
التزام نشر المشروع
→ رسالة outbox
→ Mailer يصيّر القالب
→ نقل SMTP أو ذاكرة الاختبار
```

## أبسط مثال

```ts
import { Injectable } from '@nestjs/common';
import type { Mailable } from '@nestjs/mail';

@Injectable()
export class ProjectPublishedMail implements Mailable<{ title: string; url: string }> {
  render(data: { title: string; url: string }) {
    return {
      subject: `نُشر ${data.title}`,
      template: 'project-published',
      context: { title: data.title, url: data.url },
    };
  }
}
```

التسجيل في التطوير: `transport: new FileMailTransport({ directory: 'var/mail' })` و `from: 'Raf <books@example.com>'`.

## شرح المثال

- العنوان يُمرَّر جاهزًا أو يُترجم في `render` حسب `locale` العضو، كما تفصل صفحة البريد عن كتالوج i18n: نص الرسالة ملفًا كاملًا لا مفتاحًا مبعثرًا.
- الرابط يُبنى في السياق. القالب لا يلصق عنوانًا من جسم الطلب.
- `FileMailTransport` لا يغادر الجهاز.

## ماذا يحدث داخليًا؟

1. `render` ينتج الموضوع والقالب والسياق.
2. المحرك يدرج القيم مهزّبة إلا موضع المتن في التخطيط.
3. النقل يسلّم البايتات: ملف، SMTP على `node:net` و `node:tls`، أو HTTP لمزوّد مثل Resend و Postmark و SendGrid و SES.
4. معالج `@OnOutboxMessage` يستدعي `Mailer` بعد الالتزام. فشل قابل لإعادة المحاولة يبقى للمرحّل. خطأ غير قابل للإعادة يُعلَّم حتى لا يُعاد بلا نهاية، بنمط `NonRetryableMessageError` الذي تذكره صفحة البريد مع الصندوق.
5. اختبار يقرأ الرسائل من النقل الذاكري ويفحص الرابط والنص.

## مثال عملي

نشر «موسم الهجرة» يلتزم `published` وصف الصندوق في معاملة واحدة كما في فصل الاعتمادية. المعالج يحمّل المشروع بـ `organizationId` من الحمولة ويرسل إلى بريد المالك. معاينة محلية تقرأ ملف `var/mail` أو مسار معاينة توثّقه الصفحة لعرض HTML في المتصفح بلا إرسال. لا ترسلوا من مسار `success_url` في المتصفح. ذلك المسار للعرض. التفعيل والاشتراك من حدث موقّع، والبريد تبعًا له.

## أخطاء شائعة

- استدعاء SMTP داخل نفس طلب `POST` ثم إرجاع 500 بعد ما نُشر الصف.
- الوثوق بـ `{{ }}` مع لصق HTML خام في السياق.
- اختبار بـ `jest.fn()` على `Mailer` فلا يُفحص التهريب ولا الرابط.
- قالب غير مذكور في `assets` فيُفقد داخل الصورة.

## متى نستخدمه؟

بريد عضوية ودعوة ونشر، بنقل يمكن استبداله، وبعد الالتزام.

## متى لا نستخدمه؟

لا تحملوا المرفق السري على قرص عام. الفاتورة الخاصة تبقى في تخزين موقّع من الدرس التالي. ولا تضعوا سر SMTP في المستودع.

## أسئلة مراجعة

- أي واجهة يطبّقها صنف الرسالة؟
- ماذا يوفّر `MailModule`؟
- لماذا `assets`؟
- أي نقل في الاختبار؟

## الخلاصة

`@nestjs/mail` يصيّر قالبًا مهزّبًا ويرسله بنقل قابل للاستبدال. رف ترسل بعد التزام النشر عبر الصندوق. ملف التطوير وذاكرة الاختبار يغنيان عن SMTP على الجهاز.

## ماذا بعد؟

غلاف الكتاب ملف لا رسالة. الدرس التالي أقراص `@nestjs/storage`.
