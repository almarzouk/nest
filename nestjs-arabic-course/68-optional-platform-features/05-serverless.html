Serverless

الهدف من هذا الدرس

معرفة ما يغيّره التشغيل عند الطلب في زمن إقلاع رف، ومتى يكفي createApplicationContext بدل تطبيق HTTP كامل.

المشكلة التي يحلها

دالة باردة تعيد بناء Nest واتصال قاعدة قبل أول بايت. أو مزود async يتصل بـ Redis في كل استدعاء حتى لو المسار لا يقرأ الذاكرة. أو عملية API كاملة داخل دالة واحدة بلا قياس. أو نسيان تخزين معالج Lambda فيُعاد الإقلاع على كل نداء دافئ.

الفكرة ببساطة

Serverless يشغّل الدالة حين يصل العمل ويفك الموارد حين يهدأ. البداية الباردة تشمل تحميل الشيفرة وتهيئة Nest. صفحة الأسئلة الشائعة تنشر أرقامًا على جهاز قديم: Express حوالي 8ms، و Nest مع منصة Express حوالي 197ms بلا تجميع و 81ms مع webpack، والسياق المستقل حوالي 112ms بلا تجميع و 32ms مجمّعًا. التطبيق الأكبر في الصفحة (عشر موارد) حوالي 130ms مجمّعًا، والصفحة تقول إن تشغيل المتراص كله كدالة نادرًا ما يناسب. منذ Nest 12 مساحة العمل تُجمَّع بـ Rspack افتراضيًا؛ أرقام الصفحة قيست بـ webpack على تلك الآلة فلا تُنقل كوعد لزمن رف.

التعريف التقني

قللوا العمل المتزامن في البناء. لا تجعلوا اتصالًا يُستخدم أحيانًا مزودًا يؤخر الإقلاع. LazyModuleLoader.load يستورد وحدة عند الحاجة، كما في مثال الصفحة لذاكرة التخزين. لعامل بلا مسارات: NestFactory.createApplicationContext ثم get على الخدمة. لـ HTTP على Lambda مع Express توضّح الصفحة @codegenie/serverless-express: app.init() لا listen، و getHttpAdapter().getInstance()، وتخزين handler في متغير وحدة:

server = server ?? (await bootstrap());

serverless.yml في المثال يستهدف nodejs22.x و dist/main.handler. إن لزم Swagger خلف بوابة، أصلِحوا originalUrl لمسار الواجهة حتى لا تدور إعادة التوجيه، كما في التحذير. الحراس لا يعملون على createApplicationContext. إن لزموا فـ NestFactory.create.

Mental Model

نداء بارد → إقلاع → معالج مُخزَّن
نداء دافئ → نفس المعالج
وحدة نادرة → LazyModuleLoader

أبسط مثال

import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module.js';
import { EventsService } from './events.service.js';

export const handler = async (event: unknown) => {
  const app = await NestFactory.createApplicationContext(AppModule, {
    logger: ['error'],
  });
  return app.get(EventsService).process(event);
};

هذا الشكل من الصفحة لعامل خفيف. أغلقوا السياق إن كانت المنصة لا تعيد استخدام البيئة، وأبقوه مخزّنًا إن كانت تعيد الاستخدام حتى لا تدفعوا الإقلاع كل مرة. قرار الإغلاق يتبع عمر بيئة المزود.

شرح المثال

  • logger: ['error'] يقلل العمل في القياس الذي تعرضه الصفحة.
  • process يأخذ الحدث وسيطًا. لا يوجد جسم HTTP موثوق حتى تبنوه.
  • معرف المنظمة داخل الحدث يُتحقق منه ضد توقيع المزوّد أو سجل داخلي.

ماذا يحدث داخليًا؟

  1. البيئة الباردة تحمّل الحزمة ثم تنفّذ الوحدة.
  2. create يبني Express وكل المسارات. createApplicationContext يبني الحاوية فقط، لذا رقمه في الجدول أصغر.
  3. التجميع إلى ملف واحد يقلل القراءة من node_modules. الصفحة فعلت ذلك بـ webpack و externals: [] مع تجاهل حزم خدمات مصغرة غير مثبتة.
  4. المزود غير المتزامن الذي ينتظر قاعدة يضيف زمنه إلى كل بداية باردة.
  5. الاستدعاء الدافئ يعيد handler المخزّن في المثال HTTP فلا يعيد bootstrap.

مثال عملي

واجهة رف الكاملة تبقى عملية طويلة مع Docker من المشروع الختامي. دالة منفصلة تصلح لعامل «أعِد محاولة صندوق واحد» إن قيس إقلاعها. LazyModuleLoader يحمّل وحدة الغلاف فقط حين workerType كذلك. لا تفعّلوا اشتراكًا لأن الدالة استُدعيت من عنوان نجاح في المتصفح. حدث Stripe يبقى على مسار التوقيع والـ rawBody. أرقام 81ms و 32ms في الوثائق قياس آلة 2014 لا هدف SLO لدار النيل.

أخطاء شائعة

  • نقل جدول webpack كأنه زمن Rspack على إنتاجكم.
  • اتصال Redis في onModuleInit لكل الدوال.
  • listen داخل Lambda فيعلق الإقلاع على منفذ.
  • متراص فيه GraphQL ولوحة و Stripe في دالة واحدة بلا تقسيم.

متى نستخدمه؟

عامل ضيق أو مسار قليل يتذبذب حمله إلى الصفر، بعد قياس البداية الباردة.

متى لا نستخدمه؟

بدل عملية رف التي فيها جلسات ودفق SSE واتصالات قاعدة طويلة. الصفحة نفسها تستبعد المتراص كدالة.

مقارنة

الشكل من جدول الصفحة بلا تجميع مع تجميع webpack
Express فقط ~8ms ~7ms
Nest HTTP ~197ms ~81ms
سياق مستقل ~112ms ~32ms

الآلة مذكورة في الصفحة: MacBook Pro منتصف 2014.

تمارين

تمرين سهل

لماذا الرقم المجمّع أصغر في الجدول؟

الحل

ملف واحد يقلل كلفة تحميل حزم كثيرة عند البداية الباردة. الصفحة قاست ذلك بـ webpack.

تمرين متوسط

متى تختارون createApplicationContext داخل الدالة؟

الحل

حين لا تحتاجون مسارات ولا حراسًا ولا أنابيب. العامل يستدعي خدمة بـ get. إن لزم HTTP فـ create و init ومحول المنصة.

تمرين متقدم

نداء دافئ ما زال يستغرق زمن إقلاع كامل. ماذا ينقص مثال HTTP في الصفحة؟

الحل

تخزين المعالج: server = server ?? (await bootstrap()). بلا التخزين كل نداء يعيد بناء Nest حتى داخل نفس البيئة.

أسئلة مراجعة

  • ماذا تضيف البداية الباردة؟
  • أي مصنع أخف بلا HTTP؟
  • لماذا لا يُنقل رقم 32ms كما هو؟
  • أين يُستخدم LazyModuleLoader؟

الخلاصة

Serverless يجعل إقلاع رف جزءًا من زمن الطلب. خففوا البناء، وخزّنوا المعالج، وافصلوا العامل عن المتراص. أرقام الوثائق قياس webpack على آلة محددة.

ماذا بعد؟

عملية HTTP مع مستمع رسائل في نفس التطبيق هي التطبيق الهجين، آخر درس في المسار.
