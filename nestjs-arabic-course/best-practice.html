أفضل الممارسات

مقارنة بين ما يُنسخ كثيرًا في المشاريع وما يُفضَّل في NestJS 12. الاسم التقني يبقى بالإنجليزية. التفصيل في درس كل موضوع، وهذا الملف للقرار السريع.

عندما يظهر صفان رسميان معًا، مثل ValidationPipe و StandardSchemaValidationPipe، الاثنان صالحان. الأفضل هو أن تختار واحدًا للعقد نفسه وتثبّت عليه.

الرد على HTTP

ما يُنسخ كثيرًا الأفضل لماذا
res.send و res.json داخل كل مسار return القيمة وتترك Nest تكتب JSON المعترض والتسلسل ورمز الحالة يبقون على المسار القياسي
@Res() مع return @Res({ passthrough: true }) حين تحتاج cookie أو رأسًا ثم return من غير passthrough أنت من يُنهي الرد، والقيمة المعادة لا تُرسل كما تتوقع
POST يرجع 200 POST الذي ينشئ موردًا يرجع 201، وتغيّره بـ @HttpCode إن لزم هذا افتراض Controllers في التوثيق. باقي النجاح 200
قائمة فارغة ترجع 404 200 مع [] أو { data: [] } غياب العناصر نتيجة صحيحة. 404 لعنوان مورد غير موجود
employeeId أو tenantId من الجسم المعرّف من الرمز أو من عضوية وقّعتها الجسم يقدر يغيّره صاحب الطلب من أدوات المتصفح 
@Post()
create(@Body() body: CreateNoteDto) {
  return this.notes.create(body);
}

الدخل والتحقق

ما يُنسخ كثيرًا الأفضل لماذا
interface كشكل لجسم الطلب صنف class مع class-validator، أو مخطط Zod مع StandardSchemaValidationPipe الواجهة تُمحى قبل التشغيل، فلا يوجد ما يفحصه الأنبوب
ValidationPipe بلا خيارات whitelist و forbidNonWhitelisted و transform الحقل الزائد مثل isAdmin يمر إن بقيت الخيارات مطفأة
فحص يدوي مبعثر في كل دالة أنبوب عام على حدود HTTP، والقاعدة التي تحتاج قاعدة البيانات في الخدمة شكل JSON يُرفض قبل المتحكم. «هل يتداخل الوقت؟» قرار خدمة
JSON.parse ثم الثقة بالنوع الأنبوب يتحقق من المعنى لا من أن النص JSON فقط JSON الصالح قد يحمل نوعًا خاطئًا أو حقلًا ناقصًا

class-validator ليست مهملة. StandardSchemaValidationPipe للمشاريع التي عقدها Zod أو Valibot أو ArkType. يمكن تسجيل الأنبوبين معًا: كل واحد يمرر ما لا يفهمه.

الحقن والوحدات

ما يُنسخ كثيرًا الأفضل لماذا
new UsersService() داخل المتحكم constructor(private readonly users: UsersService) {} مع تسجيل في providers new يخفي الشبكة ويمنع الاختبار من استبدال النسخة
import type للخدمة المحقونة استيراد قيمة عادي import type يمسح المعامل من design:paramtypes فينكسر الحقن
نسخ الصنف في providers كل وحدة تسجيل واحد، و exports ثم imports إعادة التسجيل تصنع نسخة ثانية في النطاق الافتراضي
@Global() على كل ميزة استيراد صريح. @Global() للإعداد العابر بعد تسجيله مرة في الجذر العالمي يخفي الرسم. ما زال يحتاج exports
forwardRef كأول علاج للدورة إعادة رسم الحد. forwardRef على الطرفين إن بقيت الدورة مؤقتًا الدورة علامة تصميم. مع REQUEST قد يبقى الطرف undefined
Scope.REQUEST لتمرير user الحارس يضع المستخدم، والدالة تستلمه وسيطًا REQUEST يُعدي كل من يحقن الخدمة ويُنشئ شجرة لكل طلب

الهوية والصلاحية

ما يُنسخ كثيرًا الأفضل لماذا
حفظ كلمة المرور كما كُتبت، أو SHA عارٍ تجزئة مخصصة لكلمات المرور مثل argon2 أو bcrypt SHA سريع عن قصد، فيصلح للتخمين الجماعي
رد مختلف لـ «البريد غير موجود» و «كلمة خاطئة» 401 بنفس النص في الحالتين الرد المختلف يخبر المهاجم أي البريد مسجّل
إرجاع passwordHash مع المستخدم DTO خرج أو @Exclude عبر ClassSerializerInterceptor التجزئة سر رغم أنها ليست الكلمة الأصلية
حارس يفحص الدور داخل كل مسار بمنطق منسوخ هوية في Guard، وإذن في Policy 401 لمن لا نعرفه. 403 لمن نعرفه وممنوع من هذا الفعل
تشغيل Passport و @nestjs/authentication على نفس الموارد مسار واحد في المشروع الاثنان رسميان. Passport وصفة Recipes وليست ملغاة. الحزمة @nestjs/authentication مسار قسم Security الحالي، و @nestjs/authorization يُركَّب معها

البيانات

ما يُنسخ كثيرًا الأفضل لماذا
synchronize: true أو تحديث المخطط مباشرة على الإنتاج ترحيل Prisma أو Doctrine، و migrate في النشر التحديث المباشر قد يسقط أعمدة فيها بيانات
new PrismaClient() داخل كل خدمة PrismaService واحدة تُصدَّر من وحدتها، تتصل عند الإقلاع وتُغلق عند الإيقاف مجمع اتصالات واحد، وإغلاق نظيف
قراءة ثم كتابة من غير معاملة $transaction مع شرط على الحالة المتوقعة طلبان متوازيان على آخر قطعة أو على نفس الاعتماد يمران معًا
إرجاع الجدول كله ثم القص في الذاكرة limit وفهرس وفرز من قائمة بيضاء القص بعد السحب يكلف القاعدة والشبكة
LIKE '%نص%' بلا سقف حد 20 أو ما يتفق عليه العقد، ومفتاح تعادل فريد مثل id من غير مفتاح فريد تتكرر الصفوف بين الصفحات
استعلام مشروع لكل صف تسجيل join أو include أو DataLoader هذا N+1. الكاش يأتي بعد جمع الاستعلام، ومع إبطال واضح

العمل المؤجل والتكامل

ما يُنسخ كثيرًا الأفضل لماذا
@nestjs/bull في مشروع جديد @nestjs/bullmq التوثيق يضع Bull في الصيانة و BullMQ في التطوير النشط. شكل الاتصال مختلف: connection هناك و redis هنا
تمرير كيان Prisma داخل وظيفة الطابور تمرير userId أو orderId الكيان الحي يفسد بعد انتهاء الطلب، وقد يحمل حقولًا سرية
انتظار PDF أو بريد قبل رد 201 رد سريع ثم عامل. في Symfony نفس الدور لـ Messenger، والرد 202 حين تقبل المهمة فقط مهلة الوكيل تقتل الطلب الطويل
تفعيل الاشتراك من صفحة success الحالة تتغير من ويب هوك موقّع على الجسم الخام المتصفح يصل لصفحة النجاح حتى لو تأخر الدفع أو أُعيد تحميلها
إعادة نفس POST تنشئ صفًا ثانيًا Idempotency-Key بقيد فريد، ونفس المفتاح مع جسم مختلف 409 انقطاع الشبكة يجعل العميل يعيد الإرسال
JSON.stringify ثم توقيع ناتج جديد HMAC على البايتات الأصلية rawBody إعادة التسلسل تغيّر المسافات وترتيب المفاتيح فيفشل التوقيع
emit ثم الحفظ، أو الحفظ ثم أمل أن الحدث يصل صف الصندوق الصادر في نفس معاملة الحفظ، والشبكة بعد الالتزام الحدث قبل الحفظ يعلن شيئًا لم يُكتب. الحدث بعده من غير جدول يضيع عند سقوط العملية

الاختبار والتشغيل

ما يُنسخ كثيرًا الأفضل لماذا
jest.fn في مشروع nest new الحديث Vitest مع vi.fn لقالب ESM. Jest يبقى لقالب CommonJS المولّد يختار المشغّل مع نظام الوحدات. لا تثبّت الاثنين معًا
اختبار يتصل بقاعدة التطوير قاعدة تُرمى في CI، أو وهم للمستودع في اختبار الوحدة الاختبار يمسح بياناتك أو يفشل على آلة الزميل
npm run start:dev داخل صورة الإنتاج npm run build ثم node dist/main.js وضع التطوير يراقب الملفات ولا يناسب الصورة
localhost لـ Postgres داخل Compose اسم الخدمة، مثل postgres localhost داخل الحاوية هو الحاوية نفسها
ESLint لأن مقالًا قديمًا ذكره oxlint و Prettier كما يولّدهما Nest CLI 12 هذا ما يضعه nest new
webpack كافتراض لمونوريبو جديد Rspack. أعلام webpack على هذا المسار قديمة مولّد المساحات الحالية يختار Rspack
قراءة process.env في كل ملف ConfigModule وفحص المفاتيح عند الإقلاع الناقص يوقف التشغيل برسالة واحدة، والاختبار يستبدل الخدمة

ما يُنسخ كثيرًا الأفضل لماذا
SQL وحساب المدة داخل Action خدمة تُحقن في البنّاء. PHP 8 يدعم constructor promotion نفس حد المتحكم الرفيع في Nest
schema:update على الإنتاج ترحيل Doctrine ثم doctrine:migrations:migrate الفرق المباشر على الإنتاج لا يُراجع في Git

قرار سريع

  1. الحدود أولًا: متحكم رفيع، خدمة تملك القاعدة، وحدة تصدّر واجهتها فقط.
  2. العقد ثانيًا: رمز HTTP، وحقول مسموحة، ومعرّف لا يأتي من الجسم.
  3. البيانات ثالثًا: ترحيل، معاملة، فهرس، حد للقائمة.
  4. التشغيل أخيرًا: بيئة مُفحوصة، صورة تشغّل dist، وجاهزية منفصلة عن الحياة.
