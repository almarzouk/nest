# N+1

## الهدف من هذا الدرس

رؤية نمط N+1 في مخطط كتب رف: استعلام للقائمة ثم استعلام لكل عنصر، وأين يُقطع في طبقة الحل لا في شكل الاستعلام الذي يكتبه العميل.

## المشكلة التي يحلها

`query { books { title author { name } } }` يبدو طلبًا واحدًا على السلك. سجل SQL يظهر `SELECT` للكتب ثم `SELECT` لكل `authorId`. مع خمسين كتابًا تصبح القاعدة هي السقف، بينما العميل ظن أنه وفّر جولات HTTP.

## الفكرة ببساطة

N هو عدد الآباء و +1 هو استعلام الآباء نفسه. كل حقل علاقة يُنفَّذ دالة مستقلة ما لم تجمع المفاتيح. العميل لا يخطئ بطلب `author`. الخادم يخطئ إن حوّل كل حقل إلى رحلة قاعدة.

## التعريف التقني

محرك GraphQL يستدعي دالة الحقل لكل أب. `@Query` التي تعيد `[Book]` تعمل مرة. `@ResolveField('author')` تعمل مرة لكل كتاب. هذا سلوك التنفيذ لا سلوك Nest الخاص. `@nestjs/graphql` لا يحوّل الحقل تلقائيًا إلى `JOIN` ولا إلى DataLoader. القطع يتم داخل الحقل: إما DataLoader كما في الدرس السابق، أو تحميل العلاقات في استعلام الجذر عندما تكون شكلًا ثابتًا تعرفه (Prisma `include`) وتقبل ثمن الأعمدة الزائدة حتى لو لم يطلبها العميل — وهذا قد يناقض طبيعة GraphQL، لذا التجميع عند الحقل أقرب لطلب العميل.

## Mental Model

```text
1  SELECT books
N  SELECT author WHERE id = ?
بدل
1  SELECT books
1  SELECT authors WHERE id IN (?)
```

## أبسط مثال

```ts
@ResolveField()
author(@Parent() book: { authorId: string }) {
  return this.prisma.author.findUnique({ where: { id: book.authorId } });
}
```

هذا هو النمط. الدالة صحيحة لمعزل واحد وخاطئة لقائمة.

## شرح المثال

- كل نداء `findUnique` رحلة.
- إضافة `@ResolveField` ثانٍ لـ `publisher` يضرب العدد مرة أخرى: N للمؤلف و N للناشر.
- السجل الذي يعد الاستعلامات أثناء اختبار القائمة هو الذي يكشف النمط، لا زمن جهاز هادئ.

## ماذا يحدث داخليًا؟

1. يصل مستند GraphQL واحد عبر HTTP.
2. الجذر يجلب الكتب.
3. لكل كتاب يُستدعى حقل `author` على حدة.
4. من غير تجميع، Prisma يرسل N استعلامات.
5. مع DataLoader تُجمع المفاتيح في دورة واحدة ويخرج استعلام `IN`، ويبقى عدد دوال الحقل N بينما عدد رحلات القاعدة ثابت.

## مثال عملي

اختبار يعد الاستعلامات على قائمة كتابين بمؤلفين مختلفين:

```ts
import { Injectable } from '@nestjs/common';

@Injectable()
export class QueryCounter {
  count = 0;
  async authorsByIds(ids: string[]) {
    this.count += 1;
    return ids.map((id) => ({ id, name: id }));
  }
}
```

الحل عبر المجمّع يستدعي `authorsByIds` مرة و `count === 1`. الحل عبر `findUnique` يجعل `count === 2` لكتابين. ثبّت هذا التوقع في اختبار الوحدة للمزمّع حتى لا يعود `findUnique` في مراجعة لاحقة.

## أخطاء شائعة

- منع العميل من طلب `author` بدل تجميع القراءة.
- `include` لكل العلاقات في الجذر ثم تجاهل أن العميل طلب حقلًا واحدًا، فيكبر الصف بلا داعٍ — مقبول كقياس مؤقت لا كشكل نهائي لكل الحقول.
- عدّ طلبات HTTP. N+1 هنا SQL رغم أن HTTP واحد.
- مجمّع بلا قيد `tenantId` فيصلح العدد ويفسد العزل.

## متى نستخدمه؟

كعدسة مراجعة على كل `@ResolveField` يصل إلى قاعدة أو إلى HTTP داخلي. إن كان لكل أب نداء، فالمسار N+1.

## متى لا نستخدمه؟

لا تسمِّ استعلام معرّف واحد N+1. ولا تعتبر صفحة REST التي تعمل `include` ثابتًا نفس المشكلة؛ هناك شكل الاستجابة مغلق وأنت اخترته.

## مقارنة

| الأسلوب | رحلات القاعدة لقائمة من N |
| --- | --- |
| `findUnique` في الحقل | 1 + N |
| DataLoader | 1 + 1 لكل نوع علاقة |
| `include` في الجذر | 1 (أو JOIN) حتى لحقول لم تُطلب |

## أسئلة مراجعة

- لماذا HTTP واحد لا ينفي N+1؟
- من الذي يكرر النداء: العميل أم دالة الحقل؟
- ماذا يثبت اختبار يعد `count`؟
- هل `@nestjs/graphql` يدرج JOIN تلقائيًا؟

## الخلاصة

N+1 هو استعلام آباء ثم استعلام لكل ابن. يظهر في `@ResolveField` الذي يلمس القاعدة مباشرة. قطعه تجميع لكل طلب، لا منع الحقل عن العميل.

## ماذا بعد؟

حتى بعد التجميع، العميل يستطيع طلب شجرة عميقة أو حقلًا غاليًا يتكرر. الدرس التالي يضع سقفًا رقميًا لتعقيد الاستعلام.
