# HTTP

## الهدف من هذا الدرس

أن تستخدم HTTP بوصفه اتفاقًا على شكل الكلام بين Client و Server: الطريقة، والعنوان، والرؤوس، والجسم، ورمز الحالة، واستقلال كل طلب.

## المشكلة التي يحلها

إذا اتفق كل فريق على شكل رسائله الخاصة، فكل عميل يحتاج مكتبة خاصة بهذا الخادم. HTTP اتفاق واسع: المتصفح، و `curl`، وتطبيق الجوال، وخادم آخر، يستطيعون إرسال الرسالة نفسها إلى NestJS و Express و Fastify.

NestJS، في مسار هذه الدورة، تطبيق HTTP. الإطار يرتب كودك. البروتوكول يبقى HTTP.

## الفكرة ببساطة

HTTP بروتوكول طلب واستجابة للوصول إلى موارد على الشبكة. المورد شيء يُسمّى بعنوان URL: كتاب، أو قائمة كتب، أو جلسة، أو ملف.

البروتوكول يحدد شكل الرسالة. هو لا يحدد أسماء حقولك ولا قواعد متجرك. هذا عملك فوقه.

## التعريف التقني

Hypertext Transfer Protocol بروتوكول طبقة تطبيق. يعمل عادة فوق TCP. الرسالة نص منظمة (ومع HTTP/2 يصبح التمثيل على السلك مختلفًا مع بقاء المعاني: طريقة، مسار، رؤوس، جسم، حالة).

خصائص تهمك الآن:

- **Request / Response**: كل دورة تبدأ بطلب من العميل.
- **Stateless**: الخادم لا يُلزم البروتوكول بأن يتذكر الطلب السابق. إذا احتاجت العملية ذاكرة، نحملها صراحة: Cookie، أو Token، أو معرّف في مخزننا. سنفصل ذلك في فصل Cookies و Sessions.
- **Resources**: العنوان يشير إلى مورد.
- **Methods**: أفعال متفق على معناها.
- **Status codes**: أعداد متفق على فئاتها.

HTTPS هو HTTP داخل قناة مشفرة عبر TLS. من جهة كود Nest، تتعامل مع الطلب نفسه. الفرق في النقل والشهادة. سنعود إلى HTTPS عند النشر.

## Mental Model

```text
URL
https://api.example.com:443/books/2?currency=usd
\___/   \______________/ \_/ \______/ \___________/
scheme   host            port  path     query

Request line:   GET /books/2?currency=usd HTTP/1.1
Headers:        Host, Accept, Authorization
Body:           غالبًا فارغ في GET

Response line:  HTTP/1.1 200 OK
Headers:        Content-Type
Body:           تمثيل المورد
```

## الطرق التي ستستخدمها

المعاني التالية هي عقد HTTP الشائع، كما تلخصه MDN وتوقعه عملاء الـ API. الفعل قرار تصميمي: الخادم هو الذي يلتزم به.

| Method | معنى عملي على مورد | هل يغيّر بيانات الخادم في الاستخدام القياسي؟ | تكرار الطلب نفسه |
| --- | --- | --- | --- |
| `GET` | اقرأ تمثيلًا | لا | آمن تكراره |
| `POST` | أنشئ أو شغّل عملية يختارها المورد | نعم غالبًا | قد ينشئ مرة أخرى |
| `PUT` | استبدل المورد كله بهذا التمثيل | نعم | التكرار يوصل إلى الحالة نفسها |
| `PATCH` | عدّل جزءًا من المورد | نعم | يعتمد على شكل التعديل |
| `DELETE` | احذف المورد | نعم | الحذف الثاني يجد المورد غائبًا |

**Safe**: `GET` لا يُفترض أن يغيّر حالة الخادم. رابط في صفحة، أو إعادة محاولة من المتصفح، قد يرسل `GET` من غير قصد تدميري.

**Idempotent**: تكرار الطلب المكافئ يترك الخادم في الحالة نفسها التي يتركها تنفيذ واحد. `GET` و `PUT` و `DELETE` ضمن هذا العقد الشائع. `POST` للإنشاء ليس كذلك: إرساله مرتين قد ينشئ كتابين. لهذا تظهر لاحقًا مفاتيح Idempotency على عمليات الدفع.

`HEAD` مثل `GET` بلا جسم. `OPTIONS` يسأل عما هو مسموح، وستقابله مع CORS.

## رموز الحالة

الفئة أهم من حفظ كل رقم:

| الفئة | المعنى | أمثلة ستتكرر |
| --- | --- | --- |
| `1xx` | معلوماتية | لن نركز عليها الآن |
| `2xx` | نجح الطلب | `200 OK`، `201 Created`، `204 No Content` |
| `3xx` | التحويل | `301`، `302`، `304 Not Modified` |
| `4xx` | الخطأ في الطلب كما وصل | `400`، `401`، `403`، `404`، `409`، `422` |
| `5xx` | الخادم فشل وهو مسؤول | `500`، `502`، `503` |

فروق ستحتاجها مبكرًا:

- `401 Unauthorized`: لا نعرف من أنت، أو إثبات الهوية مرفوض. الاسم التاريخي للرمز مربك؛ المعنى العملي: مشكلة Authentication.
- `403 Forbidden`: نعرفك، وهذا الفعل ممنوع. هذه Authorization.
- `404 Not Found`: لا مورد بهذا العنوان، أو لا نريد كشف وجوده.
- `409 Conflict`: الطلب مفهوم، ويصطدم بحالة حالية، مثل بريد مسجّل مسبقًا.
- `422 Unprocessable Content`: الطلب مفهوم نحويًا، والمعنى مرفوض. بعض الفرق تستخدم `400` للتحقق. سنثبت اختيارًا واحدًا عندما نصل إلى معالجة الأخطاء، ونلتزم به.

`400` طلب غير مفهوم أو غير صالح. التحقق من DTO في Nest ينتهي غالبًا إلى `400` مع `BadRequestException`. هذا سلوك ستراه في فصل Validation، لا تحفظ الاستثناء الآن.

## الرؤوس

الـ Header زوج اسم وقيمة، ويحمل سياقًا خارج الجسم.

| Header | اتجاه شائع | وظيفته |
| --- | --- | --- |
| `Host` | Request | أي مضيف على هذا العنوان |
| `Content-Type` | الاتجاهان | كيف نقرأ الجسم |
| `Accept` | Request | ما الذي يستطيع العميل قراءته |
| `Authorization` | Request | إثبات الهوية |
| `Location` | Response | أين المورد، غالبًا بعد `201` أو مع تحويل |
| `Set-Cookie` | Response | يطلب من العميل حفظ Cookie |
| `Cache-Control` | Response غالبًا | هل يجوز حفظ الاستجابة وإعادة استخدامها |

الرأس ليس مكان Business Logic. هو سياق للبروتوكول والوسيط والعميل.

## أبسط مثال

خادم Node من غير إطار، مأخوذ من صفحة About في موقع Node.js، بنسخة ESM. الوظيفة: أي طلب يصل إلى `127.0.0.1:3000` يأخذ الرد نفسه.

```ts
import { createServer } from 'node:http';

const hostname = '127.0.0.1';
const port = 3000;

const server = createServer((req, res) => {
  res.statusCode = 200;
  res.setHeader('Content-Type', 'text/plain');
  res.end('Hello World');
});

server.listen(port, hostname, () => {
  console.log(`Server running at http://${hostname}:${port}/`);
});
```

## شرح المثال

- `import { createServer } from 'node:http'` يستورد دالة إنشاء خادم HTTP من مكتبة Node القياسية. `node:` بادئة رسمية لمكتبات Node المدمجة.
- `hostname` و `port` عنوان الاستماع. `127.0.0.1` هو الجهاز المحلي فقط. جهاز آخر على الشبكة لا يصل إليه عبر هذا العنوان.
- `createServer` يسجّل دالة تُستدعى لكل طلب. هذه الدالة هي معالجك. Node يمرر `req` و `res`.
- `req` هنا غير مستخدم. كل المسارات وكل الطرق تأخذ الرد نفسه. هذا مقصود في مثال "أهلًا"، وهو غير كافٍ لتطبيق حقيقي.
- `res.statusCode = 200` يكتب رمز النجاح.
- `setHeader` يعلن أن الجسم نص عادي، لا JSON.
- `res.end('Hello World')` يرسل الجسم وينهي هذه الاستجابة.
- `listen` هو ما يجعل العملية تنتظر. قبلها لا يوجد منفذ مفتوح.
- الدالة داخل `listen` تعمل بعد نجاح الاستماع، وتطبع العنوان. هي ليست ردًا على عميل.

صفحة Node تقول إن كثيرًا من الاتصالات يمكن أن تُخدم معًا: عند كل اتصال تُستدعى الدالة، وإذا لم يوجد عمل فإن Node ينام. هذا تمهيد لدرس Node.js، لا شرح Event Loop كامل.

## ماذا يحدث داخليًا؟

1. `listen` يطلب من نظام التشغيل حجز المنفذ.
2. عند وصول اتصال، Node يقرأ HTTP ويبني `req`.
3. يستدعي دالتك. دالتك تعمل على خيط JavaScript الواحد. إذا انشغلت بحساب طويل من غير أن تُرجع التحكم، تأخرت الطلبات الأخرى. ستعود هذه الجملة في فصل الأداء.
4. الكتابة على `res` تتجمع حتى `end`، ثم تخرج على الاتصال.
5. بما أن البروتوكول Stateless، الطلب التالي يصل ومعه كل ما نحتاج لمعرفته. لا يوجد "المستخدم ما زال في الخطوة الثانية" داخل البروتوكول نفسه.

HTTP/1.1 يستطيع إبقاء الاتصال مفتوحًا لعدة طلبات (keep-alive) لتوفير كلفة فتح TCP. هذا تحسين نقل. كل طلب ما زال يحمل معناه كاملاً.

## مثال عملي

قراءة كتاب وتحديث سعره.

```http
GET /books/2 HTTP/1.1
Host: localhost:3000
Accept: application/json
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"id":"2","title":"Refactoring","price":40}
```

```http
PATCH /books/2 HTTP/1.1
Host: localhost:3000
Content-Type: application/json

{"price":42}
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"id":"2","title":"Refactoring","price":42}
```

`PATCH` هنا يغيّر السعر ويبقي العنوان. `PUT` كان سيطلب التمثيل الكامل الذي يجب أن يصبح الكتاب عليه. الفرق قرار تصميم ستثبّته في فصل REST API Design، بعد أن تملك Controllers.

في Express، السطر المقابل للقراءة هو:

```ts
app.get('/books/:id', handler)
```

في Nest، بعد عدة فصول، الشكل المقابل سيكون:

```ts
@Get(':id')
findOne() {}
```

لا تكتب الثاني في مشروع الآن. هو ترجمة الطريق نفسها إلى أسلوب الإطار، وسنفكها سطرًا بسطر في فصل Controllers.

## أخطاء شائعة

- استخدام `GET` للحذف لأن الرابط أسهل. المتصفحات والذاكرة الوسيطة تفترض أن `GET` آمن.
- إرجاع `500` عندما يكون المعرّف غير موجود. غياب المورد `404`. الخمسمئة تعني أننا انكسرنا.
- خلط `401` و `403`. الأول فشل إثبات الهوية، والثاني منع بعد المعرفة.
- نسيان `Content-Type` على JSON. بعض العملاء يخمنون، والتخمين ينكسر عند أول وسيط صارم.
- حشر حالة التطبيق في متغير عام على الخادم لكل مستخدم، لأن HTTP "لا يتذكر". العملية تتذكر الذاكرة التي تكتبها أنت. البروتوكول لا يربط هذه الذاكرة بالطلب التالي تلقائيًا، ووجود أكثر من عملية لاحقًا يجعل المتغير العام خطأً.

## متى نستخدم HTTP؟

لأي API يطلبها متصفح أو خدمة أخرى طلبًا ثم ينتظر ردًا. هذا المسار الافتراضي لـ NestJS: التوثيق يقول إن الإطار يبني تطبيقات خادم على Node، وتحت الغطاء يستخدم إطار HTTP مثل Express.

## متى نختار قناة أخرى؟

عندما تكون الرسالة حدثًا إلى خدمة أخرى، لا طلبًا ينتظر تمثيل مورد. الطوابير والـ Microservices تأتي بعد أن نتقن HTTP. اختيارها قبل ذلك يخفي حدود النظام.

## مقارنة مختصرة

| | HTTP | ما يبنيه Nest فوقه |
| --- | --- | --- |
| يحدد شكل الرسالة على الشبكة | نعم | يستخدمه |
| يحدد كيف تقسّم الكود | لا | Modules و Controllers و Providers |
| يحدد أسماء حقولك | لا | DTOs التي ستكتبها |

## تمارين

### تمرين سهل

اختر Method و Status لكل عملية:

1. قراءة قائمة الكتب.
2. إنشاء كتاب نجح.
3. حذف كتاب موجود.
4. قراءة كتاب غير موجود.

<details>
<summary>الحل</summary>

1. `GET`، والاستجابة `200` مع القائمة. قائمة فارغة تبقى `200` وجسمًا فارغًا من العناصر، لأن المسار موجود.
2. `POST`، والاستجابة `201`.
3. `DELETE`، والاستجابة `204` بلا جسم أو `200` مع تمثيل. الاثنان نجاح. اختر واحدًا والتزم به.
4. `GET`، والاستجابة `404`.

</details>

### تمرين متوسط

لماذا يحتاج إنشاء الطلب (checkout) حماية من التكرار، بينما استبدال عنوان كتاب عبر `PUT` بالمحتوى نفسه لا ينشئ كتابًا ثانيًا؟

<details>
<summary>الحل</summary>

`PUT` بالمحتوى نفسه يوصل المورد إلى الحالة نفسها في كل مرة، فهذا Idempotent. إنشاء عملية دفع أو طلب شراء عبر `POST` يضيف أثرًا جديدًا في كل تنفيذ ناجح. التكرار بلا مفتاح يمنع التكرار يخصم أو ينشئ مرتين.

</details>

### تمرين متقدم

طلب `GET /books/2` أعاد `200`. بين الطلب والاستجابة تغيّر السعر في قاعدة البيانات بسبب موظف آخر. أي سعر يجب أن يراه العميل، وما دور Stateless هنا؟

<details>
<summary>الحل</summary>

العميل يرى السعر الذي قرأه الخادم أثناء معالجة هذا الطلب. لا توجد "جلسة قراءة" يحفظها HTTP. الطلب التالي يرى السعر الجديد. إذا أردنا أن يشتري العميل بالسعر الذي رآه، نحفظ ذلك السعر صراحة مع عملية الشراء في تلك اللحظة، لا نعتمد على ذاكرة بروتوكول.

</details>

## أسئلة مراجعة

- ماذا يعني أن HTTP بروتوكول Stateless؟
- ما الفرق العملي بين `PUT` و `PATCH`؟
- لماذا لا نستخدم `GET` لعملية تغيّر بيانات؟
- ما فئة الرمز التي تعني خطأ العميل، وما الفئة التي تعني فشل الخادم؟
- ماذا يفعل `createServer` قبل أن يستطيع أي Client الاتصال؟

## الخلاصة

HTTP اتفاق طلب واستجابة حول موارد: Method و URL و Headers و Body ذهابًا، و Status و Headers و Body إيابًا. كل طلب يحمل معناه. NestJS سترتب كود معالجة هذا الاتفاق، ولن تستبدله.

## ماذا بعد؟

البروتوكول يعطيك أفعالًا وعناوين. REST طريقة لاستخدام هذه الأفعال والعناوين لتصميم API مفهوم. ليس كل API على HTTP تطبيقًا لـ REST.
