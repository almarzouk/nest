# Client و Server

## الهدف من هذا الدرس

تثبيت طرفي المحادثة: من يبدأ، ومن يملك المورد، ولماذا قد يصبح الخادم نفسه عميلًا لخادم آخر.

## المشكلة التي يحلها

في الدرس السابق قلنا إن Backend ينتظر الطلبات. كلمة "ينتظر" مهمة. الخادم لا يفتح متصفح المستخدم ولا يسأله ماذا يريد. هناك طرف يبدأ الاتصال، وطرف يقبل الاتصال ويقرر ماذا يعيد.

إذا اختلط الطرفان، ستضع منطق "من يسمح له" في المكان الخطأ، أو تنتظر أن الخادم يدفع البيانات إلى الصفحة من غير قناة صُممت لذلك.

## الفكرة ببساطة

- **Client**: الطرف الذي يبدأ الطلب.
- **Server**: الطرف الذي يستمع، ويقبل الطلب، ويعيد الاستجابة.

في المتصفح، الصفحة Client وخادم NestJS هو Server.

## التعريف التقني

نموذج Client/Server يفصل مقدم الخدمة عن مستهلكها. الـ Server عملية تستمع على عنوان ومنفذ. الـ Client يفتح اتصالًا نحو ذلك العنوان، يرسل طلبًا، وينتظر استجابة على الاتصال نفسه في نموذج HTTP المعتاد.

الأسماء تصف الدور في محادثة واحدة، لا هوية دائمة للبرنامج.

## Mental Model

```text
Client                         Server
  |                              |
  |  1. يفتح اتصالًا             |
  | -------------------------->  |
  |  2. يرسل Request             |
  | -------------------------->  |
  |                              | 3. يفهم الطلب
  |                              | 4. ينفّذ العمل
  |  5. يستقبل Response          |
  | <--------------------------  |
  | 6. يعرض أو يتصرف             |
```

المبادرة من اليسار. القرار من اليمين.

## أبسط مثال

تطبيق ملاحظات على هاتفك، و NestJS على خادم في شبكة الشركة.

- تطبيق الهاتف Client عندما يطلب `GET /notes`.
- NestJS هو Server لذلك الطلب.

بعد دقيقة، NestJS يحتاج سعر صرف من خدمة خارجية:

- NestJS يصبح Client.
- خدمة سعر الصرف هي Server.

البرنامج الواحد يلعب الدورين في محادثتين مختلفتين. فصل HTTP Client في الدورة يأتي متأخرًا لهذا السبب: الخادم عندنا سيكون زبونًا لغيره.

## شرح المثال

1. الهاتف يعرف عنوان خدمتنا.
2. هو الذي يقرر لحظة السؤال.
3. خدمتنا لا تعرف أن الهاتف فُتح حتى يصل الطلب.
4. عندما نسأل خدمة الأسعار، نصبح نحن الطرف الذي لا يملك سعر الصرف، وهم الطرف الذي يقرر القيمة.

## ماذا يحدث داخليًا؟

الاتصال الشبكي هنا غالبًا TCP: قناة موثوقة بين عنوانين. فوقها نضع HTTP كصيغة للكلام. سترى HTTP في الدرس الرابع. يكفي الآن:

- الخادم استدعى "استمع على هذا المنفذ" مرة عند الإقلاع.
- كل عميل ينشئ اتصالًا عندما يحتاج.
- بعد الاستجابة، HTTP بطبيعته لا يُبقي للخادم ذاكرة إلزامية عن هذه المحادثة. هذه نقطة ستعود باسم Stateless عندما نصل إلى REST.

استثناء ستدرسه لاحقًا، لا الآن: WebSocket يقلب جزءًا من الصورة لأن القناة تبقى مفتوحة ويمكن للخادم أن يرسل من غير طلب جديد لكل رسالة. المسار الأساسي لهذه الدورة طلب ثم استجابة.

## مثال عملي

ثلاثة عملاء لنفس الخادم في الدقيقة نفسها:

| Client | ماذا يطلب |
| --- | --- |
| متصفح الموظف | قائمة الطلبات |
| تطبيق الزبون | إنشاء طلب |
| مهمة مجدولة على خادم آخر | تقرير المبيعات |

NestJS واحد يمكنه خدمتهم إذا صممناه لذلك. كل واحد Client لأنه بدأ الطلب. اختلاف شكل الواجهة لا يغيّر الدور.

## أخطاء شائعة

- الظن أن Server "أقوى" تقنيًا من Client. الدور يصف من يبدأ ومن يجيب في هذه المحادثة.
- الظن أن المتصفح هو العميل الوحيد. تطبيق جوال، أو `curl`، أو اختبار، أو خادم آخر، كلها Clients.
- وضع سر، مثل مفتاح الدفع، داخل تطبيق الهاتف لأنه "عند المستخدم". التطبيق Client يستطيع أي شخص فحصه. السر يبقى عند Server.

## متى نستخدم هذا التقسيم؟

في أي API على الشبكة: طرف يطلب وآخر يملك العملية والبيانات. هذا شكل NestJS الافتراضي في هذه الدورة.

## متى لا يكفي نموذج طلب واحد واستجابة واحدة؟

عندما يجب أن يصل إشعار إلى العميل في اللحظة التي يحدث فيها شيء على الخادم، من غير أن يسأل العميل كل ثانية. هناك أدوات لذلك لاحقًا: WebSockets، و Server-Sent Events، والطوابير. لا نبدأ بها قبل أن نتقن الطلب والاستجابة.

## مقارنة مع مفاهيم مشابهة

| | Client | Server |
| --- | --- | --- |
| يبدأ المحادثة | نعم في هذه المحادثة | يستمع قبلها |
| يملك قاعدة العمل الخاصة بالمورد | يرسل رغبته | يقرر |
| مثال في مسارنا | المتصفح، تطبيق الجوال، اختبار | تطبيق NestJS |
| قد ينقلب الدور | عندما يسأل خادمنا خادمًا آخر | يصبح Client لتلك المحادثة |

في Express، الدالة التي تمررها إلى `app.get` تعمل عندما يصل طلب إلى Server. المتصفح الذي فتح `http://localhost:3000/` هو Client. سنقرأ هذا الكود في درس Express.

## تمارين

### تمرين سهل

في كل سطر، من Client ومن Server؟

1. متصفحك يفتح توثيق NestJS.
2. تطبيق NestJS يرسل بريدًا عبر مزود بريد.
3. اختبار آلي يضرب `GET /health` على تطبيقك.

<details>
<summary>الحل</summary>

1. المتصفح Client، وخادم التوثيق Server.
2. NestJS هو Client، ومزود البريد Server.
3. الاختبار Client، وتطبيقك Server.

</details>

### تمرين متوسط

لماذا لا يستطيع الخادم، في HTTP العادي، أن يحدّث شاشة المستخدم في اللحظة التي يدفع فيها زبون آخر، من غير أن يسأل المستخدم مرة أخرى؟

<details>
<summary>الحل</summary>

لأن المستخدم هو من يبدأ الطلب. بعد انتهاء الاستجابة لا توجد محادثة مفتوحة يكتب الخادم فيها إلى الشاشة. التحديث يصل عندما يرسل Client طلبًا جديدًا، أو عندما نستخدم قناة صُممت للبقاء مفتوحة، وهذا موضوع لاحق.

</details>

### تمرين متقدم

خدمة الطلبات عندك تستدعي خدمة المخزون لتعرف الكمية. خدمة المخزون تستدعي خدمة الطلبات لتعرف الحجوزات. صف الدور في كل اتصال، ثم اكتب خطر هذا الشكل بجملة واحدة. لا تقترح حلًا معماريًا كاملًا.

<details>
<summary>الحل</summary>

في الاتصال الأول: الطلبات Client والمخزون Server. في الاتصال الثاني ينعكس الدور. الخطر: كل خدمة لا تكمل عملها حتى تجيب الأخرى، وقد تنتظر كل واحدة الأخرى. هذا تلميح مبكر إلى أن اتجاه الاعتماد يجب أن يُرسم بوعي. سنعالج الدورات لاحقًا داخل Nest باسم Circular Dependency، وعلى مستوى الأنظمة في الفصول المتقدمة.

</details>

## أسئلة مراجعة

- ما الذي يعرّف Client في محادثة HTTP؟
- هل برنامج NestJS دائمًا Server؟
- لماذا نضع الأسرار على Server؟
- ماذا يتغير إذا أردنا أن يبادر الخادم بإرسال بيانات إلى المتصفح؟

## الخلاصة

Client يبدأ الطلب. Server يستمع ويقرر الاستجابة. الاسم دور في محادثة واحدة، والبرنامج قد يلعب الدورين مع أطراف مختلفة.

## ماذا بعد؟

نعرف من يتكلم. بقي أن نفتح الرسالة نفسها: ماذا داخل الطلب، وماذا داخل الرد. هذا هو Request و Response.
