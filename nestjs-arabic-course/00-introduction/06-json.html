JSON

الهدف من هذا الدرس

كتابة وقراءة تمثيل البيانات الذي ستتبادله واجهات هذه الدورة، وتمييزه عن كائن JavaScript وعن النوع الذي يكتبه TypeScript.

المشكلة التي يحلها

كائن داخل Node يعيش في ذاكرة العملية. المتصفح عملية أخرى، وربما لغة أخرى. لا نرسل المؤشرات ولا الدوال. نرسل نصًا متفقًا على شكله.

JSON هذا النص: خفيف، مقروء، ومدعوم في المتصفح و Node من غير مكتبة إضافية.

الفكرة ببساطة

JSON صيغة نصية لتمثيل بيانات شجرية: كائنات، ومصفوفات، وأرقام، ونصوص، وقيم منطقية، و null.

عندما ترى Content-Type: application/json فالجسم يُفسَّر بهذه الصيغة.

التعريف التقني

JavaScript Object Notation صيغة بيانات مستقلة عن اللغة، اشتُقت من طريقة كتابة الكائنات في JavaScript، ثم صارت معيارًا. المواصفة تفرض قواعد أضيق من JavaScript.

ما يمكن أن يظهر كقيمة:

  • نص بين علامتي اقتباس مزدوجتين "title"
  • عدد: 40 أو 19.5
  • true أو false
  • null
  • كائن: { "id": "2" }
  • مصفوفة: [1, 2, 3]

المفاتيح داخل الكائن نصوص بين اقتباس مزدوج.

        |

الرحلة تعبر نصًا. ما لا يُكتب في JSON لا يعبر.

أبسط مثال

تمثيل كتاب:

{
  "id": "2",
  "title": "Refactoring",
  "price": 40,
  "tags": ["design", "code"],
  "inStock": true,
  "replacedBy": null
}

قائمة:

[
  { "id": "1", "title": "Clean Code" },
  { "id": "2", "title": "Refactoring" }
]

شرح المثال

  • { ... } كائن واحد.
  • [ ... ] قائمة مرتبة.
  • "id": "2" المفتاح والمعرّف نصان. لو كتبنا 2 من غير اقتباس لصار عددًا. اختر نوعًا وحافظ عليه. المعرّفات النصية أصدق عندما تأتي من UUID لاحقًا.
  • 40 عدد، لا "40". الفرق يظهر عند الجمع والتحقق.
  • true منطقي. في JSON تُكتب أحرفًا صغيرة. True غير صالحة.
  • null غياب قيمة معروفة، ويختلف عن حذف المفتاح. سنتفق في الـ API متى نستخدم كلاهما.
  • الفاصلة بعد آخر عنصر غير مسموحة في JSON. في كائن JavaScript الحديث قد يسمح المحرك بها. النص على الشبكة لا يسمح.

ماذا يحدث داخليًا؟

في JavaScript:

const book = { id: '2', price: 40 };
const text = JSON.stringify(book);
const again = JSON.parse(text) as { id: string; price: number };
  • JSON.stringify يمشي على الشجرة ويكتب نصًا.
  • JSON.parse يقرأ النص ويبني قيمًا جديدة. الكائن الجديد ليس الكائن القديم. الهوية في الذاكرة انقطعت، وهذا متوقع.
  • as { ... } تلميح TypeScript لك أنت. JSON.parse يعيد any في كثير من الإعدادات، والمترجم لا يتصل بالشبكة ليتأكد. التحقق الحقيقي وقت التشغيل درس لاحق اسمه Validation.

قيم تسقط أو ترفض في الطريق:

قيمة JavaScript أثر JSON.stringify
undefined داخل كائن المفتاح يختفي
undefined داخل مصفوفة تصبح null
دالة تُحذف من الكائن
Symbol يُحذف
Date نص تاريخ مثل "2026-10-05T00:00:00.000Z" لا كائن تاريخ
BigInt يرمي خطأ
مرجع دائري يرمي خطأ

بعد JSON.parse، التاريخ نص. إذا أردت Date تعيد البناء بنفسك، أو تتركه نصًا في عقد الـ API. النص أوضح على الحدود.

مثال عملي

طلب إنشاء:

POST /books HTTP/1.1
Content-Type: application/json

{"title":"Clean Code","price":30}

رد:

{
  "id": "18",
  "title": "Clean Code",
  "price": 30
}

خطأ تحقق ستراه لاحقًا من Nest بالشكل الافتراضي المشابه لـ:

{
  "statusCode": 400,
  "error": "Bad Request",
  "message": ["title must be a string"]
}

هذا JSON أيضًا. الفشل تمثيل، وله Status منفصل كما في درس Request.

تعليق داخل JSON غير موجود:

{
  "title": "Clean Code" // هذا يكسر JSON.parse
}

JSON ليست JavaScript. لا تعليقات، ولا مفاتيح عارية، ولا اقتباس مفرد للنصوص.

أخطاء شائعة

  • إرسال كائن JavaScript والظن أن HTTP سيفهمه. من غير تحويل إلى نص ورأس Content-Type، الطرف الآخر يرى بايتات أو يرفض.
  • الوثوق بنوع TypeScript على جسم الطلب. النوع يختفي بعد الترجمة. الجسم القادم من الشبكة يحتاج فحصًا وقت التشغيل. هذا سبب DTO و Pipes لاحقًا.
  • استخدام Number لكل المعرّفات الكبيرة جدًا. أعداد JSON تمر عبر عدد JavaScript، والأعداد الصحيحة الأكبر من المجال الآمن تفقد دقتها. المعرّف النصي يتجنب ذلك.
  • تسريب حقول لأن JSON.stringify يكتب كل المفاتيح القابلة للعد. كلمة المرور أو الهاش إذا وُجدت على الكائن تخرج مع الرد. سنبني Serialization لاحقًا حتى يكون الخروج مقصودًا.

متى نستخدم JSON؟

لتمثيل الموارد في REST API بين NestJS وعملائه، وفي أغلب الأمثلة الرسمية للإطار.

متى نستخدم غيره؟

  • ملفات ثنائية ورفع ملفات: multipart/form-data، وله فصل.
  • حدث من خادم إلى صفحة عبر قناة نصية أخرى: قد يبقى JSON هو الحمولة داخل WebSocket أو SSE.
  • حاجة إلى مخطط إلزامي على السلك مثل Protobuf في gRPC. ذلك مسار Microservices، لا المسار الأول.

HTML صيغة رد أيضًا عندما نقدّم صفحات. توثيق Nest يذكر MVC مع محرك قوالب. هذه الدورة تركز على API تعيد JSON.

تمارين

تمرين سهل

أي الأسطر JSON صالح؟

  1. { title: "A" }
  2. { "title": "A" }
  3. { "ok": True }
  4. { "tags": ["a", "b"] }
الحل
  1. غير صالح: المفتاح بلا اقتباس مزدوج.
  2. صالح.
  3. غير صالح: True يجب أن تكون true.
  4. صالح.

تمرين متوسط

ماذا يعيد JSON.stringify({ id: "2", password: undefined, createdAt: new Date("2026-10-05T00:00:00Z") }) بشكل تقريبي؟ ماذا يضيع؟

الحل

نص قريب من {"id":"2","createdAt":"2026-10-05T00:00:00.000Z"}. المفتاح password يختفي لأن القيمة undefined. التاريخ يصبح نصًا. بعد parse لن تحصل على كائن Date إلا إذا بنيته.

تمرين متقدم

دالة Controller مستقبلًا ستأخذ createBookDto: CreateBookDto. لماذا لا يكفي هذا النوع لمنع عميل من إرسال { "title": 5 } إذا لم يوجد فحص وقت التشغيل؟

الحل

TypeScript يمحو الأنواع عند إنتاج JavaScript. القيمة { "title": 5 } تُبنى من JSON.parse داخل جسم HTTP، والمترجم لا يرى طلبات الإنتاج. من غير Pipe أو فحص صريح، الدالة تستقبل القيمة كما وصلت. هذا سبب ما سيأتي في فصلي DTO و Validation، لا تفصيله هنا.

أسئلة مراجعة

  • لماذا يختفي مفتاح قيمته undefined عند التحويل؟
  • ما الفرق بين نجاح JSON.parse ونجاح Validation؟
  • لماذا المعرّف النصي قرار آمن على حدود الـ API؟

الخلاصة

JSON نص متفق عليه لشجرة بيانات. stringify و parse ينقلانك بين الذاكرة والشبكة. النوع في TypeScript لا يعبر الشبكة. المعنى أدق من النحو، وفحص المعنى طبقة لاحقة.
