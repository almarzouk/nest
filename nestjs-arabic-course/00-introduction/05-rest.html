REST

الهدف من هذا الدرس

تصميم واجهة حول موارد وأفعال HTTP، بحيث يفهم عميل جديد العناوين من غير دليل سري لكل عملية.

المشكلة التي يحلها

يمكن بناء API كامل فوق HTTP هكذا:

POST /do
{ "action": "deleteBook", "id": "2" }

وكل عملية ثانية:

POST /do
{ "action": "getBook", "id": "2" }

البروتوكول يسمح بذلك. العميل لا يستفيد من معنى GET أو DELETE، ولا من الذاكرة الوسيطة، ولا من الرموز القياسية. كل فعل اسم خاص داخل JSON، والدليل يكبر مع كل زر في المنتج.

REST يضع العملية في مكانين يفهمهما أي عميل HTTP: عنوان المورد و طريقة HTTP.

الفكرة ببساطة

REST أسلوب معماري يصمم الواجهة كموارد تُسمى بأسماء، وتُدار بأفعال HTTP القياسية. الكتاب مورد. قائمة الكتب مورد. قراءة الكتاب GET. حذفه DELETE.

الاسم جاء من Roy Fielding، أحد مؤلفي HTTP، في رسالته عام 2000. ما يستخدمه معظم مطوري الـ API اليوم هو تطبيق عملي لمجموعة من تلك الأفكار، وخصوصًا: موارد، وواجهة موحدة، ورسائل تصف نفسها، وعدم حفظ حالة الجلسة داخل البروتوكول.

التعريف التقني

REST اختصار Representational State Transfer.

  • Resource: أي شيء نسميه ونخاطبه. قد يكون كيانًا (كتاب) أو مجموعة (الكتب) أو عملية نريد كشفها كمورد (عملية دفع) عندما يكون ذلك أصدق من اختراع فعل.
  • Representation: ما يُنقل عبر الشبكة هو تمثيل للمورد، غالبًا JSON، لا الكائن الحي داخل الخادم.
  • Uniform interface: نخاطب الموارد بالطريقة نفسها: URI + Method + تمثيل.
  • Stateless: الطلب يحمل ما يلزم لفهمه. حالة المستخدم تُحفظ في مخزن ونشير إليها بإثبات يرسله العميل، لا في "موقع داخل محادثة HTTP" ضمنية.

لن نحفظ القيود الأكاديمية الستة كقائمة اختبار. سنستخدم ما يغيّر تصميم المسارات.

Mental Model

اسم المورد في العنوان     الفعل في Method     التمثيل في الجسم

/books                    GET                 قائمة
/books                    POST                كتاب جديد في الطلب
/books/2                  GET                 كتاب واحد
/books/2                  PATCH               الحقول المتغيرة
/books/2                  DELETE              لا تمثيل، أو تأكيد

/books/2/reviews          GET                 مراجعات هذا الكتاب

المجموعة، ثم العنصر، ثم مورد فرعي يملكه العنصر.

أبسط مثال

كتب.

GET    /books
POST   /books
GET    /books/2
PUT    /books/2
PATCH  /books/2
DELETE /books/2

عنوان سيئ لنفس العمليات:

GET  /getAllBooks
POST /createNewBook
GET  /getBookById?id=2
POST /deleteBook

السطر الثاني يعيد اختراع الأفعال داخل الأسماء. GET /getAllBooks يقول "اجلب" مرتين، وبأسلوب خاص بك.

شرح المثال

  • /books مجموعة. GET يقرأها. POST يضيف إليها عنصرًا لأن الخادم هو الذي سيختار المعرّف غالبًا.
  • /books/2 عنصر معروف. المعرّف في المسار لأن العنوان يحدد المورد.
  • PUT /books/2 يستبدل تمثيل الكتاب كاملًا.
  • PATCH /books/2 يرسل الفرق.
  • DELETE /books/2 يحذف هذا المورد.
  • POST /deleteBook يخفي الحذف داخل جسم أو داخل اسم. الوسيط الذي يرى POST لن يعرف أنها عملية حذف.

جمع الاسم في المسار (/books) شائع لأنه جدول عناوين واضح. بعض الفرق تستخدم مفردًا. الأهم ثبات القاعدة. سنثبت قواعد التسمية في فصل REST API Design.

ماذا يحدث داخليًا؟

REST ليس بروتوكولًا يعمل داخل Nest، ولا مكتبة. لا يوجد مفسّر REST يتحقق من مساراتك. الالتزام اتفاق بشري يراجعه الفريق.

عندما يصل GET /books/2:

  1. HTTP يوصل الطريقة والمسار كما هما.
  2. إطار التوجيه — Express اليوم، و Nest لاحقًا — يطابق المسار إلى دالة.
  3. الدالة تقرأ المورد 2 من المخزن.
  4. تبني تمثيلًا مناسبًا للخارج. التمثيل قد يحذف حقولًا داخلية مثل تكلفة الجملة أو هاش كلمة المرور.
  5. تكتب 200 والتمثيل.

المورد يبقى على الخادم. العميل حصل على نسخة وصفية في هذه اللحظة.

مثال عملي

متجر صغير: كتب، ومراجعات يملكها كتاب.

GET    /books/2/reviews
POST   /books/2/reviews
DELETE /books/2/reviews/9

المراجعة 9 لا تُخاطب كـ /reviews/9 إلا إذا كانت المراجعة في منتجك موردًا مستقلًا يُبحث عنه وحده. إذا كانت دائمًا ابنة كتاب، المسار المتداخل يصدق العلاقة.

عملية ليست اسمًا بسيطًا: "انشر الكتاب".

خياران صادقان:

POST /books/2/publication

هنا عملية النشر مورد: لها لحظة، وقد يكون لها سجل. أو:

PATCH /books/2
{ "status": "published" }

هنا النشر حالة على الكتاب. اختر الشكل الذي يطابق عملك. كلاهما أوضح من:

POST /books/publishBookNow

أخطاء شائعة

  • الظن أن أي JSON على HTTP هو REST. الصيغة لا تصنع الأسلوب.
  • أفعال داخل المسار: /books/updatePrice.
  • GET يغيّر حالة، مثل GET /books/2/publish.
  • إرجاع كائن قاعدة البيانات كاملًا كأنه هو التمثيل. التمثيل عقد عام. شكل الجدول تفصيل داخلي.
  • جعل كل العمليات POST على عنوان واحد "لأن أسهل في الكود". السهولة تنتقل إلى كل عميل لاحق.

متى نستخدم REST؟

عندما يملك المنتج مواردًا واضحة، وعملاء متعددين (ويب، جوال، شركاء)، وتريد أن تكفي معرفة HTTP لتخمين نصف الواجهة.

NestJS لا يفرض REST. التوثيق يشرح Controllers كمعالجات طلبات HTTP، وتقدر أن تصمم المسارات كما تشاء. الدورة ستصممها بأسلوب REST لأن العقد يبقى مفهومًا عندما يكبر الفريق.

متى لا نستخدمه؟

  • عندما يحتاج العميل شكل شجرة بيانات تتغير مع كل شاشة، وتريد أن يطلب هو الحقول. هذا أحد دوافع GraphQL، وله فصل كامل بعد أن نتقن REST.
  • عندما يكون الحديث أحداثًا بين خدمات، لا إدارة موارد يسأل عنها عميل. الرسائل والطوابير أنسب.
  • لعملية داخلية واحدة بين برنمجين تسيطر عليهما أنت وقد يكون RPC أبسط. حتى هنا، مورد صغير غالبًا يكفي.

مقارنة

HTTP REST JSON
ما هو بروتوكول نقل أسلوب تصميم واجهة فوقه صيغة تمثيل
هل يلزم الآخرين الرسالة يجب أن تكون HTTP إذا اخترته اتفاق تصميمي اتفاق على شكل الجسم
مثال كسره طلب لا يفهمه الخادم POST /doAction لكل شيء جسم لا يُحل كـ JSON

Express:

app.get('/books', handler)
app.post('/books', handler)
app.delete('/books/:id', handler)

Nest لاحقًا:

@Get()
@Post()
@Delete(':id')

البادئة /books ستأتي من @Controller('books'). هذا تنظيم مسارات، وسنشرحه في فصله. المعنى REST واحد.

تمارين

تمرين سهل

حوّل العمليات إلى Method ومسار:

  1. قائمة مراجعات الكتاب 2.
  2. إنشاء مراجعة على الكتاب 2.
  3. حذف المراجعة 9 التابعة للكتاب 2.
الحل
  1. GET /books/2/reviews
  2. POST /books/2/reviews
  3. DELETE /books/2/reviews/9

تمرين متوسط

واجهة فيها POST /books/2/update وجسم { "price": 10 }. أعد كتابتها بأسلوب REST، وبرر الاختيار بين PATCH و PUT.

الحل

PATCH /books/2 مع الجسم { "price": 10 } لأن الطلب يغيّر جزءًا. PUT يناسب إرسال الكتاب كاملًا كما يجب أن يصبح. المسار /update يعيد الفعل داخل العنوان.

تمرين متقدم

تصميم أولي: GET /users/5/orders/8/items/3/setShipped. اقترح موردًا أوضح لعملية الشحن. اذكر Status واحدًا للنجاح.

الحل

الشحن حالة على البند أو عملية مستقلة. خيار الحالة: PATCH /users/5/orders/8/items/3 مع { "status": "shipped" } و 200. خيار العملية إذا كان للشحن سجل ووقت وشركة نقل: POST /orders/8/items/3/shipments و 201. لاحظ أن سلسلة /users/5 قد تكون زائدة إذا كان رقم الطلب فريدًا عالميًا؛ العنوان يحمل ما يلزم لتحديد المورد. GET خرج لأنه كان يغيّر حالة.

أسئلة مراجعة

  • أين يعيش الفعل في واجهة REST، وأين يعيش اسم المورد؟
  • لماذا لا يكفي إرجاع JSON لنسمي الواجهة REST؟
  • ما الفرق بين المورد وتمثيله؟
  • متى يصبح GraphQL مرشحًا، من غير أن ننتقل إليه الآن؟

الخلاصة

REST يسمي الموارد في المسار ويستخدم أفعال HTTP بمعناها. العميل يحصل على تمثيل. الخادم يبقى صاحب الحالة. الأسلوب اتفاق تصميم، لا مفتاح تشغله داخل Nest.

ماذا بعد؟

التمثيل الأشيع في هذه الواجهات هو JSON. الدرس التالي يفصله: ماذا يصلح أن يُكتب، وماذا يرفضه المفسر، ولماذا لا يكفي interface في TypeScript ليفرضه.
