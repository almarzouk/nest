# Request و Response

## الهدف من هذا الدرس

قراءة الرسالة الذاهبة والرسالة الراجعة كقطعتين واضحتين، قبل أسماء الـ Decorators التي ستستخرج منهما القيم لاحقًا.

## المشكلة التي يحلها

إذا كان "الطلب" كتلة غامضة، ستخلط بين ثلاثة أشياء مختلفة تصل معًا:

- أي عملية يريدها العميل.
- على أي مورد.
- ما البيانات المرفقة.

والرد كذلك: نجاح العملية غير شكل البيانات الراجعة. رمز `201` يخبر العميل أن موردًا أُنشئ. الجسم يخبره ما هذا المورد. إذا أهملت أحدهما، الواجهة تخمّن.

## الفكرة ببساطة

**Request** رسالة من Client إلى Server: ماذا أريد، وعلى أي عنوان، ومع أي بيانات.

**Response** رسالة من Server إلى Client: ماذا حدث، وبأي حالة، ومع أي ناتج.

## التعريف التقني

في HTTP:

- الـ Request يتكون من سطر البداية (الطريقة والمسار وإصدار البروتوكول)، ثم Headers، ثم جسم اختياري.
- الـ Response يتكون من سطر الحالة (الإصدار ورمز الحالة وسبب مختصر)، ثم Headers، ثم جسم اختياري.

NestJS و Express يعطيانك هذين الكائنين في صور أسهل، لكن المحتوى هو هذا.

## Mental Model

```text
Request
+-----------------------------+
| Method   GET | POST | ...   |
| Target   /books/2           |
| Headers  Accept, Authorization, ...
| Body     موجود أو فارغ      |
+-----------------------------+
              |
              v
           Server
              |
              v
Response
+-----------------------------+
| Status   200 | 201 | 404... |
| Headers  Content-Type, ...  |
| Body     تمثيل الناتج       |
+-----------------------------+
```

## أبسط مثال

العميل يريد كتابًا واحدًا.

Request بشكل مقروء:

```http
GET /books/2 HTTP/1.1
Host: localhost:3000
Accept: application/json
```

Response:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": "2",
  "title": "Designing Data-Intensive Applications"
}
```

هذا النص شكل البروتوكول. المكتبات تبنيه وتفكه نيابة عنك. ستقرأ الأجزاء، لا هذا النص، في معظم أيامك.

## شرح المثال

- `GET` الطريقة: اقرأ، ولا تغيّر شيئًا بهذا الطلب.
- `/books/2` الهدف على هذا الخادم. `2` معرّف الكتاب.
- `HTTP/1.1` إصدار البروتوكول في هذه الرسالة.
- `Host` رأس إلزامي في HTTP/1.1: أي موقع على هذا العنوان تقصد.
- `Accept` يخبر الخادم أن العميل يستطيع قراءة JSON. الخادم قد يحترم ذلك.
- `200` يعني أن الخادم وجد الكتاب وأعاده.
- `Content-Type: application/json` يخبر العميل كيف يفسر الجسم.
- الجسم هو تمثيل الكتاب، لا الكائن داخل ذاكرة الخادم.

سطر فارغ في الرسالة الحقيقية يفصل الرؤوس عن الجسم. هنا وضعت الرؤوس ثم الجسم للوضوح.

## ماذا يحدث داخليًا؟

1. العميل يفتح اتصالًا إلى العنوان والمنفذ.
2. يكتب بايتات الطلب.
3. الخادم يقرأ حتى يكتمل الطلب: السطر الأول، الرؤوس، ثم الجسم إن وُجد وطوله معروف أو الاتصال يحدد نهايته.
4. برنامجك — لاحقًا Express أو Nest — يضع هذه الأجزاء في كائن request.
5. بعد أن يقرر البرنامج النتيجة، يكتب سطر الحالة والرؤوس والجسم.
6. العميل يقرأ الاستجابة ويفسر الجسم حسب `Content-Type`.

في Node.js الكائنان هما IncomingMessage للطلب و ServerResponse للرد، من وحدة `node:http`. Express يمررهما إليك باسم `req` و `res`، وتوثيق Express ينص على أنهما الكائنان نفسهما اللذان يعطيهما Node، مع إضافات Express فوقهما. Nest يبني فوق ذلك طبقة ستمر عليك في فصل Controllers. لا تحفظ أسماء أصناف Nest الآن.

## مثال عملي

إنشاء كتاب.

Request:

```http
POST /books HTTP/1.1
Host: localhost:3000
Content-Type: application/json

{
  "title": "Refactoring",
  "price": 40
}
```

Response محتملة:

```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /books/18

{
  "id": "18",
  "title": "Refactoring",
  "price": 40
}
```

- `POST` إنشاء.
- الجسم يحمل ما يقترحه العميل.
- `201` أُنشئ مورد. `200` كان سيعني نجاحًا عامًا. الرمز أدق من جملة داخل JSON.
- `Location` يخبر أين يعيش المورد الجديد. رأس شائع مع الإنشاء، وستستخدمه عندما نضبط الردود في Nest.

إذا لم يوجد مسار `/books/2`:

```http
HTTP/1.1 404 Not Found
Content-Type: application/json

{
  "statusCode": 404,
  "message": "Book not found"
}
```

الرمز يقول للفئة البرمجية ماذا حدث. الجسم يشرح للإنسان أو للواجهة. الاثنان معًا.

## أخطاء شائعة

- وضع نتيجة العملية داخل JSON فقط، مع إرجاع `200` للفشل وللنجاح. العميل عندها يفتح الجسم ليعرف إن كان فشلًا. الرمز جزء من العقد.
- قراءة معرّف المورد من الجسم بينما هو أصلًا في المسار، أو العكس، من غير اتفاق. في REST الشائع: معرّف المورد القائم في المسار، وحقول الإنشاء في الجسم.
- افتراض أن غياب الجسم يعني فشلًا. `204 No Content` نجاح بلا جسم.

## متى نهتم بكل جزء؟

| الجزء | سؤال يجيبه |
| --- | --- |
| Method | ما نوع العملية؟ |
| Target / URL | على أي مورد؟ |
| Headers | سياق: نوع المحتوى، الهوية، التفضيلات |
| Body | حمولة الإنشاء أو التعديل |
| Status | ماذا قرر الخادم؟ |
| Response body | التمثيل الذي يستطيع العميل قراءته |

## مقارنة سريعة مع ما ستراه في Express

```text
Express                         معنى الجزء
app.get('/books/:id', ...)      Method + مسار
req.params.id                   قطعة من المسار
req.query                       ما بعد ?
req.body                        جسم الطلب بعد تحليله
res.status(201).json(...)       Status + جسم JSON
```

في Nest ستقابل لاحقًا `@Get` و `@Param` و `@Query` و `@Body`. الأسماء تقابل هذا الجدول. شرحها في فصل Controllers، بعد أن نبني المشروع.

## تمارين

### تمرين سهل

صنف كل سطر: Request أم Response، وأي جزء منه (Method أو Path أو Header أو Body أو Status).

1. `DELETE /books/2`
2. `404`
3. `Authorization: Bearer ...`
4. `{ "title": "Clean Code" }`

<details>
<summary>الحل</summary>

1. Request: Method هو `DELETE` و Path هو `/books/2`.
2. Response: Status.
3. Request Header في الحالة الشائعة. الخادم قد يعيد رؤوسًا أيضًا، لكن `Authorization` يرسله العميل.
4. Body. الاتجاه يعتمد على العملية: في الإنشاء يكون Request، وفي القراءة يكون Response. الشكل وحده لا يحدد الاتجاه.

</details>

### تمرين متوسط

العميل أرسل `POST /books` بجسم ينقصه العنوان. الخادم رفض الحفظ. اقترح Status وقل إن كان الجسم ضروريًا. لا تشترط نص الرسالة حرفيًا.

<details>
<summary>الحل</summary>

`400 Bad Request` يناسب بيانات عميل غير مقبولة. جسم الاستجابة مفيد لأنه يسمي الحقل الناقص، حتى تستطيع الواجهة إظهاره. الرمز وحده يقول "طلبك غير صالح" ولا يقول أي حقل.

</details>

### تمرين متقدم

طلب `GET /books/2` أعاد `200` وجسمًا فيه `"error": "not found"`. ما المشكلة في هذا العقد، وماذا تغيّر في سلوك الواجهة إذا أصلحت الرمز إلى `404`؟

<details>
<summary>الحل</summary>

الرمز `200` يعني نجاح القراءة. الواجهة التي تثق بالرمز ستعامل الكتاب كأنه موجود، ثم تتعثر عندما تقرأ الحقل `error`. مع `404` تستطيع الواجهة، وطبقة HTTP، وأي وسيط، أن تفهم الغياب من غير اتفاق سري على شكل JSON. جسم الخطأ يبقى مفيدًا للرسالة، والرمز يحمل المعنى.

</details>

## أسئلة مراجعة

- ما الأجزاء الأربعة التي تبحث عنها في Request؟
- ماذا يضيف Status ولا يغني عنه نص داخل JSON؟
- ماذا يخبرك `Content-Type`؟
- أي كائنات Node يغلّفها Express باسم `req` و `res`؟

## الخلاصة

Request يحدد العملية والهدف والسياق والحمولة. Response يحدد القرار والتمثيل. الرمز والجسم يؤديان وظيفتين مختلفتين.

## ماذا بعد؟

هذان الشكلان ليسا اختراع Express. هما HTTP. الدرس التالي يشرح البروتوكول: الطرق، والرموز، والرؤوس، ولماذا كل طلب مستقل عن الذي قبله.
