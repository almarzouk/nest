مشاكل المشاريع الكبيرة في Express

الهدف من هذا الدرس

تسمية الآلام التي تعالجها NestJS، كل ألم مع سببه، قبل أن نفتح صفحة الإطار الجديد كأنها قائمة Decorators.

المشكلة التي يحلها

Express يحل التوجيه. المشروع الكبير يسأل أسئلة أخرى:

  • أين أضع قاعدة "لا يُشحن طلب غير مدفوع"؟
  • من ينشئ كائن الوصول إلى قاعدة البيانات، وكم نسخة منه تعمل؟
  • كيف أختبر قاعدة السعر من غير فتح منفذ؟
  • كيف أعرف أن مسارًا جديدًا نسي فحص الهوية؟
  • كيف يبدأ مطور وصل هذا الأسبوع؟

إذا أجاب كل شخص بجواب مختلف، المستودع يصبح عدة تطبيقات تشترك في package.json.

توثيق Nest يضع هذا التشخيص في فقرة Philosophy: توجد مكتبات وأدوات كثيرة لـ Node، لكن مشكلة architecture تبقى من غير حل فعلي. Nest تقدم معمارية جاهزة لتطبيقات قابلة للاختبار، وقابلة للنمو، قليلة الارتباط، وقابلة للصيانة. المعمارية مستوحاة بشدة من Angular.

هذا الدرس يترجم تلك الفقرة إلى مشاهد داخل Express.

الفكرة ببساطة

الحرية الكاملة في بداية المشروع تصبح تكلفة تنسيق عندما يكبر عدد المسارات والناس. الإطار ذو الرأي يضيّق أماكن وضع الكود حتى يتشابه عمل الفريق.

التعريف التقني

مشروع Express كبير، في هذا الدرس، تطبيق HTTP طال أمده حتى صارت مسؤوليات الطلب موزعة بشكل غير قابل للتنبؤ: قواعد داخل المعالجات، وإنشاء خدمات بـ new في كل ملف، وإعدادات تُقرأ من process.env في عمق المنطق، واختبارات قليلة لأن تشغيل قطعة واحدة يتطلب تشغيل البقية.

لا يوجد حجم سطور يُعرّف "كبير". العلامة: خوف من تعديل مسار لأنك لا تعرف ماذا يلمس.

Mental Model

المطلوب في كل طلب                أين يعيش في Express حر؟

مطابقة المسار                    واضح: app.get
قواعد العمل                      غالبًا داخل المعالج
قواعد البيانات                   أحيانًا داخل المعالج أيضًا
الصلاحية                         middleware أحيانًا، و if أحيانًا
التحقق من الجسم                  في كل معالج بأسلوب مختلف
شكل الخطأ                        كل مسار يكتب JSON مختلف
بناء الكائنات                    new في أقرب ملف احتاجها

Nest لا تلغي الصفوف. تعطي كل صف اسم مكان: Controller، Service، Pipe، Guard، Exception Filter، Module.

أبسط مثال

معالج يبدو بريئًا في الأسبوع الأول:

import express from 'express';
import { db } from './db.js';

const app = express();
app.use(express.json());

app.post('/orders', async (req, res) => {
  const user = await db.query('select * from users where id = $1', [req.header('x-user-id')]);
  if (!user.rows[0]) {
    res.status(401).json({ error: 'nope' });
    return;
  }
  if (!req.body.bookId || req.body.quantity < 1) {
    res.status(400).json({ message: 'bad' });
    return;
  }
  const book = await db.query('select * from books where id = $1', [req.body.bookId]);
  const total = book.rows[0].price * req.body.quantity;
  await db.query('insert into orders(user_id, total) values ($1, $2)', [user.rows[0].id, total]);
  res.status(201).json({ ok: true });
});

app.listen(3000);

الكود يشتغل كسيناريو سعيد. وهو مثال على ما سنفككه، لا نموذج ننسخه. الاستعلامات هنا مبسطة وليست درس قاعدة بيانات.

شرح المثال

  • المسار يعرف شكل جداول users و books و orders. تغيير اسم عمود يفتح هذا الملف وكل شبيه له.
  • الهوية رأس اخترعه الفريق x-user-id. مسار آخر قد يقرأ Authorization. لا مكان واحد لقرار "من هو المستخدم".
  • التحقق if محلي. رسالة الخطأ { error: 'nope' } تختلف عن { message: 'bad' }. العميل يكتب حالتين.
  • السعر يُحسب هنا. مسار الخصم سيعيد الحساب أو ينساه.
  • db مستورد من ملف عام. الاختبار يستبدل هذا الملف أو يتصل بقاعدة حقيقية. الاثنان أغلى من تمرير اعتماد وهمي إلى دالة.
  • async بلا catch. رفض الـ Promise قد لا يتحول إلى JSON موحّد.
  • المعالج يفعل خمسة أعمال: هوية، تحقق، قراءة، حساب، كتابة. اسم post /orders لا يخبر قارئًا جديدًا أين يغيّر قاعدة الشحن عندما تُضاف.

لا شيء من هذا خطأ من Express. Express لم يعدك بمكان لهذه الأعمال. أنت لم تبنِ المكان بعد.

ماذا يحدث داخليًا عندما يكبر هذا الأسلوب؟

بعد عشرات المسارات يظهر نمط ثابت:

  1. Coupling: المعالج مربوط بالجدول وبالرأس وبالشكل الذي أرجعه. تغيير واحد يهز ثلاثة أشياء.
  2. صعوبة الاختبار: لا توجد دالة createOrder(input, deps) تستقبل اعتمادياتها. الاختبار يمر عبر HTTP و db الحقيقي، أو عبر حيل استبدال الاستيراد.
  3. نسخ متعددة من غير قصد: كل ملف يعمل new PaymentClient() فيفتح إعداداته وأسرار الاتصال بأسلوبه. لا حاوية تقول "هذه نسخة واحدة للتطبيق".
  4. نسيان العرضي: فحص المدير نُسخ في اثني عشر مسارًا وغاب عن الثالث عشر. لا يفشل البناء. يفشل الأمن في الإنتاج.
  5. لغة معمارية خاصة بالفريق: مجلد helpers و utils و services و lib من غير تعريف ما الذي يجوز أن يستورد ماذا.
  6. قراءة الإعداد في عمق القاعدة: process.env.TAX_RATE داخل الحساب. اختبار السعر يعتمد على بيئة المطوّر.

فقرة Nest تتحدث عن loosely coupled و testable. الكلمتان تصفان عكس هذه القائمة. Loose coupling: القطعة تعرف عقد جارتها لا تفاصيل جداولها. Testable: تستطيع تشغيل القطعة بمدخلات مصنوعة.

مثال عملي

شكل مجلد تراه بعد سنة إذا لم يتفق الفريق. الأسماء مألوفة وليست "خطأ إملائيًا"، والمشكلة التداخل:

src/
  routes/
    orders.js          يستورد db و stripe و mail
    ordersV2.js        نسخة لم يجرؤ أحد على حذفها
    books.js           فيه حساب الخصم أيضًا
  controllers/
    orderController.js يعيد نصف ما في routes/orders.js
  services/
    order.js
    orderService.js
  helpers/
    auth.js
    checkAuth.js
  utils/
    db.js
    price.js
  middleware/
    auth.js            غير موصول على كل الراوترات

مطور جديد يسأل: أين أضيف "إلغاء الطلب"؟ يوجد مرشحان أو ثلاثة. هذا هو ألم المعمارية، لا ألم app.get.

شكل Nest المقابل، كخريطة سنبررها لاحقًا لا كقالب تنسخه اليوم:

src/
  orders/
    orders.module.ts
    orders.controller.ts
    orders.service.ts
  books/
    books.module.ts
    books.controller.ts
    books.service.ts

المجلد حدود ميزة. الـ Controller يستقبل HTTP. الـ Service يملك القاعدة. الـ Module يصرح من يحق له استخدام من. حذف ordersV2 يصبح قرارًا لأن المكان الشرعي واحد.

أخطاء شائعة

  • لوم Express كأنه لا يصلح للإنتاج. يصلح، وكثير من الأنظمة عليه. الألم يظهر عندما لا يبني الفريق معمارية ويظن أن الإطار الرقيق سيوفرها.
  • القفز إلى Nest ونقل المعالج الضخم إلى جسد @Post كما هو. غيرت الزي وبقي الخلط. الدورة ستفصل الطبقات قبل مشروع REST.
  • إضافة طبقات Nest كلها في الأسبوع الأول (CQRS، و Microservices، وأحداث) هربًا من ملف كبير. هذا استبدال فوضى بفوضى أثقل. الفصول المتقدمة تقول متى تستحق كل أداة.
  • اعتبار الاختبار ترفًا يؤجَّل حتى "الاستقرار". الكود غير القابل للاختبار هو غالبًا الكود المرتبط بـ db و req معًا. الفصل بينهما يخدم الإنتاج قبل أن يخدم Jest أو Vitest.

متى نبقى على Express؟

خدمة حدودها مسار أو اثنان، وفريق يعرف الملف كله، ولا قواعد مخفية. أو مكتبة middleware تُستهلك داخل تطبيق آخر. Nest تستطيع أن تلف Express، لكن إدخالها له تكلفة تعلم. التكلفة تستحق عندما تظهر أعراض هذا الدرس.

متى تصبح Nest قرارًا مناسبًا؟

عندما تتكرر الأعراض: منطق داخل المسارات، إنشاء خدمات بـ new، اختبارات عالقة بالشبكة، وصلاحية تُنسى، ومجلدات بلا عقد. توثيق Nest يصف الناتج المطلوب: تطبيق قابل للاختبار، قابل للتوسع، ارتباطه ضعيف، وقابل للصيانة. هذه صفات هدف، لا سحر يحصل لأنك شغّلت nest new.

مقارنة

السؤال Express يتركه لك ما ستتعلمه في Nest
أين HTTP؟ المعالج Controller
أين القاعدة؟ حيث تشاء Service / Provider
من ينشئ الكائنات؟ new أو استيراد عام حاوية DI
من يرى من؟ أي ملف يستورد أي ملف Module يصرح بـ exports
أين التحقق؟ middleware أو if Pipe
أين المنع؟ middleware أو if Guard
أين شكل الخطأ؟ كل res.status Exception Filter
أين الالتفاف حول التنفيذ؟ دوال تغلف المعالج Interceptor

الجدول وعد دروس، لا اختصار لها.

تمارين

تمرين سهل

في معالج POST /orders أعلاه، سمِّ ثلاث مسؤوليات مختلفة يعيش بعضها فوق بعض.

الحل

إثبات هوية المستخدم، والتحقق من المدخلات، وحساب السعر مع الكتابة في الجداول. أي ثلاث من هذه تفي. تسجيل الخطأ غير الموجود مسؤولية غائبة.

تمرين متوسط

لماذا يصعب اختبار حساب total وحده في هذا الملف؟ ماذا تغيّر لو كانت الدالة priceOf(book, quantity) نقية لا ترى req ولا db؟

الحل

الحساب داخل المعالج بعد استعلامين. تشغيله يحتاج طلب HTTP وقاعدة تُرجع صفوفًا. دالة نقية تأخذ سعرًا وكمية وتعيد رقمًا تُختبر بأرقام، من غير منفذ ولا SQL. هذا فصل المسؤولية الذي سيصبح Service.

تمرين متقدم

الفريق أضاف app.use(requireAdmin) مرة واحدة قبل كل المسارات، فانكسرت صحة GET /books للزوار. ثم نقلوا الفحص إلى داخل بعض المعالجات فعاد النسيان. صف التوتر بين "مكان واحد" و "ليس كل المسارات". لا تكتب حل Nest؛ سمِّ فقط نوع الأداة التي ستبحث عنها لاحقًا.

الحل

الفحص العام يحمي المسارات الجديدة وينكسر على المسارات العامة. الفحص اليدوي يسمح بالاستثناء وينسى الحماية. نحتاج إعلانًا على المسار: هذا عام، وهذا يتطلب دورًا، مع أداة يناديها الإطار لا المطور في أول السطر. في Nest الاسم Guard، مربوط على مستوى التطبيق أو المتحكم أو المسار. تفاصيل الربط في فصل Guards، والترتيب في Request Lifecycle.

أسئلة مراجعة

  • ما المشكلة التي يقول توثيق Nest إن مكتبات Node لم تحلها جيدًا؟
  • لماذا new داخل كل مسار يصعّب الاختبار؟
  • ما العلامة العملية لمشروع Express صار "كبيرًا" بهذا المعنى؟
  • لماذا نقل المعالج كما هو إلى Nest لا يحل الازدواج؟

الخلاصة

Express يكفي للتوجيه ويترك المعمارية للفريق. عندما تتوزع القواعد والهوية والإنشاء على أسلوب كل ملف، التعديل والاختبار يصبحان تخمينًا. NestJS وُجدت لتعطي أماكن ثابتة لهذه المسؤوليات.

ماذا بعد؟

التشخيص جاهز. الدرس التالي يقرأ وعد Nest بكلمات التوثيق: ماذا تدّعي، وماذا لا تدّعي، وأي أفكار برمجة تجمعها.
