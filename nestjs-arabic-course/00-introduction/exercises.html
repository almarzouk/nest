تمارين الفصل

التمارين داخل كل درس تختبر ذلك الدرس. هذه الصفحة تربط المقدمة كلها. اكتب الجواب قبل فتحه.

لا يُطلب منك تشغيل Nest في هذا الفصل.

تمرين سهل — تسمية الأجزاء

وصل هذا السجل من أداة تطوير في المتصفح:

PATCH /books/2 HTTP/1.1
Host: localhost:3000
Content-Type: application/json
Authorization: Bearer abc

{"price": 28}

والرد:

HTTP/1.1 200 OK
Content-Type: application/json

{"id":"2","title":"Refactoring","price":28}
  1. من Client في هذه المحادثة؟
  2. ما Method، وما المورد؟
  3. أي جزء يثبت نوع الجسم؟
  4. لماذا هذا أقرب إلى REST من POST /updateBookPrice؟
الحل
  1. البرنامج الذي أرسل PATCH، غالبًا الواجهة أو أداة مثل curl. عملية المتجر هي Server.
  2. Method هي PATCH. المورد هو الكتاب 2، وعنوانه /books/2.
  3. Content-Type: application/json على الطلب وعلى الرد.
  4. لأن الفعل PATCH والمعرّف في المسار، لا فعل إنجليزي داخل عنوان خاص. الجسم يحمل الجزء المتغير فقط.

تمرين متوسط — Express ثم الحدود

اقرأ الدالة:

app.get('/books/:id/publish', async (req, res) => {
  const book = await db.query('update books set status = $1 where id = $2 returning *', [
    'published',
    req.params.id,
  ]);
  if (!req.header('x-admin')) {
    res.status(403).json({ message: 'no' });
    return;
  }
  res.json(book.rows[0]);
});
  1. ما مشكلة Method بالنسبة لمعنى HTTP؟
  2. ما مشكلة ترتيب فحص المدير بالنسبة لأثر قاعدة البيانات؟
  3. سمِّ مكانين في خريطة Nest تفصل إليهما "النشر" و "هل هو مدير؟" من غير كتابة الكود.
  4. ماذا يجعل الاختبار صعبًا هنا؟
الحل
  1. GET يغيّر status. الروابط وإعادة المحاولة والذاكرة الوسيطة تفترض أن GET لا يغيّر حالة الخادم. النشر POST على مورد عملية أو PATCH على حالة الكتاب.
  2. التحديث يحدث قبل فحص x-admin. زائر يستطيع النشر إذا وصل إلى المسار، ثم قد يرى 403 بعد أن تغيّرت البيانات. الفحص يسبق الأثر.
  3. قرار المدير في Guard. تغيير حالة الكتاب في Service يناديها Controller. التحقق من شكل المعرّف، إن وُجد، في Pipe.
  4. الدالة تحتاج HTTP و db معًا، والقاعدة مكتوبة داخل المعالج. لا توجد دالة نشر تستقبل كتابًا وصلاحية جاهزة وتُختبر وحدها.

تمرين متقدم — تتبع مسار Nest

طلب POST /books بجسم { "title": "", "price": -1 } على تطبيق فيه:

  • Middleware يحلّل JSON
  • Guard يسمح بالإنشاء للموظفين، والطلب من موظف مقبول
  • Pipe يرفض العنوان الفارغ والسعر السالب
  • Service كانت ستحفظ الكتاب
  • Filter عام يحوّل الأخطاء غير المتوقعة إلى 500

أجب:

  1. رتّب ما الذي يعمل وما الذي لا يصل إليه التنفيذ.
  2. فشل الـ Pipe يرمي استثناء تحقق. ماذا يحدث لباقي المحطات، ومن أين يبدأ اختيار الفلاتر؟
  3. لو نجح الشكل ورمت الخدمة خطأ قاعدة بيانات غير ممسوك، من يراه أولًا: فلتر على الدالة، أم فلتر على المتحكم، أم الفلتر العام؟
  4. لماذا لا نضع فحص السعر السالب داخل Middleware عام على كل المسارات؟
الحل
  1. Middleware يحلّل JSON، ثم Guard يقبل الموظف. Pipe يرفض الجسم. المتحكم والخدمة لا يعملان، ولا يُحفظ كتاب.
  2. فشل التحقق استثناء غير ممسوك بعد اختيار المسار. بقية محطات النجاح تُتخطى، والطلب يدخل Exception Filters من الأخص إلى الأعم: Route ثم Controller ثم Global. أول فلتر يلتقط هذا النوع هو الذي يكتب الرد، والافتراضي في Nest لخطأ التحقق من هذا النوع يكون ضمن فئة 400. الفلتر العام الذي يحوّل كل شيء إلى 500 يراه فقط إذا لم يسبقه فلتر أخص، ولذلك فلتر "غير متوقع" يجب أن يترك أخطاء التحقق تمر بشكلها. تفاصيل @Catch في فصل Exception Filters.
  3. فلتر الدالة (Route) أولًا، ثم فلتر المتحكم، ثم العام.
  4. Middleware العام إما يفحص أجسامًا ليست كتبًا، أو يمتلئ بشروط على المسارات. شكل الكتاب يعيش مع عقد الكتاب (DTO) ويُطبَّق حيث يُستخدم العقد.

سؤال تصميم أخير

اكتب جدولًا من خمسة صفوف لعملية "إضافة مراجعة على كتاب": HTTP الذي تختاره، ومن Client، وأين تعيش قاعدة "المراجعة لا تتجاوز 500 حرف" في خريطة Nest، وأين تعيش قاعدة "المستخدم اشترى الكتاب"، وما الذي لا يجوز أن يعرفه كائن JSON الخارج.

الحل

إجابة مقبولة:

البند الاختيار
HTTP POST /books/:id/reviews مع 201
Client الواجهة أو التطبيق الذي أرسل الطلب
حد الأحرف Pipe / DTO لأنه شكل مدخل
شرط الشراء Service لأنه قاعدة عمل تحتاج بيانات طلبات، لا شكل النص فقط
لا يخرج في JSON أسرار داخلية مثل هامش ربح الكتاب، أو بريد الموظف، أو أي حقل لم يدخل العقد

حد الأحرف يمكن أن يُعاد في الخدمة كحماية ثانية، لكن مكان إعلان العقد هو DTO.
