API و REST API

الهدف من هذا الدرس

تسمية العقد بين برنامجين، وتمييز REST API عن الصفحة وعن المكتبة الداخلية.

المشكلة التي يحلها

فريق الواجهة وفرق الجوال وفريق الخادم لا يشاركون الذاكرة. يحتاجون اتفاقًا مكتوبًا بالسلوك: أي عنوان، وأي فعل، وأي جسم، وأي رمز، وأي شكل JSON.

إذا بقي الاتفاق في رأس شخص واحد، كل عميل جديد يكتشف الواجهة بالتجربة والأخطاء.

الفكرة ببساطة

API هي الواجهة التي يسمح لك برنامج أن تستخدمه من خلالها، من غير أن تفتح داخله.

REST API هي API على HTTP مصممة بأسلوب الموارد الذي مر في الدرس السابق، وتمثيلها الشائع JSON.

التعريف التقني

Application Programming Interface: مجموعة عمليات ظاهرة، بمدخلات ومخرجات متفق عليها، تخفي التنفيذ.

في مكتبة JavaScript، الـ API هي الدوال التي تصدّرها. في هذه الدورة، عندما نقول API من غير قيد، نقصد Web API: عمليات يصل إليها Client عبر الشبكة.

REST API: Web API تخاطب موارد بعناوين HTTP وأفعاله، وتنقل تمثيلات. توثيق Nest يسمي هذا النوع من التطبيقات عند الحديث عن Controllers و OpenAPI.

Mental Model

عقد عام                         تنفيذ مخفي
GET /books/:id                 SELECT و Prisma وملفات داخل src/

العميل يرى العقد
الخادم يبدل التنفيذ من غير أن يبدل العنوان

الاستقرار المطلوب هو استقرار العقد، لا استقرار أسماء الملفات الداخلية.

أبسط مثال

عقد كتاب واحد:

البند الاتفاق
العملية قراءة كتاب
الطلب GET /books/2
نجاح 200 و JSON فيه id و title و price
غياب 404 و JSON فيه رسالة
العميل لا يعرف اسم الجدول، أو أن السعر محسوب من خصم داخلي

هذا العقد كافٍ لكتابة الواجهة بالتوازي مع الخادم.

شرح المثال

  • العنوان والفعل جزء من العقد، لا تفصيل تنفيذ.
  • أسماء الحقول جزء من العقد. تغيير title إلى name يكسر العملاء.
  • إضافة حقل جديد غالبًا أسهل على العملاء القديمين من حذف حقل أو تغيير نوعه. هذا تمهيد للإصدارات، وفصل API Versioning سيضع سياسة.
  • رمز الحالة جزء من العقد، كما ثبّتنا في درس الطلب والاستجابة.

ماذا يحدث داخليًا؟

  1. العميل يبني HTTP Request حسب العقد.
  2. الشبكة توصله إلى عملية Nest.
  3. التوجيه يجد الدالة المرتبطة بالمسار.
  4. الدالة تستدعي منطق العمل والمخزن.
  5. الناتج يُحوَّل إلى التمثيل المتفق عليه، لا إلى شكل الجدول بالضرورة.
  6. Response ترجع. العميل يبرمج ضد العقد، لا ضد سجلات خادمك.

نقطة داخلية ستكبر لاحقًا: إذا أعادت الدالة كائن JavaScript عاديًا، فهناك طبقة في Nest تحوله إلى JSON وتكتب 200 ما لم تغيّر ذلك. اسم السلوك في التوثيق Standard response handling. سنشرحه مع Controllers. الآن يكفي أن العقد هو ما يخرج على السلك، لا ما طبعته في console.log.

مثال عملي

REST API صغيرة لملاحظات:

GET    /notes
POST   /notes
GET    /notes/:id
PATCH  /notes/:id
DELETE /notes/:id

شكل الإنشاء الذي يرسله العميل:

{ "title": "شراء حبر", "body": "أسود" }

شكل ما يعيده الخادم:

{ "id": "8f0", "title": "شراء حبر", "body": "أسود", "createdAt": "2026-10-05T07:00:00.000Z" }

العميل لا يرسل id ولا createdAt عند الإنشاء. الخادم يملكهما. هذا فرق بين مدخلات العقد و مخرجاته. في Nest سيصبح لكل منهما DTO، حتى لا نثق بكل حقل يرسله العميل.

وثّق هذا الجدول قبل كتابة الواجهة. لاحقًا سيولّد @nestjs/swagger وصف OpenAPI من الكود. الأداة لا تخترع العقد إذا كان الكود بلا شكل واضح.

أخطاء شائعة

  • تسمية أي دالة داخل المشروع API. الدالة الداخلية تفصيل. الـ API هنا ما يعبر حدود العملية.
  • كسر حقل مستخدم لأن "لا أحد يفترض أن يعتمد على الاسم". إذا خرج في JSON فهناك من اعتمد عليه.
  • جعل شكل JSON نسخة من جدول قاعدة البيانات. غيّرت العمود فانكسر الجوال. التمثيل طبقة مستقلة.
  • توثيق العقد في رسالة دردشة فقط. الدردشة تضيع. العقد يعيش مع الكود، ثم مع OpenAPI.

متى ننشر REST API؟

عندما يوجد عميل آخر: صفحة، جوال، شريك، أو حتى واجهة سطر أوامر يكتبها فريق ثانٍ. حدود الشبكة هي مكان العقد.

متى لا نحتاج هذه الطبقة؟

برنامج يعمل كله في عملية واحدة ولا يناديه أحد عبر الشبكة. ما زلت تستطيع ترتيب الكود، لكن لا توجد REST API بعد. Nest يقدر أن يعمل كتطبيق Standalone بلا HTTP، وهذا درس متأخر في أدوات CLI.

مقارنة

Library API Web API REST API
أين تُستدعى داخل العملية، import عبر الشبكة عبر HTTP بأسلوب موارد
شكل الاستدعاء دالة Request Method + مسار + تمثيل
مثال JSON.parse أي خدمة HTTP GET /notes/8f0

Express ينشر Web API عندما تربط المسارات. الالتزام بأسماء الموارد هو ما يجعلها REST API. Nest لا يضيف بروتوكولًا جديدًا؛ يرتب الكود الذي يفي بهذا العقد.

Express:
app.get('/notes', handler)

NestJS لاحقًا:
@Get()
findAll() {}

تمارين

تمرين سهل

من القائمة، ما الذي يعتبر جزءًا من عقد REST API؟

  1. GET /notes/:id يعيد 404 عند الغياب.
  2. اسم ملف notes.service.ts.
  3. الحقل title نص في الاستجابة.
  4. اسم جدول SQL.
الحل

1 و 3 جزء من العقد لأن العميل يراهما. 2 و 4 تنفيذ داخلي يمكن تغييره مع بقاء العقد.

تمرين متوسط

العميل كان يرسل { "title": "..." } وأنت تريد دعم لغة ثانية. اقترح إضافة لا تكسر العملاء الحاليين، من غير نظام i18n كامل.

الحل

أبقِ title كما هو للعملاء الحاليين. أضف حقلًا جديدًا اختياريًا مثل titleAr أو كائن titles إذا اتفق الفريق على ذلك من الإصدار الأول. حذف title أو تغييره من نص إلى كائن يكسر من يقرأه كنص. الإضافة الاختيارية أهون من تغيير النوع.

تمرين متقدم

خدمة داخلية تبحث في قاعدة البيانات وتُستدعى من Controller مباشرة، ثم قررتم أن يفتحها تطبيق الجوال أيضًا. ماذا يصبح API، وما الذي يجب أن يتوقف الجوال عن معرفته؟

الحل

الـ API تصبح عمليات HTTP المتفق عليها، لا توقيع الدالة الداخلية. الجوال يعرف المسار والحقول والرموز. يتوقف عن معرفة أسماء الأعمدة وترتيب الاستدعاء داخل الخدمة. لو نقلت البحث إلى خدمة أخرى وأبقيت GET /notes?q= فالعقد يبقى.

أسئلة مراجعة

  • ما الذي تخفيه API؟
  • ما الشرطان اللذان يجعلان Web API تستحق اسم REST API في هذه الدورة؟
  • لماذا إضافة حقل أهون من تغيير نوع حقل؟
  • أين يعيش العقد: في شكل الجدول أم في شكل الرسالة؟

الخلاصة

API عقد على حدود البرنامج. REST API عقد HTTP حول موارد وتمثيلات JSON. العملاء يُبرمجون ضد العقد، والخادم حر داخل حدوده ما دام الكلام على السلك ثابتًا.

ماذا بعد؟

العقد واضح. نحتاج بيئة تشغّل JavaScript خارج المتصفح حتى نكتب الطرف الخادم. تلك البيئة هي Node.js.
