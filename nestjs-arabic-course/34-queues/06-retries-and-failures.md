# Retries و Failed Jobs

## الهدف من هذا الدرس

تحديد عدد إعادات القص والانتظار بينها، وجعل التنفيذ آمنًا إن اشتغلت المهمة مرتين.

## المشكلة التي يحلها

خطأ قرص لحظي يستحق محاولة ثانية. خطأ «الكتاب حُذف» لا يستحق خمسًا. وإن أرسلت بريد النشر من المحاولة الأولى ثم رميت بعدها، المحاولة الثانية ترسله مرة أخرى. السياسة رقم. الأمان من التكرار سلوك داخل `process`.

## الفكرة ببساطة

خيارات `add` تتضمن `attempts` و `backoff`. بعد استنفاد العدد تنتقل المهمة إلى حالة فاشلة تقدر أن تراقبها. العمل الذي له أثر خارجي، مثل البريد، يتحقق من أثر سابق قبل الإرسال. القص الذي يكتب الملف نفسه فوق نفسه أسهل تكرارًا من البريد.

## التعريف التقني

```ts
await this.covers.add('resize', payload, {
  jobId: `resize:${payload.bookId}`,
  attempts: 5,
  backoff: { type: 'exponential', delay: 1000 },
  removeOnComplete: 100,
  removeOnFail: false,
});
```

`attempts: 5` تشمل المحاولة الأولى في عدّ BullMQ المعتاد: تأكد من المعنى في إصدار المكتبة التي ثبتّها واكتب الرقم الذي ينتج أربع إعادات أو خمس تشغيلات كما قررت، وثبّته في اختبار. `backoff` الأسي يزيد الانتظار حتى لا تطرق قرصًا معطلًا كل ثانية. `removeOnFail: false` يبقي المهمة الفاشلة للتشخيص. لا تترك الفشل بلا أثر في السجل.

داخل القص الآمن للتكرار:

```ts
if (book.coverStatus === 'ready' && book.coverKey === coverKey) return;
```

إن اكتمل العمل ثم أُعيد بسبب مهلة بعد الكتابة، الخروج الهادئ يمنع قصًا بلا داعٍ. للبريد:

```ts
if (await this.mail.alreadySent(bookId, 'published')) return;
await this.mail.sendPublished(bookId);
await this.mail.markSent(bookId, 'published');
```

علّم الإرسال بعد نجاح المزوّد. إن علّمت قبله ثم رميت، لن تُعاد الرسالة. إن أرسلت ثم سقطت قبل العلامة، قد تُرسل مرتين. النافذة تضيق بالعلامة بعد النجاح وبمفتاح تكرار عند المزوّد إن وُجد.

## Mental Model

```text
فشل قابل للإصلاح -> رمي -> انتظار -> process من جديد
أثر سبق إنجازه -> return
استنفاد المحاولات -> مهمة فاشلة + coverStatus failed
```

## أبسط مثال

عند استنفاد المحاولات حدّث الصف حتى لا يبقى `pending` للأبد:

```ts
async process(job: Job<ResizePayload>): Promise<void> {
  try {
    await this.covers.resize(job.data.bookId, job.data.coverKey);
  } catch (error) {
    const last = job.attemptsMade + 1 >= (job.opts.attempts ?? 1);
    if (last) {
      await this.covers.markFailed(job.data.bookId, job.data.coverKey);
    }
    throw error;
  }
}
```

أعد الرمي حتى تسجّل BullMQ الفشل. `markFailed` لا يبتلع الخطأ.

## شرح المثال

`attemptsMade` عدد ما بدأ. على المحاولة الأخيرة اكتب `failed` على الكتاب إن كان `coverKey` ما زال مطابقًا، ثم ارمِ. الواجهة ترى `failed` لا `pending`. مهمة الإصلاح اليدوي تستطيع إعادة `add` بعد تصليح القرص.

## ماذا يحدث داخليًا؟

BullMQ تؤخر المهمة الفاشلة حسب `backoff` ثم تعيدها إلى عامل متاح. الحمولة لا تتغير بين المحاولات. لذلك إن كانت الحمولة كائنًا قديمًا فكل المحاولات القديمة. مع `bookId` كل محاولة تقرأ القاعدة من جديد، وهذا سبب تصميم المنتج. مهمة في حالة failed لا تُعاد وحدها حتى تعيد إدراجها أو تستعمل أداة المكتبة لإعادة التشغيل.

## مثال عملي

افصل الطابور إن اختلفت السياسة:

| المهمة | attempts | سبب |
| --- | --- | --- |
| `resize` | 5 بانتظار أسي | القرص يرمش |
| `sendPublished` | 3 | البريد أثر خارجي ويحتاج علامة إرسال |

لا تضع الاثنين في `process` واحد حتى لا يعيد القص إرسال البريد.

## أخطاء شائعة

- `catch` فارغ داخل `process` فيُحسب النجاح.
- إعادة لا نهائية عبر `attempts` ضخم على خطأ تحقق لن يتغير.
- بريد بلا `alreadySent`.
- `removeOnFail: true` ثم انعدام أثر للتشخيص.

## متى نستخدمه؟

على كل `add` منتج. الرقم مكتوب بجانب نوع العمل لا متروكًا للافتراض.

## متى لا نستخدمه؟

كحل لتكرار `POST` من الواجهة. الواجهة تعيد الطلب، والطابور يعيد المهمة. الاثنان يحتاجان `jobId` وعلامة أثر، لا رقمًا واحدًا مشتركًا بلا تمييز.

## مقارنة

| الخطأ | الإعادة |
| --- | --- |
| انقطاع قرص | نعم، حتى الحد |
| كتاب حُذف | لا، خروج هادئ |
| بريد أُرسل وعُلّم | لا، خروج هادئ |
| بريد أُرسل ولم يُعلَّم | قد يتكرر، ضيّق النافذة |

### تمرين متوسط

لماذا تعيد رمي الخطأ بعد `markFailed`؟

<details>
<summary>الحل</summary>

</details>

### تمرين متقدم

لماذا علامة «أُرسل» بعد نجاح المزوّد لا قبله؟

<details>
<summary>الحل</summary>

العلامة السابقة تمنع الإعادة رغم أن الرسالة لم تخرج. العلامة اللاحقة قد تسمح بتكرار نادر إن سقطت العملية بينهما، وهو أهون من ضياع الرسالة، ويُضيَّق بمفتاح عند المزوّد.

</details>

## أسئلة مراجعة

- ماذا يحدث بعد آخر محاولة؟
- لماذا القص أسهل تكرارًا من البريد؟
- أي حالة تغطيها الواجهة غير `pending` و `ready`؟

## الخلاصة

حدد `attempts` و `backoff`، واترك الفشل النهائي مرئيًا على الصف. ارمِ ما قد يُصلح، واخرج بهدوء إن كان الأثر قد تم أو لم يعد مطلوبًا.

## ماذا بعد؟

ما الذي تختلف به حزمة Bull القديمة حتى لا تُنسخ زينتها في هذا المشروع.
