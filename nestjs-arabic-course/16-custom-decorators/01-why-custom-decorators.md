# لماذا Decorators مخصصة

## الهدف من هذا الدرس

معرفة لماذا تُخفى قراءة الطلب ومفاتيح البيانات خلف زينة، وما الذي يحتاجه TypeScript حتى تعمل الزينة القديمة.

## المشكلة التي يحلها

كل دالة في الشباك تبدأ بـ `const user = request.user` أو تبحث عن النص `'roles'` و `'isPublic'` في أكثر من حارس. المفتاح النصي يُكتب غلطًا في ملف واحد فيصمت الحارس ويفتح المسار. التوقيع لا يُظهر أن الدالة تحتاج المستخدم الحالي.

## الفكرة ببساطة

الزينة المخصصة اسم يظهر عند الدالة أو المعامل: `@CurrentUser()` و `@Roles(['refund'])` و `@Public(true)`. البناء نفسه في الدروس التالية. هنا السبب، وإعداد المترجم الذي يبقي بيانات الزينة حتى الإقلاع.

## التعريف التقني

Nest مبني على زينة. زينة المعامل الجاهزة مثل `@Body()` و `@Param()` تغطي HTTP العام. ما يتكرر في تطبيقك وليس في الإطار يُلف في زينة باسم المجال.

نوعان سيُبنيان لاحقًا:

- زينة معامل عبر `createParamDecorator` ترجع قيمة إلى وسيط الدالة.
- زينة بيانات عبر `SetMetadata` أو `Reflector.createDecorator` يقرأها حارس بـ `Reflector`.

الزينة التقليدية في TypeScript، وهي التي تعتمد عليها بيانات الحقن `design:paramtypes`، تحتاج في `tsconfig`:

```json
{
  "compilerOptions": {
    "experimentalDecorators": true,
    "emitDecoratorMetadata": true
  }
}
```

ومرة عند الإقلاع:

```ts
import 'reflect-metadata';
```

مشاريع Nest CLI تضع ذلك. من غيره تُترجم الزينة بلا بيانات الأنواع التي يقرأها `ValidationPipe` والحاوية. هذا الدرس لا يستبدل ذلك بزينة معيار TC39. الإعداد أعلاه هو مسار الزينة القديمة الذي ما زال مسار البيانات الوصفية في التطبيق المولَّد.

حذف الإعداد قد يُبقي البناء أخضر ويكسر الفحص أو الحقن وقت التشغيل. ذلك امتداد درس وقت التشغيل في فصل DTO، مذكور هنا لأن الزينة الجديدة ستجلس على الإعداد نفسه.

## Mental Model

```text
قبل: request.user و SetMetadata('roles', ...)
بعد: @CurrentUser() و @Roles(['refund'])
المترجم: experimentalDecorators + emitDecoratorMetadata + reflect-metadata
```

الاسم على الدالة وثيقة. المفتاح النصي تفصيل داخل ملف الزينة.

## أبسط مثال

توقيع قبل الزينة:

```ts
@Post('refund')
refund(@Req() request: { user?: { name: string } }): { name: string } {
  const name = request.user?.name ?? 'unknown';
  return { name };
}
```

التوقيع بعد ما سيُبنى في درس `@CurrentUser`:

```ts
@Post('refund')
refund(@CurrentUser() user: { name: string }): { name: string } {
  return { name: user.name };
}
```

الدالة الثانية لا تعرف من أين جاء المستخدم. الاختبار يمرر الوسيط مباشرة إن فصلت الخدمة عن HTTP.

## شرح المثال

- `@Req()` يعرض كائن المنصة كله، ومنها ترويسات لا تحتاجها الدالة.
- الزينة تضيق المعامل إلى المستخدم.
- الحارس ما زال هو من يلصق `request.user` قبل الدالة. الزينة لا تثبت الهوية. هي تقرأ ما لصقه الحارس أو Middleware.
- `@Public` لا تفتح المسار وحدها. الحارس العام يقرأ العلامة ويرجع `true`. الزينة بلا قارئ لا تغيّر الدورة.

## ماذا يحدث داخليًا؟

عند تحميل الصنف تعمل دوال الزينة وتسجّل بيانات عبر `reflect-metadata` أو عبر ما يخزنه `Reflector.createDecorator`. عند الطلب، معامل الزينة المخصصة يُستدعى في بناء وسائط الدالة، بعد الحارس، ويمكن أن يمر عليه أنبوب إن فعّلت خياره. بيانات `@Roles` تُقرأ في الحارس قبل الدالة، لا داخلها.

`import type` لا يلصق زينة. الزينة استيراد قيمة. ملف الزينة يُستورد بلاحقة `.js` في ESM.

إن أُغلق `emitDecoratorMetadata` تبقى بعض زينات Nest التي تخزن بياناتها بنفسها، وقد يضيع نوع المعامل في الحقن. لا تفصل إعداد الزينة عن مشروع CLI من أجل ملف واحد.

## مثال عملي

ثلاثة تكرارات في الشباك اليوم: قراءة `user` في `refund` و `list` و `audit`. مفتاح `'deskRoles'` في حارس و `'roles'` في آخر فلا يُمنع الاسترداد. جمع القراءة في `@CurrentUser` والمفتاح داخل ملف `@Roles` واحد يجعل الغلط في مكان واحد يظهر في المراجعة. الصحة ما زالت مغلقة بحارس عام إلى أن تُعلَّم بـ `@Public` ويحترمها الحارس. الإعداد في `tsconfig` يبقى كما ولّده CLI.

## أخطاء شائعة

- توقع أن الزينة تستبدل الحارس أو الفلتر.
- نسخ المفتاح النصي في كل حارس بعد بناء الزينة. القارئ يستورد الثابت من ملف الزينة.
- إغلاق `experimentalDecorators` ثم مطاردة أخطاء حقن غامضة.
- وضع منطق الحجز داخل مصنع الزينة. المصنع يستخرج أو يلصق بيانات فقط.

## متى نستخدمه؟

حين يتكرر استخراج من الطلب أو تتكرر بيانات على الدالة في أكثر من مسار، والاسم يوثّق العقد أفضل من `@Req()`.

## متى لا نستخدمه؟

لاستخراج استُخدم مرة في دالة واحدة. `@Req()` هناك أوضح. ولا لقاعدة مقعد. تلك خدمة واستثناء. ولا تفتح الصحة بزينة لا يقرأها الحارس.

## مقارنة

| | `@Req()` ومفتاح نصي | زينة باسم المجال |
| --- | --- | --- |
| التوقيع | كائن الطلب | مستخدم أو أدوار |
| الغلط في المفتاح | صامت ومتفرق | محصور في ملف الزينة |
| من يقرر الإذن | ما زال الحارس | ما زال الحارس |
| المترجم | — | زينة قديمة مع إصدار البيانات |

## تمارين

### تمرين سهل

ما الذي لا تفعله `@CurrentUser()` بدل الحارس؟

<details>
<summary>الحل</summary>

لا تثبت الهوية. تقرأ `user` الذي لصقه الحارس أو Middleware. من غير لصق تصل القيمة فارغة.

</details>

### تمرين متوسط

ما الإعدادان في `compilerOptions` وما الاستيراد عند الإقلاع لمسار الزينة القديمة؟

<details>
<summary>الحل</summary>

`experimentalDecorators` و `emitDecoratorMetadata`، مع `import 'reflect-metadata'` مرة في الإقلاع.

</details>

### تمرين متقدم

حارس عام يغلق الصحة، وأُضيف `@Public` على `GET /health` من غير تعديل الحارس. لماذا الرد ما زال `401`؟

<details>
<summary>الحل</summary>

العلامة بيانات فقط. الحارس يجب أن يقرأها بـ `Reflector` ويرجع `true` قبل فحص الترويسة. الزينة بلا قارئ لا تغيّر `canActivate`.

</details>

## أسئلة مراجعة

- ماذا تخفي الزينة عن المتحكم؟
- لماذا يبقى الحارس مسؤولًا عن الإذن؟
- ما دور `reflect-metadata`؟
- متى تبقي `@Req()`؟

## الخلاصة

الزينة المخصصة اسم لعقد يتكرر: معامل أو بيانات دالة. الحارس والفلتر يبقيان من ينفذ السياسة. الزينة القديمة تحتاج إصدار البيانات و `reflect-metadata` كما في مشروع CLI.

## ماذا بعد؟

الدرس التالي `createParamDecorator`: مصنع زينة المعامل التي تقرأ السياق.
