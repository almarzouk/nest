Membership و Roles و Permissions

الهدف من هذا الدرس

تمثيل عمل الشخص داخل مكتبة رف: عضوية بدور، والدور يُترجم إلى صلاحيات تُفحص على المسار لا تُخزَّن في JWT طويل.

المشكلة التي يحلها

حقل user.role = admin يجعل الشخص مديرًا في كل المكتبات. أو تُنسخ قائمة صلاحيات داخل الرمز فتبقى بعد ما خُفض دوره إلى أن تنتهي العائلة. موظف المخزن يستطيع نشر الكتب لأن المسار فحص تسجيل الدخول فقط.

الفكرة ببساطة

Membership ثلاثية: مستخدم، منظمة، دور. الأدوار في رف قليلة: owner, editor, clerk. كل دور مجموعة صلاحيات مثل books.publish. الحارس يقرأ الدور من القاعدة (أو من ذاكرة طلب) بعد ما عرف المستأجر، ثم يسمح أو يمنع.

التعريف التقني

الجدول مفتاحه (userId, organizationId). الدور قيمة مغلقة لا نصًا حرًا من الجسم عند الدعوة إلا إن كان الداعي يملك members.invite. الصلاحيات خريطة في الكود لا صفوف يعدلها كل طلب. @nestjs/authorization في التوثيق الحالي يعبر عن الصلاحيات كسياسات؛ يمكنكم حارسًا بسيطًا يفحص الخريطة إن لم تبنوا سياسات كاملة بعد. الدور لا يُوضع في claims الدائمة لعائلة التحديث، كما في درس التدوير: validate أو حارس المستأجر يحمّل العضوية. 403 عند نقص الصلاحية بعد نجاح المصادقة. 401 إن غاب الإثبات.

Mental Model

الطلب: user + tenant
→ Membership.role
→ permissions(role)
→ books.publish ؟

أبسط مثال

const permissions = {
  owner: ['books.publish', 'members.invite', 'billing.read'],
  editor: ['books.publish'],
  clerk: ['books.read'],
} as const;

export function allows(role: keyof typeof permissions, permission: string) {
  return (permissions[role] as readonly string[]).includes(permission);
}

شرح المثال

  • الخريطة في الكود حتى تُراجع الصلاحيات في PR.
  • owner ليس تجاوزًا سحريًا في الحارس. هو دور لديه المفاتيح صراحة.
  • إضافة صلاحية تعني تعديل الخريطة واختبار المسار.

ماذا يحدث داخليًا؟

  1. السياق فيه userId و organizationId.
  2. استعلام العضوية findUnique على الزوج. الغياب 403.
  3. allows(role, 'books.publish') قبل أثر النشر.
  4. الدعوة تنشئ عضوية clerk أو editor لا owner ثانيًا إلا بقاعدة مكتوبة.
  5. إزالة العضوية تسري في الطلب التالي لأن المصدر القاعدة لا الرمز القديم وحده. access القصير قد يتأخر حتى exp إن دفنتم الدور فيه؛ لذلك لا تدفنوه.

مثال عملي

@Injectable()
export class PublishGuard implements CanActivate {
  constructor(private readonly memberships: { role: (userId: string, orgId: string) => Promise<keyof typeof permissions | null> }) {}

  async canActivate(context: ExecutionContext) {
    const req = context.switchToHttp().getRequest<{ user: { id: string } }>();
    const role = await this.memberships.role(req.user.id, currentTenantId());
    if (!role || !allows(role, 'books.publish')) throw new ForbiddenException();
    return true;
  }
}

ضعوا الحارس على POST /books/:id/publish لا على كل المتحكم إن كانت القراءة لـ clerk مباحة.

أخطاء شائعة

  • دور عام على User.
  • فحص الدور في الواجهة فقط.
  • owner في الجسم عند POST /members.
  • صلاحية نصية يرسلها العميل في ترويسة.

متى نستخدمه؟

بمجرد وجود موظف غير المالك. حتى المالك الوحيد صف عضوية حتى لا يتخصص المسار لاحقًا.

متى لا نستخدمه؟

لا تبنوا محرك صلاحيات لكل حقل كتاب في اليوم الأول. ابدأوا بأفعال واضحة. ولا تستبدلوا العزل بالدور: المدير يرى كتب مكتبته لا كتب المنصة كلها.

الفحص 401 403

تمارين

تمرين سهل

clerk ينشر كتابًا. ما الرمز؟

الحل
  1. هو معروف الهوية وعضو، والصلاحية غير موجودة في خريطة clerk.

تمرين متوسط

لماذا لا يكفي role داخل access token لعشرين دقيقة؟

الحل

خفض الدور أو حذف العضوية لن يظهر حتى ينتهي الرمز. حمّلوا العضوية من القاعدة في الحارس. أبقوا الرمز قصيرًا إن بقي فيه أي تلميح.

تمرين متقدم

مالك يدعو مالكًا ثانيًا. ما القاعدة التي تمنعون بها فقدان آخر مالك عند الحذف؟

الحل

الحذف والتخفيض يرفضان إن كان صف owner الوحيد. نقل الملكية معاملة: ترقية العضو الآخر ثم تخفيض الأول. لا delete على عضوية المالك الأخير.

أسئلة مراجعة

  • ما مفتاح العضوية؟
  • أين تعيش خريطة الصلاحيات؟
  • ما فرق 401 و 403 هنا؟
  • لماذا الدور ليس على جدول المستخدم؟

الخلاصة

العضوية تربط شخصًا بمكتبة بدور. الدور مفاتيح ثابتة في الكود. الحارس يقرأها من القاعدة بعد المستأجر. العزل يبقى قيد الاستعلام حتى للمدير.

ماذا بعد؟

المكتبة والأعضاء واضحون. الدرس التالي حد الاشتراك والفاتورة كحد خدمة لا كشاشة دفع فقط.
