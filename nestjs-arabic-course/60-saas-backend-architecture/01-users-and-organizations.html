User و Organization

الهدف من هذا الدرس

فصل الشخص عن مكتبة رف: User حساب دخول، و Organization المستأجر الذي يملك الكتب والفاتورة.

المشكلة التي يحلها

جدول users فيه libraryName و plan. الموظف الثاني لا يُضاف إلا بنسخ كلمة مرور الأول. انتقال الشخص إلى مكتبة أخرى ينسخ كتالوجًا أو يترك فواتير على بريده الشخصي.

الفكرة ببساطة

المستخدم يُوثَّق مرة. المنظمة كيان له اسم وحالة. العلاقة بينهما عضوية في الدرس التالي، لا عمود وحيد user.organizationId إن كان الشخص قد يعمل في مكتبتين. الكتب تشير إلى organizationId وهذا هو tenantId في فصل العزل.

التعريف التقني

User: id, email, أسرار الدخول في المخزن الذي لا يخرج من مستودع المصادقة. Organization: id, name, slug للنطاق slug.raf.example. لا تضعوا stripeCustomerId على المستخدم إن كانت الفاتورة على المكتبة. إنشاء أول مكتبة مع أول مدير عملية واحدة: صف منظمة وصف عضوية. حذف المستخدم لا يحذف المنظمة إن بقي أعضاء أو فواتير.

Mental Model

User ── Membership ── Organization ── Books / Subscription

أبسط مثال

model User {
  id    String @id
  email String @unique
}

model Organization {
  id   String @id
  name String
  slug String @unique
}

شرح المثال

  • البريد فريد على الشخص لا على المكتبة.
  • slug فريد لأنه مضيف. اسم العرض قد يتكرر.
  • لا علاقة books على User. الكتالوج للمنظمة.

ماذا يحدث داخليًا؟

  1. التسجيل ينشئ User فقط، أو ينشئ منظمة إن كان عقد المنتج «مكتبة فورًا».
  2. اختيار المكتبة في الجلسة يكتب سياق المستأجر.
  3. POST /organizations للشخص الذي يملك أكثر من مكتبة، مع عضوية مالك.
  4. الاستعلامات التشغيلية تستخدم organizationId من السياق.
  5. لوحة المنصة، لا API المكتبة، هي التي تسرد كل المنظمات.

مثال عملي

@Injectable()
export class OrganizationsService {
  constructor(private readonly prisma: PrismaService) {}

  createFor(ownerId: string, input: { name: string; slug: string }) {
    return this.prisma.organization.create({
      data: {
        id: input.slug,
        name: input.name,
        slug: input.slug,
        memberships: { create: { userId: ownerId, role: 'owner' } },
      },
    });
  }
}

memberships ستُفصَّل لاحقًا. هنا القصد أن المنظمة لا تُولد بلا مالك. id في المثال يساوي slug للتبسيط؛ في الإنتاج المعرّف ثابت حتى لو تغيّر الاسم.

أخطاء شائعة

  • مكتبة = مستخدم.
  • كتالوج على userId ثم مشاركة الحساب بين الموظفين.
  • slug من الجسم بلا نمط آمن يذهب إلى DNS.
  • حذف User يتسلسل إلى حذف كتب مكتبة فيها موظفون آخرون.

متى نستخدمه؟

منذ تصميم الجداول. إعادة التسمية لاحقًا من مستخدم-مكتبة إلى منظمة أغلى من العمود.

متى لا نستخدمه؟

لا تنشئوا منظمة لكل جلسة. المنظمة كيان يعيش. ولا تضعوا كل إعدادات الفوترة في هذا الدرس؛ جدول الاشتراك منفصل حتى لا يصبح صف المنظمة فاتورة.

مقارنة

تمارين

تمرين سهل

شخص في مكتبتين. كم صف User وكم صف Organization؟

الحل

صف مستخدم واحد وصفان منظمة، وبينهما عضويتان.

تمرين متوسط

لماذا email الفريد على المنظمة يفشل موظفَين بنفس عنوان العمل؟

الحل

لأن البريد عندها مفتاح المكتبة لا مفتاح الشخص. البريد على User، والمنظمة تُشار إليها بالعضوية. عنوان الفوترة حقل على المنظمة غير مفتاح الدخول.

تمرين متقدم

أول تسجيل في رف. ما الذي يُنشأ في معاملة واحدة، وما الذي يُؤجَّل؟

الحل

المستخدم والمنظمة وعضوية المالك في معاملة حتى لا تبقى مكتبة بلا مالك. اشتراك Stripe ورسالة البريد بعد الالتزام، لا داخل نفس المعاملة كاستدعاء شبكة.

أسئلة مراجعة

  • ماذا يملك الكتب؟
  • لماذا slug ليس اسم العرض؟
  • أين لا يُخزَّن عميل Stripe؟
  • ماذا يبقى إن غادر المالك وبقي موظف؟

الخلاصة

User هوية و Organization مكتبة مستأجرة. الكتالوج والفاتورة على المنظمة. الشخص يتصل بها بعضوية لا بعمود وحيد إن تعددت المكتبات.

ماذا بعد؟

الربط بين الشخص والمكتبة يحتاج دورًا. الدرس التالي العضوية والصلاحيات.
