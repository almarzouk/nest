Audit Logs

الهدف من هذا الدرس

تسجيل من غيّر ماذا داخل مكتبة رف: نشر كتاب، دعوة عضو، تغيير خطة، بحيث تُراجع الحادثة من غير قراءة سجل التطبيق الخام.

المشكلة التي يحلها

خلاف: «من نشر هذا الكتاب أمس؟» السجل التشغيلي فيه stack وأسرار، أو لا شيء لأن النشر نجح بهدوء. المدير يريد قائمة مفهومة. أنتم تريدون سطرًا لا يُحدَّث بعد كتابته.

الفكرة ببساطة

سطر تدقيق إلحاق فقط: المنظمة، الفاعل، الفعل، هدف، وقت، وملخص.diff صغير. لا كلمات مرور ولا رموز. الكتابة في نفس معاملة الأثر إن أمكن حتى لا يُنشر كتاب بلا سطر أو العكس.

التعريف التقني

جدول AuditLog بمفتاح id و organizationId وفهرس (organizationId, createdAt). الحقول: actorUserId, action مثل books.publish, targetType, targetId, metadata JSON محدود. لا update على السطر من API. القراءة GET /audit-logs للصلاحية audit.read وبقيد المستأجر. هذا ليس OpenTelemetry. المراقبة للأعطال والكمون؛ التدقيق لأفعال البشر. لا تسجلوا جسم الطلب كاملًا.

Mental Model

معاملة:
  UPDATE book SET status
  INSERT audit_logs
القراءة لاحقًا قائمة للإدارة لا تتبع أثر

أبسط مثال

export interface AuditEntry {
  organizationId: string;
  actorUserId: string;
  action: 'books.publish';
  targetId: string;
}

شرح المثال

  • action قيمة مغلقة حتى تُصفّى الواجهة.
  • actorUserId من الجلسة لا من الجسم.
  • لا حقل password و لا refreshToken.

ماذا يحدث داخليًا؟

  1. الخدمة تبدأ معاملة.
  2. تغيّر الكتاب.
  3. تدرج سطر التدقيق بنفس organizationId.
  4. الالتزام معًا. الفشل يتراجع عنهما.
  5. طلب القراءة يعيد الصفحة بـ nextCursor و 200 إن كانت فارغة، مع قيد المستأجر.

مثال عملي

await prisma.$transaction(async (tx) => {
  const book = await tx.book.update({
    where: { id: bookId },
    data: { status: 'published' },
  });
  if (book.organizationId !== tenantId) throw new Error('tenant mismatch');
  await tx.auditLog.create({
    data: {
      organizationId: tenantId,
      actorUserId,
      action: 'books.publish',
      targetType: 'book',
      targetId: bookId,
    },
  });
});

الأسلم أن يكون where مركّبًا من البداية (id + organizationId) حتى لا يُحدَّث صف جار ثم تفشل التدقيقة. المثال يُظهر أن السطرين في معاملة واحدة.

أخطاء شائعة

  • كتابة التدقيق بعد return فيصبح النشر بلا سطر عند انقطاع.
  • تخزين جسم POST وفيه سر OAuth.
  • سجل عام بلا organizationId يراه مدير مكتبة أخرى.
  • السماح بـ DELETE /audit-logs/:id للمدير. الإخفاء سياسة احتفاظ لا حذف من الواجهة.

متى نستخدمه؟

على أفعال تغيّر حالة يسأل عنها إنسان لاحقًا: نشر، دور، خطة، حذف.

متى لا نستخدمه؟

لا تسجلوا كل GET. ولا تستبدلوا به سجل الأخطاء. فشل Prisma غير المتوقع يذهب إلى السجل التشغيلي بجسم 500 ثابت.

تمارين

تمرين سهل

هل يُسجَّل GET /books؟

الحل

لا في هذا التصميم. القائمة قراءة. سجّلوا النشر والدعوة وتغيير الخطة.

تمرين متوسط

لماذا المعاملة الواحدة مع UPDATE؟

الحل

حتى لا ينجح الأثر ويفشل إدراج السطر أو العكس. القارئ للتدقيق يرى الواقع. التعويض لاحقًا يترك نافذة كاذبة.

تمرين متقدم

المدير يطلب حذف سطر محرج. ما البديل الذي يبقي السجل إلحاقًا؟

الحل

لا حذف من API. إن فرضت سياسة الاحتفاظ، وظيفة داخلية تنقل القديم إلى أرشيف بارد بعد المدة، وتبقي السلسلة بلا تعديل من مدير المكتبة. التصحيح سطر جديد books.unpublish لا تعديل سطر الأمس.

أسئلة مراجعة

  • ماذا يثبت السطر: الفاعل أم نص السجل الخام؟
  • لماذا لا جسم الطلب كاملًا؟
  • أين قيد المستأجر في القراءة؟
  • ما فرق التدقيق عن تتبع الأثر؟

الخلاصة

سجل التدقيق صفوف إلحاق لأفعال البشر داخل المكتبة، في نفس معاملة الأثر، بلا أسرار، وبلا حذف من واجهة المدير.

ماذا بعد؟

بعض هذه الأفعال يجب أن تصل إلى الإنسان فورًا: دعوة أو فاتورة. الدرس التالي الإشعارات كقناة لا كـ console.log.
