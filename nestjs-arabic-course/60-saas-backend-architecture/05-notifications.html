Notifications

الهدف من هذا الدرس

فصل إشعار رف عن الفعل الذي سببه: الدعوة والبريد رسالة تُسلَّم عبر قناة، وفشل القناة لا يعيد الكتاب إلى المسودة.

المشكلة التي يحلها

publish() تستدعي مزود البريد ثم تحفظ الكتاب. بطء البريد أو تعطله يرمي 500 والكتاب غير منشور، أو ينشر ثم يرمي فيضيع الرد. نص الرسالة مبني داخل المتحكم فيتكرر في المهمة وفي الاختبار.

الفكرة ببساطة

الأثر التجاري يُلتزم أولًا. الإشعار سجل Notification بحالة pending ثم عامل يسلّمه. القناة (بريد الآن) قابلة للاستبدال. الرسالة قالب ومعرّف لغة لا سلسلة متناثرة. المستخدم الذي أغلق القناة لا يُستدعى المزود من أجله.

التعريف التقني

جدول: organizationId, userId, kind (member.invited), payload صغير, status. الخدمة تدرج الصف في معاملة الفعل عندما يجب ألا يضيع الطلب، أو بعده مباشرة عبر نمط صادر يُستكمل في فصول لاحقة. العامل يحدّث sent أو failed. لا أسرار في payload. قالب البريد في وحدة بريد اختيارية لاحقًا؛ هنا الحد: الكتالوج لا يستورد SDK البريد. التفضيلات صف NotificationPreference يمنع kind معيّنًا.

Mental Model

دعوة عضو → COMMIT العضوية + صف pending
عامل → مزود البريد → sent | failed
فشل البريد لا يحذف العضوية

أبسط مثال

export interface Notice {
  organizationId: string;
  userId: string;
  kind: 'member.invited';
  payload: { organizationName: string };
}

شرح المثال

  • الحمولة اسم للعرض لا رمز دعوة طويل العمر إن كان الرمز في جدول الدعوات أصلًا.
  • kind يختار القالب.
  • المنظمة في الصف حتى يستطيع المدير لاحقًا رؤية إشعارات مكتبته فقط.

ماذا يحدث داخليًا؟

  1. إنشاء العضوية يلتزم.
  2. يُدرج إشعار pending إن لم يرفض التفضيل هذا الـ kind.
  3. الرد 201 للدعوة لا ينتظر SMTP.
  4. العامل يقرأ الدفعة ويرسل.
  5. الفشل يزيد عدادًا ويبقى failed للفحص. الدعوة ما زالت قائمة برابطها المخزن.

مثال عملي

@Injectable()
export class InviteNotifier {
  async enqueue(tx: { notification: { create: Function } }, notice: Notice) {
    await tx.notification.create({ data: { ...notice, status: 'pending' } });
  }
}

BooksService لا ترى هذه الدالة. MembershipService تراها داخل نفس tx حتى لا تُدعى عضوية بلا طلب إشعار عندما تكون السياسة «لا دعوة صامتة». إن كان المنتج يقبل الصمت عند تعطل الطابور، فالصف pending هو عقد التعويض لا الاستثناء للعميل.

أخطاء شائعة

  • انتظار SMTP داخل طلب النشر.
  • وضع رابط فيه رمز تجديد داخل payload المسجّل في التدقيق.
  • إشعار بلا organizationId فيظهر في مكتبة أخرى لنفس المستخدم.
  • إعادة إرسال failed بلا حد فتصبح حلقة على مزود البريد.

متى نستخدمه؟

عندما يجب أن يعرف إنسان بحدث: دعوة، فاتورة، كتاب نُشر إن اشترك في ذلك.

متى لا نستخدمه؟

لا تخطروا عن كل GET. ولا تستخدموا الإشعار كسجل تدقيق. التدقيق إلحاق للمراجعة، والإشعار قابل للفشل وإعادة المحاولة.

مقارنة

التدقيق الإشعار
الجمهور مراجع شخص على قناة
الفشل يتراجع مع الأثر إن كان في المعاملة يعيد المحاولة دون عكس العضوية
المحتوى فعل ومعرّف قالب وحمولة عرض

تمارين

تمرين سهل

تعطل البريد بعد إدراج العضوية. هل تُحذف العضوية؟

الحل

لا. تبقى العضوية ويبقى الإشعار failed أو pending لإعادة المحاولة. الرد على من أرسل الدعوة لا يصبح 500 بسبب SMTP إن التزمتم الصف.

تمرين متوسط

لماذا لا يحمل payload رمز الدعوة نفسه؟

الحل

لأن الصف يُنسخ إلى السجلات والعاملين. الرمز يعيش في جدول الدعوة ويُرسل في القناة ثم يُستهلك. الحمولة تشير إلى inviteId إن احتاج العامل أن يبني الرابط عند الإرسال لا أن يخزن السر مسبقًا.

تمرين متقدم

المستخدم أغلق member.invited ثم دُعي. ماذا يُدرج؟

الحل

لا صف بريد، أو صف بحالة skipped إن أردتم أثرًا للمراجعة. العضوية تُنشأ. التخطي قرار تفضيل لا فشل مزود، فلا يُعاد إرساله في حلقة failed.

أسئلة مراجعة

  • لماذا الإشعار بعد الالتزام لا قبله كشرط للنشر؟
  • ماذا في الحمولة وماذا يبقى خارجها؟
  • كيف يختلف عن سجل التدقيق؟
  • من يعيد المحاولة؟

الخلاصة

الإشعار صف حالة وقناة لاحقة. فشل البريد لا يلغي عضوية ولا نشرًا. الكتالوج لا يستورد مزود البريد، والتفضيل يوقف النوع قبل الإرسال.

ماذا بعد؟

التسليم نفسه عمل خلفية، وقد تخبر رف نظامًا خارجيًا. الدرس التالي يضع الطابور والويب هوك كحد معماري قبل فصليهما التفصيليين.
