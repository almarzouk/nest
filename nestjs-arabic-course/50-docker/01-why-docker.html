لماذا Docker

الهدف من هذا الدرس

معرفة ماذا يثبّت Docker لك قبل كتابة ملف: نفس Node ونفس اعتماديات النظام على جهازك وعلى الخادم، وشبكة تسمي فيها Postgres باسم خدمة لا بـ localhost.

المشكلة التي يحلها

«يعمل على جهازي» لأن Node عندك 22 وزميلتك 18، أو لأن Redis مثبت محليًا وأنت نسيت أن صورة الإنتاج بلا Redis. الحاوية تغلف العملية ونظام الملفات الذي تراه. Compose يشغّل التطبيق والقاعدة معًا بأسماء ثابتة. هذا لا يستبدل حدود الـ Modules. هو يشغّل ما بنيته.

الفكرة ببساطة

صورة تُبنى من Dockerfile. حاوية تشغيل لتلك الصورة. Compose يعرّف عدة حاويات على شبكة واحدة. اسم الخدمة postgres يُحل إلى عنوان تلك الحاوية. من داخل حاوية api، localhost هو api فقط. لذلك سلسلة الاتصال تستعمل postgres و redis.

التعريف التقني

Docker يبني طبقات من أوامر الملف ويخزنها. التشغيل يضيف طبقة قابلة للكتابة تختفي مع الحاوية إن لم تربط حجمًا. بيانات Postgres تحتاج volume حتى تبقى بعد down.

لا تشغّل nest start --watch كأمر إنتاج. التطوير على الجهاز أو خدمة command منفصلة في ملف تطوير. إنتاج الصورة: بناء ثم node dist/main.js.

إصدار Node في الصورة يجب أن يلبي تشغيل Nest: 20.19 أو أحدث على خط 20، أو 22.12 أو أحدث على خط 22. اختر وسمًا صريحًا مثل node:22.14-bookworm-slim حتى لا يسحب وسم latest إصدارًا لم تجربه. مولّدات CLI على جهازك قد تطلب أحدث من ذلك، والصورة تشغّل الناتج المبني لا المولّد.

الصورة ليست سرًا. لا تنسخ .env فيها. مرر المتغيرات عند التشغيل.

Mental Model

Dockerfile -> صورة
تشغيل -> حاوية
Compose: api , postgres , redis على شبكة
من api: المضيف postgres لا localhost

أبسط مثال

على الجهاز Postgres على 127.0.0.1. داخل Compose:

DATABASE_URL=postgresql://app:app@postgres:5432/app
REDIS_URL=redis://redis:6379

نفس الكود يقرأ المتغير. الذي يتغير العنوان لا مصدر Prisma.

شرح المثال

postgres اسم الخدمة في ملف Compose الذي سيأتي. إن كتبت localhost فعميل Prisma يتصل بنفسه ويفشل أو يتصل بشيء غير القاعدة. هذا الخطأ يتكرر مع Redis و NATS و Rabbit من الفصل السابق.

ماذا يحدث داخليًا؟

  1. المحرك يبني الصورة من الطبقات.
  2. التشغيل ينشئ حاوية من الصورة.
  3. Compose ينشئ شبكة ويربط الأسماء.
  4. عملية Node ترى متغيرات البيئة التي مررتها.
  5. المنفذ 3000 داخل الحاوية لا يظهر على جهازك حتى تنشر ports.
  6. حذف الحاوية بلا volume يحذف بيانات القاعدة التي كانت في نظام الملفات العابر.

مثال عملي

فريق يشغّل docker compose up فيراجع نفس إصدار Node ونفس Postgres. لا دليل تثبيت Redis على macOS في المستودع. الإنتاج يستعمل نفس Dockerfile مع متغيرات أخرى. اختلاف كلمة السر لا اختلاف في apt install يدوي على الخادم.

أخطاء شائعة

  • وسم node:latest بلا تثبيت.
  • start:dev في الإنتاج فيبقي المترجم والمراقبة.
  • localhost للقاعدة داخل الشبكة.
  • نسخ أسرار إلى الصورة.
  • اعتبار Docker تقسيم خدمات صغيرة. حاوية التطبيق قد تبقى Monolith.

متى نستخدمه؟

عندما تريد تشغيلًا قابلًا للتكرار للتطبيق مع Postgres و Redis.

متى لا نستخدمه؟

لا تحوّل كل وحدة Nest إلى حاوية. ولا تستبدل اختبار السياسة بتشغيل الحاوية كل مرة. الحاوية لاختبار الترجمة والتشغيل، والمزيف للسياسة.

مقارنة

المكان مضيف القاعدة
عملية على الجهاز 127.0.0.1
حاوية على شبكة Compose اسم الخدمة
صورة الإنتاج متغير من المنصة، غالبًا اسم خدمة أو عنوان مُدار

تمارين

تمرين سهل

ماذا يحل اسم postgres داخل الحاوية؟

الحل

عنوان حاوية خدمة Postgres على شبكة Compose، لا جهازك ولا حاوية api.

تمرين متوسط

لماذا localhost من api لا يصل إلى Postgres في خدمة أخرى؟

الحل

لأن localhost يشير إلى الحاوية التي تنفذ العملية، أي api.

تمرين متقدم

لماذا لا تضع npm run start:dev أمرًا لصورة الإنتاج؟

الحل

لأنه وضع مراقبة وتطوير يعتمد على المصدر والمترجم. الإنتاج يشغّل node dist/main.js بعد بناء ثابت.

أسئلة مراجعة

  • ماذا يبقى بعد حذف الحاوية بلا volume؟
  • أي إصدارات Node تشغّل التطبيق؟
  • هل الصورة مكان الأسرار؟

الخلاصة

Docker يكرر تشغيل Nest مع القاعدة والذاكرة. على شبكته الأسماء هي المضيفات، و localhost يبقى الحاوية نفسها، وأمر الإنتاج ليس start:dev.

ماذا بعد؟

Dockerfile: كيف تُبنى الصورة التي تشغّل الناتج.
