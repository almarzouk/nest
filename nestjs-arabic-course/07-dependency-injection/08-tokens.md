# Tokens

## الهدف من هذا الدرس

فهم الرمز كمفتاح بحث في الحاوية: لماذا يصلح الصنف، ومتى يتصادم النص، ولماذا هوية `Symbol` هي المتغير نفسه.

## المشكلة التي يحلها

فصل Providers عرّف النص والـ `Symbol` كأدوات تسجيل. هنا السؤال داخل الحل: الحاوية لا تبحث بالاسم الذي يراه الإنسان، بل بمفتاح. مفتاحان بوصف واحد قد يكونان خانتين، ونص واحد في سياقين قد يكون خانة تُستبدل.

## الفكرة ببساطة

الرمز مفتاح الخانة. الصنف مفتاح لأن الدالة البانية كائن فريد في الذاكرة بعد التحميل. النص مفتاح بالمساواة اللغوية، فيتطابق `'TAX'` مع `'TAX'` من ملف آخر. `Symbol` مفتاح بالهوية، فـ `Symbol('TAX')` الجديد لا يفتح الخانة التي فُتحت بـ `Symbol('TAX')` الأول.

## التعريف التقني

الاستنتاج من `design:paramtypes` يستخدم الصنف مفتاحًا. `@Inject(token)` يضع المفتاح صراحة، ويتقدم على النوع. لذلك واجهة بجانب `@Inject(TAX)` لا تحتاج أن تكون مفتاحًا.

التوثيق يسمح بنص أو `Symbol` أو `enum`. الـ `enum` العددي أو النصي كائن يبقى وقت التشغيل، فمفتاحه القيمة التي تمررها لـ `provide` و `@Inject` نفسها.

تصادم النص يحدث عندما يسجل سياقان مرئيان معًا `provide: 'CONFIG'`. أحدهما يستبدل الآخر أو يلتبس أي قيمة وصلت إلى المُنشئ. `Symbol` المصدَّر من ملف `tax.token.ts` يمنع ذلك ما دام الطرفان يستوردان المتغير نفسه.

```ts
export const TAX = Symbol('TAX');
```

لا تكتب `Symbol('TAX')` داخل `@Inject` مباشرة في كل ملف. ذلك ينشئ مفتاحًا لا يطابق التسجيل.

الصنف المجرد مفتاح من نوع «دالة بانية» لا من نوع `Symbol`. حقنه يتم بالنوع في المُنشئ. اختره عندما تريد مفتاحًا ووصف دوال في أثر واحد. اختر `Symbol` عندما يجب أن يبقى المفتاح خارج شجرة الوراثة.

`useExisting` لا يصنع قيمة جديدة؛ هو مفتاح يتبع مفتاحًا آخر عند الحل. المفتاحان مختلفان والخانة المنفَّذة واحدة.

## Mental Model

```text
خريطة السياق
  [دالة TaxPolicy] -> وصفة
  [Symbol TAX]     -> وصفة
  ["TAX"]          -> وصفة قد تصطدم بنص آخر
```

المقارنة للمفتاح كما في `Map`: الصنف والـ `Symbol` بالمرجع، والنص بالمحتوى.

## أبسط مثال

```ts
import { Inject, Injectable } from '@nestjs/common';
import type { TaxQuote } from './tax-quote.js';
import { TAX } from './tax.token.js';

@Injectable()
export class DraftService {
  constructor(@Inject(TAX) private readonly quote: TaxQuote) {}

  total(net: number) {
    return net * (1 + this.quote.rate);
  }
}
```

```ts
import { Module } from '@nestjs/common';
import { DraftService } from './draft.service.js';
import { TAX } from './tax.token.js';

@Module({
  providers: [
    DraftService,
    { provide: TAX, useValue: { rate: 0.15 } },
  ],
})
export class AcquisitionModule {}
```

## شرح المثال

- `TAX` في الملفين استيراد للمتغير نفسه، فالهوية واحدة.
- `TaxQuote` نوع فقط: `{ rate: number }` مثلًا، ولا يدخل `provide`.
- `useValue` يضع الكائن تحت الـ `Symbol` لا تحت اسم الخدمة.
- `DraftService` لا تذكر صنف ضريبة. المفتاح مستقل عن التنفيذ.

## ماذا يحدث داخليًا؟

عند قراءة معاملات `DraftService` تجد Nest بيانات `@Inject` تحمل مرجع `TAX`. تبحث في خريطة السياق بهذا المرجع. الخانة التي فُتحت بـ `provide: TAX` تُحل وتُمرَّر. بحث متوازٍ بالنص `'TAX'` لا يرى هذه الخانة.

إن حُمّل الملف مرتين بمسارين مختلفين في ESM فقد تحصل على نسختين من المتغير. في مشروع Nest المعتاد ملف الرمز يُحمَّل مرة، والاستيراد من المسار نفسه يعيد الهوية. أبقِ الرمز في ملف واحد حتى يبقى هذا الضمان واضحًا.

`enum` يعمل لأن العضو قيمة ثابتة. مرّر العضو نفسه في `provide` و `@Inject`، لا نص العضو إن كان المفتاح هو العضو العددي.

## مثال عملي

مفتاحان متعمدان لسياستين:

```ts
import { Module } from '@nestjs/common';
import { IMPORT_TAX, LOCAL_TAX } from './tax.tokens.js';

@Module({
  providers: [
    { provide: LOCAL_TAX, useValue: { rate: 0.15 } },
    { provide: IMPORT_TAX, useValue: { rate: 0.05 } },
  ],
  exports: [LOCAL_TAX, IMPORT_TAX],
})
export class TaxModule {}
```

نصان `'TAX'` ما كانا ليحملا سعرين في السياق نفسه. `Symbol` لكل سياسة خانة. المستهلك الذي يحتاج الاثنين يحقن `@Inject(LOCAL_TAX)` و `@Inject(IMPORT_TAX)` في مُنشئ واحد. التصدير ينشر المفتاحين لا الكائن فقط.

## أخطاء شائعة

| الخطأ | الأثر |
| --- | --- |
| `@Inject(Symbol('TAX'))` عند كل استخدام | مفتاح جديد في كل تقييم، والخانة لا تُفتح |
| `'CONFIG'` مشترك بين مكتبتين في Module واحدة | قيمة واحدة تزيح الأخرى تحت المفتاح اللغوي نفسه |
| البحث عن الصنف بينما `provide` هو `Symbol` | خانة الصنف غير موجودة |
| اعتبار `useExisting` مفتاحًا ينسخ القيمة | المفتاحان يتبعان حلًا واحدًا |

## متى نستخدمه؟

عندما لا يكون المفتاح صنف الخدمة نفسه: سياسة قابلة للاستبدال، أو ثابت، أو تنفيذان تحت عقد واحد. `Symbol` مصدَّر هو الافتراضي الآمن خارج الأمثلة القصيرة. الصنف الملموس يبقى مفتاحًا أفضل لخدمة واحدة مستقرة.

## متى لا نستخدمه؟

لا تضع `Symbol` على `DraftService` التي تُسجَّل باختصار وتُحقن بنوعها. مفتاح إضافي من غير تنفيذ ثانٍ يكرر الاسم. ولا تستخدم النص العام `CONFIG` في مكتبة سيعاد استعمالها داخل تطبيقات لا تملكها.

## مقارنة

| المفتاح | المساواة في الخريطة |
| --- | --- |
| صنف أو صنف مجرد | مرجع الدالة البانية |
| `Symbol` المصدَّر | مرجع ذلك الرمز |
| `Symbol('TAX')` مضمّن في كل ملف | مراجع مختلفة، خانات مختلفة |
| نص | تطابق المحتوى، واحتمال التصادم |
| `enum` | قيمة العضو نفسها في الطرفين |

## تمارين

### تمرين سهل

لماذا يفتح الصنف خانة من غير `@Inject`؟

<details><summary>الحل</summary>

الدالة البانية تبقى بعد الترجمة وتُكتب في `design:paramtypes`، فتستخدمها الحاوية مفتاح بحث.

</details>

### تمرين متوسط

لماذا لا يرى `@Inject('TAX')` قيمة سُجّلت تحت `const TAX = Symbol('TAX')`؟

<details><summary>الحل</summary>

النص والـ `Symbol` مفتاحان مختلفان في الخريطة. الحقن يجب أن يمرر `TAX` نفسه الذي وُضع في `provide`.

</details>

### تمرين متقدم

متى تفضّل صنفًا مجردًا على `Symbol` كمفتاح لسياسة الضريبة؟

<details><summary>الحل</summary>

عندما تريد أن يكون `rate()` عقدًا ورمز حاوية معًا، ويُحقن `constructor(tax: TaxPolicy)` من غير `@Inject`. `Symbol` أنسب عندما تبقى القيمة كائنًا بلا وراثة، أو عندما تخاف تصادم الأسماء في مكتبة.

</details>

## أسئلة مراجعة

- بمَ تقارن الحاوية مفتاح `Symbol`؟
- لماذا يتصادم نص `'CONFIG'`؟
- ماذا يتقدم على `design:paramtypes`؟

## الخلاصة

الرمز مفتاح خانة: مرجع للصنف وللـ `Symbol`، ومحتوى للنص. المفتاح الذي تكتبه في `provide` هو الذي يُعاد في `@Inject` أو في نوع المعامل، ومتغير `Symbol` واحد يمنع فتح خانة فارغة بالخطأ.
