# ما هي DI

## الهدف من هذا الدرس

تعريف Dependency Injection: الصنف يعلن ما يحتاجه، وطرف خارجي يمرر الكائنات الجاهزة.

## المشكلة التي يحلها

بعد رؤية سلسلة `new`، الخطوة التالية ليست «حاوية» بعد. الخطوة هي فصل الإعلان عن الإنشاء. `DraftService` تذكر `TaxPolicy` و `VendorGateway` في المُنشئ، ومن يبني الخدمة هو من يختار التنفيذ.

## الفكرة ببساطة

DI نمط يعطي الكائن اعتمادياته بدل أن يبنيها. في Nest الطرف الذي يمررها هو وقت التشغيل. السطر الذي تكتبه هو طلب، لا أمر `new`.

التوثيق يصف DI كتقنية Inversion of Control: تفويض إنشاء الاعتماديات إلى الحاوية بدل إنشائها في كودك الأمري. IoC نفسه الدرس التالي. هنا شكل الطلب والتسليم.

## التعريف التقني

```ts
constructor(
  private readonly tax: TaxPolicy,
  private readonly vendors: VendorGateway,
) {}
```

الصنف يعتمد على نوعين. هو لا يقرر عنوان البوابة ولا شهر الضريبة. من ينادي `new DraftService(tax, vendors)` — أو الحاوية في مكانه — يملك القرار.

الحقن عبر المُنشئ هو الشكل الذي تستخدمه Nest افتراضيًا. حقن دالة أو خاصية أشكال أخرى في أنظمة ثانية. داخل Nest، المُنشئ هو العقد الذي تُقرأ منه Metadata.

تمرير الضريبة وسيطًا إلى `total(net, tax)` حقن دالة واحدة. DI على الصنف تعني أن كل دواله ترى الحقول نفسها التي سُلّمت مرة عند البناء.

## Mental Model

```text
من يبني الشبكة
  يملك VendorGateway و TaxPolicy
  ينشئ DraftService ويمررهما
DraftService
  تستدعي tax.rate() و vendors.list()
  ولا تنادي new
```

## أبسط مثال

```ts
export class DraftService {
  constructor(
    private readonly tax: TaxPolicy,
    private readonly vendors: VendorGateway,
  ) {}

  total(net: number) {
    return net * (1 + this.tax.rate());
  }
}

export class TaxPolicy {
  rate() {
    return 0.15;
  }
}

export class VendorGateway {
  list() {
    return ['north'];
  }
}

const drafts = new DraftService(new TaxPolicy(), new VendorGateway());
```

## شرح المثال

- `new` بقي في سطر التركيب الأخير، وخرج من داخل `total`.
- `DraftService` تعمل مع أي كائن يوفّر `rate` بالشكل الذي تستدعيه، عندما يكون النوع متوافقًا.
- اختبار يمرر `{ rate: () => 0 }` لا يحتاج ديسمبر ولا شبكة.
- سطر التركيب ما زال يدويًا. نقل هذا السطر إلى تسجيل Module هو ما تفعله Nest، لا تعريف DI وحده.

## ماذا يحدث داخليًا؟

عند `new DraftService(tax, vendors)` تُسند المراجع إلى الحقول قبل أي نداء `total`. لا بحث عن أسماء نصية في هذا المثال اليدوي: أنت مررت المراجع. Nest لاحقًا تطابق نوع المعامل برمز مسجّل ثم تفعل الإسناد نفسه.

إذا نسيت وسيطًا، JavaScript ينادي المُنشئ بقيمة ناقصة وأنت ترى `undefined` عند أول `this.tax.rate()`. الحاوية تفشل عند الإقلاع بدل أن تنتظر أول طلب، لأن التسجيل أوضح من نداء يدوي متأخر.

## مثال عملي

اختبار يعزل الضريبة:

```ts
import { DraftService } from './draft.service.js';

const drafts = new DraftService(
  { rate: () => 0.05 },
  { list: () => ['south'] },
);

const gross = drafts.total(200);
```

`gross` يساوي 210 لأن المُنشئ استلم سياسة 0.05. `VendorGateway` الحقيقية لا تُستدعى. هذا هو مكسب DI قبل الحديث عن الحاوية: موضع بناء واحد، وتوقيع يعلن الاحتياج.

في التطبيق، Module تستبدل سطر `new DraftService(...)` بتسجيل الأصناف. الخدمة تبقى كما هي.

## أخطاء شائعة

| الخطأ | الأثر |
| --- | --- |
| حقن الصنف مع الإبقاء على `new RegionalTax()` داخله | التوقيع صادق جزئيًا والساعة ما زالت مخفية |
| وسيط دالة لكل اعتمادية على كل عملية | البناء يتكرر في كل نداء ولا حالة مشتركة مقصودة |
| اعتبار DI اسمًا لـ `@Injectable` فقط | الزينة Metadata؛ النمط هو تمرير الكائن من الخارج |
| تمرير `undefined` يدويًا ثم معالجة الخطأ داخل `total` | الفشل يتأخر إلى وقت الطلب |

## متى نستخدمه؟

عندما لصنف اعتماد على خدمة أو بوابة أو سياسة سيتبدل تنفيذها أو تُختبر وحدها. المُنشئ هو مكان الإعلان.

## متى لا نستخدمه؟

لكائن يُحسب من وسائط النداء فقط، مثل سطر فاتورة `{ net, tax }` يُنشأ داخل `total` كنتيجة لا كاعتمادية حية. تلك قيمة معادة، لا شيء تسجله الحاوية.

## مقارنة

| | البناء الداخلي | DI |
| --- | --- | --- |
| من يختار التنفيذ | الدالة التي تنادي `new` | من يبني الصنف |
| أين يظهر الاحتياج | داخل الجسم، وقد يختفي | معاملات المُنشئ |
| الاختبار | يعدل الخدمة أو يضبط حالة عامة | يمرر بديلًا عند البناء |
| في Nest | يتجاوز السجل | الحاوية تملأ المعاملات |

## تمارين

### تمرين سهل

في المثال اليدوي، من ينادي `new RegionalTax`؟

<details><summary>الحل</summary>

لا أحد داخل `DraftService`. سطر التركيب الخارجي ينشئ `TaxPolicy` ويمررها. الضريبة الإقليمية تكون ذلك السطر عندما تختارها أنت أو التسجيل.

</details>

### تمرين متوسط

ما الفرق بين `total(net, tax)` وحقن `tax` في المُنشئ؟

<details><summary>الحل</summary>

وسيط الدالة يمرر السياسة عند كل نداء وقد تختلف بين نداء ونداء. حقل المُنشئ يُسند مرة وتستخدمه كل دوال النسخة. الاثنان إمداد من الخارج؛ DI التي تتحدث عنها Nest هي شكل المُنشئ الذي تستطيع قراءة Metadata له.

</details>

### تمرين متقدم

لماذا بقاء `new SystemClock()` داخل `TaxPolicy` يعني أن DI على `DraftService` لم تكتمل للساعة؟

<details><summary>الحل</summary>

`DraftService` تستلم السياسة جاهزة، لكن السياسة ما زالت تبني الساعة. اختبار الشهر الثابت يفشل إلى أن تطلب `TaxPolicy` الساعة في مُنشئها أيضًا. الحقن المفيد يسري على السلسلة التي تريد استبدالها.

</details>

## أسئلة مراجعة

- من يمرر الاعتماديات في تعريف DI؟
- أين تعلن `DraftService` احتياجها؟
- ماذا يبقى يدويًا إلى أن تتولى الحاوية سطر التركيب؟

## الخلاصة

DI تعني أن الصنف يطلب كائنات جاهزة في المُنشئ، ومن يبنيه يختار التنفيذ. هذا يفصل الإعلان عن `new`، والحاوية في Nest هي التي تنفّذ سطر التركيب.

## ماذا بعد؟

من يملك قرار البناء أصلًا: IoC.
