كيف تحل NestJS الاعتمادية داخليًا

الهدف من هذا الدرس

ترتيب ما تفعله Nest من Metadata حتى تمرير الوسائط إلى المُنشئ، كما يصفه التوثيق.

المشكلة التي يحلها

الدروس السابقة فصلت new و DI و IoC والانقلاب والحاوية والرمز والعمر والرسم. التشغيل اليومي يصطدم برسالة واحدة: Nest لا تستطيع حل اعتمادية عند فهرس معامل. هذا الدرس يجمع الخطوات التي تؤدي إلى تلك الرسالة أو إلى نسخة جاهزة.

الفكرة ببساطة

ثلاث خطوات في توثيق Custom providers: @Injectable() يعلن أن الحاوية تدير الصنف، والمُنشئ يعلن الرمز، و providers يربط الرمز بالوصفة. عند إنشاء المستهلك تُحل الاعتماديات من الأسفل، ومع Singleton تُنشأ النسخة مرة وتُخزَّن أو تُعاد إن كانت مخزنة. التحليل يحدث أثناء الإقلاع وهو متعدٍ.

التعريف التقني

  1. NestFactory.create يبدأ من Module الجذر ويمشي على imports.
  2. كل عنصر في providers يصبح خانة. الاختصار { provide: DraftService, useClass: DraftService }.
  3. لكل صنف مُدار تُقرأ معاملات المُنشئ: @Inject إن وُجد، وإلا design:paramtypes التي أصدرها Decorator الصنف.
  4. الواجهة و import type يتركان الخانة بلا مفتاح، فتفشل الخطوة.
  5. الطلبات تُجمع في رسم متعدٍ.
  6. الحل من الأوراق: useValue تعيد المرجع، useClass تبني بعد حل مُنشئ الهدف، useFactory تُنادى بعد inject، useExisting يتبع مفتاحًا آخر.
  7. نطاق DEFAULT يخزّن الناتج في الخانة. طلب لاحق للمفتاح يعيد المخزن.
  8. الوسائط تُمرَّر إلى مُنشئ المستهلك بالترتيب.
  9. Controller يُبنى بالطريقة نفسها بعد حل خدماته، ثم تُربط مساراته.

@Optional() على معامل: الخطوة 6 عند غياب الخانة تعيد undefined لذلك الفهرس فقط.

متغير البيئة NEST_DEBUG يضيف سجلات الحل أثناء الإقلاع عندما تكبر الشجرة. هو أداة تشخيص موثّقة، لا جزءًا من الكود الإنتاجي الدائم.

أسماء أصناف داخل محرك Nest تتغير بين الإصدارات. السلوك الذي يُبنى عليه التطبيق هو هذه الخطوات، لا اسم صنف داخلي.

Mental Model

اقرأ Module
  سجّل المفاتيح
  اقرأ المُنشئات
  رتّب الأوراق ثم الجذر
  خزّن Singleton
  نادِ constructor(ready, ready)

أبسط مثال

import { Injectable, Module } from '@nestjs/common';

@Injectable()
export class SystemClock {
  now() {
    return new Date();
  }
}

@Injectable()
export class TaxPolicy {
  constructor(private readonly clock: SystemClock) {}

  rate() {
    return this.clock.now().getMonth() === 11 ? 0.05 : 0.15;
  }
}

@Injectable()
export class DraftService {
  constructor(private readonly tax: TaxPolicy) {}

  total(net: number) {
    return net * (1 + this.tax.rate());
  }
}

@Module({
  providers: [SystemClock, TaxPolicy, DraftService],
})
export class AcquisitionModule {}

شرح المثال

  • SystemClock ورقة: مصفوفة أنواعها فارغة، فالحل ينشئها أولًا ويخزنها.
  • TaxPolicy مفتاح معاملها SystemClock لأن الاستيراد قيمة و @Injectable() أصدر النوع.
  • DraftService تُبنى بعد السياسة، وداخلها الساعة أصلًا لأن الرسم متعدٍ.
  • لا يوجد new DraftService في ملف التطبيق. create على الجذر الذي يستورد هذه الـ Module يؤدي الخطوات.

ماذا يحدث داخليًا؟

فهرس المعامل في رسالة الخطأ يعدّ من الصفر: المعامل الثاني الذي نوعه ممسوح يظهر كموضع لا يُحل. أصلح ذلك الموضع: استيراد قيمة، أو @Inject، أو تسجيل المفتاح في السياق المرئي، أو exports إن كان المفتاح في Module أخرى.

useFactory غير المتزامنة توقف السلسلة عند تلك العقدة حتى يكتمل الوعد، ثم تكمل نحو الجذر. لذلك تتأخر جاهزية التطبيق إن كانت الورقة الثقيلة Singleton.

نطاق REQUEST يعيد الخطوات 6 إلى 8 لكل طلب على الفرع المصاب، بعد أن بقي التسجيل من الإقلاع. هذا الدرس لا يغيّر تلك القاعدة.

Controller:

@Controller('drafts')
export class DraftsController {
  constructor(private readonly drafts: DraftService) {}
}

@Controller يصدر أنواع المعاملات. الحل يجد DraftService في الخانة ويمررها. ثم يسجل @Get على النسخة.

دورة في الرسم توقف الخطوة 6 لأن لا ورقة تبدأ. العلاج في فصل Circular Dependencies.

مثال عملي

رسالة على المعامل الأول من DraftService بعد أن كتب أحدهم import type { TaxPolicy }. الخطوة 3 لا تجد مفتاحًا. الإصلاح إعادة استيراد القيمة. إن كانت TaxPolicy في BillingModule غير مصدَّرة، الخطوة 6 لا تجد الخانة في سياق المشتريات: أضف exports ثم imports. العَرضان رسالة حل، والخطوة الفاشلة مختلفة.

تشغيل التشخيص محليًا:

NEST_DEBUG=true npm run start

السجل يتبع المفاتيح التي تُحل. بعد الإصلاح أزل المتغير حتى يبقى الإقلاع هادئًا.

أخطاء شائعة

الخطأ الخطوة التي تفشل
نسيان الصنف في providers 6، المفتاح بلا خانة في السياق
import type أو واجهة 3، لا مفتاح في Metadata
الاعتماد على ترتيب المصفوفة لا خطوة تقرأ الترتيب كأسبقية
البحث عن اسم صنف داخلي في التوثيق السطحي السلوك موثّق بالرسم والتخزين لا بأسماء المحرك
دورة بلا كسر 6، لا ورقة تُبنى

متى نستخدمه؟

عند قراءة رسالة إقلاع أو عند تخيل طريق TaxPolicy من الملف إلى المُنشئ. تتبّع الخطوات التسعة بالترتيب بدل تجربة new داخل الخدمة.

متى لا نستخدمه؟

لا تعطّل الحل ببناء الخدمات في main ثم تمريرها إلى Nest بطريقة جانبية. الوصفة useValue موجودة إن كانت القيمة جاهزة خارج الرسم، وتبقى خانة صريحة. تجنب نسخ المحرك أو الاعتماد على حقوله الخاصة.

تمارين

تمرين سهل

ما أول مكان تبدأ منه NestFactory.create في الرسم؟

الحل

Module الجذر، ثم ما تصل إليه عبر imports.

تمرين متوسط

معامل واحد في DraftService ورسالته تقول إن الاعتمادية لا تُحل عند الفهرس 0. ماذا تراجع في Metadata قبل أن تراجع exports؟

الحل

أن TaxPolicy صنف مستورد استيراد قيمة، وأن @Injectable() على الخدمة. import type أو واجهة تعني أن الخطوة 3 بلا مفتاح، و exports لن تُصلح مفتاحًا غير موجود.

تمرين متقدم

رتّب بناء مثال هذا الدرس، ثم قل متى تُنادى useFactory غير متزامنة لو استُبدلت بـ SystemClock.

الحل

الساعة، ثم السياسة، ثم المسودة، ثم Controller إن وُجد. المصنع غير المتزامن في موضع الساعة يُنتظَر قبل بناء السياسة وما فوقها، لذلك يتأخر اكتمال create كله ضمن Singleton.

الخلاصة

Nest تسجل المفاتيح من Module، وتقرأ المُنشئات، وتحل الرسم من الأوراق، وتخزن Singleton، وتمرر الوسائط إلى المُنشئ. الرسالة عند الإقلاع تشير إلى مفتاح ممسوح أو خانة غير مرئية أو دورة، لا إلى نقص new داخل الدالة.

ماذا بعد؟

أمثلة تجمع سياسة وضريبة وساعة على مكتب المشتريات، ثم طلب HTTP يمشي على النسخ الجاهزة.
