# Dependency Graph

## الهدف من هذا الدرس

قراءة الاعتماديات كرسم يُبنى من الأوراق نحو الجذر، عبر حدود Module.

## المشكلة التي يحلها

تسجيل `DraftService` قبل `TaxPolicy` في المصفوفة يوحي أن المسودة تُبنى أولًا. الرسم يقول العكس: من لا يعتمد على أحد يُحل أولًا، ثم من يحتاجه. دورة مغلقة، حيث يطلب كل طرف الآخر، لا ورقة لها فتوقف الإقلاع. رسمها أوضح من قراءة المصفوفات.

## الفكرة ببساطة

التحليل متعدٍ: إن كانت المسودة تحتاج السياسة والسياسة تحتاج الساعة، فالساعة جزء من رسم المسودة حتى لو لم يذكرها مُنشئ المسودة. التوثيق يسمي هذا الرسم سبب الحل من الأسفل إلى الأعلى، حتى لا تدير أنت الترتيب.

## التعريف التقني

```text
DraftService -> TaxPolicy -> SystemClock
             -> VendorGateway
```

الحل: `SystemClock` و `VendorGateway` أولًا، بأي ترتيب بينهما لأنهما لا يعتمد أحدهما على الآخر، ثم `TaxPolicy`، ثم `DraftService`. Controller يعتمد على المسودة فيُبنى بعدها.

الحدود: عقدة غير مصدَّرة لا تظهر في رسم Module أخرى. تصدير `DraftService` يجعل المستورد يعتمد على تلك العقدة، لا على `SystemClock` مباشرة، ما دامت الساعة داخل مُنشئ السياسة فقط.

تسجيل الصنف مرتين في وحدتين يصنع عقدتين ونسختين Singleton. الرسم ليس «صنفًا واحدًا في العملية» بل «خانة في كل سياق».

دورة `DraftService -> AuditLog -> DraftService` بلا ورقة. Nest تتوقف عند الحل. كسر الدورة بإعادة التصميم هو المسار السليم. `forwardRef` أداة لاحقة في فصل Circular Dependencies، وتُذكر هنا حتى لا تُخترع في هذا الدرس.

## Mental Model

```text
        DraftsController
              |
        DraftService
         /        \
   TaxPolicy    VendorGateway
      |
  SystemClock
```

البناء من أسفل الرسم إلى أعلاه.

## أبسط مثال

```ts
import { Injectable } from '@nestjs/common';
import { SystemClock } from './system-clock.js';

@Injectable()
export class TaxPolicy {
  constructor(private readonly clock: SystemClock) {}

  rate() {
    return this.clock.now().getMonth() === 11 ? 0.05 : 0.15;
  }
}
```

```ts
import { Injectable } from '@nestjs/common';
import { TaxPolicy } from './tax.policy.js';
import { VendorGateway } from './vendor.gateway.js';

@Injectable()
export class DraftService {
  constructor(
    private readonly tax: TaxPolicy,
    private readonly vendors: VendorGateway,
  ) {}
}
```

## شرح المثال

- `DraftService` لا تذكر `SystemClock`، والرسم يذكرها لأن الاعتماد متعدٍ.
- `VendorGateway` ورقة إن كان مُنشئها بلا مزودات Nest.
- ترتيب معاملات المسودة لا يغيّر أن الساعة تُحل قبل السياسة.
- تسجيل الثلاثة مع الساعة في `providers` شرط ظهورهم كعقد.

## ماذا يحدث داخليًا؟

أثناء الإقلاع تُجمع الطلبات من `design:paramtypes` و `@Inject` لكل صنف في الرسم المستورد من الجذر. الحاوية تبني قائمة حل تحترم الأسبقية: لا يُنادى مُنشئ عقدة قبل حل جيرانها الصادرة. الناتج Singleton يُخزَّن في خانة الرمز قبل أن تُبنى العقدة التي فوقه.

Module التقارير التي تستورد المشتريات وتطلب `DraftService` تضيف عقدة `ReportsService` فوق المسودة، من غير نسخ عقد الضريبة إلى ملف التقارير. تلك العقد تبقى في سياق المالك وتُشارَك عبر التصدير.

دورة قصيرة تظهر في رسالة الحل التي تذكر الرموز المتبقية. العلاج الأول إزالة الاعتماد بإدخال تجريد أو بنقل الدالة إلى الصنف الذي يملك البيانات. `forwardRef` يؤجل قراءة الرمز عندما تكون الدورة متعمدة ونادرة، وفصله لاحق.

## مثال عملي

```text
AppModule
  imports AcquisitionModule
    providers SystemClock, VendorGateway
    providers TaxPolicy -> SystemClock
    providers DraftService -> TaxPolicy, VendorGateway
    exports DraftService
  imports ReportsModule
    imports AcquisitionModule
    providers ReportsService -> DraftService
```

`ReportsService` لا تستطيع طلب `SystemClock` إن لم يُصدَّر. الرسم المرئي لها يتوقف عند `DraftService`. هذا حد Module داخل الرسم لا نقص في المحرك.

نسختان من `SystemClock` تظهران إذا سجّلت `ReportsModule` الساعة مرة أخرى. رسمان فرعيان، وعدّادان إن وُجد عدّاد على الساعة.

## أخطاء شائعة

| الخطأ | الأثر |
| --- | --- |
| الاعتماد على ترتيب `providers` لبناء الأوراق | الحل يتبع الأسهم لا أسطر الملف |
| دورة بين خدمتين بلا إعادة تصميم | الإقلاع يتوقف ولا توجد ورقة تبدأ |
| إعادة تسجيل ورقة في كل Module | عقد مكررة ونسخ Singleton متعددة |
| افتراض أن المستورد يرى كل أسلاف الرسم | يرى المصدَّر فقط |

## متى نستخدمه؟

عند تتبع «من يُبنى قبل من» أو عند نقل صنف بين الوحدات. ارسم الأسهم من المستهلك إلى ما في مُنشئه، ثم كرر حتى الأوراق.

## متى لا نستخدمه؟

لا تضف اعتمادية في المُنشئ فقط ليظهر السهم في الرسم. إن كانت الدالة تحتاج الساعة في نداء واحد، مرّرها وسيطًا من الطبقة التي تملكها. سهم إضافي يصعد بـ `REQUEST` لاحقًا إن تغيّر Scope الورقة.

## مقارنة

| الشكل | اتجاه البناء |
| --- | --- |
| رسم بلا دورة | من الأوراق إلى الجذر |
| ترتيب المصفوفة | لا يحدد الأسبقية |
| تصدير الجذر فقط | المستورد يرى قمة الفرع المصدَّر |
| تسجيل مكرر للصنف | عقدتان في رسمين |
| دورة | لا ترتيب صالح حتى ينكسر السهم |

## تمارين

### تمرين سهل

من يُحل أولًا: `DraftService` أم `SystemClock`؟

<details><summary>الحل</summary>

`SystemClock`، لأنها ورقة تحت السياسة التي تحت المسودة.

</details>

### تمرين متوسط

لماذا تعرف الساعة رسم المسودة وهي غائبة عن مُنشئ `DraftService`؟

<details><summary>الحل</summary>

`TaxPolicy` تطلب الساعة، والتحليل متعدٍ. كل أسلاف السياسة أسلاف لمن يطلب السياسة.

</details>

### تمرين متقدم

`ReportsModule` تعيد `providers: [SystemClock]` وتستورد المشتريات. كم عقدة ساعة في العملية؟

<details><summary>الحل</summary>

اثنتان. خانة في سياق التقارير وخانة في سياق المشتريات. تصدير ساعة المشتريات وحذف التسجيل المحلي يدمج العقدة لمن يحقن الرمز المستورد.

</details>

## أسئلة مراجعة

- ماذا يعني أن تحليل الاعتماد متعدٍ؟
- من أين تبدأ الحاوية البناء؟
- ماذا يحدث للرسم عندما تُغلق دورة؟

## الخلاصة

الرسم أسهم من المستهلك إلى رموز مُنشئه، والحل من الأوراق إلى الجذر. التصدير يشارك عقدة قائمة، والتسجيل الثاني ينسخ الفرع، والدورة توقف الإقلاع إلى أن يُكسر السهم.

## ماذا بعد؟

خطوات Nest من قراءة Module حتى نداء المُنشئ: كيف تُحل الاعتمادية داخليًا.
