REST مقابل GraphQL

الهدف من هذا الدرس

اختيار عقد المتجر بين موارد HTTP ومخطط GraphQL، بمعيار شكل الشاشات لا بمعيار الموضة.

المشكلة التي يحلها

بعد فصول REST صار المسار اسم مورد وفعلًا. شاشة تفاصيل الكتاب قد تستدعي /books/42 ثم /authors/7 ثم /books/42/reviews?limit=3. شاشة البطاقة تستدعي المسار الأول وتتجاهل نصف JSON. كلا العيبين حقيقيان. نقل كل المتجر إلى /graphql لا يلغي الحاجة إلى أسماء واضحة، وقد يخفي عمليات كان المسار يوثّقها.

الفكرة ببساطة

REST يثبّت شكل التمثيل على المورد. GraphQL يثبّت المخطط ويجعل شكل الرد قرار العملية. الأول أوضح للتخزين المؤقت على عنوان URL ولأدوات HTTP. الثاني أوضح عندما تتنوع الشاشات على الرسم نفسه. يمكن أن يعيش الاثنان: REST للرفع والإدارة البسيطة، وGraphQL لواجهة القراءة الغنية.

التعريف التقني

سؤال REST في هذه الدورة GraphQL
أين العملية؟ المسار + Method حقل على Query أو Mutation
شكل الرد تمثيل المورد الحقول المطلوبة
الغياب 404 غالبًا null أو خطأ حقلي حسب المخطط
التخزين المؤقت الوسيط عنوان GET أصعب، لأن الجسم هو الاستعلام
الملف multipart ليس أداة الرفع هنا

حجة GraphQL الشائعة «طلب واحد بدل خمسة» صحيحة عندما تكون الخمسة شكل شاشة واحدة. هي مضللة عندما يخفي الطلب الواحد خمسة استعلامات قاعدة. ذلك N+1، ويُلمح لاحقًا.

Mental Model

REST:   GET /books/42          وثيقة كتاب
GraphQL: query { book(id) { title author { name } } }
         وثيقة بالشكل الذي رسمته الشاشة

العنوان في REST جزء من العقد. اسم الحقل في المخطط هو الجزء المقابل.

أبسط مثال

بطاقة كتاب على الرف.

REST كما قد تكتبه اليوم:

GET /books/42

{ "id": "42", "title": "NestJS", "authorId": "7", "isbn": "...", "stock": 3 }

البطاقة تعرض title فقط. الباقي سافر.

GraphQL للبطاقة نفسها:

query {
  book(id: "42") { title }
}

شاشة التفاصيل تضيف author { name } على المخطط نفسه، بلا مسار جديد إن كان الحقل معلنًا.

شرح المثال

REST يجبرك إما على تمثيل ضخم أو على تمثيل خاص بالموبايل مثل /mobile/book-card فيتكاثر العقد. GraphQL يبقي Book نوعًا واحدًا وتختار الشاشة. ثمن ذلك: العميل يتعلم المخطط، والتخزين المؤقت لم يعد «هذا الـ URL». وثمن REST: وثائق أوفر فيتش أو مسارات كثيرة.

ماذا يحدث داخليًا؟

وسيط HTTP لـ GET /books/42 يستطيع التخزين بمفتاح العنوان. طلب GraphQL المعتاد POST /graphql يحمل النص في الجسم، فوسيط عام لا يفرّق بين بطاقة وتفاصيل إلا إذا فهم اللغة. لا تبنِ أمل الأداء على «طلب واحد». قس استعلامات القاعدة. الرفع في الفصل 27 يبقى POST متعدد الأجزاء لأن GraphQL JSON لا يحمل بايتات الغلاف بشكل لائق.

مثال عملي

قرار متجر الكتب في هذه الدورة:

القدرة العقد
قراءة الكتالوج بشاشات مختلفة GraphQL Query
إنشاء كتاب بحقول معروفة Mutation أو POST /books، لا الاثنان بلا سبب
رفع الغلاف REST multipart
أصول الواجهة ServeStaticModule

إن أبقيت إنشاء الكتاب على REST، لا تكرره في mutation إلا لعميل لا يستطيع استدعاء المسار.

أخطاء شائعة

  • إعادة كتابة كل مسار REST حقلًا في أسبوع واحد.
  • وضع فعل deleteBook على Query. القراءة بلا أثر جانبي.
  • الحكم بأن REST «انتهى» لأن الشاشة الأولى احتجت حقلين زائدَين.
  • نسيان أن رمز الغياب المألوف لفريقك سيتغير شكله.

متى نستخدمه؟

GraphQL عندما تتعدد أشكال القراءة على أنواع مستقرة. REST عندما يكون المورد والفعل والرمز قصة كافية، خصوصًا للكتابة البسيطة والملفات.

متى لا نستخدمه؟

لا تستبدل رفع الملفات ولا الملفات الثابتة بمخطط. ولا تفتح GraphQL لخدمة داخلية لها عميل واحد وشكل ثابت إن كان المسار أوضح في السجلات.

مقارنة

ضغط الشاشة ما الذي يتغير
REST، حقول ناقصة مسار آخر أو تمثيل أضخم
REST، حقول زائدة تجاهل في العميل أو DTO أضيق
GraphQL نص العملية على المخطط نفسه

تمارين

تمرين سهل

أين يجلس شكل رد البطاقة في GraphQL؟

الحل

في نص العملية التي تطلب الحقول، ضمن ما يسمح به المخطط.

تمرين متوسط

لماذا يصعب تخزين POST /graphql في وسيط لا يفهم GraphQL؟

الحل

لأن العمليات المختلفة تشترك في العنوان، والنص داخل الجسم. مفتاح العنوان وحده لا يفرّق البطاقة عن التفاصيل.

تمرين متقدم

اذكر قدرة تبقى على REST في هذا المتجر ولماذا.

الحل

رفع الغلاف. العقد multipart ومتحقق الملفات من الفصل السابق. مخطط JSON لا يستقبل الملف.

أسئلة مراجعة

  • ماذا يثبّت REST وماذا يثبّت GraphQL؟
  • متى تكون «خمسة مسارات» مشكلة شاشة لا مشكلة قاعدة؟
  • أي فصل يبقى مرجع الرفع؟

الخلاصة

REST مورد وفعل. GraphQL مخطط واختيار حقول. المتجر يستطيع إبقاء الملفات على HTTP ونقل القراءة الغنية إلى المخطط.

ماذا بعد؟

شكل المخطط نفسه: النوع، والجذر Query، والجذر Mutation.
