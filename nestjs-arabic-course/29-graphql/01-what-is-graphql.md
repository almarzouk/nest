# ما هو GraphQL

## الهدف من هذا الدرس

وصف GraphQL كلغة استعلام ومخطط تنفيذ، قبل مقارنة REST وقبل زينة Nest.

## المشكلة التي يحلها

شاشة كتاب قد تحتاج العنوان واسم المؤلف وعدد المراجعات. شاشة أخرى تحتاج العنوان فقط. مسار REST يعيد شكلًا ثابتًا، فتأتي حقول لا تُرسم أو تُستدعى مسارات إضافية لإكمال الشاشة. GraphQL يجعل شكل الرد جزءًا من نص الطلب، والمخطط هو العقد الذي يحدد ما يجوز طلبه.

## الفكرة ببساطة

المخطط يسمّي الأنواع والحقول. العميل يرسل عملية: `query` أو `mutation` أو `subscription`. المحرك يتحقق من النص ضد المخطط ثم يستدعي دالة لكل حقل. الدالة اسمها resolver. الناتج شجرة تطابق ما طُلب، لا وثيقة الكتاب كاملة بالضرورة.

GraphQL ليست قاعدة بيانات ولا بديلًا تلقائيًا عن SQL. هي طبقة عقد فوق دوالك.

## التعريف التقني

مواصفة GraphQL تفصل:

- **Schema**: أنواع، وحقول، وأنواع الحجج.
- **Operation**: النص الذي يرسله العميل.
- **Resolver**: دالة تُرجع قيمة حقل. إن لم تكتبها، القيمة تُقرأ من الكائن الأب بنفس اسم الحقل.
- **Scalar**: ورقة الشجرة مثل `String` و `Int` و `ID` و `Boolean` و `Float`.

النقل المعتاد `POST` إلى مسار واحد، غالبًا `/graphql`، والجسم JSON فيه `query` وربما `variables`. هذا نقل شائع فوق HTTP، وليس تعريف اللغة نفسها. الاشتراك لاحقًا قناة أطول عمرًا.

Nest لا تنفّذ اللغة. `@nestjs/graphql` يربط المخطط بمحرك. الدورة تستخدم Apollo عبر `@nestjs/apollo`. Mercurius خيار رسمي آخر على Fastify، وليس مسار هذه الدروس.

## Mental Model

```text
schema: Book { id title author }
query { book(id: "42") { title } }
        |
        resolver Query.book ثم Book.title
        |
        { "data": { "book": { "title": "..." } } }
```

الحقل الذي لم يُطلب لا يُستدعى محلله.

## أبسط مثال

مخطط صغير ومتجر كتب:

```graphql
type Book {
  id: ID!
  title: String!
}

type Query {
  book(id: ID!): Book
}
```

عملية العميل:

```graphql
query OneBook($id: ID!) {
  book(id: $id) {
    title
  }
}
```

المتغيرات `{ "id": "42" }` تبقى خارج نص العملية حتى يُعاد استخدام النص ويُسجَّل من غير قيم المستخدم.

## شرح المثال

`Book` نوع كائن. `Query` جذر القراءة. `!` يعني القيمة مطلوبة في المخطط. العملية تطلب `title` فقط، فالرد الناجح لا يحتوي `id` رغم أنه في النوع. إن طلب العميل `price` وهو غير موجود في `Book`، المحرك يرفض النص قبل أي خدمة.

## ماذا يحدث داخليًا؟

المحرك يحلّل النص إلى شجرة، يطابقها بالمخطط، ثم يمشي الحقول. جذر `book` يستدعي الدالة المرتبطة به ومعها الحجة `id`. الناتج كائن. الحقل `title` إن لم يملك دالة خاصة يُقرأ من ذلك الكائن. الأخطاء الحقلية تظهر تحت `errors` مع `data` جزئية أحيانًا، وهذا شكل مختلف عن رمز HTTP واحد لكل الطلب. رمز النقل قد يبقى `200` رغم خطأ حقلي. لا تحكم على النجاح من رمز HTTP وحده عندما تعمل مع GraphQL.

## مثال عملي

شاشتان على المخطط نفسه:

```graphql
query Card {
  book(id: "42") { title }
}

query Detail {
  book(id: "42") { id title }
}
```

الخدمة التي تجلب الكتاب قد تُستدعى في الحالتين. الفرق ما يُسلسَل في JSON. هذا لا يلغي تكلفة الجلب إن كان المحلل يجلب الصف كاملًا. اختيار الحقول يقلل شكل الرد، وتحسين الاستعلام قرار لاحق في المحلل لا سحر في اللغة.

## أخطاء شائعة

- معاملة GraphQL كأنها SQL يصل من المتصفح إلى الجداول.
- افتراض أن كل خطأ يحمل `404`.
- تصميم نوع بحقول بلا مالك واضح ثم الاستغراب من N+1. ذلك يُلمح في درس لاحق ويُعمَّق في فصل `57-graphql-advanced`.
- نسخ نقطة `/graphql` بلا مخطط، فيصبح المسار صندوقًا بلا عقد.

## متى نستخدمه؟

عندما تتعدد أشكال الشاشات على البيانات نفسها، ويريد العميل عقدًا واحدًا يصف الحقول المسموحة.

## متى لا نستخدمه؟

لرفع ملف غلاف. ذلك multipart على HTTP كما في الفصل السابق. ولواجهة داخلية ثابتة الشكل يكفيها مسار REST واضح، المخطط تكلفة إضافية.

## مقارنة

| الفكرة | أين تعيش |
| --- | --- |
| ما يجوز طلبه | المخطط |
| ما طُلب هذه المرة | نص العملية |
| من أين تأتي القيمة | المحلل |
| أين تُخزَّن | خدمتك وقاعدتك، خارج اللغة |

## أسئلة مراجعة

- ما الفرق بين المخطط والعملية؟
- ماذا يفعل المحلل؟
- لماذا GraphQL ليست طبقة قاعدة؟

## الخلاصة

GraphQL عقد حقول زائد نص يختار منها. المحرك يتحقق ثم يستدعي المحللات. Nest ستربط هذا لاحقًا، بعد أن يصير الشكل مألوفًا بلا زينة.

## ماذا بعد؟

متى يبقى REST أوضح، ومتى يدفعك تعدد الشاشات إلى هذا العقد.
