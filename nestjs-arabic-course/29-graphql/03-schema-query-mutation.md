# Schema و Query و Mutation

## الهدف من هذا الدرس

قراءة مخطط صغير: أنواع، جذر قراءة، جذر كتابة، ونص عملية بمتغيرات.

## المشكلة التي يحلها

سماع «أرسل أي JSON إلى `/graphql`» ينتج عمليات بلا عقد. المخطط هو الذي يرفض الحقل المجهول والحجة الناقصة قبل الخدمة. من غير تمييز `Query` عن `Mutation` تُوضع الكتابة على جذر القراءة فيصعب على العميل والأدوات معرفة ما يغيّر بيانات.

## الفكرة ببساطة

SDL هي لغة وصف المخطط. `type Book` حقول. `type Query` نقاط الدخول للقراءة. `type Mutation` نقاط الدخول التي يُتوقع أن تغيّر حالة. العملية تسمي الجذر والحقول. المتغيرات تُمرر بجانب النص.

## التعريف التقني

```graphql
type Book {
  id: ID!
  title: String!
}

type Query {
  book(id: ID!): Book
  books: [Book!]!
}

type Mutation {
  createBook(title: String!): Book!
}
```

- `[Book!]!` قائمة مطلوبة، وعناصرها غير `null`. القائمة قد تكون فارغة.
- `book(id: ID!): Book` قد يعيد `null` إن كان الغياب ممثلًا بذلك. هذا قرار مخطط، ويختلف عن `404`.
- التعليق في SDL بـ `"..."` فوق الحقل وصف يظهر في أدوات المخطط.
- `subscription` جذر ثالث. قناته درس آخر في هذا الفصل.

جسم HTTP المعتاد:

```json
{
  "query": "query One($id: ID!) { book(id: $id) { title } }",
  "variables": { "id": "42" }
}
```

## Mental Model

```text
Schema  = ما يجوز
Query   = اقرأ بلا أثر جانبي مقصود
Mutation = غيّر حالة ثم أعد شجرة
Operation + variables = طلب هذه المرة
```

## أبسط مثال

قراءة ثم إنشاء، كعمليتين منفصلتين.

```graphql
query One($id: ID!) {
  book(id: $id) {
    id
    title
  }
}
```

```graphql
mutation Create($title: String!) {
  createBook(title: $title) {
    id
    title
  }
}
```

اسم العملية `One` و `Create` يظهر في السجلات. عملية بلا اسم أصعب تتبعًا عندما يرسل العميل أكثر من نص.

## شرح المثال

الحجة `$title` تُعرَّف في رأس العملية وتُربط بالحقل. القيمة تأتي من `variables` لا من لصق سلسلة المستخدم داخل النص. ذلك يمنع كسر الاقتباس ويبقي النص قابلًا للتخزين كقالب. حقول الرد بعد `createBook` اختيار للعميل: قد يطلب `id` فقط.

## ماذا يحدث داخليًا؟

الخادم يبني مخططًا قابلًا للتنفيذ من SDL أو من الأصناف لاحقًا. عند الطلب يتحقق من الأنواع. فشل التحقق خطأ قبل المحلل: حقل غير موجود، أو `ID` مفقود. إن عبر النص، تُنفَّذ حقول الجذر. مواصفة GraphQL تنفّذ حقول `Mutation` على الجذر بترتيب تسلسلي حتى لا تتسابق كتابتان في العملية نفسها. حقول `Query` يمكن أن تُجدول بالتوازي. لذلك لا تضع أثرًا جانبيًا في `Query` وتعتمد على الترتيب.

## مثال عملي

عقد كتالوج الإصدار الأول:

| الحاجة | الحقل |
| --- | --- |
| بطاقة وعنوان | `book(id: ID!): Book` |
| رف الصفحة | `books: [Book!]!` |
| إضافة عنوان | `createBook(title: String!): Book!` |

الحذف، إن أضفته، حقل على `Mutation` مثل `removeBook(id: ID!): Boolean!` وليس حقلًا على `Query`. الشكل النهائي للحذف قرار منتج: هل تعيد الكتاب المحذوف أم علمًا.

## أخطاء شائعة

- لصق معرف المستخدم داخل نص الاستعلام بدل `variables`.
- `createBook` داخل `type Query`.
- اعتبار `[Book]!` و `[Book!]!` الشكل نفسه. الأول يسمح بعنصر `null`.
- عملية واحدة فيها عدة mutations مترابطة ثم الافتراض أنها معاملة قاعدة واحدة. التسلسل ليس transaction.

## متى نستخدمه؟

هذا الشكل هو عقد الفصل: اقرأ من `Query`، واكتب من `Mutation`، وصف الحقول في الأنواع.

## متى لا نستخدمه؟

لا تخترع جذرًا ثالثًا للأوامر العادية. `subscription` للحدث المستمر فقط. ولا تضع SQL في SDL.

## مقارنة

| الجذر | أثر على البيانات | مثال المتجر |
| --- | --- | --- |
| `Query` | قراءة | `book` و `books` |
| `Mutation` | كتابة | `createBook` |
| `Subscription` | قناة أحداث | لاحقًا، تعليق جديد |

## أسئلة مراجعة

- ماذا يصف SDL؟
- لماذا ترتيب mutations على الجذر تسلسلي؟
- أين توضع عملية الحذف؟

## الخلاصة

المخطط أنواع وجذور. `Query` قراءة و `Mutation` كتابة. العملية تختار الحقول، والمتغيرات تحمل القيم.

## ماذا بعد؟

الأوراق والقوائم: scalars و enums، ثم أنواع الإدخال التي ليست أنواع إخراج.
