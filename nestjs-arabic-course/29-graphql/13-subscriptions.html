Subscriptions

الهدف من هذا الدرس

بث حدث من الخادم إلى عميل GraphQL ما دام الاتصال مفتوحًا، عبر graphql-ws لا عبر بروتوكول الاشتراك القديم.

المشكلة التي يحلها

شاشة المسودات التي تعيد query { books { title } } كل ثانيتين تدفع الثمن على القائمة كلها. عندما ينشر محرر كتابًا، العميل يحتاج عنصرًا واحدًا. الاشتراك عملية ثالثة في المخطط: الخادم يدفع قيمة عندما يقع الحدث. اتصال HTTP العادي للـ query ينتهي مع الرد.

الفكرة ببساطة

تعلن Subscription في المخطط، وتكتب @Subscription تعيد مكررًا غير متزامن. النقل في Nest الحالي مفتاح subscriptions['graphql-ws']. حزمة subscriptions-transport-ws لم تعد مقبولة. GraphiQL يستطيع تشغيل الاشتراك عندما يكون هذا المفتاح مضبوطًا.

التعريف التقني

الإعداد، كما في صفحة البداية:

GraphQLModule.forRoot<ApolloDriverConfig>({
  driver: ApolloDriver,
  autoSchemaFile: join(process.cwd(), 'src/schema.gql'),
  subscriptions: {
    'graphql-ws': true,
  },
});

بروتوكول العميل يجب أن يكون graphql-transport-ws الذي تتحدثه مكتبة graphql-ws. عميل Apollo القديم على البروتوكول السابق لا يتصل. لا تُبقِ المفتاح القديم «للتوافق» لأنه لم يعد جزءًا من الإعداد.

محلل النشر:

import { Resolver, Subscription } from '@nestjs/graphql';
import { Book } from './book.model.js';

@Resolver()
export class BooksEventsResolver {
  @Subscription(() => Book)
  bookPublished() {
    return this.events.asyncIterator('book.published');
  }
}

asyncIterator هنا من PubSub في graphql-subscriptions، وهو ناشر داخل العملية. يكفي لفهم القناة. عدة نسخ من التطبيق لا ترى حدث بعضها عبر هذا الناشر. طابور أو Redis موضوع فصول لاحقة، لا إعدادًا تخفيه داخل الاشتراك في اليوم الأول.

عند إنشاء الكتاب في الـ mutation، انشر بعد نجاح الحفظ:

await this.events.publish('book.published', { bookPublished: book });

اسم الخاصية في الحمولة يطابق اسم الحقل حتى يسلّم Apollo القيمة للمشترك.

Mental Model

عميل يفتح websocket على /graphql
  subscription { bookPublished { title } }
mutation تنجح
  publish
    المشترك يستلم { data: { bookPublished: { title } } }

أبسط مثال

نص العميل:

subscription {
  bookPublished {
    id
    title
  }
}

اتركه مفتوحًا في GraphiQL. من لسان آخر نفّذ createBook. يظهر عنوان الكتاب في لسان الاشتراك من غير إعادة الاستعلام عن الرف.

شرح المثال

الاشتراك لا يجلب الرف الحالي. العميل الذي يفتح الشاشة الآن يحتاج query للحالة الحاضرة ثم subscription لما يلي. الخلط بينهما يرسم شاشة فارغة حتى يحدث النشر التالي. أغلق GraphiQL في الإنتاج كما سبق، واشترك من عميل الواجهة بمكتبة تفهم graphql-ws.

ماذا يحدث داخليًا؟

graphql-ws: true يركب معالج الاشتراك على مسار GraphQL. الاتصال يعيش أطول من طلب POST. كل حدث من المكرر يُتحقق من حقوله كأنه رد عملية. إن رميت الكتاب كاملًا من Prisma، تسري الحقول المطلوبة فقط، وما زال النشر نفسه يحمل الكائن في الذاكرة. انشر الشكل الذي يعرفه @ObjectType، لا صف القاعدة.

Context الاتصال ليس req الخاص بـ POST دائمًا. حارس GqlAuthGuard الذي يقرأ req.headers قد لا يرى هوية اتصال الـ websocket إلا إذا ملأت context في إعداد graphql-ws عند الاتصال. إن كان النشر عامًا للكتالوج المنشور، يمكن تأجيل ذلك. إن كان الحدث مسودة لمستخدم، لا تفتح الاشتراك بلا هوية على الاتصال.

مثال عملي

افتح الرف بـ query { books { id title } } وابقَ على subscription { bookPublished { id title } }. الواجهة تلحق الحمولة محليًا. الخادم لا يدمج القائمة.

أخطاء شائعة

  • مفتاح subscriptions-transport-ws من مقال قديم.
  • توقع أن PubSub داخل العملية يبلغ نسخة ثانية من Nest.
  • نسيان query الأولية والاكتفاء بالاشتراك.
  • نشر كيان فيه حقول غير موجودة على Book ثم الاستغراب من فشل التسليم.

متى نستخدمه؟

لحدث نادر نسبيًا تشاهده شاشة مفتوحة: كتاب نُشر، توفر تغيّر، تعليق أضيف على صفحة مفتوحة.

متى لا نستخدمه؟

بديلًا عن قائمة تُحدَّث مرة في الدقيقة. الاستعلام أرخص من إبقاء مقبس لكل زائر. ولا بديلًا عن طابور العمل في فصول لاحقة. الاشتراك يبلّغ من اتصل، ولا يحفظ العمل إن لم يكن أحد يستمع.

مقارنة

الآلية عمر الاتصال من يدفع البيانات
Query طلب واحد العميل يسأل
Subscription + graphql-ws مفتوح الخادم عند publish
إعادة الاستعلام طلبات متكررة العميل

تمارين

تمرين سهل

أي مفتاح تضبطه في subscriptions؟

الحل `'graphql-ws': true`.

تمرين متوسط

لماذا تحتاج الشاشة استعلامًا واشتراكًا معًا؟

الحل الاستعلام يجلب الحالة الآن. الاشتراك يبلّغ بما يحدث بعد فتح الاتصال.

تمرين متقدم

لماذا PubSub في هذا الدرس لا يكفي لنسختين من التطبيق خلف موازن؟

الحل الناشر داخل العملية. الحدث الذي تنشره النسخة أ لا يصل مشتركًا على النسخة ب. الناقل المشترك موضوع لاحق.

أسئلة مراجعة

  • ما بروتوكول العميل المتوافق؟
  • ماذا يطابق مفتاح الحمولة؟
  • لماذا لا يغني الاشتراك عن حارس اتصال مختلف؟

الخلاصة

الاشتراك عملية ثالثة على قناة graphql-ws. انشر بعد الحفظ شكل Book، واترك الحالة الأولية لاستعلام. الناشر الداخلي لا يعبر حدود العملية.

ماذا بعد؟

WebSocket عام في Nest عبر بوابة، عندما لا يكون الحدث حقل GraphQL.
