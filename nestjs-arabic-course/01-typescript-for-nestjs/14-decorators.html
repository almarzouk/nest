Decorators

الهدف من هذا الدرس

فهم أن @Controller دالة تعمل عند تعريف الصنف، وتلصق وصفًا، ولا تنفّذ طلب HTTP بنفسها.

المشكلة التي يحلها

يمكن تسجيل المسارات في قائمة بعيدة عن الدالة. القائمة تبتعد عن الكود كلما كبر الملف. الـ Decorator يضع الإعلان فوق الدالة أو الصنف مباشرة: هذا مسار GET، وهذا الصنف وحدة.

الفكرة ببساطة

@Name فوق صنف أو دالة يستدعي دالة Name ويمرر لها الهدف. تلك الدالة قد تعدّل الهدف أو تخزن Metadata. Nest تقرأ المخزون عند الإقلاع.

Nest 12 تستخدم صيغة Decorators التقليدية في TypeScript (experimentalDecorators)، لأن مسار Metadata التصميم ما زال مرتبطًا بها. صيغة المعيار الأحدث (stage 3) ليست ما تكتبه في أمثلة التوثيق الحالية.

التعريف التقني

Decorator دالة. حسب مكانها:

  • Decorator صنف يستقبل constructor.
  • Decorator دالة (method) يستقبل prototype والاسم والواصف.
  • Decorator معامل يستقبل الهدف واسم الدالة وترتيب المعامل.

النتيجة قد تكون صنفًا بديلًا أو الواصف المعدّل، أو تكتفي بأثر جانبي: تسجيل Metadata.

في tsconfig الذي تستخدمه Nest تحتاج experimentalDecorators. ومع الحقن تحتاج emitDecoratorMetadata أيضًا، والدرس التالي.

Mental Model

تحميل الملف
   |
   v
تشغيل @Get فوق الدالة  ->  Metadata: method GET والمسار
   |
   v
تشغيل @Controller على الصنف -> Metadata: بادئة المسار
   |
   v
لاحقًا عند الإقلاع Nest تقرأ ولا تنتظر طلبًا لتشغيل الـ Decorator نفسه

أبسط مثال

Decorator تعليمي من غير Nest، ليظهر أن الاسم الذي بعد @ دالة:

function Frozen(target: Function): void {
  Object.freeze(target);
  Object.freeze(target.prototype);
}

@Frozen
class Book {}

شرح المثال

  • Frozen دالة تستقبل الصنف.
  • @Frozen فوق class Book يستدعي Frozen(Book) بعد تعريف الصنف.
  • Object.freeze أثر وقت التشغيل على الدالة والنموذج. مثال تعليمي، وليس أسلوب Nest.
  • لو وضعت @Frozen ولم تُعرَّف الدالة، فالخطأ مرجع مفقود لا سحر لغة.

Decorator دالة يسجّل اسمًا في مصفوفة على الصنف:

const routes: string[] = [];

function Get(path = '/'): MethodDecorator {
  return (_target, propertyKey) => {
    routes.push(`${String(propertyKey)} ${path}`);
  };
}

class Books {
  @Get('/books')
  list(): string[] {
    return [];
  }
}
  • Get('/books') يستدعى فورًا عند قراءة السطر، ويعيد دالة هي الـ Decorator الفعلي. هذا مصنع Decorator: الدالة الخارجية تأخذ الخيارات، والداخلية تستقبل الهدف.
  • list لا تُستدعى أثناء ذلك. الذي يشتغل هو التسجيل في routes.
  • @Get() و @Controller('books') في Nest المصنع نفسه بفكرة: الوسيط مسار، والأثر Metadata لا مصفوفة عامة كتبتها أنت.

MethodDecorator نوع TypeScript لدالة الزينة على الدوال. لا تحفظ كل تواقيع الزينة. احفظ: المصنع يأخذ خياراتك، والدالة الداخلية ترى الهدف.

ماذا يحدث داخليًا؟

عند تحميل الوحدة، التعريفات تُنفَّذ من الأعلى، والزينة تعمل بعد اكتمال تعريف الهدف الذي تزينه. الترتيب على العنصر نفسه من الأسفل إلى الأعلى في تطبيق الزينة التقليدية عند تعددها: الزينة الأقرب إلى الدالة تُطبَّق أولًا في سلسلة التغليف. في Nest أغلب الزينة لا تغلف الدالة بل تسجل Metadata، والترتيب الذي يهمك لاحقًا هو ترتيب مسار الطلب لا ترتيب تطبيق الزينة.

الطلب HTTP لا يمر داخل دالة @Get. يمر في Express ثم إلى الدالة الأصلية list بعد أن وجدت Nest الربط في Metadata.

JavaScript الناتج يستدعي دالة مساعدة __decorate. وجود reflect-metadata يسمح بتخزين مفاتيح على الهدف. Nest تخزن عليها نوع المسار والمسار وغير ذلك.

مثال عملي

قراءة وصف المسار كما ستراه، من غير تشغيل إطار:

@Controller('books')
class BooksController {
  @Get(':id')
  findOne(): string {
    return 'later';
  }
}

المعنى الذي ستبنيه الفصول القادمة، لا التنفيذ اليوم:

  • @Controller('books') بادئة.
  • @Get(':id') طريقة GET ومسار نسبي :id.
  • المسار الكامل المتوقع /books/:id.
  • findOne تُستدعى عند التطابق، لا عند تحميل الملف.

@Injectable() على خدمة مصنع بلا وسائط غالبًا: أثره تعليم الصنف حتى تُقرأ أنواع حقنه. سنفصله مع المزوّدات. لغويًا هو Decorator صنف.

أخطاء شائعة

  • توقع أن الزينة تعمل عند كل طلب. تعمل عند تحميل الصنف.
  • نسيان experimentalDecorators في tsconfig الذي يبني فعلًا، فيفشل البناء أو تُتجاهل الزينة حسب الإعداد.
  • منطق عمل داخل Decorator. يصير صعب الاختبار ويعمل وقت التحميل لا وقت الطلب. ضع العمل في الدالة.
  • الخلط مع stage 3. انسخ صيغة توثيق Nest، لا صيغة مقال عن المعيار الجديد، حتى يعلن الإطار انتقالًا.

متى نستخدم Decorator؟

عندما يقرأ إطار وصفًا بجانب الكود: مسارات، ووحدات، وحقن، وصلاحيات. ستكتب الزينة الجاهزة أولًا، ثم تصنع واحدة في فصل Custom Decorators.

متى لا نستخدمه؟

لتغليف كل دالة عادية في مشروعك "لأن Nest تفعل ذلك". دالة صريحة أوضح إن لم يكن هناك قارئ إطار.

مقارنة

تسجيل يدوي routes.push Decorator
مكان الإعلان قد يبتعد عن الدالة فوق الهدف
وقت التنفيذ عندما تصل إلى السطر عند تعريف الهدف
من يقرأ النتيجة في Nest أنت الإطار عند الإقلاع

تمارين

تمرين سهل

في مثال Get، متى تُدفع السلسلة إلى routes: عند تعريف الصنف أم عند نداء list()؟

الحل

عند تعريف الصنف وتحميله، لا عند نداء list().

تمرين متوسط

لماذا Get(path) ترجع دالة بدل أن تكون هي الزينة مباشرة؟

الحل

حتى تأخذ path من عندك وتغلق عليه (closure)، ثم تعيد الدالة التي تستقبل الهدف. @Get('/books') يمرر الخيار. @Get بلا مصنع لا يرى المسار الذي تريده.

تمرين متقدم

لو اشتغل Decorator عند كل طلب، ماذا كان سيختلف في تسجيل المسار /books/:id؟

الحل

التسجيل كان سيتكرر أو يعتمد على وصول طلب، والمسار قد لا يوجد قبل أول طلب، والوصف يختلط بالعمل. التسجيل عند التحميل يجعل جدول المسارات جاهزًا قبل listen، وهو ما تفعله Nest في الإقلاع.

أسئلة مراجعة

  • ما نوع الشيء الذي تضعه بعد @؟
  • لماذا مصنع Decorator يرجع دالة؟
  • متى تعمل الزينة مقارنة بوقت الطلب؟
  • أي خيار مترجم تحتاجه صيغة Nest الحالية؟

الخلاصة

Decorator دالة إعلان تعمل عند التعريف وتخزن وصفًا أو تعدّل الهدف. Nest تبني المسارات والحقن من هذا الوصف عند الإقلاع. الزينة لا تستبدل جسم دالة العمل.

ماذا بعد؟

الوصف يُخزَّن بمفاتيح Reflection حتى تجده Nest بعد الترجمة. هذا Metadata.
