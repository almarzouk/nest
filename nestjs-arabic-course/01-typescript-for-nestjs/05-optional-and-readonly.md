# Optional و Readonly

## الهدف من هذا الدرس

تمثيل حقل غير إلزامي، ومنع إعادة تعيين ما يجب أن يبقى ثابتًا بعد البناء. هذا يمهد لـ `private readonly` في الـ constructor.

## المشكلة التي يحلها

تحديث كتاب قد يرسل السعر فقط. إذا كان كل حقل إلزاميًا في نوع التحديث، تجبر العميل على إرسال العنوان أيضًا. وإذا سُمح لكود لاحق بتغيير `id` بعد إنشاء الكائن، المعرّف الذي مر في الطلب يضيع وسط الدالة.

## الفكرة ببساطة

`?` يعني الحقل قد يغيب. `readonly` يعني لا نعيد تعيينه من الكود العادي بعد التهيئة.

## التعريف التقني

Optional property نوعها يتضمن `undefined` عند القراءة، وقد تُحذف من الكائن. `readonly` قيد على التعيين أثناء الفحص، لا تجميد للكائن وقت التشغيل مثل `Object.freeze`.

## Mental Model

```text
CreateBook     title و price مطلوبان
UpdateBook     title? و price? اختياريان
Book           id للقراءة بعد الإنشاء
```

## أبسط مثال

```ts
interface UpdateBook {
  title?: string;
  price?: number;
}

function hasPrice(input: UpdateBook): boolean {
  return input.price !== undefined;
}
```

## شرح المثال

- `title?` يساوي تقريبًا `title?: string | undefined` في القراءة.
- الجسم `{}` صالح كـ `UpdateBook`.
- قبل استخدام `input.price` كعدد، تأكد أنه ليس `undefined`.
- `hasPrice` تضييق عملي.

## ماذا يحدث داخليًا؟

`?` و `readonly` يختفيان بعد الترجمة. كائن JavaScript يقبل `book.id = 'other'` حتى لو كان الحقل `readonly` في النوع، إلا إذا منعت ذلك بطريقة تشغيل. القيد يحمي كودك الذي يمر على المترجم، لا عميلًا خبيثًا.

في Nest، `readonly` على خدمة محقونة يذكر الفريق ألا يستبدل الاعتماد. الحقن يحدث مرة في البناء. إعادة التعيين غالبًا خطأ تصميم.

## مثال عملي

```ts
interface Book {
  readonly id: string;
  title: string;
  price: number;
}

function rename(book: Book, title: string): Book {
  return { ...book, title };
}
```

`rename` لا يغيّر `id` لأنه ينسخ الكائن ويبدل العنوان. هذا أوضح من تعديل الكائن في مكانه عندما تمرر المرجع إلى أكثر من دالة. الخدمات في Nest غالبًا تعدّل مخزنًا خارجيًا لا كائن الطلب نفسه.

`readonly string[]` يمنع استبدال المصفوفة، ولا يمنع `push` على عناصر مصفوفة عادية. إن أردت منع الدفع فالنوع `readonly string[]` أو `ReadonlyArray<string>`.

## أخطاء شائعة

- معاملة الحقل الاختياري كأنه موجود في JSON دائمًا.
- الظن أن `readonly` يخفي الحقل عن `JSON.stringify`. الحقل يُسلسَل. الإخفاء عن الرد Serialization لاحقًا.
- استخدام الاختياري بدل اتحاد واضح مع `null` من غير اتفاق. اختر: الغياب بحذف المفتاح، أو `null` الصريح، واتركه ثابتًا في العقد.

## متى نستخدم optional؟

في التحديث الجزئي المقابل لـ `PATCH`، وفي إعدادات لها افتراض داخلي.

## متى لا نستخدمه؟

لحقل إن غاب فالعملية بلا معنى، مثل عنوان عند الإنشاء. اجعله مطلوبًا وافشل التحقق إن غاب.

## مقارنة

| | `?` | `readonly` |
| --- | --- | --- |
| يمنع | إلزام المستدعي بالحقل | إعادة التعيين في الكود المفحوص |
| وقت التشغيل | لا يفرض شيئًا وحده | لا يجمّد الكائن وحده |

### تمرين متوسط

لماذا `book.id = '3'` يفشل في الفحص وينجح إذا تجاوزت المترجم بـ `as Book` ثم التعيين في JavaScript ناتج بلا فحص؟

<details>
<summary>الحل</summary>

`readonly` قاعدة مترجم. التحويل القسري `as` يسكت الفحص في تلك النقطة. الناتج كائن عادي قابل للتغيير. لا تعتمد على `readonly` كحماية أمنية.

</details>

### تمرين متقدم

صمّم نوع `PatchBook` بحيث يمكن إرسال `price` وحده، ولا يمكن إرسال `id` ضمن التحديث.

<details>
<summary>الحل</summary>

```ts
interface PatchBook {
  title?: string;
  price?: number;
}
```

عدم وجود `id` في النوع يمنع المستدعي المكتوب بـ TypeScript من إرساله كحقل معروف. الحقول الزائدة على حدود الشبكة ما زالت تصل حتى يحذفها `whitelist` لاحقًا.

</details>

## أسئلة مراجعة

- ماذا يغير `?` في نوع الحقل؟
- هل `readonly` يصل إلى JSON الخارج؟
- أين يناسب الاختياري فعل `PATCH`؟

## الخلاصة

الاختياري يصف الغياب في العقد المكتوب. `readonly` يذكر الكود ألا يعيد التعيين. كلاهما فحص مترجم، والشبكة لها طبقة تحقق لاحقة.

## ماذا بعد؟

أحيانًا المجموعة المغلقة من القيم تُكتب كـ Enum. سترى متى يكون اتحاد النصوص أوضح.
