# Token Rotation

## الهدف من هذا الدرس

تجديد رمز وصول رف القصير برمز تحديث يُستهلك مرة واحدة، بحيث كل تجديد يصدر خلفًا ويلغي استخدام السلف.

## المشكلة التي يحلها

جوال رف يحفظ refresh token لأسبوعين. إن بقي نفس الرمز يعمل في كل تجديد، فنسخه من نسخة احتياطية للجهاز يكفي لصنع access token جديد كل ربع ساعة من غير أثر. انقطاع الرد بعد التجديد يدفع التطبيق لإعادة الرمز القديم فيُرفض أو يُصدر جلسة ثانية.

## الفكرة ببساطة

`TokenService.issue` يعطي access token قصير العمر و refresh token معتمًا يُخزَّن كتجزئة. `refresh` يستهلك الرمز ويعيد خلفًا مع access token جديد. سلسلة الخلفاء عائلة واحدة. إعادة رمز مُستهلك تعني أن نسختين تملكانه، فتُبطَل العائلة كلها.

## التعريف التقني

في `@nestjs/authentication`، `accessToken` في إعداد الوحدة: `key` لا يقل عن 32 بايتًا، و `issuer` و `audience` و `ttl` مثل `15m`. من غير `key` لا يقلع التطبيق. `JwtBearerProvider` يتحقق من التوقيع و `exp` و `iss` و `aud` ثم يستدعي `validate` لتحميل المستخدم الحالي من `sub`. `POST` التجديد يستدعي `tokenService.refresh(refreshToken)`. الرموز المعتمة تُخزَّن مجزأة. كل رمز يعمل مرة. إعادة المستخدم أو المنتهي أو المجهول ترمي `RefreshTokenError` وهو `AuthenticationError` وتجيب الوحدة بـ 401 بلا `try/catch` إضافي في المتحكم. `claims` التي تمررونها إلى `issue` تُحفظ مع العائلة وتدخل كل access token لاحق، لذلك لا تضعوا فيها دورًا يتغير. Passport ليس مطلوبًا لهذا التدوير؛ إن كان المشروع على Passport فتدويره يُبنى هناك لا بمزج الخدمتين.

## Mental Model

```text
issue → access A0 + refresh R0
refresh(R0) → access A1 + refresh R1    و R0 ميت
refresh(R0) مرة أخرى → إلغاء العائلة كلها
```

## أبسط مثال

```ts
import { Body, Controller, HttpCode, Post } from '@nestjs/common';
import { Public, TokenService } from '@nestjs/authentication';

@Public()
@Controller('auth/token')
export class TokensController {
  constructor(private readonly tokens: TokenService) {}

  @Post('refresh')
  @HttpCode(200)
  refresh(@Body('refreshToken') refreshToken: string) {
    return this.tokens.refresh(refreshToken);
  }
}
```

## شرح المثال

- 200 لا 201. لا يُنشأ مستخدم، يُستبدل إثبات.
- الجسم فيه الرمز الجديد. التطبيق يحذف `R0` ويحفظ `R1` قبل أي نداء آخر.
- لا تسجّلوا `refreshToken` في السجل.

## ماذا يحدث داخليًا؟

1. `refresh` يبحث عن تجزئة الرمز.
2. إن كان حيًا يعلّمه مستهلَكًا ويكتب الخلف في نفس العائلة.
3. يوقّع access token جديدًا بنفس مطالبات الدخول (`amr` وغيرها مما خُزّن مع العائلة) لا بأدوار حية من الجدول.
4. `validate` على كل طلب API يحمّل المستخدم من `sub` حتى لا يعيش الدور القديم داخل JWT طويلًا. عمر الوصول قصير أصلًا (`ttl`).
5. إن وصل `R0` بعد الاستهلاك، الخدمة تعتبر العائلة مسروقة وتبطلها. التطبيق الشرعي الذي تأخر في حفظ `R1` سيحتاج دخولًا جديدًا. هذا ثمن اكتشاف النسخ.

## مثال عملي

إصدار أول بعد كلمة المرور، من الصفحة:

```ts
return this.tokens.issue(user.id, {
  method: 'password',
  claims: { amr: ['pwd'] },
});
```

`amr` يصف كيف تم الدخول ويُنسخ إلى الرموز المجددة. لا تضعوا `roles` داخل `claims` لأن تغيير دور الموظف لن يظهر حتى تنتهي العائلة. `JwtBearerProvider.validate` يقرأ الدور من القاعدة كل طلب.

## أخطاء شائعة

- إعادة استخدام نفس refresh token حتى ينتهي أسبوعه.
- حفظ الأدوار داخل access token طويل بلا تحميل في `validate`.
- تجديد على مسار بلا `HttpCode` مفهوم ثم اعتبار 201 إنشاء جلسة ثانية في الواجهة.
- تدوير رمز Google نفسه بدل إصدار عائلة رموز رف.

## متى نستخدمه؟

لجوال أو عميل عام بلا كعكة جلسة، كلما طُلب access token جديد.

## متى لا نستخدمه؟

لجلسة متصفح تديرها كعكة الخادم في الحزمة. هناك تجديد جلسة لا عائلة refresh. ولا لتدوير كلمة المرور؛ ذلك تغيير سر لا استبدال رمز.

## مقارنة

| | رمز تحديث ثابت | تدوير |
| --- | --- | --- |
| كل تجديد | نفس السر | خلف جديد وسلف ميت |
| ظهور السلف بعد موته | ما زال يعمل | تلغى العائلة |
| الأدوار | إن دُفنت في الرمز تتجمد | تُقرأ من القاعدة في `validate` |

## تمارين

### تمرين سهل

بعد `refresh` ناجح، هل يصلح `R0` لتجديد ثانٍ؟

<details>
<summary>الحل</summary>

لا. يُستهلك مرة. استخدامه مرة أخرى يلغي العائلة حسب وصف `TokenService`.

</details>

### تمرين متوسط

انقطع الرد بعد التجديد فأعاد التطبيق `R0` بينما كان `R1` قد حُفظ على الخادم. ماذا يحدث للحساب؟

<details>
<summary>الحل</summary>

تُبطل العائلة وعلى الطرفين تسجيل دخول من جديد. لذلك يحفظ التطبيق `R1` فورًا، ويعامل هذا الفشل كحدث أمن لا كإعادة محاولة عادية.

</details>

### تمرين متقدم

لماذا `ttl: '15m'` على access token جزء من سياسة التدوير لا تفصيل توقيع؟

<details>
<summary>الحل</summary>

لأن الرمز المسروق يعمل حتى `exp`. التجديد المتكرر بلا تدوير يطيل نافذة refresh، والتدوير يقصّر حياة كل refresh، و `ttl` يقصّر حياة access. الاثنان معًا يحدان النافذة. الدور لا يُخزَّن في الرمز حتى لا يبقى ربع ساعة زائد عمر العائلة على دور قديم.

</details>

## أسئلة مراجعة

- ماذا يعيد `refresh` غير access token؟
- أين تُخزَّن رموز التحديث؟
- ماذا تفعل إعادة الرمز المستهلك؟
- لماذا تبقى الأدوار خارج `claims`؟

## الخلاصة

تدوير رف: كل refresh token يُستخدم مرة ويصدر خلفًا. إعادة السلف تبطل العائلة. access token قصير و `validate` يحمّل المستخدم الحي. هذا `TokenService` في الحزمة الرسمية، لا إلغاء لوصفة Passport.

## ماذا بعد؟

التدوير يكتشف النسخ. الدرس التالي إبطال صريح: تسجيل خروج جهاز، أو إنهاء كل جلسات الحساب.
