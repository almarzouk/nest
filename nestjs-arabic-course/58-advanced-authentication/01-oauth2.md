# OAuth 2.0

## الهدف من هذا الدرس

تمييز التفويض في رف: العميل يطلب إذنًا محدودًا من مالك حساب، ويحصل على رمز وصول إلى مورد، من غير أن يقرأ كلمة مرور المالك.

## المشكلة التي يحلها

شريك شحن يريد إنشاء طلبات كتب نيابة عن مكتبة وافقت، لا أن تخزّن المكتبة كلمة مرور رف عند الشريك. نسخ كلمة المرور إلى تطبيق الشريك يجعل التسريب عند الشريك تسريبًا لحساب رف كله.

## الفكرة ببساطة

OAuth 2.0 إطار تفويض. الأطراف: مالك المورد (المكتبة)، العميل (تطبيق الشريك)، وخادم التفويض الذي يصدر الرمز، وخادم المورد الذي يقبل الرمز. العميل لا يرى كلمة المرور. الرمز يحمل نطاقًا (scopes) لا «كل الحساب».

## التعريف التقني

التدفق المناسب لتطبيق خادم مع متصفح هو Authorization Code: المتصفح يذهب إلى خادم التفويض، يعود برمز قصير العمر (code) إلى عنوان إعادة توجيه مسجّل، والخادم يستبدله بـ access token. PKCE يمتد إلى عملاء لا يضمنون سرًا ثابتًا. سر العميل يبقى على خادم رف لا في صفحة أو جوال. الرمز الذي يظهر في رابط المتصفح ليس جلسة API دائمة. صفحة المصادقة في Nest تبني OpenID Connect فوق هذه الأفكار بحزمة `@nestjs/authentication`؛ وصفة Passport ما زالت في Recipes ولم تُحذف. هذا الدرس يثبت المصطلح قبل Google.

## Mental Model

```text
مكتبة توافق في المتصفح
→ code إلى خادم رف
→ خادم رف يستبدل code برمز وصول
→ الشريك ينادي /orders بالرمز لا بكلمة المرور
```

## أبسط مثال

```text
client_id     تطبيق الشريك المسجّل
redirect_uri  https://partner.example/callback  مطابق حرفيًا للمسجّل
scope         orders:create
code          يُستبدل مرة على الخادم
```

## شرح المثال

- `redirect_uri` غير المسجّل يُرفض حتى لا يذهب الرمز إلى موقع المهاجم.
- `scope` يحد ما سيفعله الرمز. إنشاء الطلبات لا يعني قراءة كلمات المرور.
- `code` في عنوان المتصفح مكشوف لسجل المتصفح، لذلك عمره قصير والاستبدال يتم من الخادم.

## ماذا يحدث داخليًا؟

1. تطبيق الشريك يوجّه المتصفح إلى خادم التفويض مع `client_id` و `redirect_uri` و `state`.
2. المكتبة توافق على النطاق.
3. المتصفح يعود إلى `redirect_uri` ومعه `code` و `state`.
4. خادم الشريك يتحقق أن `state` هو الذي أرسله، ثم يستبدل `code` بسر العميل.
5. access token الناتج يُستخدم على API المورد. تجديده أو إبطاله درس لاحق؛ هنا يكفي أنه ليس كلمة المرور.

## مثال عملي

رفض إعادة التوجيه المفتوحة في رف إن أصبح هو خادم التفويض لشركائه:

```ts
export function assertRedirect(registered: string[], candidate: string) {
  if (!registered.includes(candidate)) {
    throw new Error('redirect_uri is not registered');
  }
  return candidate;
}
```

المقارنة حرفيّة. `https://partner.example/callback` لا يطابق `https://partner.example/callback/evil` ولا `https://partner.example.evil/callback`. لا تبنِ خوارزمية توقيع رمز من الصفر؛ الإصدار يتم بمكوّن مصادقة راجعتم توثيقه.

## أخطاء شائعة

- وضع سر العميل في تطبيق الجوال أو في صفحة.
- اعتبار OAuth «تسجيل دخول» فقط. التسجيل هوية، وقد تُبنى فوقه بـ OpenID Connect في الدرس التالي.
- تخزين `code` كجلسة أسبوعية.
- نطاق `*` غير مكتوب في العقد ثم استخدام الرمز لكل المسارات.

## متى نستخدمه؟

عندما يصل برنامج آخر إلى موارد مكتبة بموافقة صاحبها، أو عندما يفوّض المتصفح خادم رف لدى مزود خارجي.

## متى لا نستخدمه؟

لتسجيل موظف رف بكلمة مرور تملكونها أصلًا على قاعدتكم. هناك مسار الجلسة أو رمز الوصول الخاص بكم. ولا كذريعة لتخزين كلمة مرور Google.

## مقارنة

| | كلمة مرور منسوخة | OAuth 2.0 |
| --- | --- | --- |
| ماذا يرى الشريك | سر الحساب | رمز بنطاق |
| الإلغاء | تغيير كلمة المرور | إبطال الرمز |
| مكان السر | عند الشريك | سر العميل على خادم مسجّل |

## تمارين

### تمرين سهل

أين يُستبدل `code`: في المتصفح أم على الخادم؟

<details>
<summary>الحل</summary>

على الخادم، مع سر العميل إن كان العميل سريًا. المتصفح ينقل `code` فقط إلى عنوان إعادة التوجيه.

</details>

### تمرين متوسط

لماذا `state` جزء من التدفق لا زينة؟

<details>
<summary>الحل</summary>

يربط العودة بالمحاولة التي بدأها نفس المتصفح. من غيره يمكن إنهاء تدفق لم يبدأه الضحية إن تسرّب رابط العودة. تحقق الخادم أن القيمة التي رجعَت هي التي أصدرها.

</details>

### تمرين متقدم

شريك يطلب نطاق `orders:create` ثم يستخدم الرمز على `DELETE /books`. أين يُرفض ذلك؟

<details>
<summary>الحل</summary>

عند خادم المورد: الرمز بلا هذا النطاق. رفض الخادم التفويض عند الإصدار لا يكفي إن لم يفحص المورد النطاق على كل مسار.

</details>

## أسئلة مراجعة

- ماذا يفوّض OAuth 2.0: الهوية أم الوصول إلى مورد؟
- لماذا لا يُخزَّن سر العميل في الصفحة؟
- ما دور `redirect_uri` المسجّل؟
- هل اختفاء Passport شرط لفهم OAuth هنا؟

## الخلاصة

OAuth 2.0 يعطي العميل رمز وصول بنطاق بعد موافقة المالك، عبر code يُستبدل على الخادم. هو ليس نسخ كلمة المرور، وليس بذاته إثبات «من الشخص».

## ماذا بعد؟

رف تريد معرفة من الشخص لا إذنًا على بريده فقط. الدرس التالي يضع طبقة الهوية OpenID Connect فوق هذا التفويض.
