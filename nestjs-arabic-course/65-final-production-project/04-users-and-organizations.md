# Users و Organizations

## الهدف من هذا الدرس

إنشاء مكتبة رف وربط صاحب الحساب بعضوية `owner`، وجعل الطلبات التالية تعمل بمستأجر من ترويسة لا من جسم المشروع.

## المشكلة التي يحلها

عمود `user.libraryName` يمنع الموظف الثاني. أو `POST /organizations` يأخذ `ownerId` من الجسم فيصبح أي شخص مالكًا. أو الترويسة تُقبل بلا فحص عضوية.

## الفكرة ببساطة

`POST /organizations` بالاسم و slug، والمالك هو `user.id` من الإثبات. المعاملة تنشئ المنظمة والعضوية. بعدها يرسل العميل `X-Tenant-Id` بمعرّف منظمة هو عضو فيها. الحارس يرفض الغياب والتعارض مع الجسم.

## التعريف التقني

جداول `Organization` و `Membership` بمفتاح `(userId, organizationId)` ودور `owner`. slug فريد وآمن للنطاق لاحقًا. لا كتب بعد؛ المشروع درس تالٍ حتى لا يُنشر كتالوج بلا مالك. `TenantGuard` من فصل العزل: المصدر الترويسة، ثم العضوية، والجسم إن حمل `organizationId` مخالفًا يُرفض بـ 400. سياق `AsyncLocalStorage` يحمل المعرّف للخدمات singleton.

## Mental Model

```text
إثبات user
→ إنشاء منظمة + owner
→ كل طلب لاحق: ترويسة + عضوية
→ current organizationId
```

## أبسط مثال

```prisma
model Organization {
  id   String @id
  name String
  slug String @unique
}

model Membership {
  userId         String
  organizationId String
  role           String
  @@id([userId, organizationId])
}
```

## شرح المثال

- المفتاح المركب يمنع عضويتين مكررتين.
- الدور نص مغلق في الخدمة لا في قاعدة بلا فحص: `owner` فقط عند الإنشاء.
- المنظمة بلا مشاريع بعد مقبولة.

## ماذا يحدث داخليًا؟

1. الحارس العام يعرف المستخدم. المسار ليس `@Public`.
2. المعاملة تدرج المنظمة والعضوية.
3. الرد 201 فيه `id` و `slug` لا قائمة مشاريع.
4. الطلب التالي بلا ترويسة 403.
5. ترويسة منظمة أخرى ليس عضوًا فيها 403 ولا تكشف مشاريعها.

## مثال عملي

```ts
@Post()
@HttpCode(201)
create(@CurrentUser('id') userId: string, @Body() body: { name: string; slug: string }) {
  return this.orgs.createFor(userId, body);
}
```

`createFor` لا يقرأ `body.userId`. slug يطابق `^[a-z0-9-]+$` وإلا 400.

## أخطاء شائعة

- مالك من الجسم.
- ترويسة تكفي بلا عضوية.
- إنشاء مشروع تجريبي داخل معاملة المنظمة فيصعب حذف المكتبة في الاختبار.
- slug فيه أحرف تسمح بخلط المضيف لاحقًا.

## متى نستخدمه؟

مباشرة بعد التسجيل وقبل أي كتاب. كل الجداول التالية تحمل `organizationId`.

## متى لا نستخدمه؟

لا تبنوا دعوة الموظف في هذه الشريحة إن لم تحتاجوها قبل المشاريع. الدعوة تعود مع الإشعارات. المالك وحده يكفي لأول نشر.

## مقارنة

| الطلب | النتيجة |
| --- | --- |
| `POST /organizations` | 201 ومالك من الإثبات |
| ترويسة بلا عضوية | 403 |
| جسم `organizationId` مخالف | 400 |
| قائمة منظمات الشخص | 200 وقد تكون فارغة |

## تمارين

### تمرين سهل

من يُكتب في عضوية الإنشاء؟

<details>
<summary>الحل</summary>

`CurrentUser` لا حقل الجسم. الدور `owner`.

</details>

### تمرين متوسط

لماذا 403 لا 404 لترويسة منظمة لا ينتمي إليها الشخص؟

<details>
<summary>الحل</summary>

لأن العقد هنا عن العضوية لا عن غياب مورد كتاب. 404 تُحفظ لمشروع بمعرّف داخل المكتبة لا يوجد. المنظمة التي لا تملكونها ليست «غير موجودة» بالضرورة.

</details>

### تمرين متقدم

شخص في مكتبتين. ماذا يتغير بين الطلبين؟

<details>
<summary>الحل</summary>

الترويسة فقط. الإثبات نفسه. الحارس يحمّل عضوية الزوج `(user, tenant)` كل مرة. لا دور داخل الرمز يغطي المكتبتين.

</details>

## أسئلة مراجعة

- ماذا تُنشئ المعاملة؟
- من أين يُؤخذ المستأجر بعد الإنشاء؟
- ماذا يُرفض في الجسم؟
- لماذا slug مقيّد؟

## الخلاصة

المنظمة مكتبة والمالك من الإثبات في معاملة مع العضوية. الطلبات التالية ترويسة وعضوية. الجسم لا يختار المستأجر.

## ماذا بعد؟

داخل المكتبة يُنشأ كتاب قيد التجهيز. الدرس التالي المشاريع.
