# سطح GraphQL

## الهدف من هذا الدرس

إضافة استعلام قراءة لمشاريع منظمة رف عبر GraphQL، بنفس العزل، من غير نقل كل API ومن غير ادّعاء أن الحماية المتقدمة ديكور واحد.

## المشكلة التي يحلها

الواجهة ستطلب المشروع فقط ثم تُغرى بإضافة مؤلف ومراجعات فيصبح N+1. أو المخطط يفتح كل المنظمات. أو يُنسخ منطق العزل بطريقة أضعف من REST فترى دار النيل مشاريع غيرها.

## الفكرة ببساطة

استعلام `projects` يعيد عنوان المشروع وحالته للمنظمة في السياق. نفس `TenantGuard` أو ما يعادله على طلب GraphQL. لا mutation في هذه الشريحة؛ الإنشاء يبقى REST حتى لا يتفرع العقد. DataLoader لا يُضاف حتى يظهر حقل علاقة. التعقيد والعمق والاتحاد ليست جزءًا من السطح الأول.

## التعريف التقني

`GraphQLModule` من `@nestjs/graphql` كما في التوثيق، code first أو schema first واحد فقط. الحقل يقرأ `currentTenantId()` ويستدعي `ProjectsService.list` حتى لا يتفرع `where`. قائمة فارغة مصفوفة فارغة لا خطأ. 404 للفرد عبر union أو خطأ GraphQL موثّق، لكن هذه الشريحة قائمة فقط حتى يبقى السطح صغيرًا. لا `@nestjs/apollo` federation هنا.

## Mental Model

```text
REST يبقى للإنشاء والنشر
GraphQL projects → نفس الخدمة ونفس المنظمة
```

## أبسط مثال

```ts
@Resolver()
export class ProjectsResolver {
  constructor(private readonly projects: ProjectsService) {}

  @Query(() => [ProjectType])
  projects() {
    return this.projects.listRows(currentTenantId());
  }
}
```

`listRows` تعيد الصفوف التي يغلفها REST داخل `data`. لا تعيدوا غلاف REST داخل GraphQL إن كان المخطط يعد بمصفوفة؛ اتفقوا على شكل واحد في هذا الاستعلام واتركوا الغلاف لـ REST.

## شرح المثال

- الخدمة المشتركة تمنع اختلاف العزل.
- لا وسيط `organizationId` في الاستعلام.
- النوع يعرض `id` و `title` و `status` فقط.

## ماذا يحدث داخليًا؟

1. سياق HTTP يملأ المستأجر قبل الحل إن كان المسار خلف نفس التطبيق.
2. `projects` تستدعي القائمة المقيّدة.
3. صفر صفوف مصفوفة فارغة.
4. لا resolver حقل إضافي فلا N+1 بعد.
5. REST `POST` لم يُحذف.

## مثال عملي

```graphql
query Shelf {
  projects {
    id
    title
    status
  }
}
```

اختبار يطلب الاستعلام بترويسة منظمة بلا مشاريع ويتوقع `[]`. اختبار ثانٍ بمشروع الجار لا يظهر العنوان. لا تختبروا عمقًا عشوائيًا؛ المخطط لا يسمح به.

## أخطاء شائعة

- وسيط `organizationId` في GraphQL يثق بالجسم.
- نقل النشر إلى mutation بلا `PlanPolicy`.
- تفعيل GraphiQL في الإنتاج مع استعلامات حرة بلا قائمة محفوظة إن فتحتم الباب لاحقًا.
- نسخة ثانية من `findMany` داخل الـ resolver.

## متى نستخدمه؟

بعد استقرار REST للقراءة البسيطة التي تريدها الواجهة في جولة واحدة لاحقًا. اليوم الجولة حقل واحد.

## متى لا نستخدمه؟

لا تستبدلوا Checkout أو الويب هوك بـ GraphQL. ولا تضيفوا Federation لمكتبة واحدة.

## مقارنة

| | REST في رف | هذا السطح |
| --- | --- | --- |
| إنشاء | `POST` 201 | غير موجود |
| قائمة فارغة | 200 و `data: []` | `[]` |
| العزل | الخدمة | نفس الخدمة |
| تعقيد و DataLoader | — | عند ظهور علاقة فقط |

## تمارين

### تمرين سهل

لماذا لا وسيط منظمة في `projects`؟

<details>
<summary>الحل</summary>

المصدر السياق بعد العضوية. الوسيط يعيد ثقب الجسم الذي رُفض في REST.

</details>

### تمرين متوسط

القائمة فارغة. هل ترمي خطأ GraphQL؟

<details>
<summary>الحل</summary>

لا. المصفوفة الفارغة نتيجة صحيحة مثل 200 في REST.

</details>

### تمرين متقدم

أضفتم حقل `owner { email }` لكل مشروع بلا مجمّع. ماذا يفسد، وماذا لا تفعلونه اليوم؟

<details>
<summary>الحل</summary>

N+1 على المستخدمين. لا تضيفوا الحقل في هذه الشريحة. إن أُضيف لاحقًا فـ DataLoader لكل طلب لا ديكور خيالي شامل.

</details>

## أسئلة مراجعة

- أي خدمة تُستدعى؟
- ماذا لا يُنقل إلى GraphQL بعد؟
- كيف تبدو القائمة الفارغة؟
- متى يظهر DataLoader؟

## الخلاصة

سطح GraphQL قراءة مشاريع المنظمة عبر الخدمة الموجودة. الإنشاء والنشر والدفع تبقى REST. لا علاقة فلا مجمّع بعد.

## ماذا بعد؟

عقد REST يحتاج وثيقة تقرأها الواجهة. الدرس التالي Swagger.
