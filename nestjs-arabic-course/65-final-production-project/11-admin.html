Admin

الهدف من هذا الدرس

فصل إدارة منصة رف عن مالك المكتبة: مسار يقرأ عبر المنظمات بصلاحية منصة، من غير إعادة استخدام ترويسة المستأجر كتجاوز.

المشكلة التي يحلها

المالك يرسل X-Tenant-Id لمكتبة أخرى ويُقبل لأنه «أدمن» في مكتبته. أو دعم رف يعدّل الكتب بجسم organizationId. أو قائمة المنصة تستخدم نفس ProjectsService.list فتُقيَّد بالسياق الخطأ.

الفكرة ببساطة

PlatformRole على المستخدم (support أو لا شيء) من قاعدة تتحكمون فيها لا من جسم. مسارات /admin/... حارس مختلف لا يقرأ ترويسة المستأجر كإذن. القراءة للدعم فقط. الكتابة على كتب العملاء خارج النطاق إلا تعليق حالة مكتبة. كل استعلام إداري يصرّح organizationId وسيطًا من مسار اختير بعد البحث لا من جسم حر بلا سجل.

التعريف التقني

لا تضعوا support في خريطة أدوار العضوية. العضوية داخل مكتبة. المنصة علم على User يمنحه تشغيلكم. AdminGuard يرفض الباقي بـ 403. GET /admin/organizations بلا عزل مستأجر واحد لأنه عبر الكل، وهذا الاستثناء الوحيد ويعيش في وحدة AdminModule لا تُستورد دوالها من ProjectsController. التدقيق بفاعل الدعم على فعل إداري.

Mental Model

مالك مكتبة → ترويسة + عضوية → مشاريعه
دعم منصة   → علم support → قائمة منظمات
لا سهم من الترويسة إلى تجاوز المنصة

أبسط مثال

@Injectable()
export class AdminGuard implements CanActivate {
  canActivate(context: ExecutionContext) {
    const req = context.switchToHttp().getRequest<{ user?: { platformRole?: string } }>();
    if (req.user?.platformRole !== 'support') throw new ForbiddenException();
    return true;
  }
}

شرح المثال

  • لا ينظر إلى X-Tenant-Id.
  • العلم من المستخدم المحمّل في validate من القاعدة.
  • المالك العادي 403 حتى لو كان owner.

ماذا يحدث داخليًا؟

  1. الدعم يسجّل دخوله كأي مستخدم.
  2. الحارس يقرأ platformRole.
  3. القائمة تعيد منظمات بلا مشاريع الجار داخل استجابة مكتبة.
  4. فتح مكتبة للدعم مسار /admin/organizations/:id يمرر المعرّف صراحة إلى استعلام مكتوب في وحدة الإدارة.
  5. ProjectsService.list(currentTenantId()) لا تُستدعى من هنا حتى لا تعتمد على ترويسة يمكن نسيانها.

مثال عملي

@Get('organizations')
@UseGuards(AdminGuard)
list() {
  return this.admin.organizations();
}

organizations() استعلام منصة. لا currentTenantId(). اختبار يثبت أن owner يأخذ 403 على هذا المسار وأن الدعم لا يستطيع POST /projects بنيابة صامتة عبر الترويسة وحدها.

أخطاء شائعة

  • دور admin داخل كل المنظمات.
  • إعادة استخدام خدمة القائمة العادية بلا وسيط.
  • قبول organizationId من جسم الدعم بلا تدقيق.
  • إخفاء مسار المنصة عن سجل التدقيق.

متى نستخدمه؟

عندما يحتاج الدعم أن يرى «أي مكتبة علّقت». ليس لعمل المحرر اليومي.

متى لا نستخدمه؟

لا تنشروا مشروع عميل من لوحة المنصة في هذا الفصل. ولا تمنحوا العلم من POST /users العام.

مقارنة

مالك دعم
المستأجر ترويسة وعضوية لا ترويسة كإذن
المشاريع مكتبته قراءة عبر مسار إداري
منح العلم لا عملية تشغيل

تمارين

تمرين سهل

هل owner يفتح /admin/organizations؟

الحل

لا. 403. العلم support فقط.

تمرين متوسط

لماذا لا تُستدعى list(currentTenantId()) من الإدارة؟

الحل

لأن السياق قد يكون فارغًا أو ترويسة يتحكم بها العميل. استعلام الإدارة وسيطه معرّف مسار بعد ما نجح حارس المنصة.

تمرين متقدم

كيف تمنعون الدعم من النشر نيابة عن مكتبة بحذف الترويسة فقط في المتحكم؟

الحل

POST /projects يبقى على TenantGuard والعضوية لا على علم المنصة. الدعم بلا عضوية يأخذ 403. لا فرع if (support) skip tenant في خدمة المشاريع.

أسئلة مراجعة

  • أين يُخزَّن علم المنصة؟
  • لماذا ليس دور عضوية؟
  • أي مسار لا يقرأ currentTenantId؟
  • ماذا يُمنع على الدعم في هذا الفصل؟

الخلاصة

الإدارة حارس علم منصة ومسارات لا تثق بالترويسة. مالك المكتبة ليس دعمًا. خدمة المشاريع لا تُفتح بشرط خاص للدعم.

ماذا بعد؟

العميل يريد عنوان المشروع وحالته في استعلام واحد. الدرس التالي سطح GraphQL محدود.
