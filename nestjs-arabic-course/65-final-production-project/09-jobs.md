# Jobs

## الهدف من هذا الدرس

جدولة عمل غلاف المشروع في رف بعد التزام النشر، بحمولة فيها المنظمة، على Redis، من غير إبقاء الطلب مفتوحًا.

## المشكلة التي يحلها

`publish` يحوّل الصورة داخل الطلب فيهلك المهلة. أو المهمة تُجدول قبل الالتزام فيعمل العامل على مشروع ما زال `draft` لأن المعاملة تراجعت. أو الحمولة بلا `organizationId` فيحدّث العامل أول مكتبة في الخريطة.

## الفكرة ببساطة

بعد نجاح معاملة النشر والتدقيق، أضيفوا مهمة `project.cover` بمعرّفات فقط. العامل يحمّل المشروع بتلك المنظمة. الفشل يعيد المحاولة ولا يعيد `draft`. Redis من `@nestjs/bullmq` أو طابور مكافئ. إن لم يُشغَّل Redis في اختبار الوحدة، استبدلوا الطابور بذاكرة.

## التعريف التقني

الحمولة `{ organizationId, projectId }`. المعالج ينفّذ `tenantStorage.run` ثم يقرأ Prisma. لا سياق HTTP. عدد المحاولات محدود. المهمة ليست ويب هوك الشريك؛ تلك صف تسليم لاحق. لا تضعوا ملف الصورة كاملًا في Redis.

## Mental Model

```text
COMMIT published + audit
queue.add cover
رد للعميل
عامل: يقرأ بنفس المنظمة
```

## أبسط مثال

```ts
await this.queue.add('project.cover', { organizationId, projectId });
```

بعد `await` المعاملة لا قبلها.

## شرح المثال

- الاسم ثابت.
- المعرّفات لا عنوان URL داخلي يختاره العميل.
- فشل `add` بعد الالتزام فجوة؛ صندوق الصادر في فصل لاحق يضيقها. هنا على الأقل لا جدولة قبل الكتابة.

## ماذا يحدث داخليًا؟

1. المعاملة تنجح.
2. Redis يستلم الرسالة.
3. الرد 200 أو 204 للعميل حسب عقد النشر (التحديث 200 غالبًا).
4. العامل يحمّل `where: { id: projectId, organizationId }`.
5. إن غاب الصف لا يعالج مشروعًا آخر.

## مثال عملي

```ts
@Processor('covers')
export class CoverProcessor {
  @Process('project.cover')
  async handle(job: { data: { organizationId: string; projectId: string } }) {
    const { organizationId, projectId } = job.data;
    return tenantStorage.run({ tenantId: organizationId }, () => this.covers.build(organizationId, projectId));
  }
}
```

الأسماء `Processor` و `Process` من الحزمة التي تختارونها (Bull). الفكرة: البيانات من `job.data` فقط.

## أخطاء شائعة

- انتظار العامل قبل رد HTTP.
- جدولة ثم معاملة.
- حمولة فيها السر.
- إعادة المشروع إلى `draft` عندما تفشل الصورة.

## متى نستخدمه؟

لعمل الغلاف أو التصدير بعد النشر. Redis في Compose يأتي مع درس Docker؛ الاختبار يستبدل الطابور.

## متى لا نستخدمه؟

لفحص الخطة أو العزل. ذلك يبقى في الطلب قبل الالتزام.

## مقارنة

| | داخل الطلب | مهمة |
| --- | --- | --- |
| فحص الخطة | نعم | لا تعيد القرار |
| تحويل الغلاف | لا | نعم |
| فشل لاحق | — | لا يلغي `published` |

## تمارين

### تمرين سهل

من أين يأخذ العامل المكتبة؟

<details>
<summary>الحل</summary>

من `job.data.organizationId` لا من ترويسة ولا من طلب سابق.

</details>

### تمرين متوسط

لماذا الجدولة بعد `COMMIT`؟

<details>
<summary>الحل</summary>

حتى لا يُبنى غلاف لمشروع تراجعت كتابته. العكس (ضياع المهمة بعد الالتزام) أهون ويُعالج بإعادة بناء من الصفوف أو بصندوق صادر.

</details>

### تمرين متقدم

اختبار نشر بلا Redis. ماذا تستبدلون؟

<details>
<summary>الحل</summary>

منفذ `queue.add` في الذاكرة يسجّل الحمولة. الاختبار يتوقع نداءً واحدًا بعد النجاح ولا يتوقع نداءً عندما تفشل الخطة. لا تشغّلوا Redis لوحدة الخدمة.

</details>

## أسئلة مراجعة

- ماذا في الحمولة؟
- ماذا لا يُلغى عند فشل الغلاف؟
- أين لا يُجدول العمل؟
- كيف يُعزل الاستعلام داخل العامل؟

## الخلاصة

مهمة الغلاف تُجدول بعد التزام النشر بحمولة منظمة ومعرّف. العامل لا يرى HTTP. الفشل لا يعيد المسودة.

## ماذا بعد؟

الشريك الخارجي يحتاج حدثًا موقّعًا، والمزود يحتاج مسارًا خامًا. الدرس التالي الويب هوك في المشروع.
