Idempotency Keys

الهدف من هذا الدرس

تطبيق @Idempotent() من @nestjs/idempotency على مسار ينشئ أثرًا في رف، بحيث تعيد المحاولة نفس النتيجة داخل نطاق المستخدم.

المشكلة التي يحلها

الجوال أعاد POST /projects بعد انقطاع الرد فصار كتابان. أو مفتاح مشترك بين مكتبتين فأعاد مستخدم نتيجة مستخدم آخر. أو المفتاح على GET بلا داعٍ.

الفكرة ببساطة

العميل يرسل Idempotency-Key ثابتًا للمحاولة. الحزمة تشغّل المعالج مرة وتخزن الرد. الإعادة تعيد المخزن. النطاق scope يفصل مستخدمًا عن آخر. الويب هوك الذي يعتمد على معرّف المزود قد يضع scope: false عن قصد لأن المفتاح عالمي للحدث لا لكل مستخدم.

التعريف التقني

npm i @nestjs/idempotency. IdempotencyModule.forRoot({ scope: (req) => req.user?.id }) في الجذر. المعترض لا يغيّر المسارات بلا @Idempotent(). @Idempotent({ required: true }) يرفض الطلب بلا ترويسة. المفتاح يتبع مسودة IETF التي تذكرها الصفحة. الحراس يعملون قبل المعترض فـ req.user جاهز للنطاق. مفتاح بلا نطاق على مسار فيه مستخدم يسجّل تحذيرًا. جسم مختلف لنفس المفتاح لا يُنفَّذ كأثر ثانٍ؛ سلوك التعارض في الصفحة. لا تضعوا المفتاح من عنوان الكتاب.

Mental Model

Idempotency-Key + userId → رد مخزن
إعادة نفس الزوج → نفس 201 ونفس id
مستخدم آخر بنفس النص → خانة أخرى

أبسط مثال

import { Body, Controller, Post } from '@nestjs/common';
import { Idempotent } from '@nestjs/idempotency';

@Controller('projects')
export class ProjectsController {
  @Post()
  @Idempotent({ required: true })
  create(@Body() body: { title: string }) {
    return this.projects.create(currentTenantId(), body.title);
  }
}

أبقوا @HttpCode(201) حتى الرد الأول والإعادة يتفقان مع العقد إن خزنت الحزمة الوضع.

شرح المثال

  • required يجعل الغياب 400 لا إنشاءً صامتًا.
  • currentTenantId() داخل التنفيذ الأول فقط. الإعادة لا تنشئ صفًا.
  • النطاق يجب أن يشمل المستخدم. إن اشتركت مكتبتان في مستخدم واحد فأضيفوا المنظمة إلى منطق النطاق حتى لا تُعاد مسودة مكتبة على ترويسة أخرى.

ماذا يحدث داخليًا؟

  1. الحارس يصدق المستخدم ويملأ المستأجر.
  2. المعترض يقرأ الترويسة و scope.
  3. الغياب في المخزن يشغّل المتحكم ويحفظ الوضع والجسم.
  4. الإصابة تعيد المحفوظ ولا تستدعي create.
  5. السباق على نفس المفتاح يحتاج مخزنًا بقيد، وPostgres أو Redis في الصفحة لا Map يضيع عند إعادة التشغيل.

مثال عملي

IdempotencyModule.forRoot({
  scope: (req: { user?: { id: string } }) => req.user?.id,
});

لمسار الويب هوك الذي بلا user والمفتاح event.id من المزود، الصفحة تسمح بـ scope: false عندما تكون الخانة المشتركة مقصودة. لا تستخدموا ذلك على POST /projects.

أخطاء شائعة

  • نطاق غائب فيتصادم مفتاح «1» بين القراء.
  • مخزن ذاكرة ثم عمليتا API.
  • @Idempotent على النجاح فقط ونسيان أن 201 يجب أن تُعاد كما هي.
  • استبدال هذا عن قيد isbn داخل المنظمة.

متى نستخدمه؟

على إنشاء مشروع وبدء Checkout وأي POST يعيد العميل إرساله.

متى لا نستخدمه؟

على GET /projects. وعلى حدث Stripe إن كان القيد على event.id يكفي؛ لا تزدوجوا المفتاحين بشكل يتعارض.

مقارنة

المسار المفتاح النطاق
POST /projects ترويسة العميل مستخدم، والمنظمة إن لزم
Checkout مفتاح Stripe أو هذه الترويسة المكتبة
ويب هوك event.id scope: false إن كان الحدث عالميًا

أسئلة مراجعة

  • أي ترويسة؟
  • ماذا يفعل required: true؟
  • لماذا النطاق؟
  • أي مسار يضع scope: false عن قصد؟

الخلاصة

@Idempotent يخزن نتيجة المحاولة ضمن نطاق المستخدم. الإعادة لا تنشئ أثرًا ثانيًا. الويب هوك العالمي حالة scope: false منفصلة عن إنشاء المشروع.

ماذا بعد؟

المفتاح لا يحل «التزم الصف ثم ضاعت الرسالة». الدرس التالي صندوق الصادر كما تنفذه الحزمة.
