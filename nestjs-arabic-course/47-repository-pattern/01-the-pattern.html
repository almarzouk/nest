النمط

الهدف من هذا الدرس

تعريف Repository كنمط: واجهة تشبه مجموعة كائنات في الذاكرة للجذر التجميعي، تخفي كيف يُحفظ، وتفصل لغة الدومين عن SQL.

المشكلة التي يحلها

الخدمة التي تنثر findUnique و update وشكل الجداول في قواعد العمل لا تستطيع الحديث عن «احفظ الطلب» من غير أعمدة. النمط، كما استقر بعد Evans و Fowler، يقدّم مجموعة: أضف، اجلب بالمعرف، أزل. المستدعي يتكلم عن الجذر. التنفيذ يتكلم عن الجداول. الخلط مع صنف Repository الذي يولّده ORM هو درس تالٍ. هنا العقد فقط.

الفكرة ببساطة

للتجميع Order منفذ فيه العمليات التي تحتاجها السياسة على المجموعة، لا كل استعلامات التقارير. findById يعيد الجذر أو فراغًا متفقًا عليه. save يحفظ الجذر كاملًا بما فيه السطور التي يحميها. لا saveLine عام يستدعيه أي متحكم. التقرير المعقد استعلام خارج المجموعة، بجانب النمط لا داخله.

التعريف التقني

export interface OrdersRepository {
  findById(id: string): Promise<Order | null>;
  save(order: Order): Promise<void>;
}

export const ORDERS = Symbol('ORDERS');

Order كيان الدرس السابق، بلا Prisma. الواجهة في مجلد السياسة. لا دالة query(sql: string). لا إرجاع صف القاعدة.

النمط ليس طبقة إلزامية في Nest. خدمة تستدعي PrismaService مباشرة ما زالت صحيحة عندما لا يوجد جذر يحمي لامتغيرات ولا اختبار سياسة يمنع القاعدة. النمط يُشترى عندما تريد استبدال الحفظ أو عندما تتعدد الكتابات على التجميع ويجب أن تمر من save(order).

اسم Repository في الكود يصف هذا العقد. إن سمّيت صنف Prisma OrdersRepository وهو يعيد أنواع العميل، فالاسم يدّعي النمط والتنفيذ يسرّب التفصيل. إما تسمية PrismaOrderStore بلا ادعاء، أو واجهة نظيفة وتنفيذ خلفها.

Mental Model

سياسة: orders.save(order)
مجموعة وهمية من Order
تنفيذ: جداول orders و order_lines في معاملة واحدة

المستدعي لا يرتب الجداول.

أبسط مثال

async cancel(id: string): Promise<void> {
  const order = await this.orders.findById(id);
  if (order === null) {
    throw new Error('الطلب غير موجود');
  }
  order.cancel();
  await this.orders.save(order);
}

cancel() على الكيان يرفض الإلغاء بعد الشحن. المستودع لا يعرف القاعدة. هو يحفظ الحالة بعد أن غيّرها الجذر.

شرح المثال

الجلب ثم التعديل ثم الحفظ وحدة عمل على التجميع. تنفيذ save يكتب الرأس والسطور في معاملة. إن حفظ المتحكم السطر وحده ضاع فحص cancel. هذا جوهر النمط أكثر من عدد الدوال في الواجهة.

ماذا يحدث داخليًا؟

  1. السياسة تطلب الجذر بالمعرف.
  2. التنفيذ يركّب Order من الصفوف.
  3. الدالة على الكيان تغيّر الحقول الخاصة.
  4. save يترجم الحالة إلى كتابة.
  5. null يعني غيابًا كما اتفق ليسكوف، لا صفًا فارغًا.
  6. استعلام «أفضل عشرة كتب مبيعًا» لا يدخل هذه الواجهة. قارئ تقارير منفصل حتى لا تنتفخ المجموعة.

مثال عملي

BooksRepository للمجموعة: findById و save. صفحة المتجر التي تعرض عنوانًا وسعرًا فقط تقرأ عبر CatalogQuery يعيد DTO قراءة. خلط الاثنين في find(filter: any) يعيد النمط إلى مساعد استعلام عام. ابدأ بعمليتين حقيقيتين تستعملهما cancel أو place، وأضف دالة عندما تناديها سياسة لا عندما «قد تلزم».

أخطاء شائعة

  • واجهة بكل أفعال CRUD مولَّدة.
  • save(data: unknown).
  • إرجاع كائن Prisma من findById.
  • وضع SQL داخل Order.cancel.
  • تسمية النمط لكل PrismaService بلا جذر.

متى نستخدمه؟

جذر تجميعي تُحفظ تغييراته من مكان واحد، وتريد اختبار السياسة على مجموعة وهمية.

متى لا نستخدمه؟

قراءة للواجهة بلا قواعد على الكيان. استعلام في الخدمة أو قارئ مخصص أوضح من مجموعة شكلية.

مقارنة

الأسلوب لغة المستدعي ما يُخفى
النمط جذر المجموعة الجداول والمعاملة
استدعاء Prisma في الخدمة أعمدة واستعلامات لا شيء
تقرير منفصل DTO قراءة لا يمر عبر save

تمارين

تمرين سهل

ماذا يعيد findById عند غياب الطلب؟

الحل

null، والسياسة تقرر رسالة الغياب. التنفيذ لا يرمي استثناء HTTP.

تمرين متوسط

لماذا save(order) لا saveLine من المتحكم؟

الحل

لأن اللامتغيرات على الجذر. حفظ السطر من الخارج يتخطاها. المعاملة داخل save تكتب ما يقرره الجذر.

تمرين متقدم

أين يوضع استعلام الأكثر مبيعًا؟

الحل

قارئ أو استعلام قراءة يعيد DTO، لا على OrdersRepository الذي يشبه مجموعة الجذور.

أسئلة مراجعة

  • ماذا يحاكي النمط؟
  • ماذا لا تضعه على الواجهة؟
  • متى الاسم Repository ادعاء فارغ؟

الخلاصة

المستودع النمطي مجموعة للجذر: اجلبه، غيّره عبر دواله، واحفظه. أخفِ الجداول، ولا تحوّل الواجهة إلى مساعد استعلام لكل الشاشات.

ماذا بعد؟

ORM Repository: ماذا يعني Repository<Entity> في TypeORM نسبة إلى هذا النمط.
