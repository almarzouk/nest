DEFAULT

الهدف من هذا الدرس

تثبيت معنى Scope.DEFAULT: نسخة واحدة من الـ Provider لكل التطبيق، عمرها عمر العملية، وهي النطاق الذي تبقى عليه حتى يثبت أن الطلب يحتاج سواه.

المشكلة التي يحلها

من يأتي من نموذج خيط لكل طلب يظن أن مشاركة PrismaService بين الطلبات خطر. في Node الطلبات تتشارك عملية واحدة وحلقة أحداث. النسخة الواحدة آمنة للحالة التي لا تخص طلبًا بعينه، وأرخص، وهي الوحيدة التي ترى خطافات دورة الحياة.

الفكرة ببساطة

DEFAULT يعني Singleton. الحاوية تبني المزود مرة، تخبئه، وتعيد المرجع نفسه لكل من يحقنه. التوثيق يوصي بهذا النطاق لمعظم الحالات لأن التهيئة تحدث أثناء الإقلاع والنسخة تُستعمل من الجميع.

التعريف التقني

Scope يُستورد من @nestjs/common. عدم كتابة scope يعني Scope.DEFAULT. التصريح الصريح:

import { Injectable, Scope } from '@nestjs/common';

@Injectable({ scope: Scope.DEFAULT })
export class BooksService {}

هذا مكافئ لحذف الخاصية. في المزود المخصص تُكتب scope على الكائن الطويل. التوثيق: عمر النسخة مربوط بدورة حياة التطبيق. بعد الإقلاع تكون مزودات Singleton قد أُنشئت.

المشاركة آمنة لأن Node لا يعالج كل طلب في خيط معزول. حالة داخل الخدمة تبقى بين الطلبات، لذلك لا تخزن userId الطلب الحالي على حقل في Singleton.

خطافات OnModuleInit وما بعدها تعمل على هذا النطاق. بوابات WebSocket واستراتيجيات Passport ومتحكمات Cron يجب أن تبقى Singleton، والتوثيق يمنع عليها نطاق الطلب.

Mental Model

الإقلاع -> نسخة واحدة في الحاوية
كل الطلبات -> المرجع نفسه
app.close -> الخطافات ثم يمكن جمع النسخة مع العملية

النسخة رخيصة لأنها لا تُبنى ألف مرة. الحقل الذي يخص طلبًا واحدًا يفسد الطلب الذي يليه.

أبسط مثال

import { Injectable } from '@nestjs/common';

@Injectable()
export class SequenceService {
  private n = 0;

  next(): number {
    this.n += 1;
    return this.n;
  }
}

طلبان متتاليان يريان 1 ثم 2 لأن الحقل على النسخة الوحيدة. هذا صحيح لعداد عملية، وخطأ إن ظننت أن n هو رقم طلب المستخدم.

شرح المثال

@Injectable() بلا خيارات يسجّل DEFAULT. BooksModule يضع الصنف في providers. أي متحكم يحقن SequenceService يأخذ الكائن نفسه الذي حقنته خدمة الفواتير. اختبار يعيد بناء التطبيق عبر Test.createTestingModule يحصل على حاوية جديدة، لا على نسخة عملية التطوير.

ماذا يحدث داخليًا؟

  1. أثناء الإقلاع تحلل الحاوية الرسم وتبني Singleton.
  2. أول حقن يخزن المرجع، والحقن التالي يعيد المخزون.
  3. لا يُنشأ context id لكل طلب من أجل هذا المزود.
  4. خطاف onModuleInit يعمل مرة، فـ $connect مرة واحدة منطقي.
  5. إن حقن Singleton مزود REQUEST، يعدي النطاق إلى الأعلى ويخسر هذا المزود بقاءه Singleton. العدوى موضوع الدرس التالي. هنا يكفي أن تبقي سلسلة القاعدة كلها على الافتراضي.

مثال عملي

عميل القاعدة الذي فتحته في فصل دورة الحياة:

import { Injectable, OnModuleDestroy, OnModuleInit } from '@nestjs/common';
import { PrismaClient } from '@prisma/client';

@Injectable()
export class PrismaService
  extends PrismaClient
  implements OnModuleInit, OnModuleDestroy
{
  async onModuleInit(): Promise<void> {
    await this.$connect();
  }

  async onModuleDestroy(): Promise<void> {
    await this.$disconnect();
  }
}

مجمع الاتصالات داخل العميل مصمم ليُشارك. نسخه لكل طلب يفتح مجمعات بلا داعٍ ويسقط خطاف الإغلاق. مرر userId وسيطًا إلى findForUser(userId) بدل تخزينه على الخدمة.

أخطاء شائعة

  • حقل currentUser على Singleton يسبقه طلب لاحق.
  • كتابة Scope.DEFAULT ثم حقن REQUEST وتوقع بقاء النسخة واحدة.
  • إنشاء new PrismaClient() داخل الدالة رغم أن الخدمة Singleton، فيتعدد العملاء.
  • افتراض عزل بين الاختبارات إن أعادت استعمال التطبيق نفسه من غير close.

متى نستخدمه؟

خدمات بلا حالة طلب، عملاء قواعد وطوابير، قراءات إعداد، وسجلات. هذا الافتراض في كل مزود جديد.

متى لا نستخدمه؟

عندما يجب أن تختلف النسخة نفسها بين الطلبات، كما في مصدر بيانات لكل مستأجر يُبنى من ترويسة. ذلك REQUEST مع كلفته، أو شجرة durable لاحقًا. تمييز المستخدم الحالي يتم في Guard وديكور، ويبقى المزود Singleton.

مقارنة

النطاق كم نسخة خطاف التطبيق
DEFAULT واحدة للعملية يعمل
REQUEST واحدة لكل طلب ولمن يحقنها لا يعمل
TRANSIENT واحدة لكل مكان حقن لا يعدي المستهلك

تمارين

تمرين سهل

ماذا يعني حذف scope من @Injectable()؟

الحل

Scope.DEFAULT: نسخة واحدة مشتركة عمرها عمر التطبيق.

تمرين متوسط

لماذا مشاركة PrismaService بين الطلبات متوافقة مع نموذج Node؟

الحل

لأن الطلبات تتشارك العملية وحلقة الأحداث، والمجمع مصمم للطلبات المتزامنة على عميل واحد. العزل المطلوب هو عزل بيانات الاستعلام، لا عزل كائن العميل.

تمرين متقدم

عداد next() على Singleton أعطى أرقامًا متداخلة تحت طلبين متزامنين. أين الخلل إن كان المطلوب رقمًا فريدًا لكل عملية لا لكل طلب؟

الحل

this.n += 1 ليس عملية ذرية منطقيًا إن تخللتها await بين القراءة والكتابة. لعداد عملية استخدم زيادة متزامنة بلا فاصل، أو مصدرًا خارجيًا. النطاق الافتراضي ما زال صحيحًا؛ الخلل في تعليق الدالة في منتصف التحديث.

أسئلة مراجعة

  • متى تُبنى مزودات Singleton نسبة إلى الإقلاع؟
  • لماذا لا يُخزن المستخدم الحالي على حقل فيها؟
  • أي أنواع مزودات يوثّق Nest أنها تبقى Singleton؟

الخلاصة

DEFAULT نسخة عملية واحدة، رخيصة، وترى خطافات العمر. ابدأ منه، وحافظ على حقوله خالية من بيانات الطلب.

ماذا بعد؟

REQUEST: متى تُبنى نسخة لكل طلب، وكيف يعدي ذلك من يحقنه.
