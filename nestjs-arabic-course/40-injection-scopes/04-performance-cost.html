الأثر على الأداء

الهدف من هذا الدرس

قياس كلفة Scope.REQUEST على زمن الرد: إعادة بناء الشجرة الفرعية لكل طلب، لا ثمن تعليمة واحدة.

المشكلة التي يحلها

النطاق يبدو إعدادًا محليًا على صنف واحد. العدوى تجعله إعدادًا على المتحكم وكل من فوق المزود. تحت حمل حقيقي تُبنى آلاف النسخ وتُجمع، ويرتفع زمن الرد حتى لو كان جسم الدالة بسيطًا. التوثيق يحذّر من هذا ويطلب الإبقاء على Singleton ما لم يكن النطاق ضروريًا.

الفكرة ببساطة

Nest يخزن metadata ما أمكن، لكن نسخة الصنف تُخلق لكل طلب. إن صار مزود قريب من الجميع نطاق طلب، مثل مصدر بيانات أو مسجّل عام، أصبحت أغلب الشجرة تُعاد. تلميح التوثيق: تطبيق مصمم بعناية لا ينبغي أن يزيد التأخير أكثر من نحو 5٪ بسبب مزودات الطلب. تجاوز ذلك غالبًا يعني أن النطاق صعد أوسع من الحاجة.

التعريف التقني

وجود مزود REQUEST واحد محقون في المتحكم، أو أعمق داخل مزوداته، يجعل المتحكم نطاق طلب. المتحكم يُعاد إنشاؤه لكل طلب ثم يُجمع. لثلاثين ألف طلب متوازٍ توجد ثلاثون ألف نسخة مؤقتة من المتحكم ومن مزودات الطلب التابعة.

إن كان مزود مشترك تعتمد عليه أغلب الخدمات نطاق طلب، تصعد تلك الخدمات كلها. هذا ما يضرب متعدد المستأجرين عندما يقرأ «مصدر البيانات» الترويسة لكل طلب ويسحب معه الكتالوج والفواتير.

TRANSIENT لا يعيد بناء المتحكم لكل طلب. كلفته عدد المستهلكين عند البناء، لا عدد الطلبات. DEFAULT يبني مرة أثناء الإقلاع.

قراءة المستخدم أو المستأجر أو اللغة من غير تغيير النطاق تتم بمتجر لكل طلب على AsyncLocalStorage، فتبقى المزودات Singleton في HTTP ومعالجات الرسائل ومهام الطوابير. إن استعملت أداة تُبقي هذا المتجر، تكتب القيمة فيه وتقرأها من الأسفل. التوثيق يذكر هذا البديل صراحة كي لا يُستخدم نطاق الطلب كمخزن للفاعل الحالي.

Mental Model

Singleton: بناء عند الإقلاع، كل الطلبات تشير إليه
REQUEST على ورقة عميقة يحقنها الجميع:
  كل طلب = متحكم جديد + سلسلة جديدة + جمع قمامة
TRANSIENT: كائنات بعدد مواقع الحقن، الطلب لا يعيد البناء

الكلفة في التخصيص والجمع، وفي فقدان كاش النسخة، لا في اسم الـ Decorator.

أبسط مثال

قبل:  BooksController DEFAULT -> BooksService DEFAULT -> Prisma DEFAULT
بعد:   BooksService صارت REQUEST لأن حقنت TenantDb
النتيجة: BooksController يُبنى لكل GET /books

زمن findMany نفسه قد يبقى مللي ثانية، ويبني الإطار حوله كائنات جديدة في كل مرة. راقب الفرق بمقارنة مسارين، لا بشعور واحد.

شرح المثال

المسار قبل التعديل يعيد المتحكم من الكاش. المسار بعد التعليم يعيد سياقًا فرعيًا. إن أضفت عشر خدمات تحقن TenantDb صعدت العشر. إصلاح التمرير هو إخراج قراءة الترويسة إلى Guard أو وسيط يمرر tenantId: string إلى دالة Singleton، أو تجميع الطلبات في شجرة durable في الدرس التالي إن كان المستأجر قليل العدد.

ماذا يحدث داخليًا؟

  1. يصل الطلب فينشئ الإطار context id.
  2. يمشي سلسلة هذا المتعامل ويبني كل مزود صعد نطاقه.
  3. المزودات DEFAULT خارج السلسلة تبقى المشاركات القديمة.
  4. بعد إرسال الرد تصبح النسخ المؤقتة قابلة للجمع.
  5. تحت التزامن يرتفع عدد الكائنات الحية حتى ينتهي الرد.
  6. خطافات الإقلاع لا تعوض التهيئة لكل طلب؛ تلك الأصناف لا تستقبلها، فأي تهيئة داخل constructor تتكرر مع كل بناء.

مثال عملي

قياس صغير على مسار واحد قبل تعميم النطاق:

import { Injectable } from '@nestjs/common';

@Injectable()
export class BooksService {
  findPage(tenantId: string): { tenantId: string } {
    return { tenantId };
  }
}

المتحكم يمرر tenantId من الديكور. قارن تحت أداة حمل زمن GET /books مع تمرير الوسيط، ثم مع TenantDb محقونة في هذه الخدمة. إن قفز الزمن أكثر من هامش التلميح (نحو 5٪) فالنطاق أوسع من تصميم «مزود طلب واحد منعزل». أعد الخدمة إلى الافتراضي.

أخطاء شائعة

  • قياس طلب واحد على البارد واستنتاج أن النطاق رخيص.
  • تعليم Logger العام REQUEST فيصعد التطبيق كله.
  • تجاهل الجمع: الذاكرة تهتز حتى لو بقي المتوسط مقبولًا.
  • نقل المستخدم إلى AsyncLocalStorage ثم ترك scope: Scope.REQUEST على الخدمة.
  • مقارنة TRANSIENT بكلفة الطلب. العابر لا يتكرر مع الزيارات.

متى نستخدمه؟

عندما تقرر الإبقاء على REQUEST بعد قياس، والمزود منعزل في فرع ضيق، والبديل لا يحفظ صحة العزل.

متى لا نستخدمه؟

كتبرير افتراضي لكل ترويسة. القيمة التي تُقرأ مرة وتُمرر وسيطًا تُبقي الشجرة على DEFAULT وتترك القياس لقاعدة البيانات لا للإطار.

مقارنة

القرار ماذا يُبنى لكل طلب
سلسلة DEFAULT لا شيء من المزودات
REQUEST على فرع ضيق ذلك الفرع والمتحكم الذي يحقنه
REQUEST على مزود يحقنه الجميع أغلب الرسم
TRANSIENT لا شيء إضافي لكل طلب

تمارين

تمرين سهل

ماذا يعيد الإطار خلقه عندما يصبح المتحكم نطاق طلب؟

الحل

نسخة المتحكم ومزودات الطلب في سلسلته، لكل طلب، ثم تُجمع بعد الرد.

تمرين متوسط

ما هامش التأخير الذي يذكره التوثيق لتصميم يستعمل نطاق الطلب بعناية؟

الحل

لا ينبغي أن يزيد التأخير أكثر من نحو 5٪.

تمرين متقدم

خدمة سجل يحقنها أربعون مزودًا عُلّمت REQUEST لقراءة x-request-id. كيف تبقي المعرف في السجلات وتُرجع الأربعين إلى Singleton؟

الحل

اقرأ المعرف في Middleware أو Guard مرة، وخزّنه في AsyncLocalStorage أو مرره حيث يلزم، واجعل المسجّل DEFAULT يقرأ المتجر عند الكتابة. أزل Scope.REQUEST حتى لا تصعد الشجرة.

أسئلة مراجعة

  • لماذا مزود مشترك واحد قد يبطئ التطبيق كله؟
  • ما الذي لا يتكرر مع كل طلب في TRANSIENT؟
  • أي بديل يذكره التوثيق لقيمة تخص الطلب من غير تغيير النطاق؟

الخلاصة

كلفة REQUEST هي إعادة الشجرة الصاعدة لكل طلب. ضيّق الفرع، وقِس، وأبقِ القيمة العابرة خارج عمر المزود.

ماذا بعد؟

متى تبقى على Singleton، ومتى تبرر شجرة durable لمستأجرين قليلين.
