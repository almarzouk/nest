# متى تبقى على Singleton

## الهدف من هذا الدرس

قرار عملي: ابقَ على `Scope.DEFAULT` لتمرير المستخدم والمستأجر، واستعمل المزود الدائم `durable` فقط عندما تتجمع الطلبات على عدد صغير من السياقات وتحتاج شجرة معزولة أطول من طلب واحد.

## المشكلة التي يحلها

نطاق الطلب لكل ترويسة مستأجر يعيد بناء الكتالوج والفواتير آلاف المرات بينما المستأجرون عشرة. التوثيق يسمي هذا الخلل ثم يعرض المزودات الدائمة: شجرة فرعية لكل مجموعة طلبات تتشارك صفات، لا لكل طلب. البقاء على Singleton ما زال القرار الأول إن كانت الصفة وسيطًا لا اتصالًا مختلفًا.

## الفكرة ببساطة

إن كان العزل «لا يقرأ أ طلبَ ب» يتحقق بتمرير `tenantId` إلى استعلام Prisma على عميل واحد، فالنسخة الواحدة تكفي. إن كان لكل مستأجر مصدر بيانات مختلف ويجب ألا تُبنى الشجرة لكل طلب، سجّل استراتيجية `ContextIdStrategy` وعلّم المزود `Scope.REQUEST` مع `durable: true`. الإطار يعيد شجرة ذلك المستأجر بين طلباته.

## التعريف التقني

العلم `durable` يُقرأ على من صرّح `Scope.REQUEST`. من صعد بالعدوى فقط يرث الديمومة من اعتمادياته إن كانت كلها دائمة، ما لم يُصرَّح `durable: false`. الديمومة تصعد مثل نطاق الطلب.

الاستراتيجية تُسجَّل مرة قبل وصول الطلبات:

```ts
import { ContextIdFactory } from '@nestjs/core';
import { AggregateByTenantContextIdStrategy } from './tenant.strategy.js';

ContextIdFactory.apply(new AggregateByTenantContextIdStrategy());
```

شكل `attach` من التوثيق يجمع `x-tenant-id` في `Map` ويعيد context id لذلك المستأجر عندما تكون الشجرة دائمة، ويعيد context الطلب الأصلي لغير ذلك. إعادة كائن `{ resolve, payload }` تجعل `@Inject(REQUEST)` يستقبل `payload` مثل `{ tenantId }` بدل طلب HTTP كامل.

```ts
import { Injectable, Scope } from '@nestjs/common';

@Injectable({ scope: Scope.REQUEST, durable: true })
export class CatsService {}
```

على المزود المخصص: `scope: Scope.REQUEST` و `durable: true` معًا. التحذير: الاستراتيجية غير مناسبة لعدد كبير من المستأجرين لأن الخريطة تحتفظ بشجرة لكل مفتاح.

تمرير المستخدم العادي لا يدخل هنا. Guard يضع `request.user` وديكور `@CurrentUser()` يقرأه، والخدمة `DEFAULT` تستقبل `userId`.

## Mental Model

```text
قيمة تُمرَّر إلى SQL          -> DEFAULT
شجرة مختلفة لكل طلب          -> REQUEST مكلف
شجرة لكل مستأجر من عشرة      -> REQUEST + durable + strategy
مئات الآلاف من المفاتيح      -> لا تحتفظ بشجرة لكل مفتاح
```

`payload` يحل محل الطلب داخل الشجرة الدائمة. لا تفترض `request.headers` هناك.

## أبسط مثال

```ts
import { Injectable } from '@nestjs/common';
import { PrismaService } from './prisma.service.js';

@Injectable()
export class BooksService {
  constructor(private readonly prisma: PrismaService) {}

  list(tenantId: string) {
    return this.prisma.book.findMany({ where: { tenantId } });
  }
}
```

عميل واحد، شرط في الاستعلام، والمزود Singleton يرى `onModuleInit`. هذا ما تبقى عليه في المتجر ذي القاعدة المشتركة.

## شرح المثال

العزل هنا في السطر `where`، لا في هوية كائن `BooksService`. اختبار يمرر مستأجرين يثبت أن الصفوف لا تختلط من غير نطاق طلب. إن انتقلت لاحقًا إلى قاعدة لكل مستأجر، عندها تُراجع الديمومة، وبعد قياس، وبعد أن يكون عدد المفاتيح صغيرًا.

## ماذا يحدث داخليًا؟

1. `ContextIdFactory.apply` يستبدل طريقة ربط الطلب بشجرة.
2. `attach` يقرأ صفة التجميع ويبحث عن context id موجود أو ينشئ واحدًا.
3. للمكوّن ذي الشجرة الدائمة يُستخدم معرف المستأجر، فتعيد الحاوية الشجرة المخزنة.
4. لغير الدائم يبقى معرف الطلب الفريد فيُبنى ثم يُجمع.
5. `payload` المسجّل هو ما يراه من يحقن `REQUEST` داخل الشجرة الدائمة.
6. مفتاح جديد في الخريطة يعني شجرة جديدة تبقى. لذلك العدد الكبير يأكل الذاكرة.

## مثال عملي

عشرة متاجر، لكل منها `DataSource`، والكتالوج يحقن المصدر. علّم المصدر `durable` وسجّل الاستراتيجية على `x-tenant-id`. الكتالوج يصعد ويصبح دائمًا إن كانت اعتمادياته الطلبية كلها دائمة، فتُحفظ شجرة المتجر وتُعاد في الطلب التالي لنفس الترويسة. أبقِ مسجّل التطبيق و `Prisma` العام خارج هذه السلسلة إن كانا مشتركين، حتى لا تُجبرهما الديمومة على التعدد.

## أخطاء شائعة

- `durable: true` من غير `Scope.REQUEST` الصريح. العلم يُقرأ على التصريح الصريح.
- خريطة مستأجرين بلا حد حتى تمتلئ الذاكرة.
- قراءة `request.url` داخل شجرة استبدلت `payload` بالحمولة.
- استخدام الديمومة لتمرير `userId` بينما الاستعلام على عميل مشترك يكفي.
- نسيان تسجيل الاستراتيجية قبل أول طلب.

## متى نستخدمه؟

ابقَ على Singleton عندما العزل شرط في الاستعلام أو وسيط دالة. استخدم الديمومة عندما تتعدد المصادر فعلًا والمستأجرون قلة والطلب نفسه لا يحمل حالة فريدة يجب أن تموت معه، مثل UUID للطلب فقط.

## متى لا نستخدمه؟

عدد مفاتيح ضخم، أو بوابة WebSocket، أو رغبة في «نظافة» معمارية من غير مصدر بيانات مختلف. النطاق الافتراضي أصدق في هذه الحالات.

## مقارنة

| الموقف | القرار |
| --- | --- |
| `user` على الطلب | Guard + ديكور، خدمة `DEFAULT` |
| كاش يموت مع الرد | `REQUEST` ضيق |
| عشرة مصادر بيانات | `durable` مع استراتيجية |
| عميل Prisma واحد | `DEFAULT` و `where` |

## تمارين

### تمرين سهل

ماذا تبقى عليه لتمرير المستخدم إلى `findFor(userId)`؟

<details>
<summary>الحل</summary>

`Scope.DEFAULT`. Guard وديكور يقرآن المستخدم، والدالة تستقبل المعرف.

</details>

### تمرين متوسط

على أي مزود يُقرأ علم `durable`؟

<details>
<summary>الحل</summary>

على من صرّح `Scope.REQUEST`. من صعد بالعدوى يرث الديمومة من اعتماديات طلبية كلها دائمة.

</details>

### تمرين متقدم

لماذا تحذير التوثيق من عدد كبير من المستأجرين مع `Map` السياقات؟

<details>
<summary>الحل</summary>

كل مفتاح يحتفظ بشجرة فرعية. المفاتيح التي لا تُحد تحوّل الديمومة إلى تسريب ذاكرة، وتفقد معنى التجميع.

</details>

## أسئلة مراجعة

- متى Singleton أصح من `REQUEST` للمستخدم؟
- ماذا يعيد `payload` في الشجرة الدائمة؟
- لماذا الاستراتيجية تُستدعى قبل الطلبات؟

## الخلاصة

الافتراض Singleton. الديمومة تحسين لمتعدد مستأجرين بعدد صغير ومصادر مختلفة، لا بديل عن تمرير معرف في وسيط.
