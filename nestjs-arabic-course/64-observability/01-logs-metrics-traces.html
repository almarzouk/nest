Logs و Metrics و Traces

الهدف من هذا الدرس

تفرقة ثلاث إشارات تشغيل في رف: سجل يروي طلبًا، مقياس يعدّ، وأثر يتبع مسار النشر عبر الدوال.

المشكلة التي يحلها

كل شيء console.log. عند البطء لا تعرفون إن كان العدد ارتفع أم أن طلبًا واحدًا علق في Stripe. عند 500 تبحثون في نص بلا معرّف. الصحة من Terminus تقول إن العملية حية ولا تقول أي مسار تباطأ بعد النشر.

الفكرة ببساطة

السجل حدث نصي أو JSON لطلب أو لعطل: ماذا حدث. المقياس رقم عبر الزمن: كم نشرًا، ما p95. الأثر شجرة مدد: المتحكم، الخدمة، استعلام القاعدة. الثلاثة معًا تجيب «كم» و«أي طلب» و«أين ذهب الوقت». لا إشارة تغني عن الأخريين.

التعريف التقني

Logger من @nestjs/common للسجلات. لا كلمات مرور ولا rawBody ولا أسرار Stripe. المقاييس عدادات ومدد (معدل 5xx، مدة publish). الأثر spans باسم الدالة لا باسم عام «request» فقط. صفحة Deployment تفرّق فحص الصحة والسجل عن معرفة أي مسار تباطأ، وتشير إلى المراقبة. سجل التدقيق للمراجع البشري ليس هذا السجل؛ ذاك صف أعمال في القاعدة.

Mental Model

Log:     publish failed  bookId=b1
Metric:  publish_duration_ms p95
Trace:   HTTP → BooksService → prisma

أبسط مثال

import { Logger } from '@nestjs/common';

const logger = new Logger('BooksService');

export function logPublish(organizationId: string, bookId: string) {
  logger.log({ msg: 'book published', organizationId, bookId });
}

شرح المثال

  • JSON أو كائن يسهّل الجمع. النص الحر يصعب فرزه.
  • المعرّفات لا العنوان الكامل إن كان حساسًا.
  • Logger أفضل من console حتى يمر على تنسيق التطبيق.

ماذا يحدث داخليًا؟

  1. الطلب يدخل. السجل يسجل البداية أو يترك ذلك للمعترض حتى لا يتكرر في كل خدمة.
  2. عند النجاح أو الفشل يُكتب سطر بمستوى مناسب: log للنجاح المهم، error لغير المتوقع فقط لا لكل 404.
  3. المقياس يزيد بغض النظر عن نص السجل.
  4. الأثر يفتح span حول Prisma ويغلقه بالمدة.
  5. 404 المتوقعة لا ترفع عداد الأعطال الحرجة.

مثال عملي

export function recordPublish(metrics: { observe: (ms: number, ok: boolean) => void }, started: number, ok: boolean) {
  metrics.observe(Date.now() - started, ok);
}

عداد منفصل publish_total{result} أفضل من استنتاج النجاح بعدّ أسطر السجل. السجل يبقى للتفاصيل، والمقياس للرسم.

أخطاء شائعة

  • error لكل BookNotFound.
  • قياس p95 من متوسط السجلات اليدوي.
  • أثر بلا اسم خدمة فيضيع بين النسخ.
  • دمج سجل التدقيق مع سجل التشغيل في نفس الجدول.

متى نستخدمه؟

من أول مسار نشر في الإنتاج. ابدأوا بسجل JSON ومقياس للمسار الساخن ثم الأثر.

متى لا نستخدمه؟

لا تسجلوا كل حقل في كل GET ناجح بمستوى error. ولا تستبدلوا فحص /health بمقياس؛ الموازن يحتاج المسار.

مقارنة

سجل مقياس أثر
السؤال ماذا في هذا الطلب؟ كم وكم السرعة؟ أين الوقت داخل الطلب؟
الحجم سطر لكل حدث مهم أرقام مجمّعة شجرة لكل طلب عينة أو للكل
404 info أو لا شيء عداد منفصل span قصير بلا إنذار

تمارين

تمرين سهل

أي إشارة تجيب: هل p95 للنشر ارتفع بعد النشر الأخير؟

الحل

المقياس عبر الزمن، لا قراءة ألف سطر. السجل يفسّر طلبًا بطيئًا بعد ما يدل المقياس على الانحدار.

تمرين متوسط

لماذا 404 ليس logger.error؟

الحل

لأن الغياب متوقع وعقده 404. ضجيج error يخفي انقطاع القاعدة. سجّلوا غير المتوقع في فلتر 500.

تمرين متقدم

Terminus أخضر وموظفون يشتكون من النشر. ماذا تنقصكم الإشارة؟

الحل

الصحة لا تقيس المسار. تحتاجون مدة publish وأثرًا يفرّق Prisma عن Stripe. السجل وحده بلا تجميع لا يرسم p95.

أسئلة مراجعة

  • ماذا يروي كل من الثلاث؟
  • لماذا لا يُستنتج المقياس من عدّ السجلات فقط؟
  • أي مستوى لغياب كتاب؟
  • ما فرق سجل التشغيل عن التدقيق؟

الخلاصة

السجل تفاصيل طلب، والمقياس سلوك عبر الزمن، والأثر مسار داخل الطلب. 404 ليس عطلًا، والصحة ليست p95.

ماذا بعد؟

توحيد الأسماء بين اللغات والأدوات يتم بمعيار. الدرس التالي OpenTelemetry.
