# Idempotency

## الهدف من هذا الدرس

منع تكرار أثر الدفع في رف: مفتاح على إنشاء جلسة Checkout عند إعادة الطلب، وقيد على `event.id` عندما تعيد Stripe التسليم.

## المشكلة التي يحلها

الموظف يضغط «ادفع» مرتين فتفتح جلستان وعميلان. أو `evt_1` يصل مرتين فتُمدَّد الفترة أو يُرسل بريد «تم الدفع» مرتين. شبكة انقطعت بعد ما أنشأت Stripe الجلسة وقبل ما وصل الرابط، وإعادة الطلب بلا مفتاح تنشئ جلسة ثانية.

## الفكرة ببساطة

لأوامر API إلى Stripe مرّروا `idempotencyKey` ثابتًا لنفس محاولة المكتبة. لإعادة الحدث، أدرجوا `event.id` بقيد فريد قبل الأثر كما في ويب هوك رف. المفتاحان ليسا مفتاح الجوال الذي ينشئ كتابًا، لكن القاعدة واحدة: إعادة نفس العملية لا أثرًا ثانيًا.

## التعريف التقني

عميل Stripe يقبل `{ idempotencyKey }` في خيارات الطلب. المفتاح سلسلة ثابتة لمحاولة Checkout هذه (مثل `checkout:${organizationId}:${plan}` خلال نافذة قصيرة، أو UUID يولّده العميل في `Idempotency-Key` ويُخزَّن). إعادة نفس المفتاح خلال مدة Stripe تعيد نفس الجلسة لا جلسة جديدة. أحداث الويب هوك لها `id` مثل `evt_...` يبقى في الإعادات. قيد فريد عليه. 200 على المكرر. لا تضعوا `active` في المسار الذي يعيد الجلسة حتى لو كان المفتاح جديدًا.

## Mental Model

```text
نفس idempotencyKey → نفس Checkout Session
نفس event.id       → أثر محلي واحد
success URL        → لا مفتاح ولا أثر
```

## أبسط مثال

```ts
await this.stripe.checkout.sessions.create(params, {
  idempotencyKey: `checkout:${organizationId}:pro`,
});
```

## شرح المثال

- المفتاح من حقائق المحاولة لا من وقت `Date.now()` وإلا تغيّر كل ضغطة وصنع جلسة جديدة.
- إن غيّرتم السعر، غيّروا المفتاح حتى لا يعيد Stripe جلسة الخطة القديمة.
- هذا لا يحفظ `event.id`. ذلك جدول آخر.

## ماذا يحدث داخليًا؟

1. الطلب الأول ينشئ الجلسة عند Stripe ويحفظ الرابط.
2. الطلب الثاني بنفس المفتاح يستلم نفس الكائن.
3. لاحقًا يصل `evt_1`. INSERT ينجح وتُحدَّث الحالة.
4. إعادة `evt_1` تصطدم بالقيد وترد 200 بلا تحديث ثانٍ وبلا بريد ثانٍ.
5. فتح success لا يولّد مفتاحًا ولا يكتب الصف.

## مثال عملي

```ts
export async function markEvent(tx: { event: { create: Function } }, eventId: string) {
  try {
    await tx.event.create({ data: { id: eventId, source: 'stripe' } });
    return true;
  } catch (error) {
    if (typeof error === 'object' && error && 'code' in error && error.code === 'P2002') return false;
    throw error;
  }
}
```

`true` يعني طبّقوا المزامنة والبريد داخل نفس المعاملة. `false` يعني أرجعوا 200 وتوقفوا. أنشئوا الجلسة بمفتاحها في المسار الآخر.

## أخطاء شائعة

- مفتاح من الطابع الزمني.
- معالجة الحدث المكرر بـ 500 فيعيد Stripe طويلًا.
- الاعتماد على مفتاح Checkout لمنع تكرار الويب هوك. هما طبقتان.
- تفعيل الاشتراك في فرع «أول مفتاح» داخل `startCheckout`.

## متى نستخدمه؟

على `sessions.create` وأي أمر Stripe له أثر مالي، وعلى كل `event.id` وارد.

## متى لا نستخدمه؟

لا تشاركوا مفتاحًا واحدًا لكل المكتبات. ولا تستعملوا مفتاح الجلسة كبديل عن توقيع الويب هوك.

## مقارنة

| الطبقة | المفتاح | التكرار |
| --- | --- | --- |
| إنشاء الجلسة | `idempotencyKey` لـ Stripe | نفس `url` |
| الحدث | `event.id` محلي | بلا مزامنة ثانية |
| زر الواجهة success | — | بلا كتابة حالة |

## أسئلة مراجعة

- أين يُمرَّر مفتاح إنشاء الجلسة؟
- ما مفتاح تكرار الويب هوك؟
- لماذا ليس الطابع مفتاحًا؟
- هل success URL يدخل أيًا من الطبقتين؟

## الخلاصة

Checkout يُنشأ بمفتاح idempotency ثابت للمحاولة. أحداث Stripe تُطبَّق مرة بقيد `event.id`. لا طبقة منهما تكتب `active` لأن المتصفح فتح صفحة النجاح.

## ماذا بعد؟

الدفع حدوده واضحة. الفصل التالي يوسّع ما بعد الطلب: أحداث نطاق داخل رف وأحداث تكامل بين الخدمات، واتساق يتأخر.
