Prisma: Migrations

الهدف من هذا الدرس

تحويل تغيير schema.prisma إلى ملفات SQL محفوظة تُعاد على التطوير والاختبار والإنتاج بالترتيب نفسه.

المشكلة التي يحلها

تعديل الجدول من شاشة رسومية على جهاز واحد يترك الزملاء وCI والإنتاج على شكل قديم. إعادة إنشاء القاعدة من الصفر تمسح بيانات الإنتاج. نسخ أوامر متفرقة في محادثة لا يُراجع في Git.

الفكرة ببساطة

prisma migrate dev في التطوير يقارن المخطط بترحيلات سابقة، يكتب مجلدًا فيه migration.sql، ويطبّقه على قاعدة التطوير. الملفات تُرفع. على الإنتاج تُطبَّق الترحيلات الموجودة ولا يُولَّد شكل جديد من جهاز المطوّر.

التعريف التقني

من صفحة Nest، بعد إضافة النماذج:

npx prisma migrate dev --name init

الأمر ينشئ SQL وينفّذه. إن لم تكن القاعدة موجودة يحاول إنشاءها وفق إعدادك. الملفات تحت prisma/migrations/ مع migration_lock.toml.

prisma migrate dev لا يشغّل prisma generate نيابة عنك في التوثيق الحالي لـ Nest. بعد تغيير المخطط شغّل التوليد حتى يطابق العميل الجداول.

للإنتاج، أمر Prisma الذي يطبّق الترحيلات المرفوعة من غير إنشاء ترحيل جديد هو:

npx prisma migrate deploy

لا تشغّل migrate dev على قاعدة الإنتاج. هو مسار تطوير قد يطلب إعادة ضبط إن انحرف السجل.

اسم الترحيل يصف التغيير: init، ثم add_member_email_unique. SQL داخل المجلد قابل للمراجعة. يمكن إضافة فهرس أو أمر خاص قبل الدمج إن كنت تعرف أثره.

السجل في جدول _prisma_migrations داخل القاعدة يتذكر ما طُبّق. بيئة جديدة تشغّل المعلّق فقط.

Mental Model

تعديل schema.prisma
        |
 migrate dev --name add_books
        |
 prisma/migrations/.../migration.sql   -> Git
        |
 تطوير: طُبّق الآن
 إنتاج: migrate deploy يطبّق الملف نفسه

أبسط مثال

-- prisma/migrations/20260101120000_init/migration.sql
CREATE TABLE "Book" (
    "id" INTEGER NOT NULL PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    "title" TEXT NOT NULL,
    "published" BOOLEAN NOT NULL DEFAULT false
);

CREATE TABLE "Member" (
    "id" INTEGER NOT NULL PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    "email" TEXT NOT NULL,
    "name" TEXT
);

CREATE UNIQUE INDEX "Member_email_key" ON "Member"("email");

الصيغة الدقيقة يولّدها Prisma لـ PostgreSQL. لا تكتب هذا الملف بيدك ما دامت الأداة تولّده، إلا لتعديل راجعته.

شرح المثال

الجدولان يطابقان نموذجي الدرس السابق. الفهرس الفريد على البريد هو أثر @unique. رفع المجلد يعني أن آلة الاختبار تبني القاعدة نفسها بأمر واحد.

إن حذفت المجلد وأبقيت الجداول، السجل يضيع. لا تحذف ترحيلًا طُبّق على بيئة مشتركة.

ماذا يحدث داخليًا؟

Prisma يحسب الفرق بين المخطط وسجل الترحيلات، ويكتب SQL أماميًا. migrate dev ينفّذه داخل معاملة عندما يستطيع المحرك ذلك. فشل منتصف الترحيل يترك القاعدة على آخر ترحيل ناجح إن نجحت الإعادة، وعليك قراءة رسالة PostgreSQL قبل إعادة المحاولة.

بيانات موجودة قد تمنع إضافة NOT NULL بلا DEFAULT. الترحيل حينها يحتاج ملء القيم القديمة. هذا قرار SQL، لا خيار Nest.

generate بعد ذلك يحدّث العميل. التطبيق الذي يعمل أثناء الترحيل قد يرى عمودًا جديدًا قبل أن يعرف عميله القديم، لذلك رتّب النشر: الترحيل المتوافق أولًا، ثم النسخة التي تقرأه.

مثال عملي

إضافة published افتراضيًا false تسمح بنشر الكود الذي يقرأ الحقل بعد أن تملأ الصفوف القديمة عبر الافتراضي. إسقاط عمود name في الخطوة نفسها يكسر النسخة السابقة إن كانت ما زالت تقرأه. قسّم الترحيل: أضف العمود الجديد، انشر الكود، ثم أسقط القديم في ترحيل لاحق.

أخطاء شائعة

  • تعديل الجدول يدويًا ثم مفاجأة migrate dev بفرق لا تفهمه.
  • تشغيل migrate dev على الإنتاج.
  • نسيان رفع مجلد migrations.
  • خلط generate بمعنى «القاعدة تحدّثت».

متى نستخدمه؟

لكل تغيير عمود أو فهرس أو جدول في مسار Prisma.

متى لا نستخدمه؟

لتجربة عابرة على قاعدة محلية ستُحذف. حتى هناك، الترحيل أرخص من نسيان ما فعلته.

مقارنة

تعديل يدوي migrate dev ثم deploy
أثر على جهاز واحد SQL في Git
بلا ترتيب مضمون سجل _prisma_migrations
خطر على البيانات يُراجع قبل الإنتاج

تمارين

تمرين سهل

ماذا يُرفع إلى Git بعد migrate dev --name init؟

الحل

مجلد الترحيل وفيه migration.sql، وملف القفل، والمخطط. لا يُرفع .env ولا العميل المولَّد.

تمرين متوسط

لماذا لا يكفي prisma generate لزميل سحب الفرع على قاعدة فارغة؟

الحل

التوليد يبني عميل TypeScript. الزميل يحتاج تطبيق SQL عبر الترحيلات حتى تُنشأ الجداول.

تمرين متقدم

كود الإنتاج القديم يقرأ عمود name، والترحيب الجديد يحذف العمود. ما ترتيب النشر الآمن؟

الحل

أبقِ العمود حتى يعمل الإصداران، انشر الكود الذي لا يقرأه، ثم ترحيل الحذف. لا تحذف عمودًا ما زال إصدار يعمل يكتبه.

أسئلة مراجعة

  • ماذا يفعل migrate dev في التطوير؟
  • ماذا يشغّل الإنتاج لتطبيق الملفات الموجودة؟
  • هل generate يحدّث الجداول؟

الخلاصة

الترحيل أثر SQL قابل للإعادة. التطوير يولّده ويطبّقه، والإنتاج يطبّق المرفوع، والتوليد يواكب العميل.
