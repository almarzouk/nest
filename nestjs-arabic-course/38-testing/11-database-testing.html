اختبار قاعدة البيانات

الهدف من هذا الدرس

عزل قاعدة الاختبار عن الإنتاج، وجعل كل حالة تبدأ من بيانات تعرفها وتنتهي بلا أثر على التالية.

المشكلة التي يحلها

DATABASE_URL واحد للتطوير والاختبار يمسح كتبًا حقيقية أو يجعل الاختبار يعتمد على صف أضفته يدويًا. تشغيل التكامل على الإنتاج خطأ تشغيلي لا تفصيل إعداد. والاختبارات التي تنجح منفردة وتفشل معًا تشارك صفوفًا.

الفكرة ببساطة

عنوان ثانٍ، اسمه واضح مثل bookstore_test. الهجرات تُطبَّق عليه لا على قاعدة العمل. كل حالة تنظّف الجداول التي تلمسها، أو تعمل داخل معاملة تُلغى. الاختبارات الوحدوية لا تفتح هذا العنوان أصلًا. الرحلات التي لا تحتاج SQL تستبدل Prisma.

التعريف التقني

قواعد المتجر:

النوع القاعدة
وحدة خدمة وهم، بلا عنوان
تكامل Prisma bookstore_test فقط
رحلة HTTP القاعدة الاختبارية أو وهم
الإنتاج ممنوع في *.spec.ts

تطبيق الهجرات على الاختبار من سكربت CI يشير إلى العنوان الثاني. لا تشغّل migrate reset على عنوان بلا لاحقة _test في الاسم. إن غاب المتغير، افشل الإقلاع:

const url = process.env.DATABASE_URL ?? '';
if (!url.includes('bookstore_test')) {
  throw new Error('refusing to test without bookstore_test');
}

هذا الحارس رخيص ويمنع حادثًا. ليس بديلًا عن مستخدم قاعدة بلا صلاحية على الإنتاج.

التنظيف:

afterEach(async () => {
  await prisma.book.deleteMany();
});

deleteMany مقبول والجداول صغيرة. إن وُجدت مفاتيح أجنبية فاحذف الأبناء أولًا أو استخدم TRUNCATE ... CASCADE في قاعدة الاختبار فقط. معاملة تُفتح في beforeEach وتُلغى في afterEach تترك القاعدة فارغة بلا حذف يدوي، بشرط أن الخدمة تستعمل العميل نفسه داخل المعاملة. Prisma تحتاج تمرير عميل المعاملة إلى الخدمة، وإلا فالكتابة خارج المعاملة تبقى بعد التراجع. إن صعب ذلك، التنظيف الصريح أوضح.

لا تشارك صف id: 42 بين ملفات بلا تنظيف. ولّد معرفًا لكل حالة أو ابدأ من جداول فارغة.

Redis الاختباري، إن لزم لتكامل طابور نادر، مثيل أو قاعدة منطقية أخرى. لا FLUSHALL على Redis التطوير الذي فيه مهامك.

Mental Model

وحدة: بلا SQL
تكامل: bookstore_test -> فعل -> قراءة -> تنظيف
إنتاج: لا يدخل الأمر

أبسط مثال

beforeEach(async () => {
  await prisma.book.deleteMany();
  await prisma.book.create({ data: { id: '42', title: 'NestJS', status: 'DRAFT' } });
});

الحالة تعرف أن 42 مسودة. لا تعتمد على بذرة عامة سحرية في المشروع.

شرح المثال

الترتيب: امسح ثم ازرع ثم نفّذ ثم اقرأ. المسح في beforeEach يصلح أيضًا إن سقطت الحالة السابقة قبل afterEach. اجمع الاثنين إن كان الإنشاء ثقيلًا، ولا تترك الفشل يلوث التالي.

ماذا يحدث داخليًا؟

Prisma يتصل بالعنوان في البيئة التي يمررها المشغّل. في CI المتغير يُضبط في الخطوة لا في .env المطور. ملف .env الذي يحمّله الاختبار قد يعيد عنوان التطوير بالصمت. اطبع في الحارس اسم القاعدة لا كلمة السر، أو افحص اللاحقة كما سبق. الاتصال يُغلق في afterAll حتى لا يبقى Jest أو Vitest منتظرًا مقابض.

اختبار يفتح معاملة ثم يستدعي خدمة بعميل عام يرى بيانات غير ملتزمة أو لا يرى صفوف المعاملة حسب العزل. لذلك تمرير العميل نفسه جزء من التصميم إن اخترت التراجع. التنظيف أبسط حتى تكبر البيانات.

مثال عملي

طبقات المتجر في CI:

  1. npm test للوحدة بلا Docker قاعدة.
  2. خطوة تكامل تشغّل Postgres خدمة وتضبط DATABASE_URL على bookstore_test وتهجّر ثم تشغّل *.integration.spec.ts.
  3. لا خطوة تتصل بإنتاج.

إن لم يوجد Postgres في التمرين المحلي، لا تضعّف الحارس. شغّل الوحدة فقط. التكامل يعمل حيث توجد الخدمة.

بذور عشوائية من الإنترنت لا تدخل الجدول. البيانات سطر create في الاختبار أو مصنع صغير { title: 'NestJS' } في المستودع.

أخطاء شائعة

  • عنوان الإنتاج في .env يحمّله المشغّل.
  • deleteMany على قاعدة العمل لأن الاسم لم يُفحص.
  • حالة تعتمد على صف من حالة سابقة.
  • FLUSHALL على Redis المشترك.

متى نستخدمه؟

لتكامل الخدمة مع الجدول ولرحلة تحتاج قيدًا حقيقيًا. ليس لكل فرع.

متى لا نستخدمه؟

داخل اختبار الخريطة أو المتحكم الرقيق. الوهم أسرع وأأمن. ولا تستخدم قاعدة الإنتاج «لأنها فيها بيانات جاهزة».

مقارنة

الأسلوب العزل الصعوبة
وهم Prisma تام منخفض
bookstore_test + حذف جيد متوسط
معاملة ملغاة جيد إن مر العميل نفسه أعلى
قاعدة الإنتاج معدوم ممنوع

تمارين

تمرين سهل

ما العلامة في عنوان الاختبار التي يرفض الحارس غيابها؟

الحل

وجود bookstore_test في DATABASE_URL، أو قاعدة اسمها واضح أنها للاختبار لا للعمل.

تمرين متوسط

لماذا المسح في beforeEach لا يكفي إن كانت الخدمة تكتب بعميل خارج معاملة ظننت أنك ألغيتها؟

الحل

لأن الكتابة خارج المعاملة تُثبَّت. التراجع لا يراها. إمّا تمرر عميل المعاملة إلى الخدمة وإما تمسح الجداول صراحة.

تمرين متقدم

اختبار تكامل طابور استعمل Redis التطوير ثم FLUSHALL. ما الضرر وما البديل؟

الحل

يمسح مهام القص ومفاتيح المخبأ المحلية. استعمل قاعدة Redis منطقية أو مثيلًا للاختبار، ونظّف مفاتيح الطابور الاختباري فقط.

أسئلة مراجعة

  • أي أنواع اختبار لا تفتح SQL؟
  • متى تُطبَّق الهجرات؟
  • لماذا معرف ثابت بين ملفات خطر؟

الخلاصة

قاعدة باسم اختبار، هجرات عليها، تنظيف كل حالة، وحارس يرفض عنوان العمل. الوحدة لا تصل إلى هذا العنوان، والإنتاج لا يصل إلى المشغّل.

ماذا بعد؟

دورة حياة التطبيق: ماذا يجري عند الإقلاع والإيقاف بعد أن صارت الاختبارات تغلق ما تفتحه.
