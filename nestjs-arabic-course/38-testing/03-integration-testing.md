# Integration Testing

## الهدف من هذا الدرس

تشغيل أكثر من وحدة حقيقية معًا، غالبًا الخدمة مع قاعدة اختبار، بلا طلب HTTP كامل.

## المشكلة التي يحلها

وهم `prisma.book.update` لا يكتشف أن اسم العمود تغيّر أو أن الحالة المخزّنة `PUBLISHED` تخالف القيد. اختبار الوحدة يبقى أخضر والاستعلام في الإنتاج ينكسر. التكامل يمر على الجسر بين الخدمة والقاعدة، وما زال لا يمر على الحارس والمسار.

## الفكرة ببساطة

قاعدة خاصة بالاختبار، فارغة أو داخل معاملة تُلغى. الخدمة الحقيقية و `PrismaClient` الحقيقي. الطابور والناشر يبقيان وهمًا حتى لا يختلط تكامل القاعدة بتكامل Redis. بعد كل حالة، لا صفوف تتسرب إلى الحالة التالية.

## التعريف التقني

التكامل هنا: `BooksService` + Prisma + قاعدة اختبار. ليس Supertest. ليس ناشر ISBN الحي.

```ts
const prisma = new PrismaClient();
const events = { emitAsync: async () => [] };
const service = new BooksService(prisma, events as never);

await service.publish(bookId);
const row = await prisma.book.findUnique({ where: { id: bookId } });
expect(row?.status).toBe('PUBLISHED');
```

`bookId` صف أنشأته في الإعداد لهذه الحالة. عنوان القاعدة من `DATABASE_URL` يشير إلى اسم مثل `bookstore_test` لا إلى إنتاج. الاستراتيجية الكاملة في آخر درس قاعدة. هذا الدرس يحدد الحدود: ماذا يكون حقيقيًا.

`TestingModule` يمكنه بناء الخدمة وحقن Prisma إن سجّلت المزود. `new` يكفي إن كان الباني واضحًا. الحاوية مفيدة عندما يجمع التكامل وحدتين Nest مثل `IsbnModule` مع مخزن وهمي.

## Mental Model

```text
قاعدة اختبار
  BooksService حقيقية

```

## أبسط مثال

```ts
await prisma.book.create({ data: { id: '42', title: 'NestJS', status: 'DRAFT' } });
await service.publish('42');
```

ثم اقرأ الصف. لا تفحص الوهم فقط. الوهم يثبت الإعلان، والقراءة تثبت الكتابة. الاثنان معًا تكامل الخدمة مع الجدول.

## شرح المثال

إن نسيت `await` على `update` داخل الخدمة، الوحدة بوهم قد تمر إن كان الوهم يعيد وعدًا لم يُفحص، والتكامل يقرأ `DRAFT` ويفشل. هذا ما يدفع ثمن قاعدة الاختبار.

## ماذا يحدث داخليًا؟

Prisma يفتح اتصالًا بقاعدة الاختبار وينفّذ SQL الحقيقي. القيود والمفاتيح تظهر هنا. لا يمر الطلب على `ValidationPipe` ولا على معترض السجل إلا إذا ركّبت التطبيق. لذلك فشل DTO ليس فشل هذا الملف. أغلق العميل بعد الملف حتى لا تبقى وصلات. إن استعملت معاملة تُرجع للخلف، لا تغلق العميل قبل نهاية المعاملة.

المستمع الحقيقي للبريد لا يُسجَّل هنا. وإلا أصبح الاختبار تكامل SMTP. سجّله في رحلة أوسع أو اختبره وحدة بنداء `handle`.

## مثال عملي

حالات التكامل القليلة الثمينة:

| الحالة | حقيقي | وهم |
| --- | --- | --- |
| نشر يكتب `PUBLISHED` | Prisma | الأحداث |
| `lookup` مع خادم HTTP محلي | `HttpService` | — |
| `resize` يكتب `ready` | Prisma وقرص مؤقت | — |

خادم ISBN المحلي تكامل عميل لا وحدة. لا تجعله الافتراضي لكل تشغيل. أغلب CI يكتفي بالوحدة للخريطة وبتكامل واحد للعميل إن وُجد خادم ثابت.

## أخطاء شائعة

- `DATABASE_URL` الإنتاج في ملف الاختبار.
- الاعتماد على ترتيب الملفات لأن الصفوف تبقى.
- تشغيل BullMQ الحقيقي في كل تكامل خدمة.
- تسمية الاختبار e2e لأنه لمس قاعدة. الاسم في هذا الفصل للرحلة HTTP.

## متى نستخدمه؟

عندما يكذب الوهم عن شكل الجدول أو عن SQL. عدد أقل من اختبارات الوحدة.

## متى لا نستخدمه؟

لكل فرع `if` في الخريطة. تلك وحدة. ولا كبديل عن رحلة تثبت ربط المتحكم.

## مقارنة

| المستوى | القاعدة | HTTP |
| --- | --- | --- |
| وحدة | وهم | لا |
| تكامل | حقيقية اختبار | لا في هذا الدرس |
| رحلة | غالبًا حقيقية اختبار | Supertest |

## أسئلة مراجعة

- أي عنوان قاعدة ممنوع؟
- ماذا تغلق في نهاية الملف؟
- أي طبقة ما زالت غير مغطاة؟

## الخلاصة

التكامل يشغّل الخدمة على قاعدة اختبار ويبقي الطابور والناشر وهمًا إلا إن كانا هما موضوع الجسر. الصف يُقرأ بعد الفعل، ولا يتسرب إلى الحالة التالية.

## ماذا بعد؟

رحلة HTTP من الطلب حتى الرمز، وهي ما يسميه هذا الفصل e2e.
