Unit Testing

الهدف من هذا الدرس

اختبار صنف واحد بقيم تدخل وتخرج، مع استبدال كل اعتماد خارجي، بلا HTTP وبلا قاعدة حقيقية.

المشكلة التي يحلها

تجربة النشر من الواجهة تمر على الحارس والتحقق وPrisma. عندما تفشل لا تعرف أي طبقة. اختبار الوحدة يثبت قاعدة «بعد التحديث نعلن book.published» في جزء من الثانية. هو لا يثبت أن المسار POST مربوط.

الفكرة ببساطة

ابنِ الخدمة بكائنات وهمية في الباني. نادِ الدالة. افحص القيمة ونداءات الوهم. لا listen ولا Redis. إن احتجت الشبكة فالاختبار لم يعد وحدة.

التعريف التقني

وحدة في هذا الفصل تعني: دالة أو صنف، اعتماداته ممررة، ولا I/O حقيقي. مثال النشر:

const prisma = {
  book: {
    update: async () => ({ id: '42', status: 'PUBLISHED' }),
  },
};
const events = { emitAsync: async () => [] };
const service = new BooksService(prisma as never, events as never);
await service.publish('42');

as never اختصار للتمرين حتى لا نبني نوع Prisma كاملًا. في المشروع استخرج واجهة صغيرة BooksStore فيها update إن كبر العدد. التوقع:

expect(events.emitAsync).toHaveBeenCalledWith(bookPublished, { bookId: '42' });

شكل expect واحد في Jest و Vitest. الاستيراد يختلف في درس المشغّلين. هنا السلوك.

لا تستدعِ IsbnService.lookup الحقيقي. إما تختبر خريطة الأخطاء بدالة mapAxios المستخرجة، وإما تمرر HttpService وهميًا يعيد تيار throwError.

Mental Model

وهم -> BooksService.publish -> توقع update و emit

بلا TestingModule إن كان البناء new يكفي. الوحدة عندما تحتاج الحاوية درس لاحق.

أبسط مثال

خريطة ISBN بلا شبكة:

expect(mapStatus(404)).toBeNull();
expect(() => mapStatus(503)).toThrow(BadGatewayException);

إن كانت الخريطة دالة نقية، فالوحدة لا تحتاج حتى وهمًا. هذا أفضل أشكال الاختبار. استخرجها من catch إن كانت مدفونة.

شرح المثال

mapStatus لا تعرف Axios. الاختبار يمرر رقمًا. بذلك تثبت العقد: الغياب null والعطل 502. مهلة ECONNABORTED دالة ثانية أو فرع في الدالة النقية نفسها. لا تشغّل lookup كاملًا لتثبت جدولًا.

ماذا يحدث داخليًا؟

المشغّل ينفّذ الملف في عملية الاختبار. new BooksService لا يمر على Nest، فلا حراس ولا أنابيب. هذا مقصود. إن كان الخطأ في @UseGuards فلن يظهر هنا وسيظهر في رحلة HTTP. لا تضف Test.createTestingModule لكل دالة نقية. الحاوية تكلفة وسببها الحقن والزينة لا if.

مثال عملي

حالات publish:

الحالة التوقع
تحديث ينجح emitAsync بـ { bookId: '42' }
تحديث يرمي لا emitAsync
المعرف فارغ رمي قبل Prisma إن كان ذلك عقد الخدمة

الحالة الثانية تمنع إعلانًا بعد فشل الحفظ. اكتبها صراحة لأن ترتيب الأسطر سهل كسره.

أخطاء شائعة

  • تشغيل Redis «لأن الوحدة تحتاج الطابور». استبدل المنتج.
  • توقع نص السجل بدل الأثر.
  • تغطية كل فروع المتحكم بنداء الخدمة فقط.
  • any يخفي أن الوهم لم يعد يطابق الباني.

متى نستخدمه؟

لقواعد الخدمة والمستمع وخريطة الأخطاء. هو أغلب عدد الاختبارات.

متى لا نستخدمه؟

لإثبات أن ValidationPipe يرفض الجسم. ذلك مستوى أعلى. ولا لترتيب middleware المعرف. الوحدة لا تشغّل الوسيط.

مقارنة

يثبت لا يثبت
ترتيب الحفظ ثم الإعلان ربط POST
خريطة 404 إلى null مهلة Axios الحقيقية
أن المستمع ينادي enqueue أن الاسم في registerQueue مطابق

تمارين

تمرين سهل

هل اختبار الوحدة يفتح منفذًا؟

الحل

لا. لا HTTP ولا listen.

تمرين متوسط

ماذا تثبت حالة «التحديث يرمي»؟

الحل

أن emitAsync لا يُستدعى إن فشل الحفظ، حتى لا يُعلن نشر لم يحدث.

تمرين متقدم

لماذا تستخرج mapStatus بدل اختبار lookup مع وهم Axios لكل رمز؟

الحل

لأن الجدول نقي وأوضح. وهم Axios يبقى لاختبار أن lookup تستدعي الخريطة، لا لتكرار الجدول كله.

أسئلة مراجعة

  • ما الذي يُستبدل في الباني؟
  • أي خطأ لا يظهر في هذا المستوى؟
  • متى new أفضل من الحاوية؟

الخلاصة

الوحدة صنف بلا I/O: وهم، نداء، توقع. خريطة الأخطاء تستحق دالة نقية. الربط على HTTP مستوى آخر.

ماذا بعد؟

اختبار التكامل عندما تجتمع وحدتان حقيقيتان، مثل الخدمة مع قاعدة اختبار.
