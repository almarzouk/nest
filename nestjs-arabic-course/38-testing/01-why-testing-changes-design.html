لماذا يغيّر الاختبار شكل التصميم

الهدف من هذا الدرس

ملاحظة أن الاختبار السهل يكشف اقترانًا سيئًا قبل الحديث عن Jest أو Vitest.

المشكلة التي يحلها

publish التي تفتح Prisma وترسل SMTP وتكتب Redis لا تُختبر إلا بتشغيل كل شيء، فتتأجل الاختبارات. عندما تحاول تمرير وهم بريد، لا يوجد مكان لتمريره لأن النداء smtp.send داخل الدالة لا في الباني. التصميم الذي يقبل الاختبار هو الذي يقبل بديلًا لكل حد خارجي.

الفكرة ببساطة

إن لم تستطع استدعاء السلوك بمعرفات وهمية في الذاكرة، فالوحدة ما زالت تمسك الشبكة أو القرص. الفصول السابقة فصلت IsbnService و EventEmitter2 وحمولة { bookId }. الاختبار هو السبب العملي لتلك الحدود، لا حفلًا بعد ما يكتمل التطبيق.

التعريف التقني

ثلاثة أسئلة على كل صنف قبل كتابة أداة:

السؤال إن كانت الإجابة لا
هل الاعتماد في الباني؟ لن تبدّله في الاختبار
هل الأثر الخارجي خلف واجهة؟ ستتصل بالناشر الحقيقي
هل النتيجة تُعاد لا تُطبع فقط؟ لن تستطيع expect

BooksService.publish التي تعيد الكتاب وتستدعي emitAsync تُختبر بوهم المُصدِر. التي تطبع فقط وتستدعي SMTP لا تُختبر إلا بمراقبة العالم.

هذا الدرس لا يثبت مشغّلًا. يثبت شكل الدالة.

Mental Model

سلوك صغير
  اعتمادات في الباني
    وهم في الاختبار
      توقع على القيمة أو على النداء

أبسط مثال

صعب:

async publish(bookId: string) {
  await fetch('https://mail.example', { method: 'POST' });
}

أسهل:

constructor(private readonly events: EventEmitter2) {}

async publish(bookId: string) {
  await this.prisma.book.update({ where: { id: bookId }, data: { status: 'PUBLISHED' } });
  await this.events.emitAsync(bookPublished, { bookId });
}

السطر الثاني ما زال يحتاج قاعدة أو وهم Prisma. لكنه لم يعد يحتاج شبكة بريد. وهم Prisma يتوقع update، ووهم الأحداث يتوقع الاسم والحمولة.

شرح المثال

fetch داخل الجسم اعتماد مخفي. كل اختبار ينشر كتابًا يصبح اختبار شبكة. نقله إلى مستمع يدرج طابورًا يجعل اختبار publish عن الحالة والإعلان، واختبار المستمع عن enqueuePublished. هذا هو تغيير الشكل: ليس إضافة describe حول الدالة القديمة.

ماذا يحدث داخليًا؟

اختبار الوحدة يستبدل الباني. لا يوجد سحر يقطع fetch إن لم تمر من بوابة تستطيع استبدالها. مكتبة نقر الشبكة موجودة وتُستعمل في رحلات أوسع، لكنها تعوض عن تصميم صعب لا تغني عن الحد. عندما يكون Prisma في الباني، تمرر كائنًا فيه book.update التي ترجع صفًا في الذاكرة. الدالة لا تعرف الفرق إن كانت تستدعي التابع فقط.

مثال عملي

حدود كتب المتجر التي صار اختبارها رخيصًا:

الدالة الوهم
publish Prisma و EventEmitter2
IsbnService.lookup HttpService أو استبدال الخدمة كلها
resize Prisma وقرص في مجلد مؤقت
معترض السجل لا تتوقع نص stdout، استخرج التنسيق

resize على قرص مؤقت أقرب إلى تكامل صغير. الوحدة الصرف تتوقف عند «استُدعي الكتابة بهذا المفتاح».

أخطاء شائعة

  • اختبار يدق الناشر الحقيقي لكل حفظ عنوان.
  • منطق في المتحكم لا يُرى إلا عبر HTTP حتى في أول اختبار.
  • console.log هو الناتج الوحيد.
  • تأجيل كل الاختبار حتى «نصب CI».

متى نستخدمه؟

هذا المعيار وأنت تفصل خدمة جديدة: إن عجزت عن تسمية الوهم، أعد الحد قبل كتابة الحالة.

متى لا نستخدمه؟

كذريعة لحذف رحلة HTTP. الشكل الجيد يجعل الوحدة رخيصة والرحلة أقل عددًا، لا صفرًا. الرحلة تثبت أن الوحدة رُبطت.

مقارنة

الشكل أول اختبار
fetch داخل publish شبكة أو لا اختبار
حدث في الباني توقع emitAsync
SQL في المتحكم خادم وقاعدة لكل فرع

تمارين

تمرين سهل

أين يجب أن يظهر اعتماد البريد حتى يُستبدل؟

الحل

في الباني، أو خلف مستمع لا تستورده publish مباشرة. لا fetch داخل الجسم.

تمرين متوسط

ماذا يتوقع اختبار publish بعد الفصل؟

الحل

أن update استُدعي بحالة PUBLISHED وأن الإعلان book.published حمل { bookId }.

تمرين متقدم

لماذا وهم الشبكة أضعف من نقل fetch إلى مستمع؟

الحل

لأن الوهم يرمم نداءً مخفيًا. نقل النداء يجعل الاختبار يصف العقد الذي تريده: حالة ثم إعلان، لا تفاصيل عنوان البريد.

أسئلة مراجعة

  • ما علامة الاعتماد المخفي؟
  • ماذا تعيد الدالة حتى تُفحص؟
  • أي اختبار لا يُحذف عندما تصبح الوحدة سهلة؟

الخلاصة

الاختبار الرخيص يطلب اعتمادات في الباني وآثارًا خلف واجهات. إن صعب الوهم، غيّر التصميم لا الأداة أولًا.

ماذا بعد؟

ماذا يثبت اختبار الوحدة وحده، وماذا يترك للأعلى.
