Authentication و Authorization

الهدف من هذا الدرس

تفريق «من هذا؟» عن «هل يُسمح له بهذه الدالة؟»، وتحديد ما يُبنى في هذا الفصل وما يُؤجَّل.

المشكلة التي يحلها

كلمة auth في الكود تغطي الاثنين. حارس واحد يتحقق من الرمز ويفرض دور المشرف ويحوّل المقعد يصعب اختباره. الصفحة نفسها تفصل: Middleware مناسب للمصادقة التي تلصق هوية لأنها لا تحتاج سياق الدالة، والحارس مناسب للتفويض لأنه يرى ExecutionContext.

الفكرة ببساطة

Authentication تجيب عن الهوية: هل الترويسة تثبت شخصًا، ومن هو. Authorization تجيب عن الإذن: هل هذا الشخص يجوز له reserve أو refund. هذا الفصل يعلّم البوابة التي تقدر أن تحمل أيًا منهما. إستراتيجية الرمز وكلمة المرور والجلسة فصول لاحقة. زينة @Roles و @Public فصل الزينة المخصصة.

التعريف التقني

الصفحة تصف حارس التفويض بأنه شائع لأن بعض المسارات تتاح فقط لصاحب صلاحية. وتقول إن المصادقة عادة تتعاون معه. المثال التعليمي في التوثيق يتحقق من طلب ثم يرجع منطقيًا، ويحيلك إلى فصل المصادقة لمثال واقعي.

حد هذا المجلد:

  • يجوز لحارس أن يرفض طلبًا بلا دليل هوية برمز 401، كآلية throw.
  • يجوز لحارس أن يرجع false فيصير 403 حين تكون الهوية معروفة والإذن ناقصًا.
  • لا نثبّت JWT ولا Passport ولا جدول مستخدمين هنا.
  • إلصاق request.user بعد التحقق من رمز يمكن أن يعيش في Middleware أو في حارس مصادقة. كلاهما مذكور في التوثيق. ما لا يعيش في Middleware هو قرار يعتمد على بيانات الدالة، لأن تلك الطبقة لا تعرف المعالج التالي.

التفويض الذي يقرأ أدوارًا مكتوبة على reserve يحتاج getHandler() ثم Reflector. قراءة الزينة تُكتب حين تُبنى الزينة. هنا تعرف لماذا المكان حارس لا أنبوب.

Mental Model

من أنت؟          مصادقة     401 إن غابت الهوية
هل تفتح reserve؟ تفويض     403 إن منعت البوابة
هل seat عدد؟     شكل       400 من الأنبوب
هل المقعد مبيع؟  أعمال     409 من الخدمة

أبسط مثال

import {
  type CanActivate,
  type ExecutionContext,
  Injectable,
  UnauthorizedException,
} from '@nestjs/common';

type DeskRequest = { headers: Record<string, string | undefined>; user?: { name: string } };

@Injectable()
export class IdentifyDeskGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest<DeskRequest>();
    const name = request.headers['x-desk-name'];
    if (!name) {
      throw new UnauthorizedException();
    }
    request.user = { name };
    return true;
  }
}

هذا حارس مصادقة تعليمي: يثبت وجود اسم شباك ويلصقه. لا يقرر إن كان الاسم يجوز له الاسترداد. حارس ثانٍ لاحقًا يقرأ request.user وبيانات الدالة ويرجع false للتفويض. الفصل لا يملأ الحارس الثاني بجدول أدوار حقيقي.

شرح المثال

  • 401 لغياب الهوية، لا 403. الضيف لم يُعرَف بعد.
  • request.user أثر على طلب هذه الدورة فقط، يُقرأ من السياق لا من حقل على الصنف.
  • return true يعني «الهوية حاضرة»، لا «كل العمليات مباحة».
  • الترويسة x-desk-name بديل مؤقت عن رمز. استبدلها في فصل المصادقة، وأبقِ شكل الحارس.

ماذا يحدث داخليًا؟

إن رُبط الحارسان معًا، ترتيب @UseGuards هو ترتيب التنفيذ: التعريف أولًا ثم التفويض. التفويض الذي يقرأ request.user قبل لصقه يرى undefined. دورة الطلب لا تعيد ترتيب الحراس حسب النية. الدرس الأخير في الفصل يثبت الترتيب العام ثم المتحكم ثم المسار.

الأنبوب ما زال بعد الاثنين. فشل الهوية لا يفحص DTO. نجاح الهوية وفشل الإذن كذلك.

Middleware يستطيع لصق user أيضًا إن كان العمل لا يقرأ زينة الدالة. إن بدأت المصادقة هناك، الحارس في هذا الدرس يبقى للتفويض فقط حتى لا تُقرأ الترويسة مرتين.

مثال عملي

شباك: IdentifyDeskGuard ثم بوابة استرداد ترجع false لغير المشرف. اليوم بوابة الاسترداد يمكن أن تقارن request.user.name بقائمة ثابتة في الاختبار. غدًا تقرأ @Roles(['refund']) من الدالة. الاختبار الأول يثبت الفرق بين غياب الترويسة (401) واسم لا يملك الاسترداد (403). لا تختبر مكتبة JWT في هذا الملف.

أخطاء شائعة

  • رمز 403 عند غياب الهوية. العميل يظن أنه معروف وممنوع.
  • رمز 401 عند نقص الدور بعد أن عُرفت الهوية. المعنى الشائع عندئذ المنع 403.
  • حشر فحص المقعد في حارس التفويض.
  • اعتبار هذا الملف فصل المصادقة مكتملًا لأنه لصق user.

متى نستخدمه؟

حين تقسم البوابات: واحدة تثبت الهوية وتلصقها، وواحدة تقرر الإذن على الدالة. الآلية هنا، والمزوّد الحقيقي لاحقًا.

متى لا نستخدمه؟

لا تكتب تحقق كلمة المرور ولا توقيع الرمز في هذا الدرس. لا تضع التفويض في ValidationPipe. لا تقرأ دور الدالة من Middleware.

مقارنة

السؤال الطبقة رمز شائع عند الفشل
من أنت؟ مصادقة، حارس أو Middleware بلا زينة 401
هل تُفتح هذه الدالة؟ تفويض في حارس 403
هل الشكل صحيح؟ Pipe 400
هل الحالة تسمح؟ خدمة 409 أو 404

تمارين

تمرين سهل

ما رمز غياب الهوية، وما رمز نقص الإذن بعد معرفة الشخص؟

الحل

الغياب 401 عبر UnauthorizedException. نقص الإذن 403 عبر return false أو ForbiddenException.

تمرين متوسط

لماذا يصلح Middleware للمصادقة التي تلصق user فقط، ولا يصلح لتفويض يعتمد على الدالة؟

الحل

المصادقة هنا لا تحتاج معرفة المعالج التالي. التفويض يحتاج ExecutionContext ليعرف أي دالة ستعمل وما بياناتها. Middleware لا يملك هذا السياق.

تمرين متقدم

حارس واحد يتحقق من الرمز ويفرض الدور ويفحص seat. كيف تقسمه على الطبقات من غير تنفيذ JWT؟

الحل

إثبات الهوية في حارس مصادقة أو Middleware يلصق user. الدور في حارس تفويض يقرأ الدالة. seat في ValidationPipe على DTO. الحجز المبيع في الخدمة. هذا الفصل يكتب البوابتين كآلية، والرمز لاحقًا.

أسئلة مراجعة

  • ما سؤال المصادقة وما سؤال التفويض؟
  • لماذا 401 غير 403؟
  • ماذا نؤجل إلى فصل المصادقة؟
  • أين يعيش فحص الشكل؟

الخلاصة

المصادقة تثبت الهوية. التفويض يفتح الدالة أو يمنعها. الحارس يقدر أن يحمل الاثنين كآلية، والأوضح فصلهما. الرمز والجلسة والأدوار المزيّنة فصول تالية على هذه البوابة لا بدلًا عنها.

ماذا بعد؟

الدرس التالي مستويات الربط: تطبيق، متحكم، ومسار، ولماذا الحارس العام يغلق تسجيل الدخول والصحة.
