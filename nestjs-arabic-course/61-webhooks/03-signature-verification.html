التحقق من التوقيع

الهدف من هذا الدرس

إثبات أن جسم ويب هوك رف لم يُبدَّل وأن من أرسله يملك السر، بحساب HMAC على البايتات نفسها التي وصلت.

المشكلة التي يحلها

مسار POST /webhooks/billing عام. من يعرف العنوان يرسل { "type": "customer.subscription.updated", "status": "active" } فيفتح الخطة. سر في ترويسة من غير ربطها بالجسم يُنسخ مع جسم آخر.

الفكرة ببساطة

المرسل يحسب HMAC-SHA256 على الجسم الخام (وأحيانًا الطابع الزمني) بالسر المشترك، ويضع الناتج في ترويسة. أنتم تحسبون نفس الحساب وتقارنون بنتيجة ثابتة الزمن. الاختلاف 400 ولا تحديث. الطابع يحد إعادة إرسال قديم.

التعريف التقني

createHmac('sha256', secret).update(rawBody).digest('hex') من node:crypto. المقارنة بـ timingSafeEqual على Bufferين بنفس الطول. لا تقارنوا بـ === على السلاسل. الجسم هو البايتات قبل JSON.parse؛ إن سلسلة Nest الكائن ثم أعدتم JSON.stringify فقد يتغير الترتيب والمسافات فيختلف HMAC رغم أن المعنى واحد. لذلك الدرس التالي يبقي rawBody. للصادر، رف تحسب التوقيع وشريط الشريك يتحقق بنفس العقد المكتوب: اسم الترويسة وقاعدة النص الموقَّع (الجسم فقط أو timestamp.body).

Mental Model

سر + بايتات الجسم → HMAC
يرسل في الترويسة
المستقبل يعيد الحساب
تطابق آمن زمنيًا → يكمل

أبسط مثال

import { createHmac, timingSafeEqual } from 'node:crypto';

export function sign(secret: string, raw: Buffer) {
  return createHmac('sha256', secret).update(raw).digest('hex');
}

export function signaturesMatch(expectedHex: string, givenHex: string) {
  const a = Buffer.from(expectedHex);
  const b = Buffer.from(givenHex);
  if (a.length !== b.length) return false;
  return timingSafeEqual(a, b);
}

شرح المثال

  • update على Buffer لا على كائن.
  • اختلاف الطول يرفض قبل timingSafeEqual لأن الدالة ترمي إن اختلف الطول.
  • السداسي يجب أن يكون ناتج نفس الترميز عند الطرفين. وثّقوا hex لا base64 في عقد رف الصادر.

ماذا يحدث داخليًا؟

  1. تصل الترويسة والجسم الخام.
  2. ترفضون إن غاب الطابع أو كان أقدم من النافذة (مثل خمس دقائق) إن كان الطابع جزءًا من العقد.
  3. تحسبون HMAC على نفس سلسلة البايتات التي وقّعها المرسل.
  4. التطابق يكمل إلى تحليل JSON.
  5. الفشل 400 بلا تفاصيل تخبر أي بايت اختلف. السجل الداخلي يحفظ معرّف الحدث فقط.

مثال عملي

عقد صادر بسيط توقّعه رف:

export function signedPayload(secret: string, timestamp: string, raw: Buffer) {
  const signed = Buffer.concat([Buffer.from(`${timestamp}.`), raw]);
  return sign(secret, signed);
}

الشريك يعيد البناء من الطابع والجسم الخام لا من JSON المعاد تسلسله. documentوا أن النقطة بين الطابع والجسم جزء من العقد. تغييرها يكسر كل الأطراف.

أخطاء شائعة

  • توقيع JSON.stringify(req.body) بعد التحليل.
  • مقارنة === تسرّب زمنًا نظريًا وتختلف مع حالة الأحرف.
  • سر واحد لكل المكتبات في الصادر فيستطيع عنوان مكتبة التحقق من أحداث أخرى إن تسرّب.
  • قبول التوقيع ثم أخذ tenantId من الجسم كما في الدرس الوارد.

متى نستخدمه؟

على كل وارد من مزود وكل صادر إلى شريك. بلا توقيع لا تحديث حالة.

متى لا نستخدمه؟

لا توقّعوا طلبات القارئ التي تحمل Bearer. ذلك إثبات آخر. ولا تبنوا خوارزمية جديدة؛ HMAC-SHA256 كافٍ لهذا العقد.

مقارنة

الفحص ماذا يمنع
سر في ترويسة فقط لا يمنع استبدال الجسم
HMAC على JSON المعاد يفشل على مسافات أو يمر على جسم مُعدَّل إن أسأتم البناء
HMAC على البايتات + طابع يربط السر بالجسم وبالزمن

تمارين

تمرين سهل

لماذا يفشل التوقيع الصحيح بعد JSON.parse ثم stringify؟

الحل

لأن البايتات قد تختلف (ترتيب مفاتيح، مسافات) عن التي وقّعها المرسل. الحساب يكون على rawBody.

تمرين متوسط

طول التوقيع القادم يختلف عن طول حسابكم. ماذا تعيدون ولماذا لا تنادون timingSafeEqual مباشرة؟

الحل

ترفضون. timingSafeEqual ترمي إن اختلف الطول. الرفض 400 من غير تحديث.

تمرين متقدم

الطابع داخل النافذة والتوقيع صحيح لكن الحدث عمره يوم في طابور المزود الذي يعيد المحاولة. أي طبقة تمنع الأثر المكرر إن كان التوقيع سيمر كل مرة؟

الحل

التوقيع يثبت الأصل لا الحداثة عبر أيام إن كانت النافذة تُفحص عند أول وصول فقط، ولا يمنع إعادة المزود المشروعة. مفتاح التكرار على معرّف الحدث هو الذي يمنع الأثر مرتين. الطابع يحد إعادة اللصق المتأخرة خارج النافذة، والتكرار يعالج الإعادات داخل العقد.

أسئلة مراجعة

  • على ماذا يُحسب HMAC؟
  • لماذا المقارنة ثابتة الزمن؟
  • ماذا يضيف الطابع؟
  • لماذا سر لكل عنوان صادر؟

الخلاصة

التوقيع HMAC على البايتات الخام مع مقارنة timingSafeEqual. التحليل إلى JSON يأتي بعد التطابق. الطابع يحد اللصق القديم، ولا يغني عن مفتاح التكرار.

ماذا بعد؟

الحساب يحتاج البايتات الأصلية داخل Nest. الدرس التالي rawBody.
