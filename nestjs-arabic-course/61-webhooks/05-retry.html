Retry

الهدف من هذا الدرس

تصميم إعادة المحاولة لوارد المزود ولصادر رف بحيث التعطل المؤقت يُستأنف، والفشل الدائم يتوقف، والأثر لا يتكرر رغم تكرار الطلب.

المشكلة التي يحلها

شبكة انقطعت بعد ما حدّث رف الاشتراك وقبل ما وصل 200 إلى Stripe، فأعاد المزود الحدث. أو شريك المخزون أعاد 500 فأعاد عامل رف الإرسال كل ثانية بلا سقف حتى حُظر العنوان. أو أعدتم فورًا على 400 لأن التوقيع خاطئ فلا أمل في المحاولة.

الفكرة ببساطة

أعيدوا عندما يكون الفشل مؤقتًا: مهلة، 429، 500. لا تعيدوا على 400 توقيع أو جسم مرفوض. باعدوا بين المحاولات (backoff) وتوقفوا بعد حد. الوارد: ردوا 2xx فقط بعد حفظ دائم لمعرّف الحدث حتى تكون إعادة المزود آمنة. الصادر: نفس معرّف الحدث في كل المحاولات.

التعريف التقني

المزود يملك جدول إعادة الوارد؛ أنتم تملكون جدول الصادر (attempts, nextAttemptAt). التصنيف: أخطاء الشبكة و 408 و 429 و 5xx مؤقتة. 4xx غير 429 نهائي. حد مثل 8 محاولات ثم failed يظهر في واجهة المكتبة. لا حلقة while داخل طلب الموظف. صفحة Webhooks تتوقع أن الطرفين يتفقان على إعادة الإرسال؛ مفتاح التكرار في الدرس التالي هو الذي يجعل الإعادة صحيحة.

Mental Model

مؤقت → حاول لاحقًا بمعرّف نفسه
نهائي → قف وسجّل
2xx → قف نجاحًا

أبسط مثال

export function nextDelayMs(attempt: number) {
  const base = 1_000 * 2 ** Math.min(attempt, 6);
  return Math.min(base, 60_000);
}

export function shouldRetry(status: number | null) {
  if (status === null) return true;
  if (status === 429 || status >= 500) return true;
  return false;
}

شرح المثال

  • status === null انقطاع بلا رد، مؤقت.
  • 400 لا يُعاد. أصلحوا التوقيع أو العنوان.
  • السقف 60 ثانية يمنع التباعد اللانهائي بين المحاولات داخل الحد العددي.

ماذا يحدث داخليًا؟

  1. العامل يرسل الصادر.
  2. إن كان shouldRetry و attempts تحت الحد، يكتب nextAttemptAt.
  3. عامل لاحق يلتقط الصف عندما يحين الوقت. حمولة الحدث نفسها.
  4. للوارد، المزود يقرر إعادة الإرسال إن لم ير 2xx. أنتم تخزّنون event.id قبل الرد.
  5. بعد الحد، الصف failed ولا يُلمس الكتالوج المنشور.

مثال عملي

export function classifyInbound(stored: boolean) {
  if (!stored) return 500;
  return 200;
}

إن فشل INSERT قبل الالتزام، أرجعوا 500 حتى يعيد المزود. إن نجح الحفظ، أرجعوا 200 حتى لو كانت المهمة التالية (بريد) ما زالت في الطابور. إعادة المزود ستجد المعرّف مخزنًا ولن تكرر تحديث الاشتراك، وهذا يحتاج درس التكرار. إرجاع 200 قبل الحفظ يفقد الحدث.

أخطاء شائعة

  • 200 ثم الحفظ فيفشل الحفظ ولا إعادة.
  • إعادة 400 توقيع كل دقيقة.
  • محاولات صادرة بلا تباعد فتشبه هجومًا على الشريك.
  • محاولة جديدة بمعرّف حدث جديد.

متى نستخدمه؟

على التسليم الصادر دائمًا، وعلى الوارد بالاتفاق مع جدول المزود عبر رموزكم.

متى لا نستخدمه؟

لا تعيدوا طلب القارئ POST /books بهذا الجدول؛ هناك Idempotency-Key. ولا تعيدوا إلى ما لا نهاية عنوانًا أعطى 404.

مقارنة

الوضع وارد عندكم صادر منكم
لم يُحفظ 500 ليعيد المزود حاول لاحقًا
حُفظ 200 أرسل 2xx من الشريك ينهي
400 توقيع لا أثر لا تعيدوا نفس التوقيع المكسور

تمارين

تمرين سهل

الشريك أعاد 503. هل تعيدون فورًا عشر مرات في نفس الدورة؟

الحل

لا. صنّفوه مؤقتًا، زادوا attempts، وحددوا nextAttemptAt عبر nextDelayMs. نفس event.id.

تمرين متوسط

لماذا 200 قبل INSERT خطر؟

الحل

المزود لن يعيد. إن سقطت العملية قبل الحفظ ضاع تحديث الاشتراك. احفظوا ثم أرجعوا 200.

تمرين متقدم

بعد 8 محاولات ما زال الشريك 500. ماذا يرى مدير المكتبة، وماذا لا يتغير في الكتاب؟

الحل

صف التسليم failed يمكن عرضه في إعدادات الويب هوك. الكتاب يبقى منشورًا. إعادة التفعيل زر يجدول محاولة جديدة بنفس معرّف الحدث لا نشرًا ثانيًا.

أسئلة مراجعة

  • أي الرموز تُعاد وأيها تتوقف؟
  • متى تردون 200 للوارد؟
  • لماذا التباعد؟
  • هل الإعادة تغيّر معرّف الحدث؟

الخلاصة

أعيدوا الفشل المؤقت بتباعد وحد، وتوقفوا عند الرفض النهائي. الوارد: الحفظ ثم 200. الصادر: نفس الحدث حتى 2xx أو حتى failed. الإعادة بلا منع تكرار لا تكفي وحدها.

ماذا بعد؟

الإعادة ستصل مرتين. الدرس التالي يجعل المعالجة مرة واحدة لكل معرّف حدث.
