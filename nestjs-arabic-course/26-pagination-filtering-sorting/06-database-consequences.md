# أثر النمط على الاستعلام

## الهدف من هذا الدرس

جعل عقد القائمة يطابق فهرسًا وخطة تنفيذ، حتى لا يصبح `skip` أو المرشح مسحًا للجدول.

## المشكلة التي يحلها

`where` صحيح و`orderBy` آمن، والطلب يبطؤ عند `page=400` أو عند `published=true` مع فرز `title`. PostgreSQL يقرأ صفوفًا كثيرة ليرميها في `OFFSET`، أو يرتّب الناتج في الذاكرة لأن الفهرس على `id` فقط لا يخدم الشرط. `count` على نفس الجدول يضيف رحلة ثانية تبدو بريئة في التطوير.

## الفكرة ببساطة

فهرس القائمة يغطي أعمدة المساواة في `WHERE` ثم أعمدة `ORDER BY`. الإزاحة العميقة تبقى مكلفة حتى مع فهرس، لأن المحرك يعدّ حتى موضع البداية. المؤشر يحوّل الطلب إلى مدى على ذلك الفهرس. `count` اختياري حين تكتفي الواجهة بـ `nextCursor`. لا تُنشأ فهرسًا لكل عمود «احتياطًا». كل فهرس يبطئ الكتابة.

## التعريف التقني

في `schema.prisma` لمسار المنشورات الشائع: زائر يطلب `published = true` مرتبًا بـ `id`.

```prisma
model Post {
  id        Int     @id @default(autoincrement())
  title     String
  published Boolean @default(false)
  authorId  Int
  @@index([published, id])
  @@index([authorId, id])
}

model Comment {
  id     Int @id @default(autoincrement())
  postId Int
  @@index([postId, id])
}
```

الهجرة عبر `prisma migrate`. الفهرس يُراجع في الهجرة مثل أي عمود. استعلام الزائر `findMany` مع `where: { published: true }` و `orderBy` على `id` يطابق `[published, id]`. فرز `title` بعد ذلك الشرط يحتاج فهرسًا يبدأ بـ `published` ثم `title` ثم `id` إن صار المسار شائعًا. من غير قياس لا تضف فهرسًا إضافيًا.

مؤشر التعليقات: `where: { postId }` و `orderBy` على `id` و `cursor` مع `skip: 1` و `take: limit + 1`. الفهرس `[postId, id]` يخدم المساواة والمدى.

`count({ where })` يبقى في لوحة الأرقام ويُترك حين يكفي `nextCursor`. `select` يقتصر على حقول `PostResponse`. `EXPLAIN` على حجم يشبه الإنتاج يميّز `Index Scan` من `Seq Scan`.

## Mental Model

```text
WHERE مساواة ثم ORDER BY
  = ترتيب أعمدة الفهرس
OFFSET العميق يعدّ الصفوف
المؤشر يقفز في الفهرس
count رحلة إضافية
```

## أبسط مثال

```sql
EXPLAIN ANALYZE
SELECT id, title, published
FROM "Post"
WHERE published = true
ORDER BY id ASC
OFFSET 0 LIMIT 20;
```

## شرح المثال

شغّل الاستعلام الذي يولّده Prisma لا استعلامًا تخيلته. إن رأيت فرزًا منفصلًا عن المسح، الفهرس لا يطابق الترتيب. إن رأيت `Index Scan` على `Post_published_id_idx` فالعقد والخطة متفقان على الصفحة الأولى. كرّر بـ `OFFSET 10000` وقارن الزمن. الفرق هو سبب المؤشر على الخيوط الطويلة.

أسماء الفهارس عند Prisma قد تختلف. المهم الأعمدة والترتيب.

## ماذا يحدث داخليًا؟

المخطط يقدّر الصفوف. فهرس مركّب يُستخدم من اليسار: شرط `authorId` يستخدم `[authorId, id]`، وشرط `published` يستخدم الفهرس الآخر. شرط على `title` فقط لا يستخدم `[published, id]` كبداية مساواة. لذلك مفتاح فرز جديد في الخريطة سؤال فهرس لا سؤال DTO فقط.

`OFFSET` يطلب تخطي N صفوف مطابقة. الفهرس يسرّع إيجادها وما زال يزورها. المؤشر مع ترتيب تصاعدي يبدأ بعد المفتاح. قِس بعد تحديث إحصاءات الجدول على نسخة كبيرة، لا على عشرين صفًا فقط.

## مثال عملي

بعد هجرة الفهرسين، قائمة الزائر ولوحة «مقالاتي» بـ `authorId` من الجلسة. تعليق على مقال يستخدم `[postId, id]`. اختبار لا يثبت زمنًا هشًا. يثبت وجود الهجرة. قياس `EXPLAIN` مرة على نسخة فيها آلاف الصفوف وتُسجَّل الملاحظة في وصف الهجرة إن تغيّر الفهرس.

أزل فهرسًا تجريبيًا لم يظهر في خطة المسارات الحقيقية حتى لا تدفع كل `INSERT` ثمنه.

## أخطاء شائعة

- فهرس على `id` وحده وتوقع أنه يخدم `published = true ORDER BY title`.
- `OFFSET` عميق مع الإصرار على أرقام الصفحات في خيط ضخم.
- `count` في كل طلب مؤشر.
- `select` لكل الأعمدة في قائمة.
- `synchronize: true` لإنشاء الفهرس على الإنتاج.
- فهرس لكل مرشح نادر.

## متى نستخدمه؟

عند تثبيت عقد قائمة سيُستدعى كثيرًا، وبعد أي مفتاح فرز أو مرشح جديد.

## متى لا نستخدمه؟

قبل أن يوجد استعلام حقيقي. فهرس بلا `WHERE` يطابقه يبطئ الكتابة. والقياس على عشرين صفًا لا يبرر قرار الإنتاج وحده.

## مقارنة

| إزاحة مع فهرس | مؤشر مع الفهرس نفسه |
| --- | --- |
| صفحة قريبة رخيصة | العمق يبقى مدى |
| رقم صفحة | `nextCursor` |
| `count` للوحة | غالبًا بلا `count` |
| تهتز مع الحذف | أثبت على مفتاح متزايد |

### تمرين سهل

### تمرين متوسط

<details>
<summary>الحل</summary>

</details>

### تمرين متقدم

أضفت `sort=title` للزائر على المنشورات. ماذا تراجع قبل الإطلاق؟

<details>
<summary>الحل</summary>

خطة `EXPLAIN` لـ `published` ثم `title` ثم `id`. إن صار المسار شائعًا، فهرس بهذا الترتيب عبر هجرة. المؤشر يجب أن يحمل `title` و `id`.

</details>

## أسئلة مراجعة

- أي فهرس لتعليقات مقال؟
- متى تُسقط `count`؟
- كيف تُضاف الفهارس في هذه الدورة؟

## الخلاصة

العقد والفهجرة متلازمان: مساواة ثم ترتيب في الفهرس، إزاحة للصفحات القريبة، مؤشر للعمق، و`count` حين تحتاج الواجهة الرقم. الإنتاج بلا `synchronize`.
