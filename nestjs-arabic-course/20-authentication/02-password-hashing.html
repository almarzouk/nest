Password Hashing

الهدف من هذا الدرس

تخزين ما يثبت كلمة المرور من غير حفظ الكلمة نفسها، باستخدام PasswordHasher من @nestjs/authentication.

المشكلة التي يحلها

عمود password بنص واضح يجعل أي نسخة احتياطية أو سجل خطأ حسابات جاهزة. التشفير القابل للفك بمفتاح على الخادم يعيد الكلمة إن سُرق المفتاح مع القاعدة. المساواة بين نصين في الذاكرة لا تبطئ التخمين.

الفكرة ببساطة

التجزئة دالة باتجاه واحد: من الكلمة إلى سلسلة تخزين، لا العكس. عند الدخول تُجزَّأ المحاولة وتُقارن بالناتج المخزن بوقت ثابت. لكل كلمة ملح عشوائي حتى لا تتساوى النتائج لكلمة تتكرر بين المستخدمين. الخوارزمية بطيئة عن قصد أمام التخمين.

التعريف التقني

PasswordHasher في الحزمة الرسمية يستخدم scrypt من node:crypto على مجمع libuv، فلا يحجز حلقة الأحداث بحلقة JavaScript. المعاملات الافتراضية التي تذكرها صفحة التشفير وصفحة المصادقة هي توصية OWASP: N=2^17 و r=8 و p=1، نحو 128 MiB لكل تجزئة. الناتج سلسلة تصف نفسها، مثل $scrypt$ln=17,r=8,p=1$...، وفيها الملح والمعاملات.

الدوال: hash(password) و verify(password, storedHash) و needsRehash(storedHash). verify تقارن بوقت ثابت. إن مرّرت undefined لأن البريد غير مسجّل، تفحص تجزئة وهمية حتى لا يكشف زمن الاستجابة وجود الحساب. الكلمة تُطبَّع NFKC قبل التجزئة. hash يرفض الفارغ وما فوق 4 KiB بـ RangeError. قاعدة الطول الأدنى، مثل 12 في DTO التسجيل، فحصك قبل الاستدعاء.

needsRehash بعد نجاح verify يعني أن المعاملات المخزنة أضعف من الحالية. أعد hash وخزّن الناتج وأنت تملك الكلمة في طلب الدخول فقط.

الحزمة تسجّل المزوّد حين تستورد AuthenticationModule. خارجها يمكن new PasswordHasher(). في الاختبار اخفض logN إلى 10 حتى لا يستهلك كل تشغيل 128 MiB. السقف في الصفحة: حتى 1 GiB و 16 ضعف العمل الافتراضي، ومع r=8 يتوقف logN عند 20.

بدائل تذكرها الصفحة: argon2 أو bcrypt من حزمها، داخل مزوّد تكتبه. bcrypt يقرأ أول 72 بايتًا فقط. الدورة تستخدم PasswordHasher مع مسار الحزمة.

Mental Model

تسجيل: password -> hash() -> passwordHash في الصف
دخول:  password + passwordHash -> verify()
        لا يوجد عمود password
        السر المسروق من القاعدة لا يعيد الكلمة بسهولة

أبسط مثال

import { Injectable } from "@nestjs/common";
import { PasswordHasher } from "@nestjs/authentication";

@Injectable()
export class PasswordCheck {
  constructor(private readonly passwordHasher: PasswordHasher) {}

  async store(password: string) {
    return this.passwordHasher.hash(password);
  }

  async matches(password: string, storedHash: string | undefined) {
    return this.passwordHasher.verify(password, storedHash);
  }
}

شرح المثال

store لا يستقبل البريد. التجزئة سر الكلمة لا هوية الصف. matches يقبل undefined حتى يوحّد الزمن. لا تسجّل password ولا الناتج في السجل.

العمود في Prisma يبقى passwordHash. استجابة GET /users/:id تبقى على select بلا هذا الحقل، كما في مشروع REST.

ماذا يحدث داخليًا؟

scrypt يشتق مفتاحًا من الكلمة والملح بتكلفة ذاكرة. المعالج الذي يخمّن ملايين الكلمات يصطدم بالذاكرة لا بسرعة الهاش السريعة مثل SHA-256 المجرد. SHA-256 وحده غير مناسب لكلمات المرور لأنه سريع بلا تكلفة ذاكرة.

بعد verify الناجح، needsRehash يقرأ المعاملات من السلسلة. إن رفعت logN في خيار password للوحدة، الحسابات القديمة تُرقّى عند أول دخول تالٍ. لا توجد طريقة لترقيتها من غير الكلمة.

مثال عملي

تسجيل ada يخزّن الناتج في passwordHash ويرجع { id, email, name }. دخول بكلمة خاطئة يرجع رفضًا موحدًا من غير أن يقول «البريد موجود». دخول ببريد مجهول يستدعي verify على undefined ويفشل بالزمن المقارب. بعد رفع التكلفة، الدخول الصحيح يستبدل السلسلة القديمة.

اختبار يستخدم new PasswordHasher({ logN: 10 }) أو الخيار الذي يتيحه البنّاء في الاختبار، لا معاملات الإنتاج.

أخطاء شائعة

  • عمود password واضح أو مشفّر بمفتاح قابل للفك على القرص نفسه.
  • مقارنة === بين تجزئتين قد تسرّب الزمن.
  • رسالة «البريد غير موجود» مختلفة عن «كلمة خاطئة».
  • تجزئة SHA-256 بلا ملح وبتكلفة صفر.
  • تسجيل الكلمة في استثناء التحقق.

متى نستخدمه؟

لكل كلمة مرور حساب في UsersService قبل أن يُكتب الصف، وعند كل دخول.

متى لا نستخدمه؟

لسر يجب أن يعود كما هو، مثل مفتاح API يُعرض مرة عند الإنشاء ثم يُخزَّن ناتج بحثه فقط بطريقة أخرى، أو لتشفير نسخة احتياطية قابلة للاسترجاع. التجزئة لا تُفك.

مقارنة

تجزئة تشفير
لا تُعكس بالمفتاح تُفك بالمفتاح
لكلمات المرور لأسرار يجب استرجاعها
PasswordHasher node:crypto كما في صفحة التشفير

تمارين

تمرين سهل

ماذا يُحفظ في الجدول بعد التسجيل؟

الحل

ناتج hash()، سلسلة scrypt تصف معاملاتها، لا كلمة المرور.

تمرين متوسط

لماذا verify مع مستخدم مجهول لا ترجع فورًا؟

الحل

حتى لا يختلف زمن «لا حساب» عن زمن «كلمة خاطئة». الصفحة تمرّر التجزئة الوهمية داخل verify عند غياب السلسلة.

تمرين متقدم

رفعت logN. متى تُستبدل السلاسل القديمة، ولماذا لا تُستبدل بمهمة ليلية من غير كلمات المرور؟

الحل

عند دخول ناجح حين needsRehash صحيح، لأن الكلمة موجودة في الطلب. من غير الكلمة لا يمكن بناء تجزئة جديدة.

أسئلة مراجعة

  • لماذا ليست SHA-256 وحدها كافية هنا؟
  • ماذا يفعل needsRehash؟
  • أين يعيش الملح؟

الخلاصة

كلمة المرور تُجزَّأ بـ PasswordHasher وتُفحص بـ verify. العمود سر أحادي الاتجاه. الرسالة والزمن لا يكشفان وجود البريد.

ماذا بعد؟

Sessions و Access Token و Refresh Token كيف يتذكر الخادم الشخص بعد أول نجاح.
