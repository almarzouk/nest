# Redis

## الهدف من هذا الدرس

نقل المخبأ من ذاكرة العملية إلى Redis حتى تشترك نسخ Nest في مفاتيح ISBN.

## المشكلة التي يحلها

بعد تشغيل نسختين خلف موازن، كل واحدة تخزّن `isbn:978...` وحدها. تصحيح عبر `del` على العقدة التي خدمت لوحة الإدارة لا يفرغ العقدة الثانية. الزائر يتنقل بين عنوانين حتى تنتهي المدد. Redis مخزن واحد ترى الجميع فيه المفتاح نفسه.

## الفكرة ببساطة

`cache-manager` يتحدث إلى مخازن عبر Keyv. التوثيق الحالي لـ Redis يستعمل `@keyv/redis` و `createKeyv`. تسجّل المخزن داخل `CacheModule.registerAsync`. الدوال `get` و `set` و `del` في `IsbnService` تبقى كما هي.

لا تستخدم حزمة `cache-manager-redis-store` القديمة كمسار هذا الدرس.

## التعريف التقني

```bash
npm i @keyv/redis
```

```ts
import { CacheModule } from '@nestjs/cache-manager';
import { createKeyv } from '@keyv/redis';

CacheModule.registerAsync({
  useFactory: () => ({
    stores: [createKeyv('redis://localhost:6379')],
  }),
});
```

العنوان من الإعداد في التطبيق الحقيقي:

```ts
useFactory: (config: ConfigService) => ({
  stores: [createKeyv(config.getOrThrow<string>('REDIS_URL'))],
}),
inject: [ConfigService],
```

`ttl` على `set` يبقى بالميلي ثانية. إن وُجد متجر ذاكرة ومتجر Redis معًا، الصفحة تصف مصفوفة `stores` حيث الأول افتراضي والبقية احتياط. لمخبأ مشترك بين النسخ ابدأ بمتجر Redis واحد حتى لا تظن أن الكتابة وصلت الجميع وهي في ذاكرة العقدة فقط.

Redis هنا مخزن مفاتيح تنتهي، لا قاعدة كتب. فقدان المفتاح يعيد الحساب من الناشر.

## Mental Model

```text
نسخة أ  \
         Redis  isbn:978 -> { title } حتى TTL
نسخة ب  /
```

`del` من أي نسخة يزيل المفتاح للجميع.

## أبسط مثال

`IsbnService` بلا تغيير توقيع:

```ts
await this.cache.set(key, fresh, isbnTitleTtlMs);
```

الفرق في الوحدة: `stores` تشير إلى Redis بدل الذاكرة. اختبار الوحدة ما زال يحقن مديرًا وهميًا ولا يفتح Redis.

## شرح المثال

الخدمة لا تستورد `ioredis` ولا تعرف المنفذ. إن غيّرت العنوان في `REDIS_URL` يتغير المصنع عند الإقلاع. `lookup` تبقى: `get`، ثم الناشر، ثم `set`، وبلا `set` عند الرمي.

## ماذا يحدث داخليًا؟

`createKeyv` يفتح عميلًا نحو Redis. `set` يكتب مفتاحًا بأمر انتهاء يوافق المدة. النسخة الثانية على `get` تقرأ القيمة نفسها. إن تعطل Redis، فشل `get` أو `set` استثناء جديد على مسار البطاقة. قرر: إما تعتبر المخبأ اختياريًا وتلتقط الخطأ ثم تنادي الناشر، أو تفشل الطلب لأن البنية التحتية للمخبأ جزء من جاهزية القراءة. للمتجر، فشل المخبأ يجب ألا يحوّل ISBN إلى `500` إن كان الناشر متاحًا. التقط خطأ المخزن واحسب من المصدر. لا تلتقط `GatewayTimeoutException` في ذلك الفرع عن طريق جملة `catch` واسعة.

```ts
let cached: { title: string } | null | undefined;
try {
  cached = await this.cache.get(key);
} catch {
  cached = undefined;
}
```

هذا الالتقاط لخطأ المخزن فقط، بعد أن تميّزه إن كانت المكتبة ترمي نوعًا خاصًا. جملة `catch` عريضة حول `lookup` كله تبتلع أخطاء الناشر. أبقِها حول `get` و `set`.

## مثال عملي

تطوير بلا Redis يبقى `CacheModule.register({ ttl })` في الذاكرة. إنتاج يبدّل المصنع إلى `createKeyv`. الاختبارات لا تتصل بـ `localhost:6379`. إن أردت اختبار تكامل فخادم Redis منفصل أو حاوية، لا قاعدة الإنتاج.

المفتاح ما زال `isbn:${isbn}` بلا بيانات مستخدم. مشاركة Redis لا تغيّر قاعدة «المفتاح يحدد من يرى القيمة».

## أخطاء شائعة

- الاعتقاد أن Redis يصحح TTL الخاطئة. هو يشاركها فقط.
- `cache-manager-redis-store` من مقال قديم.
- `catch` حول `lookup` كاملًا عند معالجة سقوط Redis.
- وضع أسرار الناشر قيمًا في Redis بلا حاجة. القيمة `{ title }` أو `null`.

## متى نستخدمه؟

عندما يعمل أكثر من نسخة Nest وتريد إصابة مشتركة وحذفًا يراه الجميع.

## متى لا نستخدمه؟

لنسخة واحدة في تمرين محلي. الذاكرة أوضح. ولا كبديل عن Postgres لجدول `Book`.

## مقارنة

| المخزن | النسخ المتعددة | بعد إعادة التشغيل |
| --- | --- | --- |
| ذاكرة العملية | كل عقدة مستقلة | فارغ |
| Redis | مفتاح مشترك | يبقى حتى TTL إن كانت Redis نفسها تعمل |

`createKeyv`.

</details>

### تمرين متوسط

لماذا لا يتغير كود `set` عند تبديل الذاكرة بـ Redis؟

<details>

</details>

### تمرين متقدم

لماذا لا تلتقط كل الأخطاء حول `lookup` عندما يسقط Redis؟

<details>
<summary>الحل</summary>

لأن المهلة و `502` من الناشر يجب أن يصلا إلى الزائر أو إلى سياسة الإثراء. التقط فشل `get` و `set` فقط ثم احسب من المصدر.

</details>

## أسئلة مراجعة

- ماذا يوحّد Redis بين العقد؟
- أي حزمة لا تُنسخ من المقالات القديمة؟
- هل تُخزَّن أسرار الناشر؟

## الخلاصة

Redis عبر `createKeyv` يجعل مفتاح ISBN مشتركًا بين النسخ. الخدمة تبقى على `get` و `set`. سقوط المخزن لا يبتلع خطأ الناشر.

## ماذا بعد؟

ما الذي يتحول إلى خطر إن دخل المخزن: صلاحية المستخدم، والأخطاء.
