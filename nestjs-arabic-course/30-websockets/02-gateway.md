# Gateway

## الهدف من هذا الدرس

معرفة البوابة كصنف مزوّد يستقبل رسائل المقبس، مقابل المتحكم الذي يستقبل HTTP.

## المشكلة التي يحلها

وضع منطق التعليق داخل `CommentsController` ثم مناداة `socket.emit` من المتحكم يخلط بابين. طلب `POST` يحفظ الصف. المقبس ينضم إلى غرفة ويبث. البوابة هي باب المقبس: حقن خدمات، ورسائل بأسماء، ودورة حياة اتصال لا توجد على `@Get`.

## الفكرة ببساطة

البوابة صنف عليه `@WebSocketGateway()` ويُذكر في `providers`. ليست في `controllers`. دوالها تعالج رسائل لا مسارات. الخدمة نفسها التي يحفظ بها المتحكم التعليق يمكن حقنها هنا للبث بعد الحفظ، أو يحفظ المتحكم وتكتفي البوابة بالإعلام. الحد: لا SQL منسوخ داخل الدالة المزينة.

## التعريف التقني

من صفحة البوابات: البوابة صنف مزود بالزينة، والأفكار من بقية Nest — حقن، ومرشحات، وأنابيب، وحراس — تسري عليها حيث أمكن. المنصات الجاهزة Socket.IO و `ws`. الافتراض في التطبيق المعتاد Socket.IO، ودرسه لاحقًا.

البوابة تسمع على منفذ HTTP نفسه ما لم تغيّر المنفذ. `@WebSocketGateway(3001)` يفصل المنفذ. فضاء الاسم خيار في كائن الزينة، مثل `{ namespace: 'comments' }`، حتى لا تختلط أحداث التعليقات بأحداث أخرى على المقبس نفسه.

الصنف singleton كالمزوّد العادي. حالة «من في الغرفة» إن حفظتها في `Map` على الصنف فهي حالة العملية. لا تضع تعليق المستخدم الحالي في خاصية واحدة تتبدل مع كل رسالة.

## Mental Model

```text
CommentsController   POST يحفظ ثم يعيد JSON
CommentsGateway      رسالة join / comment على المقبس
CommentsService      القاعدة لكليهما إن لزم
```

## أبسط مثال

تسجيل بلا رسالة بعد:

```ts
import { WebSocketGateway } from '@nestjs/websockets';

@WebSocketGateway({ namespace: 'comments' })
export class CommentsGateway {}
```

```ts
import { Module } from '@nestjs/common';
import { CommentsGateway } from './comments.gateway.js';

@Module({
  providers: [CommentsGateway],
})
export class CommentsModule {}
```

الوحدة مستوردة من الجذر. بوابة غير مذكورة في `providers` لا تُنشأ ولا تسمع.

## شرح المثال

`namespace: 'comments'` يفصل عنوان المقبس عن بوابة ثانية قد تخدم التنبيهات. العميل يتصل بفضاء الاسم هذا لا بالجذر فقط. الصنف الفارغ يثبت التسجيل. الرسائل في `@SubscribeMessage` لاحقًا. إبقاء الصنف في `controllers` لا يركّب البوابة.

## ماذا يحدث داخليًا؟

عند الإقلاع تقرأ Nest الزينة وتبني مقبس الخادم عبر المحول، Socket.IO ما لم تبدّل المحول. كل اتصال جديد كائن عميل تمرره الخطافات لاحقًا. الدوال التي ستزينها تُربط بأسماء الرسائل. الحقن يعمل: تستطيع استلام `CommentsService` في الباني إن كانت مسجّلة في الوحدة نفسها أو مصدّرة إليها. البوابة لا تمر بسلسلة `POST` الخاصة بالمتحكم. حارس HTTP على المتحكم لا يحمي الرسالة.

## مثال عملي

حد المتجر:

| العمل | الباب |
| --- | --- |
| `POST /books/:id/comments` | المتحكم يحفظ ويعيد التعليق |
| الانضمام إلى صفحة الكتاب | البوابة |
| إعلام الموجودين في الصفحة | البوابة بعد أن نجح الحفظ |

المتحكم يمكنه حقن البوابة واستدعاء دالة `broadcast` عامة تكتبها أنت. البوابة لا تستقبل `@Body()` الخاص بـ HTTP. إن حقنت المتحكم في البوابة والبوابة في المتحكم صنعت دورة. اجعل البث دالة على البوابة ويستدعيها المتحكم، أو انشر حدثًا داخليًا لاحقًا في فصل الأحداث. للدورة هنا: المتحكم يحفظ، ثم يستدعي البوابة.

## أخطاء شائعة

- تسجيل البوابة في `controllers`.
- نسخ استعلام Prisma داخل البوابة لأن «أسرع».
- `Map` على البوابة يحمل نص التعليق الأخير لكل المستخدمين.
- نسيان استيراد الوحدة من الجذر.

## متى نستخدمه؟

عندما تصل رسالة من مقبس وتريد خدمات Nest معك: تعليق حي، إشعار، لوحة داخلية.

## متى لا نستخدمه؟

لعملية لها مسار HTTP واضح بلا مستمعين. `POST` يكفي. ولا تستبدل بوابة GraphQL subscription إن كان العقد حقلًا في المخطط والعميل GraphQL فقط.

## مقارنة

| | المتحكم | البوابة |
| --- | --- | --- |
| الزينة | `@Controller` | `@WebSocketGateway` |
| التسجيل | `controllers` | `providers` |
| المدخل | مسار وMethod | رسالة على مقبس |
| العمر | الطلب | الاتصال |

## أسئلة مراجعة

- ما فضاء الاسم في المثال؟
- لماذا البوابة singleton تمنع تخزين «التعليق الحالي» في حقل واحد؟
- أي فصل سبق وشرح قناة داخل المخطط بدل البوابة؟

## الخلاصة

البوابة مزوّد لرسائل المقبس. المتحكم يبقى باب HTTP. الخدمة أو دالة بث واحدة تجمع الحفظ بالإعلام بلا دورة حقن.

## ماذا بعد؟

شكل الزينة `@WebSocketGateway` والمنفذ وCORS قبل أول `@SubscribeMessage`.
