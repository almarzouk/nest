@MessagePattern و @EventPattern

الهدف من هذا الدرس

ربط دالة متحكم بنمط طلب-رد أو بنمط حدث، ومعرفة أن الإطار يتجاهل الزخرفة خارج المتحكم.

المشكلة التي يحلها

العميل يرسل { cmd: 'sum' } والعملية الأخرى لا تعرف أي دالة تقصد. النمط مفتاح التوجيه. @MessagePattern للنداء الذي يرجع ناتجًا. @EventPattern للإشعار. وضعهما على خدمة بلا @Controller لا يسجل مستمعًا.

الفكرة ببساطة

النمط سلسلة أو كائن يُسلسل مع الحمولة. المعالج دالة على متحكم. الحمولة أول معامل أو @Payload(). يمكن async. يمكن إرجاع Observable في الطلب-الرد فيُرسل أكثر من قيمة حتى الاكتمال. الحدث لا يبني ردًا للناشر.

التعريف التقني

import { Controller } from '@nestjs/common';
import { EventPattern, MessagePattern, Payload } from '@nestjs/microservices';

@Controller()
export class MathController {
  @MessagePattern({ cmd: 'sum' })
  sum(@Payload() data: number[]): number {
    return (data || []).reduce((a, b) => a + b, 0);
  }

  @EventPattern('order.cancelled')
  cancelled(@Payload() data: { orderId: string }): void {
    void data.orderId;
  }
}

نمط الكائن { cmd: 'sum' } يجب أن يطابق ما يرسله client.send. نمط السلسلة يطابق emit('order.cancelled', payload).

@Ctx() يعطي سياق الناقل عندما تحتاج قناة الرد الأصلية أو إقرار الرسالة، حسب الناقل. لا تمرره إلى الخدمة.

Pipe على @Payload() يتحقق من الشكل قبل الدالة. فشل الشكل خطأ يعبر للعميل عبر RpcException إن حوّلته، لا صفحة HTML.

الاستثناء من الدالة: ارمِ RpcException من @nestjs/microservices برسالة أو كائن صغير. HttpException تبقى لمدخل HTTP في التطبيق الهجين.

Mental Model

نمط مطابق -> دالة المتحكم -> خدمة
MessagePattern -> ناتج للعميل
EventPattern  -> معالجة محلية بلا رد العقد

أبسط مثال

sum أعلاه. العميل send({ cmd: 'sum' }, [1, 2]) يحصل على 3 بعد الاشتراك. غيّر المفتاح إلى sum نصًا من غير أن تغيّر العميل فلن يصل النداء إلى الدالة.

شرح المثال

المفتاح جزء من العقد مثل POST /sum. كائن cmd يسمح بحقول إضافية للتمييز إن اتفق الفريق، وسلسلة واحدة أبسط للأحداث. ثبّت الأسلوب في الخدمة: أوامر بكائن وأحداث بسلسلة، واكتب ذلك في مكان واحد.

ماذا يحدث داخليًا؟

  1. عند الإقلاع تُجمع الزخارف من المتحكمات فقط.
  2. تصل رسالة فتُقارن بالنمط بعد فك التسلسل.
  3. تُستدعى الدالة بالحمولة.
  4. في الطلب-الرد يُسلسل الناتج إلى قناة الرد.
  5. في الحدث تنتهي مسؤولية الناشر عند التسليم للناقل.
  6. دالة على @Injectable فقط بلا متحكم لا تدخل الجدول.

مثال عملي

@MessagePattern({ cmd: 'invoice.issue' }) تستدعي invoices.issue وترجع { invoiceId }. @EventPattern('invoice.issued') في عملية البحث تحدّث الفهرس. النمطان اسمان مختلفان حتى لا يُستهلك الإشعار كطلب رد. رمي new RpcException('order missing') عندما لا طلب. العميل يرى الخطأ على Observable الخاص بـ send.

أخطاء شائعة

  • الزخرفة على الخدمة.
  • عدم تطابق النمط بين send والمعالج حرفًا أو شكل كائن.
  • @EventPattern مع توقع return يصل للناشر.
  • نسيان @Payload() عند وجود @Ctx() فيختلط ترتيب الوسائط.
  • منطق خصم داخل المتحكم بدل الخدمة.

متى نستخدمه؟

على متحكم عملية تستمع للناقل، لكل عقد رسالة.

متى لا نستخدمه؟

لمسار HTTP. أبقِ @Get. ولا على دالة مساعدة خاصة.

تمارين

تمرين سهل

لماذا لا يعمل @MessagePattern على صنف @Injectable بلا متحكم؟

الحل

الإطار يسجل الأنماط من المتحكمات فقط ويتجاهل الزخرفة على المزودات.

تمرين متوسط

ماذا يجب أن يطابق { cmd: 'sum' }؟

الحل

النمط الذي يمرره العميل إلى send، لا اسم الدالة sum وحده.

تمرين متقدم

متى تضيف @Ctx() ومتى تبقيه خارج الخدمة؟

الحل

في المتحكم عندما يحتاج الناقل إقرارًا أو خاصية قناة. الخدمة تستقبل القيم المستخرجة فقط.

أسئلة مراجعة

  • ما شكل النمط؟
  • أي زخرفة بلا رد؟
  • أي استثناء يعبر للعميل البعيد؟

الخلاصة

النمط مفتاح على المتحكم: @MessagePattern ينتظر ناتجًا و @EventPattern يستهلك إشعارًا. طابق العميل، وارمِ RpcException للخطأ العابر.

ماذا بعد؟

ClientProxy: send و emit من العملية الأخرى.
