# Redis

## الهدف من هذا الدرس

استعمال Redis ناقلًا لرسائل Nest عبر النشر والاشتراك، وتمييز ذلك عن Redis الذاكرة المؤقتة أو طابور BullMQ.

## المشكلة التي يحلها

TCP لا يوصل عدة نسخ من نفس المستمع بنمط واحد بسهولة. Redis موجود أصلًا في كثير من مشاريع Nest للكاش. `Transport.REDIS` يمرر الرسائل عبر Pub/Sub. هذا ليس ضمان طابور أعمال ولا تخزين تيار مثل Kafka. الرسالة تُنشر لمن هو مشترك حينها. إن لم يكن المستمع متصلًا ضاع الحدث. لا تستبدل به BullMQ ولا جلسة المستخدم.

## الفكرة ببساطة

المستمع والعميل `transport: Transport.REDIS` و `options.host` و `options.port`. داخل Compose المضيف `redis` لا `localhost`. الحزمة التي يتوقعها النقل تُثبت مع `@nestjs/microservices` حسب صفحة Redis في التوثيق (`ioredis` في الإصدارات الحديثة). الأنماط نفسها `@MessagePattern` و `@EventPattern`.

## التعريف التقني

```ts
{
  transport: Transport.REDIS,
  options: {
    host: process.env.REDIS_HOST ?? '127.0.0.1',
    port: 6379,
  },
}
```

نفس الشكل في `createMicroservice` و `ClientsModule`. `REDIS_HOST=redis` في شبكة Compose.

الطلب-الرد ممكن على هذا النقل لأن Nest يوفّر مسار رد فوق Pub/Sub حيث يلزم، بتكلفة أوضح من NATS. للأحداث الخفيفة بين النسخ الحدث أصدق.

لا تشارك اتصال الكاش واتصال الناقل في خيار واحد مشوش إن كان الكاش حساسًا للزمن. قاعدة Redis واحدة مقبولة في التطوير. في الإنتاج راقب الذاكرة لأن Pub/Sub لا يُخزن لك إعادة المعالجة.

BullMQ من فصل الطوابير وظيفة مختلفة: مهمة تُعاد ولها محاولات. لا تضع `@EventPattern` مكان `Processor` إن كنت تحتاج إعادة محاولة ومتأخرات.

كلمة المرور و `tls` في `options` عندما لا تكون الشبكة خاصة. لا تنشر Redis على الإنترنت بلا حماية.

## Mental Model

```text
ناشر -> Redis Pub/Sub -> كل مشترك حاضر
الغائب لا يستلم لاحقًا
ليس طابور BullMQ وليس كاش المفاتيح
```

## أبسط مثال

خدمتا فوترة تشتركان على نفس النمط الحدثي. `emit('invoice.issued', { invoiceId })` من الكتالوج. كل نسخة حاضرة تتلقى الحدث. إن كانت المعالجة يجب أن تتم مرة واحدة فهذا النمط خاطئ لـ Redis Pub/Sub التقليدي لأنه يبث. للعمل مرة واحدة استعمل طابورًا (BullMQ أو RabbitMQ) لا بثًا.

## شرح المثال

البث مفيد لإبطال كاش محلي في كل نسخة: كل نسخة تحذف مفتاحًا في ذاكرتها. ضار لإرسال بريد: كل نسخة ترسل رسالة. اختر النمط حسب «مرة لكل نسخة» أو «مرة في العنقود».

## ماذا يحدث داخليًا؟

1. العميل يتصل بـ Redis.
2. `emit` ينشر على قناة يشتقها الإطار من النمط.
3. المستمعون المشتركون يستلمون.
4. من اتصل بعد النشر لا يرى الرسالة القديمة.
5. `send` يستخدم مسار الرد الذي يبنيه Nest فوق Redis.
6. انقطاع Redis يفشل الطرفين معًا، وهو حد مشترك جديد لم يكن في TCP المباشر فقط بل في الوسيط.

## مثال عملي

إبطال ذاكرة عناوين الكتب في كل نسخة كتالوج عند `book.updated`. الحدث Redis. إصدار الفاتورة يبقى طلب-رد على NATS أو TCP نحو عملية واحدة، أو طابور إن وجب التخزين. لا تجعل Redis الناقل الوحيد لكل شيء لأنه يعمل في التطوير.

## أخطاء شائعة

- توقع إعادة المحاولة كـ BullMQ.
- بث يرسل بريدًا مكررًا.
- `localhost` من حاوية التطبيق.
- استعمال نفس مفتاح الكاش كحمولة رسالة ضخمة.
- خلط `Transport.REDIS` مع `CacheModule` كأنهما إعداد واحد بلا قصد.

## متى نستخدمه؟

بث خفيف لمن هو متصل، خصوصًا إبطال حالة محلية بين نسخ، و Redis أصلًا لديك.

## متى لا نستخدمه؟

مهمة يجب أن تُنفذ مرة وتُعاد عند الفشل. استعمل طابورًا. ولا كبديل Kafka لسجل دائم.

## مقارنة

| الدور | الأداة |
| --- | --- |
| بث رسائل Nest | `Transport.REDIS` |
| كاش مفاتيح | CacheModule |
| مهمة مع إعادة محاولة | BullMQ |
| سجل دائم | Kafka |

## أسئلة مراجعة

- ماذا يبث Redis هنا؟
- بماذا لا يُستبدل BullMQ؟
- أين يُضبط المضيف؟

## الخلاصة

`Transport.REDIS` ناقل بث خفيف فوق وسيط تعرفه، لا طابور مهام ولا كاش. استعمله عندما يجب أن تسمع كل نسخة حاضرة، وانقل العمل الذي يُنفذ مرة واحدة إلى طابور.

## ماذا بعد؟

RabbitMQ: طابور يبقى فيه العمل حتى يعالجه مستهلك.
