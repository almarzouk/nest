# RabbitMQ

## الهدف من هذا الدرس

وضع العمل في طابور RabbitMQ عبر `Transport.RMQ` حتى ينتظر المستهلك، مع طابور دائم واسم يُعرَّف في الخيارات.

## المشكلة التي يحلها

Redis Pub/Sub يضيع الرسالة إن غاب المستمع. فاتورة يجب أن تُصدر بعد عودة العملية تحتاج وسيطًا يخزن. RabbitMQ طابور: الرسالة تبقى حتى يستهلكها عامل ويقرّها، أو تُعاد حسب إعداد الطابور. Nest يصل إليه بـ `Transport.RMQ` وحزمة `amqplib`.

## الفكرة ببساطة

المستمع والعميل يشيران إلى `urls` مثل `amqp://guest:guest@rabbitmq:5672` واسم `queue`. داخل Compose المضيف `rabbitmq` لا `localhost`. `queueOptions.durable: true` يبقي الطابور بعد إعادة تشغيل الوسيط إن كانت الرسائل دائمة أيضًا. المعالجة في `@MessagePattern` أو `@EventPattern` على متحكم. الحدث هنا ما زال رسالة في طابور Nest، لا بث Redis.

## التعريف التقني

```ts
import { MicroserviceOptions, Transport } from '@nestjs/microservices';

const options: MicroserviceOptions = {
  transport: Transport.RMQ,
  options: {
    urls: [process.env.RABBITMQ_URL ?? 'amqp://guest:guest@127.0.0.1:5672'],
    queue: 'invoices',
    queueOptions: { durable: true },
  },
};
```

ثبّت `amqplib`. العميل في `ClientsModule.register` بنفس النقل واسم الطابور الذي يستمع إليه المعالج.

`prefetch` في خيارات المستهلك يحد كم رسالة غير مُقرَّة يأخذها العامل. ابدأ بعدد صغير حتى لا تتكدس في عملية واحدة.

الطلب-الرد مدعوم عبر أنماط Nest فوق الطابور. للأعمال التي تُعاد، فضّل حدثًا مع إقرار بعد نجاح `issue`، وسجّل الفشل لإعادة المحاولة. لا تُقر قبل الحفظ.

ضيف `guest` للتطوير فقط. في الإنتاج مستخدم وكلمة من البيئة، وشبكة خاصة.

رسالة مكررة ممكنة عند إعادة التسليم بعد انقطاع قبل الإقرار. اجعل `issue` قابلة للتكرار بمعرف طلب: الإصدار الثاني يرى الفاتورة موجودة ويعيد المعرف نفسه.

## Mental Model

```text
ناشر -> طابور invoices الدائم -> مستهلك واحد من مجموعة العمال
إقرار بعد الحفظ
إعادة التسليم عند العطل قبل الإقرار
```

## أبسط مثال

```ts
@EventPattern('invoice.issue')
async issue(@Payload() data: { orderId: string }): Promise<void> {
  await this.invoices.issue(data.orderId);
}
```

العميل `emit('invoice.issue', { orderId })`. أوقف عملية الفوترة ثم أعدها: الرسالة ما زالت في الطابور إن كانت دائمة ولم تُقر. هذا الفرق العملي عن TCP و Redis.

## شرح المثال

النمط اسم التوجيه الذي يربط Nest بالطابور الذي ضبطته في `options.queue`. طابور لكل سياق عمل أوضح من طابور واحد لكل الأنماط إن اختلفت سرعة الإصدار عن سرعة البريد. ابدأ بطابور `invoices` واحد حتى تتضح الحدود.

## ماذا يحدث داخليًا؟

1. `amqplib` يتصل بـ `urls`.
2. يُعلن الطابور حسب `queueOptions`.
3. `emit` ينشر الرسالة.
4. مستهلك Nest يسلمها للمعالج.
5. النجاح يقر الرسالة فتُزال.
6. قتل العملية قبل الإقرار يعيد الرسالة لعامل حي.

## مثال عملي

`RABBITMQ_URL=amqp://app:secret@rabbitmq:5672` في Compose. الكتالوج ينشر إصدار الفاتورة ولا ينتظر إن كانت الواجهة لا تحتاج `invoiceId` فورًا. إن كانت تحتاجه فـ `send` مع مهلة، مع علم أن انقطاع المستهلك يؤخر الرد بينما الرسالة قد تُعاد. لا تبنِ الرد على أمل أن الإقرار يعني أن البريد وصل. البريد معالج لاحق أو طابور ثانٍ.

## أخطاء شائعة

- `localhost` من حاوية.
- إقرار قبل `save`.
- `durable` على الطابور ورسائل غير دائمة فتختفي بعد إعادة تشغيل الوسيط.
- معالجة غير قابلة للتكرار مع إعادة التسليم.
- حساب `guest` في الإنتاج.

## متى نستخدمه؟

عمل يُخزن ويُوزع على عمال، مع إعادة تسليم عند العطل، ووسيط تشغّله.

## متى لا نستخدمه؟

بث لكل النسخ الحاضرة. ذلك Redis. وسجل مرتب طويل الأمد للتحليل. ذلك Kafka. ونداء داخل العملية. دالة.

## مقارنة

| | RabbitMQ هنا | Redis Pub/Sub | TCP |
| --- | --- | --- | --- |
| التخزين | طابور | لا | لا |
| الغائب | يستلم لاحقًا | يضيع | يفشل فورًا |
| التكرار | ممكن عند إعادة التسليم | بث مكرر | لا |

## الخلاصة

RabbitMQ مع `Transport.RMQ` طابور يبقى فيه العمل حتى يُقر بعد النجاح. اجعل المعالجة قابلة للتكرار، ولا تستعمل `localhost` بين الحاويات، ولا تقر قبل الحفظ.
