Monolith

الهدف من هذا الدرس

تسمية ما تبنيه الآن: تطبيق واحد في عملية نشر واحدة، فيه كل السياقات، قبل الحديث عن عملية ثانية.

المشكلة التي يحلها

تسمية «خدمة» لكل وحدة Nest تدفع فريقًا صغيرًا إلى مستودعات وحاويات متعددة بينما الفشل ما زال مشتركًا في قاعدة واحدة. الـ Monolith هنا عملية Node واحدة تشغّل NestFactory.create وتفتح HTTP. كل الميزات في هذا البناء. النشر نسخة واحدة. هذا ليس عيبًا. هو شكل التوثيق عندما لا تختار نقلًا آخر، وشكل هذه الدورة حتى يثبت حد الفشل.

الفكرة ببساطة

مستودع واحد، أمر تشغيل واحد، قاعدة واحدة غالبًا، وحد وحدات داخل العملية. مستخدم واحد يرى API واحدًا. فريق واحد ينشر الكل معًا. التعطل يعطل المسارات معًا، والتتبع داخل عملية أسهل من تتبع رسالة بين خمس خدمات.

التعريف التقني

main.ts يستدعي NestFactory.create(AppModule) ثم listen. لا createMicroservice بعد. AppModule يستورد وحدات الكتالوج والفوترة. التواصل دالة وحقن لا شبكة. EventBus من CQRS إن وُجد يبقى داخل العملية.

النشر: صورة واحدة أو عملية node dist/main.js واحدة. التوسيع الأفقي لاحقًا يعني عدة نسخ من هذا الـ Monolith خلف موزع، لا استخراج فوترة في مستودع آخر. النسخ المتعددة تحتاج جلسة خارج الذاكرة إن كانت الحالة على العملية، وذلك في فصل الإنتاج.

حد هذا الشكل: دورة إصدار الفوترة تنتظر الكتالوج، وعطل بحث ثقيل يزاحم حلقة الأحداث لكل المسارات. هذه كلفة مقبولة حتى يبررها قياس أو فريقان يتعارضان على النشر.

Nest يسمي التطبيق التقليدي monolithic في مدخل الخدمات الصغيرة، ثم يبني النقل كطبقة أخرى. لا تحوّل التسمية إلى خطة تقسيم.

أبسط مثال

import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module.js';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  app.enableShutdownHooks();
  await app.listen(process.env.PORT ?? 3000);
}
await bootstrap();

AppModule يستورد الميزتين. إلغاء الطلب دالة داخلية لا @MessagePattern.

شرح المثال

عملية واحدة تستمع على منفذ. الإيقاف الذي بنيته في دورة الحياة يغلق هذه العملية. لا ناقل تعرّف عليه المنسّق. هذا ملف إنتاج الـ Monolith حتى فصل Docker.

ماذا يحدث داخليًا؟

  1. بناء واحد يحمّل كل الوحدات الساخنة.
  2. طلب HTTP يبقى في العملية.
  3. قاعدة البيانات اتصال مشترك من PrismaService.
  4. نشر نسخة جديدة يبدّل كل المسارات معًا.
  5. سجل الأخطاء في مكان واحد.
  6. لا ClientProxy ولا تسلسل رسالة.

مثال عملي

متجر الفريق الصغير يبقى هذا الملف. قياس بطء البحث يُعالج بفهرس أو قارئ، لا بخدمة شبكة. عندما تنشر الفوترة أسبوعيًا والكتالوج يوميًا ويتوقف أحدهما عن الآخر، اكتب الحد الذي تريد استقلاله. حتى ذلك الحين الـ Monolith هو المنتج.

أخطاء شائعة

  • مستودع Git لكل وحدة مع عملية واحدة.
  • تسمية الوحدة Microservice في التعليقات.
  • مشاركة قاعدة بلا حدود وحدات ثم لوم الـ Monolith.
  • تقسيم مبكر ثم استدعاءات HTTP دائرية.
  • تجاهل enableShutdownHooks لأن الشكل «بسيط».

متى نستخدمه؟

طوال ما كان النشر والفشل والفريق على إيقاع واحد.

متى لا نستخدمه؟

عندما تحتاج جزءًا أن يسقط أو يُنشر من غير إيقاف الباقي، وحد السياق جاهز من فصل المعمارية. عندها تدرس الخدمة الصغيرة لا قبل ذلك.

الخلاصة

الـ Monolith عملية ونشر واحد لكل السياقات، والنداء داخلي. أبقِه حتى يستقل الإيقاع أو الفشل، وحسّن الحدود داخله أولًا.

ماذا بعد؟

Modular monolith: نفس العملية مع وحدات صارمة كتحضير لأي فصل لاحق.
