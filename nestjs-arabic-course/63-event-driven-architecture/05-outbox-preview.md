# لمحة عن Transactional Outbox

## الهدف من هذا الدرس

رؤية الفجوة بين «التزم الكتاب» و«أُرسلت الرسالة»، وكيف يقرّب صندوق الصادر الإرسال من نفس معاملة الكتابة، قبل تفصيل النمط في فصل الاعتمادية.

## المشكلة التي يحلها

`markPublished` التزمت ثم قُتلت العملية قبل `queue.add`. الكتاب منشور ولا رسالة `book.published`. الفهرس والشريك لا يلحقان أبدًا. العكس أسوأ: أرسلتم الرسالة ثم تراجعت المعاملة فيعمل الشريك على كتاب غير منشور.

## الفكرة ببساطة

في نفس معاملة `UPDATE` أدرجوا صفًا في جدول `outbox` فيه حدث التكامل. عامل منفصل يقرأ الصفوف غير المرسلة ويدفعها إلى الناقل ثم يعلّمها. إن سقطت العملية بعد الالتزام فالصف ما زال هناك ويُرسل لاحقًا. إن تراجعت المعاملة فلا صف ولا رسالة.

## التعريف التقني

هذه لمحة لا تنفيذ `@nestjs` جاهز باسم Outbox في قلب الإطار. الصفحة الرسمية للنمط في فصل Reliability: https://docs.nestjs.com/reliability/outbox. هنا يكفي الشكل: الجدول أعمدة `id`, `type`, `payload`, `createdAt`, `sentAt`. الإدخال مع نشر الكتاب في `prisma.$transaction`. الناشر يعلّم `sentAt` بعد ما يقبل الوسيط الرسالة. المستهلك ما زال يحتاج معرّف تكرار لأن العلامة قد تفشل بعد الإرسال فيُعاد الإرسال. لا تبنوا العامل الكامل في هذا الدرس.

## Mental Model

```text
BEGIN
  UPDATE books
  INSERT outbox
COMMIT
عملية أخرى تقرأ outbox حيث sentAt فارغ
```

## أبسط مثال

```ts
export interface OutboxRow {
  id: string;
  type: 'book.published';
  payload: { bookId: string; organizationId: string };
  sentAt: Date | null;
}
```

## شرح المثال

- `payload` حدث تكامل لا صنف Prisma.
- `sentAt` الفارغ يعني «لم يُسلَّم للوسيط بعد» لا «الشريك لم يعالج».
- `id` هو معرّف الحدث الذي يراه المستهلك.

## ماذا يحدث داخليًا؟

1. معاملة واحدة تكتب الكتاب والصف.
2. الرد للموظف يمكن أن يعود بعد الالتزام، والرسالة قد تتأخر حتى يمر العامل. هذا ما زال اتساقًا مؤجَّلًا للإسقاط، لكنه لا يضيع.
3. العامل يرسل ثم يحدّث `sentAt`.
4. إن أُرسلت الرسالة وسقط التحديث، الإرسال يتكرر والمعرّف يحمي المستهلك.
5. لا `emit` ذاكري بديل عن الصف إن كان الضياع ممنوعًا.

## مثال عملي

```ts
await prisma.$transaction(async (tx) => {
  await tx.book.update({
    where: { id: bookId, organizationId },
    data: { status: 'published' },
  });
  await tx.outbox.create({
    data: {
      id: eventId,
      type: 'book.published',
      payload: { bookId, organizationId },
    },
  });
});
```

العامل ليس في المقطع. وجود الصف بعد الالتزام هو الوعد. فصل الاعتمادية يفصل القفل والقراءة. هنا لا تنسوا قيد المستأجر على `update`.

## أخطاء شائعة

- إدراج الصندوق بعد المعاملة في نافذة أخرى للضياع.
- اعتبار `sentAt` إثبات أن الشريك أنهى المخزون.
- حمولة الصندوق كائن نطاق يتغير شكله.
- بناء ناشر يعيد الكتاب مسودة عند فشل الشريك.

## متى نستخدمه؟

عندما رسالة التكامل يجب أن تُخلق إن وفقط إن التزمت الكتابة، وتتحملون تأخر التسليم لا ضياعه.

## متى لا نستخدمه؟

لمستمع ذاكرة يجوز أن يضيع، أو لأثر داخل نفس المعاملة أصلًا (التدقيق). لا تضيفوا صندوقًا قبل أن يوجد ناقل خارجي فعلًا.

## مقارنة

| الترتيب | الخطر |
| --- | --- |
| إرسال ثم معاملة | رسالة بلا حقيقة |
| معاملة ثم إرسال في الذاكرة | حقيقة بلا رسالة |
| معاملة فيها صف صادر | الحقيقة والرسالة تُخلقان معًا، والتسليم لاحق |

## تمارين

### تمرين سهل

قُتلت العملية بعد `COMMIT` وقبل العامل. هل يضيع الحدث؟

<details>
<summary>الحل</summary>

لا. صف `outbox` بلا `sentAt` سيقرأه العامل بعد الإقلاع.

</details>

### تمرين متوسط

لماذا قد تُرسل الرسالة مرتين رغم الصندوق؟

<details>
<summary>الحل</summary>

لأن الوسيط قد يستلم قبل تعليم `sentAt`. المستهلك يطبّق قيد `id`. الصندوق يقلل الضياع ولا يلغي التكرار.

</details>

### تمرين متقدم

التدقيق والبريد ورسالة الشريك. ماذا يدخل المعاملة وماذا يدخل الصندوق؟

<details>
<summary>الحل</summary>

حالة الكتاب وسطر التدقيق في المعاملة. حدث التكامل للشريك (والبريد إن وجب ألا يضيع) صف صندوق. مستمع ذاكرة اختياري لا يحل محل الصف.

</details>

## أسئلة مراجعة

- ماذا يُدرج مع `UPDATE`؟
- ماذا يثبت `sentAt` وماذا لا يثبت؟
- لماذا التكرار ما زال ممكنًا؟
- أين التفاصيل التشغيلية لاحقًا؟

## الخلاصة

صندوق الصادر صف حدث تكامل في معاملة الحقيقة. العامل يسلّم لاحقًا. هذا يمنع «نُشر بلا رسالة» و«رسالة بلا نشر». التعليم بعد الإرسال قد يكرر، والمعرّف عند المستهلك يبقى لازمًا.

## ماذا بعد؟

الفجوة بين الكتابة والإسقاط تحتاج أن تُرى في التشغيل: سجلات ومقاييس وأثر. الفصل التالي المراقبة.
