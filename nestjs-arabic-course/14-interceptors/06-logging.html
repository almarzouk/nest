Logging

الهدف من هذا الدرس

تسجيل مرور الطلب على المعالج: الطريقة والمسار والمدة، من غير تغيير جسم الرد.

المشكلة التي يحلها

console.log داخل كل دالة تذاكر ينسى مسارًا جديدًا ويخلط نص السجل بشكل JSON. القياس داخل Middleware لا يرى لحظة الرجوع من الخدمة.

الفكرة ببساطة

معترض واحد على متحكم التذاكر. قبل handle يحفظ الساعة والطريقة والمسار. tap بعد النجاح تطبع المدة. الجسم الراجع يمر كما هو لأن tap لا تستبدله.

التعريف التقني

الصفحة تعرض LoggingInterceptor بهذا النمط: console.log('Before...') ثم next.handle().pipe(tap(() => ...)). نطبّقه على الشباك بحقول أوضح.

tap لا تُستدعى عند الخطأ. للمدة في الحالتين أضف finalize من rxjs. هذا الدرس يطبع النجاح بـ tap ويسجّل الفشل بـ tap ذات المعالجين حتى ترى الشكلين من عامل واحد.

لا تسجّل جسم الحجز كاملًا إن فيه بيانات شخصية. المسار والمدة واسم الدالة تكفي هنا. context.getHandler().name يعطي اسم الدالة.

المسجل الذي يُحقن من حاوية لاحقًا يستبدل console.log. الواجهة نفسها. الربط على الصنف لا على التطبيق حتى لا تمتلئ صحة GET /health بسطور التذاكر.

Mental Model

دخول: method + url + started
نجاح: tap next  → سطر بالمدة
فشل:  tap error → سطر بالفشل
الجسم إلى العميل لم يتغير

أبسط مثال

import {
  type CallHandler,
  type ExecutionContext,
  Injectable,
  type NestInterceptor,
} from '@nestjs/common';
import { type Observable } from 'rxjs';
import { tap } from 'rxjs/operators';

@Injectable()
export class TicketLogInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<unknown> {
    const http = context.switchToHttp();
    const request = http.getRequest<{ method: string; url: string }>();
    const started = Date.now();
    const label = `${request.method} ${request.url}`;
    return next.handle().pipe(
      tap({
        next: () => console.log(`${label} ${Date.now() - started}ms`),
        error: () => console.log(`${label} failed ${Date.now() - started}ms`),
      }),
    );
  }
}

شرح المثال

  • label يُغلق عليه من الدخول.
  • tap بالكائن تفرّق النجاح عن الخطأ. القيمة لا تُستبدل في أي فرع.
  • لا map. عقد الرد يبقى عقد الدالة.
  • failed لا يبتلع الخطأ. بعد tap يكمل الخطأ إلى الفلتر. هذا مهم: التسجيل ليس catchError يرجع of.

ماذا يحدث داخليًا؟

الاشتراك يشغّل السلسلة. عند الإصدار يمر العامل next في tap ثم تكمل القيمة إلى Nest لتُكتب JSON. عند الخطأ يمر فرع error ثم يستمر الخطأ ما لم تُرجع تيارًا بديلًا. tap لا ترجع تيارًا بديلًا، فهي آمنة للسجل.

المدة تشمل ما لفّه هذا المعترض: أنابيب أقرب إلى الدالة، والمتحكم، والخدمة، ومعترضات داخلية على طريق الخروج قبل هذا العامل. ليست مدة SQL وحدها. الصفحة تذكر أن هذا القياس المصغّر يشبه ما تفعله أدوات المراقبة، من غير أن تستبدلها.

حارس رفض الطلب قبل المعترض: لا سطر. هذا متوقع. السجل هنا لمن عبر البوابة.

مثال عملي

TicketsController عليه @UseInterceptors(TicketLogInterceptor). POST /tickets الناجح يطبع المدة. POST يفشل في @Min(1) بعد دخول المعترض العام على المتحكم: سطر failed لأن الأنبوب داخل الالتفاف، ولا جسم { data } إضافي. GET /health بلا الزينة لا يطبع. الدعم يقرأ المسار والمدة من غير فتح كل خدمة.

أخطاء شائعة

  • catchError تسجّل ثم ترجع of(null) فيصير الفشل 200.
  • طباعة request.body وفيه كلمة مرور أو اسم زائر كامل.
  • الربط العام ثم ضجيج على كل فحص صحة.
  • قياس المدة في Middleware واعتبارها مدة reserve.

متى نستخدمه؟

حين تريد أثرًا موحدًا حول مجموعة مسارات، على النجاح والفشل، من غير تغيير العقد.

متى لا نستخدمه؟

لا تسجّل أسرارًا. لا تستبدل الفلتر الذي يشكّل جسم الخطأ. السطر في السجل والJSON للعميل قراران مختلفان. لا تضع هذا الصنف مكان حارس.

مقارنة

المكان مدة reserve يغيّر JSON يرى رفض الحارس
Middleware لا يرى الخروج قد يكتب ترويسة نعم لأنه قبل الحارس
هذا المعترض نعم لا لا
console.log في الدالة جزء فقط لا لا

تمارين

تمرين سهل

لماذا لا نستخدم map في معترض السجل هذا؟

الحل

لأن السجل أثر جانبي. map يبدّل القيمة التي يراها العميل. tap تمررها.

تمرين متوسط

فشل @Min(1) وطُبع failed. لماذا لم يُطبع شيء لحارس أعاد false؟

الحل

الأنبوب بعد المعترض في الدخول، ففشل الشكل يحدث داخل التيار. الحارس قبل المعترض، فالرفض لا يدخل intercept.

تمرين متقدم

تريد المدة في السجل وجسم الخطأ للعميل كما هو. لماذا catchError الذي لا يعيد throwError يفسد الهدف؟

الحل

لأنه يستبدل الخطأ بقيمة نجاح. أبقِ tap على فرع الخطأ حتى يُسجَّل ثم يكمل الاستثناء إلى الفلتر الذي يكتب الجسم.

أسئلة مراجعة

  • أي عامل يسجّل من غير تغيير الرد؟
  • لماذا تُحفظ الساعة قبل handle؟
  • هل tap على الخطأ تبتلع الاستثناء؟
  • لماذا الربط على متحكم التذاكر لا على التطبيق في المثال؟

الخلاصة

معترض السجل يقرأ الطريق في الدخول ويطبع المدة في tap على النجاح وعلى الفشل، ويمرر القيمة والخطأ كما هما. التغليف والحارس والفلتر تبقى أصنافًا أخرى.

ماذا بعد؟

الدرس التالي يغيّر شكل الرد عمدًا: map إلى غلاف { data }.
