# قبل التنفيذ وبعده

## الهدف من هذا الدرس

تفريق السطور التي قبل `next.handle()` عن العوامل التي داخل `pipe` بعد أن يصدر المعالج.

## المشكلة التي يحلها

عداد زمن يُطرح في المكان الخطأ فيقيس صفرًا، أو يغلف الرد قبل أن توجد قيمة. الفريق يضع كل الكود فوق `return` لأن الدالة تبدو متزامنة.

## الفكرة ببساطة

ما يُكتب قبل نداء `handle` يعمل في طريق الدخول، بعد الحارس وقبل إكمال السلسلة الداخلية. ما يُكتب داخل `tap` أو `map` على التيار يعمل في طريق الخروج، بعد الدالة، أو لا يعمل إن أخطأ التيار قبل العامل.

## التعريف التقني

صفحة المعترضات تقول ذلك حرفيًا: المنطق قبل المعالج يوضع قبل نداء `handle`. ما بعد التنفيذ عوامل على الـ `Observable` الذي ترجعه `handle`.

```ts
intercept(context: ExecutionContext, next: CallHandler): Observable<unknown> {
  const started = Date.now();
  return next.handle().pipe(
    tap(() => console.log(Date.now() - started)),
  );
}
```

`started` يُلتقط في الدخول. الطرح داخل `tap` في الخروج. الفرق هو زمن ما بين اللحظتين، ومنه الأنبوب والدالة إن كان هذا المعترض يلفهما.

`tap` لا تُستدعى إن أخطأ المعالج، إلا إذا مررت كائن مراقب فيه `error`، أو استخدمت `finalize` الذي يعمل عند الاكتمال أو الخطأ. الصفحة تذكر هذا الحد حتى لا تظن أن «بعد» يشمل الفشل تلقائيًا.

`map` في الخروج تغيّر القيمة الصاعدة. سطر قبل `handle` لا يرى تلك القيمة لأنها لم تصدر.

رمي استثناء قبل `return` يمنع بناء التيار في ذلك المعترض. رمي داخل `map` خطأ على التيار يقدر معترض خارجي أن يلتقطه بـ `catchError`.

## Mental Model

```text
دخول: كود فوق handle     لا يرى جسم الرد
        handle() يصف الداخل
خروج: pipe(tap, map)     يرى القيمة أو يفشل قبلها
```

المتغير `started` يُغلق عليه من الدخول إلى الخروج. هذا جسر بين الوجهين، لا قراءة للمستقبل.

## أبسط مثال

```ts
import { type CallHandler, type ExecutionContext, Injectable, type NestInterceptor } from '@nestjs/common';
import { type Observable } from 'rxjs';
import { tap } from 'rxjs/operators';

@Injectable()
export class DeskTimingInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<unknown> {
    const request = context.switchToHttp().getRequest<{ method: string }>();
    const method = request.method;
    const started = Date.now();
    return next.handle().pipe(
      tap(() => {
        console.log(`${method} ${Date.now() - started}ms`);
      }),
    );
  }
}
```

`method` يُقرأ في الدخول لأن الطلب معروف قبل الدالة. المدة تُطبع في الخروج بعد النجاح فقط.

## شرح المثال

- قراءة `method` قبل `handle` صحيحة. الرد غير موجود بعد.
- `tap` ترى لحظة الإصدار لا لحظة دخول `intercept` إلا عبر `started`.
- فشل `reserve` برمي استثناء يتخطى هذه `tap`. أضف `finalize` من `rxjs` إن أردت سطرًا في الحالتين: `finalize(() => log(Date.now() - started))`.
- لا تحسب المدة قبل `return` بطرح `Date.now()` من نفسه. الخروج لم يحدث.

## ماذا يحدث داخليًا؟

عند الاستدعاء يعمل جسم `intercept` حتى `return`. في تلك النافذة الأنابيب الداخلية والدالة لم تعمل بعد إن كان هناك معترضات أقرب لم تُشغَّل. ثم يشترك الإطار. الداخل يعمل. عند الإصدار تنفرج عوامل هذا الـ `pipe` من الداخل نحو هذا المعترض.

لذلك «قبل» في معترض عام قد يحيط بمعترض المسار كله: كود العام قبل كود المسار في الدخول، وعامل العام بعد عامل المسار في الخروج. الدرس الأخير يرسم ذلك. هنا يكفي أن وجهي الدالة نفسها مختلفان.

`catchError` عامل خروج. لا يلتقط رميًا حدث في سطر فوق `handle` في المعترض نفسه قبل بناء `pipe`. ضع ما تريد التقاطه على التيار.

## مثال عملي

سجل الشباك يطبع `POST` فور دخول المعترض، ثم يطبع المدة حين يرجع `{ id }` من الحفظ. طلب يفشل في `ParseIntPipe` قبل الدالة: سطر الدخول طُبع، و `tap` النجاح لم تُطبع، و `finalize` إن أضفتها تطبع المدة حتى الفشل. هكذا تفرّق «وصلنا إلى الالتفاف» عن «المقعد حُفظ».

## أخطاء شائعة

- وضع `map` التي تقرأ ناتج الدالة فوق `handle`.
- قياس الزمن كله فوق `return` فيصبح صفرًا تقريبًا.
- توقع أن `tap` تسجّل أخطاء الحفظ.
- كتابة الرد على `response` قبل `handle` ثم تكرار الكتابة من القيمة الراجعة.

## متى نستخدمه؟

اقرأ الطلب والساعة والعنوان قبل `handle`. غيّر القيمة أو سجّل النجاح داخل `pipe`. سجّل الطرفين، نجاحًا وفشلًا، بـ `finalize` أو بفرعي `tap`.

## متى لا نستخدمه؟

لا تفحص الإذن في وجه الدخول. الحارس سبقك. لا تحوّل `seat` هنا إن كان الأنبوب لم يعمل بعد وأنت داخل معترض يلف الأنبوب: القيمة الخام قد تكون ما زالت نصًا في تلك اللحظة على الطريق إلى الأنبوب، بينما وجه الخروج يرى ما بعد الدالة.

## مقارنة

| المكان | يرى الطلب | يرى ناتج الدالة | عند رمي الدالة |
| --- | --- | --- | --- |
| قبل `handle` | نعم | لا | قد لا يُستأنف إن رميت أنت |
| `tap` بلا خطأ | بعد النجاح | نعم | لا تُستدعى |
| `finalize` | — | لا يبدّل القيمة | يُستدعى أيضًا |
| `map` | — | يبدّلها | لا تُستدعى إن سبقها الخطأ |

## تمارين

### تمرين سهل

أين تضع `const started = Date.now()` وأين تطبع الفرق؟

<details>
<summary>الحل</summary>

القراءة قبل `next.handle()`. الطرح داخل `tap` أو `finalize` على `pipe`.

</details>

### تمرين متوسط

لماذا لا تسجّل `tap(() => ...)` فشل `reserve`؟

<details>
<summary>الحل</summary>

`tap` بالدالة الواحدة تعمل عند الإصدار الناجح. الخطأ يمر بجانب هذا المسار. استخدم معالج الخطأ في `tap` أو `finalize` أو `catchError`.

</details>

### تمرين متقدم

تريد رقم الحالة HTTP في السجل بعد التنفيذ. هل تقرؤه قبل `handle`؟

<details>
<summary>الحل</summary>

لا. الحالة النهائية تُحدَّد بعد الناتج أو الاستثناء. على النجاح اقرأها في عامل الخروج. قبل `handle` قد تكون الحالة ما زالت الافتراضية ولم تكتب الدالة شيئًا.

</details>

## أسئلة مراجعة

- ماذا يعمل قبل `handle` وماذا يعمل داخل `pipe`؟
- لماذا المدة فوق `return` وحدها مضللة؟
- كيف تسجّل الفشل أيضًا؟
- هل `map` ترى قيمة قبل الدالة؟

## الخلاصة

وجه الدخول سطور قبل `handle`: طلب وساعة. وجه الخروج عوامل التيار: قيمة أو خطأ بعد التنفيذ. أغلق على ما احتجته من الدخول، ولا تقرأ الناتج قبل أن يصدر.

## ماذا بعد؟

الدرس التالي معترض تسجيل يطبع الطريقة والمسار والمدة باستخدام هذا الفرق.
