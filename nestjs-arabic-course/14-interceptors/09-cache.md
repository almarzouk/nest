# Cache

## الهدف من هذا الدرس

معاينة معترض يتخطى المعالج ويرجع قيمة محفوظة عبر `of`، من غير بناء نظام تخزين كامل.

## المشكلة التي يحلها

قائمة العروض تتغير كل دقيقة، و `GET /shows` يضرب المخزن في كل طلب لوحة. الصفحة تذكر التخزين كسبب لاستبدال تنفيذ الدالة. الحزمة `cache-manager` وفصل التخزين لاحقان. هنا الفكرة: إن وُجدت قيمة، لا تنادِ `handle`.

## الفكرة ببساطة

خريطة في الذاكرة من مسار القراءة إلى القيمة. عند الإصابة أرجع `of(cached)` ولا تستدعِ `handle`. عند الغياب استدعِ `handle` واحفظ الإصدار في `tap`. الكتابة `POST` لا تُخزَّن في هذه المعاينة.

## التعريف التقني

مثال الصفحة يرجّع `of([])` حين يكون العلم `isCached` صحيحًا، وإلا `next.handle()`. الغرض أن تيار `of` لا يشغّل المعالج.

المعاينة هنا أصدق قليلًا من علم ثابت، وما زالت ناقصة عن الإنتاج: لا مدة صلاحية، ولا حد لحجم الخريطة، ولا إبطال عند `POST /shows`. الصفحة تقول إن TTL والإبطال والحجم خارج ذلك المثال. نكرر الحد حتى لا يُشحن هذا الصنف إلى الإنتاج كما هو.

`of` من `rxjs` تيار يصدر القيمة فور الاشتراك ثم يكتمل.

مفتاح الخريطة في المعاينة `GET` مع `url`. طلبان مختلفان في الاستعلام مفتاحان مختلفان. `POST` يرجع `next.handle()` دائمًا.

الخريطة على الصنف تعني حالة مشتركة بين الطلبات. هذا مقصود للتخزين ومقبول في معاينة عملية واحدة. عدة نسخ من التطبيق لا ترى الخريطة نفسها. ذلك سبب وجود مخزن خارجي لاحقًا.

لا تخزّن ردودًا فيها بيانات زائر. القائمة العامة للعروض فقط.

## Mental Model

```text
GET /shows موجود في الخريطة → of(value) → الدالة لا تعمل
GET /shows غائب → handle → tap تحفظ → القيمة للعميل
POST /shows → handle دائمًا، والخريطة قد تبقى قديمة
```

## أبسط مثال

```ts
import { type CallHandler, type ExecutionContext, Injectable, type NestInterceptor } from '@nestjs/common';
import { type Observable, of } from 'rxjs';
import { tap } from 'rxjs/operators';

@Injectable()
export class ShowListCacheInterceptor implements NestInterceptor {
  private readonly hits = new Map<string, unknown>();

  intercept(context: ExecutionContext, next: CallHandler): Observable<unknown> {
    const request = context.switchToHttp().getRequest<{ method: string; url: string }>();
    if (request.method !== 'GET') {
      return next.handle();
    }
    const key = request.url;
    const cached = this.hits.get(key);
    if (cached !== undefined) {
      return of(cached);
    }
    return next.handle().pipe(tap((value) => this.hits.set(key, value)));
  }
}
```

أول `GET /shows` يشغّل الدالة ويحفظ. الثاني يرجع النسخة المحفوظة.

## شرح المثال

- `of(cached)` لا ينادي `handle`. لا أنبوب ولا خدمة على طريق تلك القيمة المحفوظة. الأنابيب التي تسبق المعالج في الدورة تكون قد عملت قبل المعترض في طريق الدخول فقط إن كان ترتيبها كذلك. في الدورة الأنبوب بعد المعترض في الدخول، فتخطي `handle` يتخطى الأنبوب والدالة معًا إن كان المعترض يلفهما. على `GET` بلا جسم هذا مقبول. لا تستخدم التخطي على `POST` يحتاج فحص DTO.
- `tap` تحفظ بعد النجاح فقط. الخطأ لا يُخزَّن.
- `cached !== undefined` يسمح بحفظ مصفوفة فارغة. الإصابة بالمصفوفة الفارغة تبقى إصابة.
- الخريطة بلا حذف. هذا حد المعاينة.

## ماذا يحدث داخليًا؟

عند الإصابة يشترك Nest في `of`. القيمة تصدر من غير `ShowsService`. معترضات خارجية ما زالت ترى القيمة في عوامل خروجها، مثل غلاف `{ data }` إن كان خارج هذا المعترض. معترض داخلي لا يعمل لأن `handle` لم يُستدعَ.

عند الغياب السلسلة كاملة تعمل، ثم `tap` يكتب الخريطة. الطلب الموازي الثاني قد يدخل قبل `tap` الأول فيُستدعى المخزن مرتين. المعاينة لا تقفل المفتاح. الإنتاج يحتاج قفلًا أو مخزنًا جاهزًا.

`POST` لا يمسح `GET /shows`. اللوحة قد تعرض قائمة قديمة حتى إعادة التشغيل. اذكر ذلك في التعليق فوق الصنف إن أبقته في فرع تجريبي.

## مثال عملي

لوحة العروض العامة على `ShowsController` فقط. اختبار أول `GET` يتوقع نداء خدمة واحدًا. اختبار ثانٍ فورًا يتوقع ألا تُستدعى الخدمة. `POST /shows` ما زال ينادي الخدمة. بعده `GET` في هذه المعاينة قد يرجع القائمة القديمة. الاختبار الثالث يوثّق هذا القصور بدل أن يصلحه بمكتبة كاملة.

## أخطاء شائعة

- علم `isCached = true` دائمًا كما في المقتطف التعليمي المبسط، فيصبح كل رد مصفوفة فارغة إن نسخت المثال حرفيًا.
- تخزين `POST` فيرجع الحجز القديم لعميل آخر.
- حفظ جسم فيه اسم زائر على مفتاح URL عام.
- اعتبار الخريطة بديلًا عن فصل التخزين و `cache-manager`.

## متى نستخدمه؟

كمعاينة لفكرة «تيار جاهز بدل `handle`» على قراءة عامة رخيصة التغيير، ومع اختبار يوثّق غياب الإبطال.

## متى لا نستخدمه؟

في الإنتاج على بيانات خاصة أو على كتابة. ولا كبوابة إذن. ولا لتخزين أخطاء `500`.

## مقارنة

| | `return of(cached)` | `return next.handle()` |
| --- | --- | --- |
| الخدمة | لا تُستدعى | تُستدعى عند الاشتراك |
| الأنبوب داخل السلسلة | لا يعمل | يعمل |
| مصدر القيمة | الخريطة | الدالة |

## تمارين

### تمرين سهل

أي دالة RxJS تبني تيارًا من قيمة محفوظة من غير المعالج؟

<details>
<summary>الحل</summary>

`of(cached)`.

</details>

### تمرين متوسط

لماذا المصفوفة الفارغة المحفوظة يجب ألا تُعامل كغياب؟

<details>
<summary>الحل</summary>

لأن القائمة العامة قد تكون فارغة فعلًا. فحص `undefined` فقط يبقي الإصابة. غياب المفتاح هو الغياب.

</details>

### تمرين متقدم

بعد `POST /shows` ما زال `GET /shows` يرجع قائمة بلا العرض الجديد. ما الحد الذي قبلته المعاينة، وما الذي لا نضيفه في هذا الدرس؟

<details>
<summary>الحل</summary>

لا يوجد إبطال. المعاينة توثّق القصور. مدة الصلاحية والحذف عند الكتابة ومخزن مشترك بين العمليات درس التخزين لاحقًا، لا خريطة أكبر في هذا الملف.

</details>

## أسئلة مراجعة

- متى لا يُستدعى `handle`؟
- لماذا `POST` خارج الخريطة؟
- ماذا ينقص المعاينة حتى تكون إنتاجًا؟
- هل معترض خارجي ما زال يرى القيمة المخزنة؟

## الخلاصة

تخطي المعالج يتم بإرجاع `of(value)` بدل `handle`. المعاينة خريطة لقراءة عامة وتوثّق أنها بلا صلاحية ولا إبطال. التخزين الحقيقي فصل لاحق، والفكرة هنا هي التيار البديل فقط.

## ماذا بعد؟

الدرس التالي مستويات الربط وترتيب المراقبات: من يدخل أولًا ومن يرى الرد أولًا على طريق الخروج.
