Event Loop وما يسدّه

الهدف من هذا الدرس

أن ترى لماذا يتأخر GET /books في متجر رف بينما المعالج لا يفعل شيئًا «ثقيلًا» في نظرك: خيط Node واحد يدور على حلقة أحداث، وأي عمل متزامن طويل يمنع بقية الطلبات من التقدم.

المشكلة التي يحلها

تحت الحمل، زمن الاستجابة يقفز لكل المسارات دفعة واحدة، بما فيها مسار الصحة. السبب غالبًا ليس Nest ولا عدد الـ Controllers، بل دالة حبست الحلقة: حلقة على مصفوفة ضخمة، JSON.parse لملف كتالوج كامل، أو bcrypt المتزامن، أو fs.readFileSync على مسار ساخن.

الفكرة ببساطة

الحلقة تسلّم الطلب إلى معالجك، ثم تنتظر أن تُرجع الدالة السيطرة. انتظار قاعدة البيانات أو fetch يُرجع السيطرة. الحساب المتزامن لا يُرجعها. الطلبات الأخرى تقف في الطابور خلف ذلك الحساب حتى ينتهي.

التعريف التقني

عملية Node تشغّل JavaScript على خيط واحد. I/O يذهب إلى libuv ويعود كـ callback أو Promise. ما دام المكدس مشغولًا بكود متزامن، لا تُعالَج مؤقتات ولا استجابات I/O المكتملة. في Nest، الـ Handler الذي يعمل await prisma.book.findMany() يحرر الحلقة أثناء انتظار Postgres. الـ Handler الذي يفرز 200 ألف سعر في الذاكرة قبل return لا يحررها.

Mental Model

طلب أ يبدأ فرز كتالوج ضخم     الحلقة مشغولة
طلب ب (صحة)                   ينتظر دوره
طلب أ ينتهي                   ثم يُرد على ب

قياس واحد: إذا تأخر /health كلما اشتغل مسار التقارير، فالمسار يسد الحلقة. إذا تأخر مسار الكتب وحده وبقي /health سريعًا، فالوقت داخل انتظار قاعدة ذلك المسار.

أبسط مثال

import { Controller, Get } from '@nestjs/common';

@Controller('reports')
export class ReportsController {
  @Get('prices')
  prices() {
    const started = Date.now();
    let n = 0;
    for (let i = 0; i < 50_000_000; i++) n += i % 7;
    return { n, blockedMs: Date.now() - started };
  }
}

شرح المثال

  • الحلقة لا تنتظر شبكة. هي تحسب. طوال blockedMs لا يُكتب رد أي طلب آخر على هذه العملية.
  • نقل الحساب إلى async لا يفيد. async بلا await حقيقي يبقى متزامنًا حتى أول نقطة انتظار.
  • مسار الصحة في العملية نفسها يتأخر بالقيمة نفسها تقريبًا إذا وصل أثناء الحلقة.

ماذا يحدث داخليًا؟

  1. محول HTTP (Express افتراضيًا) يستلم الطلب ويضعه في طابور الحلقة.
  2. Nest يشغّل الـ Guards والـ Pipes ثم الـ Handler.
  3. أثناء الحلقة المتزامنة، libuv قد يكون أنهى I/O، لكن الـ callbacks لا تعمل حتى يفرغ المكدس.
  4. بعد return، Nest يسلسل الجسم ويرسله، ثم تلتقط الحلقة الطلب التالي.
  5. إن كان العمل CPU حقيقيًا ومستمرًا، مكانه worker_threads أو عملية منفصلة، لا داخل الـ Handler.

مثال عملي

تقرير خصومات رف يقرأ الصفوف (هذا I/O) ثم يبني المدرج التكراري بخيط عامل حتى لا يتوقف البيع:

import { Injectable } from '@nestjs/common';
import { Worker } from 'node:worker_threads';
import { PrismaService } from '../prisma/prisma.service.js';

@Injectable()
export class PriceReportService {
  constructor(private readonly prisma: PrismaService) {}

  async histogram() {
    const rows = await this.prisma.book.findMany({
      select: { priceCents: true },
    });
    return new Promise((resolve, reject) => {
      const worker = new Worker(new URL('./histogram.worker.js', import.meta.url), {
        workerData: rows.map((row) => row.priceCents),
      });
      worker.once('message', resolve);
      worker.once('error', reject);
    });
  }
}

await findMany يحرر الحلقة. بناء المدرج يحدث في الخيط العامل. ملف histogram.worker.js يستقبل workerData ويرسل الناتج بـ parentPort.postMessage. لا تنقل كائنات Prisma نفسها إلى العامل؛ انقل أرقامًا.

أخطاء شائعة

  • قياس الأداء بطلب واحد على جهازك واستنتاج أن الإطار بطيء. الحلقة تظهر تحت التزامن.
  • استدعاء bcrypt.hashSync أو readFileSync داخل طلب تسجيل الدخول.
  • بناء PDF أو صورة غلاف داخل نفس العملية لكل طلب شراء.
  • الاعتقاد أن setTimeout(fn, 0) يلغي التكلفة. هو يؤجلها دورة واحدة فقط.

متى نستخدمه؟

عندما يتأخر كل شيء معًا، أو عندما تعرف أن مسارًا يعمل حسابًا أو تحليلًا طويلًا على بيانات في الذاكرة. عندها قس /health أثناء الضغط على ذلك المسار.

متى لا نستخدمه؟

عندما يكون الزمن كله في استعلام SQL أو في شبكة خارجية. نقل ذلك إلى Worker لا يسرع Postgres. أصلح الاستعلام أولًا، وهذا درس الفهارس.

مقارنة

العمل أثره على الحلقة الاتجاه
await لاستعلام يحرر الحلقة أثناء الانتظار أبقه في الخدمة
حلقة على مئات الآلاف يسد كل الطلبات عامل أو عملية
JSON.stringify لجسم صغير قصير عادة اتركه
ضغط الاستجابة داخل العملية CPU لكل رد كبير وكيل عكسي، درس الضغط

تمارين

تمرين سهل

مساران على العملية نفسها: GET /health يعيد { ok: true } فورًا، و GET /reports/prices فيه حلقة 50 مليون. ماذا يحدث لزمن /health إذا أُرسل أثناء الحلقة؟

الحل

يتأخر حتى تنتهي الحلقة، لأن الخيط الواحد لا يرد على الصحة قبل أن يفرغ المكدس. هذا دليل سد، لا دليل أن Terminus معطوب.

تمرين متوسط

دالة async تعمل JSON.parse على ملف كتالوج 80 ميغابايت ثم await لحفظ الناتج. أي جزء يسد الحلقة؟

الحل

JSON.parse يسد، لأنه متزامن ويستهلك CPU على السلسلة كلها قبل أن تصل الدالة إلى await. الانتظار بعده يحرر الحلقة. إن تكرر التحليل لكل طلب، حلّله مرة خارج الطلب أو في عامل.

تمرين متقدم

صمم قياسًا يفصل «سد الحلقة» عن «SQL بطيء» لمتجر رف من غير أداة APM.

الحل

شغّل ضغطًا على مسار الكتب، وطلبًا خفيفًا ثابتًا على /health لا يلمس القاعدة. إذا صعد زمن الصحة مع زمن الكتب، فهناك عمل متزامن على الحلقة. إذا بقيت الصحة سريعة وتأخرت الكتب، فالوقت في الاستعلام أو في تجمع الاتصالات. كرر بعد إزالة أي Sync وأي حلقة ثقيلة.

أسئلة مراجعة

  • ما الذي يحرر حلقة الأحداث داخل Handler؟
  • لماذا async وحدها لا تمنع السد؟
  • أي إشارة عملية تقول إن السد عام لا خاص بقاعدة البيانات؟
  • أين يذهب حساب المدرج التكراري إن وجب أن يبقى البيع سريعًا؟

الخلاصة

الأداء في Node يبدأ بالحلقة. I/O المنتظر يتشارك العملية بأمان. العمل المتزامن الطويل يوقف كل العملاء على تلك العملية، ومكانه خيط عامل أو مسار لا يمس كل طلب.

ماذا بعد؟

الحلقة سليمة وقد يظل الطلب غاليًا لأن Nest ينشئ شجرة حقن جديدة لكل طلب. الدرس التالي يقيس كلفة Scope.REQUEST.
