# قاعدة البيانات والفهارس

## الهدف من هذا الدرس

ربط بطء `GET /books` بخطة Postgres: أي فهرس يخدم التصفية والترتيب اللذين يرسلهما العميل فعلًا، وأي فهرس يزيد الكتابة بلا أن يلمس هذا المسار.

## المشكلة التي يحلها

القائمة في رف تعرض الكتب المنشورة لمستأجر واحد مرتبة بأحدث نشر، مع تصفية اختيارية بالمؤلف. الجدول يكبر والرد يتجاوز مئات الميلي ثواني. إضافة فهرس على كل عمود لا تغيّر الخطة، لأن الاستعلام يصفّي بعمودين ويرتب بثالث.

## الفكرة ببساطة

الفهرس هيكل بحث يسرّع نمط قراءة محدد. المخطط بلا فهرس مناسب يجعل القاعدة تقرأ الجدول (sequential scan) ثم ترتبه في الذاكرة. الفهرس الزائد يبطئ `INSERT` و `UPDATE` لأن القاعدة تحافظ عليه عند كل كتابة.

## التعريف التقني

في Prisma، `@@index` يصرّح بالأعمدة التي تُفهرس معًا. ترتيب الأعمدة في الفهرس المركب يتبع ترتيب الاستخدام: مساواة أولًا (`tenantId`, `status`) ثم نطاق أو ترتيب (`publishedAt`). الاستعلام الذي لا يطابق بادئة الفهرس قد يتجاهله المخطط. `EXPLAIN ANALYZE` هو الحكم، لا اسم الفهرس. صفحة Prisma في توثيق Nest تضع الوصول إلى البيانات خلف خدمة؛ الفهرس قرار مخطط لا قرار Controller.

## Mental Model

```text
WHERE tenantId = $1 AND status = 'published'
ORDER BY publishedAt DESC
LIMIT 20

فهرس مفيد: (tenantId, status, publishedAt DESC)
فهرس ضعيف لهذا المسار: (title) وحده
```

## أبسط مثال

```prisma
model Book {
  id          String   @id @default(cuid())
  tenantId    String
  status      String
  author      String
  publishedAt DateTime
  title       String

  @@index([tenantId, status, publishedAt(sort: Desc)])
  @@index([tenantId, author])
}
```

## شرح المثال

- الفهرس الأول يخدم قائمة الرف المنشورة مرتبة.
- الفهرس الثاني يخدم `?author=` داخل المستأجر. من غير `tenantId` في الفهرس قد يقرأ المؤلف عبر كل المكتبات.
- `title` بلا فهرس هنا مقبول إن كان البحث النصي مسارًا آخر بأداة بحث، لا `LIKE '%كلمة%'` على هذا الجدول.

## ماذا يحدث داخليًا؟

1. الخدمة تبني `where` و `orderBy` من عقد القائمة، لا من سلسلة حرة يلصقها العميل في SQL.
2. Prisma يرسل SQL معاملات.
3. المخطط يختار فهرسًا إن كانت بادئته مطابقة ويقدّر أن تكلفته أقل من مسح الجدول.
4. `LIMIT` مع ترتيب يطابق الفهرس يوقف القراءة بعد عشرين صفًا.
5. إن غاب الترتيب عن الفهرس، قد يُجلب عدد كبير ثم يُفرز (`Sort`) قبل القص.

## مثال عملي

```ts
import { Injectable } from '@nestjs/common';
import { PrismaService } from '../prisma/prisma.service.js';

@Injectable()
export class BooksService {
  constructor(private readonly prisma: PrismaService) {}

  list(tenantId: string, author?: string) {
    return this.prisma.book.findMany({
      where: {
        tenantId,
        status: 'published',
        ...(author ? { author } : {}),
      },
      orderBy: { publishedAt: 'desc' },
      take: 20,
      select: { id: true, title: true, author: true, publishedAt: true },
    });
  }
}
```

`select` يُبقي الصفوف ضيقة. عند تصفية المؤلف، الفهرس `(tenantId, author)` يجد المرشحين، وقد تحتاج فهرسًا يغطي المؤلف مع `publishedAt` إذا صار هذا النمط هو الأشيع. القرار بعد `EXPLAIN` لا قبله.

## أخطاء شائعة

- فهرس على `id` فقط ثم التعجب من بطء القائمة. المفتاح الأساسي لا يخدم `WHERE status`.
- `OR` عريض أو `LIKE '%نجيب%'` يفسد استخدام الفهرس العادي.
- جلب العلاقات في حلقة: كتاب ثم مؤلفه باستعلام لكل صف. هذا N+1 في SQL، ويُجمع بـ `include` واعٍ أو استعلام واحد.
- فتح `PrismaClient` داخل كل طلب بدل نسخة واحدة و pool جاهز.

## متى نستخدمه؟

عندما `EXPLAIN` على الاستعلام الحقيقي (بقيم تشبه الإنتاج) يظهر Seq Scan أو Sort على جدول كبير، والمسار يصفّي ويرتب بنفس الأعمدة كل مرة.

## متى لا نستخدمه؟

لتسريع حلقة في Node أو ضغط HTTP. ولجداول صغيرة تُقرأ كلها في الذاكرة أصلًا. ولكل عمود «احتياطًا» على جدول كثير الكتابة مثل سجلات التدقيق.

## مقارنة

| النمط | ما يفيده |
| --- | --- |
| مساواة ثم ترتيب | فهرس مركب بهذا الترتيب |
| بحث `LIKE` في الطرف الأيسر | فهرس B-tree العادي لا يكفي |
| كتابة كثيرة وقراءة نادرة | فهارس أقل |
| عمود فريد أصلًا | القيد الفريد يغطي البحث بالمساواة |

## تمارين

### تمرين سهل

القائمة دائمًا `where tenantId + status` و `orderBy publishedAt desc`. أي ترتيب أعمدة أقرب؟

<details>
<summary>الحل</summary>

`(tenantId, status, publishedAt DESC)`. وضع `publishedAt` أولًا لا يخدم مساواة المستأجر. وضع `title` في الفهرس لا يغير هذه الخطة.

</details>

### تمرين متوسط

بعد إضافة الفهرس ما زال p95 عاليًا، و `EXPLAIN` يقول Index Scan لكن الصفوف العائدة آلاف قبل أن تقصها الخدمة في JavaScript. أين الخطأ؟

<details>
<summary>الحل</summary>

القص حدث بعد جلب الجدول تقريبًا. ضع `take` في الاستعلام نفسه. الفهرس يسرّع إيجاد الصفوف؛ `LIMIT` هو الذي يمنع سحبها كلها إلى Node.

</details>

### تمرين متقدم

مسار المؤلف اختياري. متى تبقي فهرسين، ومتى تدمجهما؟

<details>
<summary>الحل</summary>

أبقِ `(tenantId, status, publishedAt)` للقائمة العامة. أضف فهرس المؤلف إذا كان `EXPLAIN` لمسار `author` يمسح كثيرًا. ادمجهما فقط إذا صار النمط الغالب `tenantId + author + order publishedAt` وتبيّن أن الفهرس الأعرض يخدم الحالتين من غير أن يثقل الكتابة. القياس على النسبتين، لا على شكل الكود.

</details>

## أسئلة مراجعة

- لماذا ترتيب الأعمدة داخل الفهرس المركب جزء من التصميم؟
- ماذا يثبت `EXPLAIN ANALYZE` مما لا يثبته وجود `@@index`؟
- أين يُقص العدد: في SQL أم بعد وصول المصفوفة إلى Nest؟
- ما أثر فهرس لا يستخدمه أي استعلام ساخن؟

## الخلاصة

الفهرس يعد مسار قراءة واحدًا. في رف، قائمة المستأجر المنشورة تحتاج فهرسًا يطابق `where` ثم `orderBy` ثم `take`. ما لا يظهر في تلك الجملة لا يستحق فهرسًا حتى يفرضه مسار آخر مقاس.

## ماذا بعد؟

الاستعلام رخيص، وبعض القوائم لا تتغير بين الطلبات. الدرس التالي يقرر ماذا يُخزَّن ومتى يُبطَل.
