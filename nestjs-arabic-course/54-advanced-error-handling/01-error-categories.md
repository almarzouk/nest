# أنواع الأخطاء

## الهدف من هذا الدرس

تثبيت قائمة قصيرة لأنواع الفشل في متجر رف، حتى تتفق الخدمة والفلتر والعميل على الاسم قبل الاتفاق على رمز HTTP.

## المشكلة التي يحلها

فريق الواجهة يرى أحيانًا `200` مع `book: null`، وأحيانًا `500` لأن العنوان فارغ، وأحيانًا `400` لأن الكتاب محذوف. كل مسار اخترع رده. العميل لا يستطيع رسم حالة واحدة للغياب وحالة واحدة لتعارض النشر.

## الفكرة ببساطة

صنّف الفشل حسب من يملك القرار: المدخلات، قاعدة المجال، الغياب، تعارض الحالة، أو عطل لم تتوقعه. التصنيف يحدث في الكود كأنواع. الرمز على السلك يأتي لاحقًا في درس التحويل، لا داخل هذا التصنيف.

## التعريف التقني

في Nest، فشل التحقق من `ValidationPipe` أو `StandardSchemaValidationPipe` خطأ حدّي يتعلق بشكل الطلب. `HttpException` وأصنافها (`NotFoundException`, `ConflictException`, ...) أخطاء تعرف وضع HTTP مسبقًا. خطأ المجال صنف تملكه أنت ويرميه الـ Service بلا استيراد `@nestjs/common`. العطل غير المتوقع أي شيء آخر: انقطاع Prisma، `TypeError`، رفض لم تلتقطه. الاستراتيجية الناضجة تبقي هذه الخانات منفصلة حتى يترجمها فلتر واحد.

## Mental Model

```text
شكل الجسم        تحقق
قاعدة نشر        مجال
لا صف            غياب
الحالة تمنع      تعارض
سقوط اتصال       غير متوقع
```

## أبسط مثال

```ts
export class BookNotFound extends Error {
  constructor(readonly bookId: string) {
    super(`Book ${bookId} was not found`);
  }
}

export class BookAlreadyPublished extends Error {
  constructor(readonly bookId: string) {
    super(`Book ${bookId} is already published`);
  }
}
```

## شرح المثال

- الاسمان يخبران الخدمة ماذا حدث، لا ماذا يكتب المتحكم.
- `bookId` يصل إلى السجل لاحقًا. رسالة `Error` للبشر داخل العملية.
- لا حقل `statusCode` هنا. وجوده يخلط التصنيف بالبروتوكول.

## ماذا يحدث داخليًا؟

1. الـ Pipe يرفض الشكل قبل الخدمة. هذا تحقق.
2. الخدمة تبحث. صفر صفوف يعني غيابًا، فترمي `BookNotFound`.
3. إن وجدت الصف والحالة `published` وأمر النشر تكرر، ترمي `BookAlreadyPublished`. هذا تعارض.
4. إن رمى العميل Prisma `P2002` على قيد فريد، فهذا تعارض ثبات أيضًا لكن مصدره القاعدة، ويُترجم في نفس الخانة.
5. انقطاع الشبكة إلى القاعدة لا يدخل أي خانة مجال. يبقى غير متوقع.

## مثال عملي

```ts
export type ShelfFailure =
  | { kind: 'validation'; field: string }
  | { kind: 'not-found'; bookId: string }
  | { kind: 'conflict'; bookId: string; state: string }
  | { kind: 'unexpected' };

export function classify(error: unknown): ShelfFailure['kind'] {
  if (error instanceof BookNotFound) return 'not-found';
  if (error instanceof BookAlreadyPublished) return 'conflict';
  return 'unexpected';
}
```

الدالة لا تكتب HTTP. هي العقد الذي سيستهلكه الفلتر في الدرس الثالث. التحقق أصلًا لا يصل إليها إن أوقف الـ Pipe الطلب.

## أخطاء شائعة

- خانة واحدة اسمها `AppError` فيها `status` اختياري فيمتلئ بكل شيء.
- معاملة الغياب كقائمة فارغة في `GET /books/:id` ومعاملته كنجاح في القائمة. القائمة الفارغة نجاح بحث؛ المعرّف الغائب غياب. تفصيل الرموز في فصل التصميم، والتصنيف هنا يفصل الحالتين.
- تسجيل أخطاء التحقق بنفس مستوى سقوط القاعدة، فيختفي العطل داخل الضجيج.
- رمي `Error` نصي: `throw new Error('not found')` ثم البحث في الرسالة.

## متى نستخدمه؟

في بداية أي ميزة تغيّر حالة كتاب: انشر، أوقف، احذف. اكتب الأنواع قبل المتحكم.

## متى لا نستخدمه؟

لا تضف نوعًا لكل سطر `if`. إن لم يتغير سلوك العميل ولا السجل، أبقِ الفشل داخل التحقق أو داخل نوع موجود.

## مقارنة

| النوع | من يرميه عادة | هل يعرف HTTP؟ |
| --- | --- | --- |
| تحقق | Pipe | نعم، 400 عبر الأنبوب |
| غياب / تعارض مجال | Service | لا |
| `HttpException` جاهز | الحد، أو كود قرر الارتباط بـ HTTP | نعم |
| غير متوقع | أي طبقة | لا |

## تمارين

### تمرين سهل

`publish()` وجد الكتاب منشورًا. أي نوع من القائمة؟

<details>
<summary>الحل</summary>

تعارض حالة. الكتاب موجود، والعملية لا تجوز في هذه الحالة. ليس غيابًا وليس عطلًا.

</details>

### تمرين متوسط

`findMany` أعاد `[]` لتصفية لا تطابق شيئًا، و `findUnique` أعاد `null`. هل هما نوع واحد؟

<details>
<summary>الحل</summary>

لا. مصفوفة فارغة نتيجة بحث ناجحة. `null` على معرّف محدد غياب. النوعان يُترجمان لاحقًا إلى ردّين مختلفين.

</details>

### تمرين متقدم

Prisma رمى انتهاك مفتاح فريد على `isbn` أثناء الإنشاء. في أي خانة تضعه، ولماذا لا تضعه مع سقوط الاتصال؟

<details>
<summary>الحل</summary>

تعارض ثبات: العميل يستطيع تصحيح ISBN. سقوط الاتصال لا يصلحه العميل بإعادة إرسال نفس الجسم، فهو غير متوقع حتى لو كانت الرسالة من Prisma أيضًا. ميّز بالكود (`P2002`) لا بنوع الاستثناء العام للمكتبة.

</details>

## أسئلة مراجعة

- ما الخانات الخمس التي تكفي رف في هذا الدرس؟
- لماذا لا يحمل نوع المجال `statusCode`؟
- ما فرق القائمة الفارغة عن المعرّف الغائب؟
- أي الأخطاء يصل أصلًا قبل الخدمة؟

## الخلاصة

التصنيف أسماء ثابتة للفشل: تحقق، مجال، غياب، تعارض، غير متوقع. الرمز والشكل قرار لاحق على الحد. الرسالة النصية ليست نوعًا.

## ماذا بعد؟

الخانات واضحة. الدرس التالي يكتب أصناف المجال التي يرميها `BooksService` من غير Nest HTTP.
