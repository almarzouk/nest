Command و Query

الهدف من هذا الدرس

فصل كائن الأمر الذي يغيّر الحالة عن كائن الاستعلام الذي يقرأ، كما تعرّفهما وصفة @nestjs/cqrs، من غير خلطهما بدالة خدمة واحدة بالاسم فقط.

المشكلة التي يحلها

خدمة place التي ترجع أيضًا لوحة إحصاء تجعل معالج الكتابة يعرف شكل القراءة. الأمر مهمة («أبطل التنين»، «ألغِ الطلب») لا حقول CRUD عامة. الاستعلام سؤال («أعطني البطل») لا يغيّر الحالة. الفصل يسمح لاحقًا بمعالج ونموذج لكل جانب. الكائنان وحدهما، بلا معالج، لا يكفيان لتشغيل Nest. هذا الدرس يسمي الحمولة.

الفكرة ببساطة

الأمر صنف يحمل مدخلات التغيير. توسيع Command<Result> من @nestjs/cqrs اختياري ويثبت نوع ناتج CommandBus.execute. الاستعلام صنف يوسع Query<Result> بنفس الفكرة. لا منطق داخل الكائن سوى البيانات. المعالج في الدرس التالي ينفذ. المتحكم أو الخدمة تبني الكائن وتمرره للحافلة عندما تصل إليها، أو تستدعي المعالج في الاختبار.

التعريف التقني

من الوصفة:

import { Command } from '@nestjs/cqrs';

export class KillDragonCommand extends Command<{ actionId: string }> {
  constructor(
    public readonly heroId: string,
    public readonly dragonId: string,
  ) {
    super();
  }
}

توسيع Command يحدد أن execute على الحافلة يُستنتج كـ Promise<{ actionId: string }>. بلا التوسيع يبقى الأمر صالحًا ويفقد الاستنتاج.

import { Query } from '@nestjs/cqrs';

export class GetHeroQuery extends Query<Hero> {
  constructor(public readonly id: string) {
    super();
  }
}

الأمر بلغة مهمة: CancelOrderCommand فيه orderId و reason، لا UpdateOrderDto بكل الأعمدة القابلة للكتابة. الاستعلام GetInvoiceViewQuery يعيد شكل اللوحة لا كيان الكتابة.

لا تضع prisma داخل الأمر. لا تضع فحص الحارس داخل الاستعلام. الحارس بقي على المسار. الأمر يفترض فاعلًا مسموحًا له وصلت هويته في الحقول (requestedBy).

القراءة لا تُنفذ عبر Command حتى لو كانت SELECT ثقيلًا. الكتابة لا تُنفذ عبر Query حتى لو أرجعت الكيان الجديد. إن أرجع الأمر actionId فتلك نتيجة المهمة لا نموذج القراءة الكامل. اجلب اللوحة باستعلام بعدها إن لزم.

Mental Model

CancelOrderCommand  -> سيغيّر حالة
GetInvoiceViewQuery -> سيقرأ نموذجًا

المعالج سلوك

أبسط مثال

export class CancelOrderCommand extends Command<void> {
  constructor(public readonly orderId: string) {
    super();
  }
}

export class GetOrderQuery extends Query<{ id: string; status: string }> {
  constructor(public readonly orderId: string) {
    super();
  }
}

المتحكم لاحقًا يرسل الأول على CommandBus والثاني على QueryBus. اليوم يكفي أن الملفين لا يستوردان بعضهما.

شرح المثال

void يعني أن نتيجة الأمر لا تحمل لوحة. الواجهة بعد الإلغاء تستعلم إن احتاجت الشكل الجديد. هذا يمنع معالج الإلغاء من معرفة أعمدة العرض. إن كان المسار يجب أن يرجع الجسم فورًا ونموذج القراءة هو كيان الكتابة نفسه، فدالة الخدمة في درس CRUD أصدق من أمرين متلازمين دائمًا.

ماذا يحدث داخليًا؟

  1. new CancelOrderCommand(id) كائن عادي.
  2. لا شيء يُحفظ عند البناء.
  3. الحافلة لاحقًا تطابق الصنف إلى معالج.
  4. نوع Command<void> يوثق الناتج للمستدعي.
  5. الاستعلام لا يُمرر إلى CommandBus. لكل حافلة نوع.
  6. الكائنات رخيصة. الكلفة في المعالجات والنماذج المزدوجة لا في class.

مثال عملي

IssueInvoiceCommand يحمل orderId لا جسم الفاتورة كاملًا من العميل. المعالج يحسب الضريبة. GetInvoicePdfQuery يقرأ نموذجًا مولَّدًا. العميل لا يرسل الضريبة في الأمر. هذا فرق المهمة عن DTO الذي يعكس الجدول. أبقِ DTO على المتحكم وحوّله إلى أمر بعد التحقق، حتى لا يصبح الأمر شكل HTTP.

أخطاء شائعة

  • أمر اسمه UpdateEverythingCommand بكل الحقول.
  • استعلام يحفظ «آخر مشاهدة» فيخالف القراءة.
  • منطق cancel داخل الصنف الأمر.
  • توسيع Command ثم إرجاع شكل مختلف من المعالج عن المعامل النوعي.
  • مسار CRUD بسيط صار أمرًا واستعلامًا بلا اختلاف نموذج.

متى نستخدمه؟

عندما قررت فصل المعالجات: مهمة كتابة واضحة وسؤال قراءة واضح.

متى لا نستخدمه؟

داخل BooksService.create التي ما زالت خط الأساس. لا تعِد تسمية الدالة command في تعليق وتبقِ التدفق نفسه بلا حافلة إلا للتوثيق الشخصي. إما CRUD أو أصناف الحزمة.

تمارين

تمرين سهل

ماذا يحمل KillDragonCommand من التوثيق؟

الحل

heroId و dragonId، ويمتد Command بنوع الناتج مثل { actionId: string }.

تمرين متوسط

لماذا لا ترجع لوحة الإحصاء من أمر الإصدار؟

الحل

حتى لا يعرف معالج الكتابة شكل القراءة. الاستعلام يجلب اللوحة من نموذجها.

تمرين متقدم

متى تُبقي CreateBookDto على المتحكم بدل جعل الأمر هو جسم HTTP؟

الحل

الجسم عقد HTTP قد يحوي حقولًا للعرض أو للتحقق. الأمر مهمة بعد Pipe: الحقول التي يحتاجها المعالج فقط، مثل معرف الطلب لا عمود الضريبة المحسوب.

أسئلة مراجعة

  • هل توسيع Command إجباري؟
  • أي حافلة لأي صنف؟
  • ماذا يبقى خارج صنف الأمر؟

الخلاصة

الأمر حمولة مهمة تغيّر الحالة، والاستعلام حمولة سؤال. النوع الاختياري يوثق الناتج. السلوك في المعالج لا في الكائن، والفصل بلا اختلاف نموذج لا يستحق الصنفين.

ماذا بعد؟

Handlers: من ينفذ الأمر والاستعلام وأين يُسجَّل.
