تدفق CRUD البسيط

الهدف من هذا الدرس

تثبيت التدفق الذي يكفي معظم وحدات Nest قبل CQRS: متحكم يفوض، خدمة تحمل القاعدة، مستودع أو عميل يحفظ، وكيان يحمل القيم.

المشكلة التي يحلها

فتح @nestjs/cqrs لمسار POST /books يضيف أمرًا ومعالجًا وحافلة بينما القراءة والكتابة تستعملان الجدول نفسه. توثيق الوصفة يبدأ من هذا التدفق ويصفه كافيًا للتطبيقات الصغيرة والمتوسطة. الدرس يثبّته كخط أساس حتى يكون الانتقال لاحقًا إجابة عن ألم، لا قالبًا.

الفكرة ببساطة

  1. المتحكم يستقبل HTTP ويفوض.
  2. الخدمة تطبق قاعدة العمل.
  3. الخدمة تستعمل مستودعًا أو PrismaService للحفظ والقراءة.
  4. الكيان أو DTO وعاء للقيم. إن وُجد جذر ففيه دوال قليلة، لا معالجات أوامر.

نفس الخدمة تخدم GET و POST ما دام الشكل واحدًا. لا فاصل قسري بين ملف قراءة وملف كتابة.

التعريف التقني

الوصفة الرسمية تلخص التدفق هكذا: طبقة المتحكمات، ثم الخدمات حيث أغلب المنطق، ثم مستودعات أو DAO، ثم كيانات بحقول. Nest يوفّر لهذا @Controller و @Injectable وحقن المستودع الذي بنيته.

@Controller('books')
export class BooksController {
  constructor(private readonly books: BooksService) {}

  @Post()
  create(@Body() dto: CreateBookDto) {
    return this.books.create(dto);
  }

  @Get(':id')
  findOne(@Param('id') id: string) {
    return this.books.findOne(id);
  }
}

create و findOne على الخدمة نفسها مقبولان هنا. تقسيمهما مبدأ عزل واجهات عندما يختلف المستهلك، لا لأن اختصار CQRS يطلب ملفين.

لا CommandBus في هذا المسار. النداء دالة على مزود تعرفه الوحدة. الفشل استثناء تترجمه الحافة. الاختبار inMemory أو مزيف خدمة كما في الفصل السابق.

عندما ينفصل شكل قائمة المتجر عن شكل كتابة الكتاب (مجاميع، بحث، جدول قراءة) تصبح الخدمة مكانًا ضيقًا. ذلك شرط الدرسين الأخيرين في فصل CQRS، لا شرط هذا الملف.

Mental Model

HTTP -> BooksController -> BooksService -> OrdersRepository أو Prisma
                      \-> نفس الخدمة للقراءة

سهم واحد داخل الوحدة. لا حافلات.

أبسط مثال

مقطعا المتحكم. الخدمة:

@Injectable()
export class BooksService {
  constructor(@Inject(BOOKS) private readonly books: BooksRepository) {}

  create(dto: CreateBookDto) {
    return this.books.save(new Book(dto.title, dto.priceMinor));
  }

  findOne(id: string) {
    return this.books.findById(id);
  }
}

إن كان Book بلا سلوك، فـ DTO إلى prisma.book.create داخل الخدمة ما زال هذا التدفق. لا تصطنع كيانًا فارغًا لأجل الرسم.

شرح المثال

المتحكم لا يعرف الرمز BOOKS. الخدمة مكان القاعدة («السعر غير سالب» إن وُجدت). المستودع مكان الترجمة. إضافة GET لا تحتاج صنف GetBookQuery. أضف دالة.

ماذا يحدث داخليًا؟

  1. الطلب يدخل المتحكم بعد Pipe و Guard.
  2. الخدمة تُستدعى مباشرة على النسخة Singleton.
  3. المستودع ينفذ القراءة أو الكتابة.
  4. الناتج يرجع على نفس المكدس، لا عبر حافلة.
  5. لا معالجات تُكتشف ولا أحداث تُنشر إلا إذا استدعيت ناقلًا أنت.
  6. تتبع الخطأ من المتحكم إلى الدالة أسهل من تتبع أمر إلى معالج مسجّل بالاسم.

مثال عملي

وحدة فواتير بهذا التدفق حتى تظهر لوحة تحتاج جدول invoice_view مختلفًا عن جدول الكتابة. عندها اقرأ من استعلام مخصص داخل نفس العملية أولًا، قبل حزمة CQRS. الفصل التالي يسمي الأمر والاستعلام عندما تختار الحزمة. اليوم BillingService.issue و BillingService.get كافيان.

أخطاء شائعة

  • معالج أمر لكل مسار من اليوم الأول.
  • كيان بكل حقول الجدول بلا دالة.
  • مستودع عام لأن التدفق «يجب أن يكون طبقيًا».
  • نقل القراءة إلى خدمة ثانية بلا اختلاف نموذج.
  • اعتبار هذا التدفق مضادًا للاختبار. المزيف على المستودع يكفيه.

متى نستخدمه؟

الوحدة التي تقرأ وتكتب النموذج نفسه، وفريق يستطيع تتبع الدالة.

متى لا نستخدمه؟

عندما تصبح الكتابة أحداثًا كثيرة والقراءة نموذجًا آخر مُحدَّثًا منها، أو عندما يتعدد الكتّاب على نفس القواعد بمعالجات مستقلة تختبرونها وحدها. ذلك باب CQRS لا عيب في CRUD.

مقارنة

CRUD هنا CQRS لاحقًا
الدخول دالة خدمة أمر أو استعلام على حافلة
القراءة والكتابة خدمة واحدة غالبًا نماذج مفصولة
الملفات لكل مسار قليلة معالج لكل واحد
الحزمة لا @nestjs/cqrs CqrsModule.forRoot()

تمارين

تمرين سهل

من يستدعي المستودع في هذا التدفق؟

الحل

الخدمة، لا المتحكم ولا CommandBus.

تمرين متوسط

لماذا GET و POST على BooksService ليسا خرقًا تلقائيًا؟

الحل

لأن النموذج واحد وسبب التغيير ما زال «سلوك الكتاب». التقسيم يأتي عند اختلاف الشكل أو المستهلك لا من اسم CQRS.

تمرين متقدم

لوحة البحث تحتاج أعمدة مجمّعة والكتابة تبقى جدولًا مطبّعًا. ماذا تغيّر قبل إضافة الحزمة؟

الحل

استعلام قراءة داخل الوحدة أو قارئ DTO منفصل عن save. راقب التكرار. إن صار تحديث نموذج القراءة عبئًا مستقلًا، انتقل إلى أحداث وأوامر كما في بقية الفصل.

أسئلة مراجعة

  • ما الطبقات الأربع التي يذكرها مدخل الوصفة؟
  • ماذا لا تضعه في المتحكم؟
  • ما إشارة بقاء CRUD؟

الخلاصة

CRUD في Nest متحكم وخدمة وتخزين وكيان أو DTO، على نداء مباشر. أبقِه خط الأساس حتى يختلف نموذج القراءة أو تنفجر الآثار بعد الكتابة.

ماذا بعد؟

Command و Query: كيف تسمي الكتابة والقراءة عندما تختار الفصل.
