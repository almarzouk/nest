Sorting

الهدف من هذا الدرس

السماح لـ GET /posts بترتيب النتائج بحقل واتجاه من قائمة ثابتة، مع إبقاء ترتيب افتراضي مستقر.

المشكلة التي يحلها

orderBy: { id: "asc" } يخفي المقال الجديد في آخر صفحة. إن قبلت ?sort= كنص يُمرَّر إلى Prisma، العميل يطلب عمودًا غير موجود أو حقلًا لا تريد كشفه، أو يرسل اتجاهًا يكسر الاستعلام.

الفكرة ببساطة

معاملان: sort و order. القيم المسموحة لـ sort هي id و title. القيم المسموحة لـ order هي asc و desc. الغياب يعني id تصاعديًا كما في درس الترقيم. أي قيمة أخرى 400. الترتيب يُطبَّق مع skip حتى لا تتداخل الصفحات.

التعريف التقني

import { IsIn, IsOptional } from "class-validator";

export class ListPostsQueryDto {
  @IsOptional()
  @IsIn(["id", "title"])
  sort: "id" | "title" = "id";

  @IsOptional()
  @IsIn(["asc", "desc"])
  order: "asc" | "desc" = "asc";
}

أبقِ حقول الصفحة والفلتر في الصنف نفسه حتى يبقى استعلام القائمة عقدًا واحدًا.

في الخدمة لا تبنِ المفتاح من نص مفتوح إن استطعت تجنّب ذلك. بعد @IsIn القيمة مضيّقة:

const orderBy =
  query.sort === "title"
    ? { title: query.order }
    : { id: query.order };

return this.prisma.post.findMany({
  where,
  orderBy,
  skip,
  take: query.pageSize,
});

الفرع يرضي المدقّق ويمنع مفتاحًا خارج القائمة حتى لو تعطّل الأنبوب في اختبار نسيت فيه ValidationPipe.

رتّب ثانيًا بـ id حين تختار title، حتى لا تتبادل صفوف بنفس العنوان بين الطلبات:

orderBy: [{ title: query.order }, { id: "asc" }]

Prisma يقبل مصفوفة orderBy.

Mental Model

sort=title order=asc
        |
 قائمة بيضاء
        |
 ORDER BY title ASC, id ASC
        |
 ثم skip/take

أبسط مثال

GET /posts?published=true&sort=title&order=asc&page=1&pageSize=20 HTTP/1.1

العناصر المنشورة فقط، مرتبة بالعنوان ثم بالمعرّف، وأول عشرين بعد هذا الترتيب لا قبل الترتيب.

شرح المثال

التصفية أولًا في WHERE، ثم الترتيب، ثم القطع. لو قطعت ثم رتّبت في الذاكرة لكانت الصفحة عشوائية بالنسبة للعميل. كل ذلك في استعلام القاعدة لا في Array.prototype.sort بعد جلب الكل.

الافتراضي id يناسب الإدراج الزمني التقريبي ما دام المفتاح متزايدًا. إن صار المعرّف UUID لاحقًا، الافتراضي يتغيّر إلى حقل وقت. لا تغيّره في هذا المشروع.

ماذا يحدث داخليًا؟

من غير فهرس مناسب، الترتيب على title مع OFFSET كبير يكلّف فرزًا أوسع. الجدول التعليمي صغير. الفصل 26 يربط الاتجاه والفهرس. هنا يكفي أن الاسم لا يُحقن في SQL كنص لاصق: Prisma يربط الترتيب كبنية استعلام.

تعارض مع عميل يطلب sort=body: @IsIn يفشل التحقق قبل الخدمة.

مثال عملي

ثلاثة عناوين جيم و ألف و باء كلها منشورة. sort=title&order=asc يعيد ألف ثم باء ثم جيم. order=desc يعكسها. كرّر الطلب وتوقع الترتيب نفسه، وبفضل id الثانوي لا تتبدّل صفوف متساوية العنوان. sort=password يعيد 400.

أخطاء شائعة

  • تمرير query.sort مباشرة كمفتاح من غير قائمة.
  • ترتيب في الذاكرة بعد findMany بلا take.
  • صفحات بلا ترتيب فتتغيّر عند كل إدراج في الوسط.
  • نسيان أن الفلتر والفرز يشتركان في DTO واحد.

متى نستخدمه؟

حين يعرض العميل عمودًا قابلًا للنقر، والعمود من القائمة البيضاء.

متى لا نستخدمه؟

لفرز حسب طول النص أو حسب عدد التعليقات قبل أن يوجد هذا الحقل في الاستعلام بوعي. احسبه في الخدمة أو في SQL تكتبه أنت، لا من اسم دالة يرسلها العميل.

تمارين

تمرين سهل

ما الترتيب إن غاب sort و order؟

الحل

id تصاعديًا، من قيم الافتراضي في DTO.

تمرين متوسط

لماذا يُضاف id كترتيب ثانٍ مع title؟

الحل

عناوين متساوية بلا مفتاح كسر تتبدّل بين الطلبات، فتتكرر أو تختفي عناصر على حدود الصفحات.

تمرين متقدم

عميل يريد sort=commentsCount. ماذا ينقص قبل قبول الاسم؟

الحل

حقل أو تجميع حقيقي في الاستعلام، ثم إضافته إلى @IsIn والفرع الذي يبني orderBy. قبول الاسم قبل وجود العمود يعيد 400 أو خطأ Prisma. لا تمرّر النص مباشرة.

أسئلة مراجعة

  • أي قيم مسموحة لـ sort؟
  • أين يُرفض sort=body؟
  • لماذا الترتيب قبل skip؟

الخلاصة

الترتيب قائمة بيضاء واتجاهان، مع افتراضي مستقر ومفتاح كسر id. النص الحر لا يصبح اسم عمود.
