Interceptors بعد Controller

الهدف من هذا الدرس

تثبيت طريق العودة: Interceptors من المسار إلى Controller ثم إلى العام، لأن Observable أول داخل آخر خارج.

المشكلة التي يحلها

مؤقت عام يقيس زمن الدالة إن خرج قبل مؤقت المسار سيرى زمنًا ناقصًا أو مكررًا. طريق الدخول كان من العام إلى المسار. الخروج عكسه، والقيمة المعادة أو الخطأ يصعدان في هذا العكس. معاملة الخروج كترتيب @UseInterceptors المكتوب على الملف تقلب القياس.

الفكرة ببساطة

بعد Service، البند 8: Interceptor المسار، ثم Interceptor الـ Controller، ثم العام. إن تعددوا داخل المستوى، فترتيب الدخول كان ترتيب الربط، والخروج يعكسه أيضًا لأن كل غلاف يحيط بالذي يليه.

التوثيق يلخص المستويات: 8.1 المسار، 8.2 Controller، 8.3 العام. أغلفة الدخول G1 ثم G2 ثم C1 ثم R1 تخرج R1 ثم C1 ثم G2 ثم G1.

التعريف التقني

القيمة التي ترجع من المعالج تصدر من أضيق Observable إلى الأوسع. Interceptor يقدر أن يبدّل القيمة في طريق الصعود، مثل إضافة حقل وقت، ما دام الأسلوب القياسي شغالًا.

@Res() من غير passthrough يوقف هذا التعاقد: أنت تكتب الرد، و Interceptors التي تعتمد على القيمة المعادة لا ترى السلوك القياسي. passthrough: true يبقي الصعود.

خطأ من الدالة أو الخدمة أو Pipe يصعد في الأغلفة نفسها عبر catchError بدل قيمة نجاح. معالج catchError الذي يرجع قيمة بديلة يكمل كنجاح من تلك النقطة إلى الأغلفة الأوسع. الذي يعيد الرمي يبقي الاستثناء لـ Exception Filters.

Guards لا تشارك في هذا الصعود؛ هي انتهت قبل الدخول إلى اللف.

كتابة map و tap فصل Interceptors. هنا اتجاه الصعود فقط.

Mental Model

دخول: G1 -> G2 -> C1 -> R1 -> Pipes -> الدالة
خروج: R1 -> C1 -> G2 -> G1 -> طبقة الاستجابة

أبسط مثال

import { Controller, Get, UseInterceptors } from '@nestjs/common';
import { LoansService } from './loans.service.js';
import { C1 } from './c1.interceptor.js';
import { G1 } from './g1.interceptor.js';
import { G2 } from './g2.interceptor.js';
import { R1 } from './r1.interceptor.js';

@UseInterceptors(C1)
@Controller('loans')
export class LoansTimingController {
  constructor(private readonly loans: LoansService) {}

  @UseInterceptors(R1)
  @Get('open')
  open() {
    return this.loans.openList();
  }
}

افترض الربط العام @UseInterceptors العالمي أو APP_INTERCEPTOR بالترتيب G1 ثم G2. الدخول G1 ثم G2 ثم C1 ثم R1. الخروج بعد openList هو R1 ثم C1 ثم G2 ثم G1.

شرح المثال

  • openList تعيد قائمة فتصعد JSON بعد آخر غلاف، برمز 200.
  • R1 أول من يستطيع استبدال القائمة.
  • G1 آخر من يراها قبل إرسال Nest.
  • قياس في G1 على طريق الخروج يشمل ما استهلكته الأغلفة الداخلية بعد رجوع الدالة، لا Middleware التي سبقت اللف.

ماذا يحدث داخليًا؟

الاشتراك في الـ Observable الخارجي يشغّل الداخلي حتى الدالة. عندما تُحل القيمة تُطبق عمليات الغلاف الداخلي أولًا ثم الخارجي. هذا معنى أول داخل آخر خارج على طريق الاستجابة، وهو ما يلخصه التوثيق بـ «من المسار إلى Controller إلى العام».

عدة Interceptors في @UseInterceptors(G1, G2) على المستوى العام: G1 دخل أولًا لذا خرج آخرًا. لا حاجة إلى قاعدة ثانية غير اللف.

بعد آخر غلاف عام تأخذ طبقة الاستجابة القيمة: كائن أو مصفوفة إلى JSON، وقيمة أولية كما هي، ورمز 200 أو 201 لـ POST. @HttpCode و @Header ما زالا جزءًا من ذلك الإرسال.

مثال عملي

غلاف مسار يضيف handled: true وغلاف عام يضيف tookMs. العميل يرى الحقلين لأن العام يخرج آخرًا ويرى كائن المسار بعد الإضافة. إن أضاف العام الحقل ثم استبدله غلاف المسار، فالترتيب المقلوب يعني أن المسار يعمل أولًا في الخروج ولا يرى حقل العام بعد. ضع الإضافة النهائية على الغلاف الأوسع.

رمي openList لا يمرر القائمة على map النجاح. catchError في R1 إن رجعت { handled: false } يراها C1 ثم G2 ثم G1 كقيمة. المرشح لا يعمل.

أخطاء شائعة

الخطأ الأثر
إضافة حقل نهائي داخل Interceptor المسار وتوقع أن العام سبقه العام يلف من الخارج ويخرج آخرًا
قياس Middleware داخل غلاف الخروج Middleware خارج سلسلة Observable هذه
@Res() بلا passthrough وتوقع map على القيمة الأسلوب القياسي متوقف
اعتبار ترتيب الخروج نسخة من ترتيب Guards Guards بلا صعود قيمة

متى نستخدمه؟

لتعديل القيمة بعد القاعدة أو لقياس يشمل الدالة: حقل استجابة، زمن، أو تسجيل الناتج. الأوسع يحيط بالأضيق في القياس الكلي.

متى لا نستخدمه؟

لمنع الطلب. الحارس انتهى. لتحويل id قبل الخدمة. Pipe سبقت الدالة. لرد خطأ بعد استثناء غير ممسوك. ذلك Exception Filter، إلا إذا اخترت أن catchError يحوّل الخطأ إلى قيمة ويكمل نجاحًا.

مقارنة

الاتجاه الترتيب
دخول Interceptor عام، Controller، مسار
خروج Interceptor مسار، Controller، عام
داخل المستوى عند الخروج عكس ترتيب الربط
Exception Filter بعد أن يبقى الخطأ غير ممسوك، لا على طريق القيمة

تمارين

تمرين سهل

من يرى القيمة أولًا بعد return من الدالة: Interceptor المسار أم العام؟

الحل

Interceptor المسار. العام آخر أغلفة الخروج.

تمرين متوسط

العام مربوط G1 ثم G2. أي منهما يلمس القيمة آخرًا؟

الحل

G1. دخل أولًا فخرج آخرًا داخل المستوى نفسه، وبعده لا غلاف Interceptor.

تمرين متقدم

R1 في catchError يرجع { ok: false } بعد رمي الخدمة. ماذا يصل إلى G1، وهل يعمل مرشح المسار؟

الحل

G1 يرى { ok: false } كقيمة صاعدة من الأغلفة الأضيق. مرشح المسار لا يعمل لأن الاستثناء مُسك وأُبدِل بقيمة.

أسئلة مراجعة

  • ما البنود 8.1 و 8.2 و 8.3؟
  • لماذا G1 يخرج بعد G2 إن رُبطا بهذا الترتيب؟
  • متى لا تصعد القيمة في هذه الأغلفة بالأسلوب القياسي؟

الخلاصة

بعد الخدمة تصعد القيمة من Interceptor المسار إلى Controller ثم العام، وعكس الربط داخل المستوى، لأن Observable أول داخل آخر خارج. آخر غلاف عام يسبق إرسال Nest. الخطأ غير الممسوك لا يكتمل كقيمة نجاح.
