# متى يُتخطى باقي المسار

## الهدف من هذا الدرس

حصر الحالات التي لا تكمل فيها الدورة حتى الاستجابة القياسية: منع، رمي، إنهاء مبكر، أو كتابة الرد بنفسك.

## المشكلة التي يحلها

مؤقت على Interceptor لا يسجل `PATCH`، أو JSON لا يخرج رغم `return`. السبب غالبًا أن مرحلة سابقة أوقفت الطريق أو أن `@Res()` أخرج الإرسال من Nest. من غير قائمة التخطي تبدو الدورة «ناقصة ترتيب» وهي سارت حتى نقطة قطع.

## الفكرة ببساطة

طريق النجاح كامل فقط عندما تنادي كل مرحلة التالية ولا يُرمى استثناء غير ممسوك ولا يُنهى الرد من الخارج. أول قطع يترك ما بعده في قائمة النجاح. المرشحات بديل عن الباقي عند الاستثناء، لا خطوة إضافية بعد نجاح.

## التعريف التقني

الحالات:

1. Middleware لا تنادي `next()` وتنهي الرد. Guards وما بعدها لا تبدأ.
2. Middleware ترمي. لا مرشح مسار ولا Controller. Exception Filter العام فقط.
3. Guard يعيد `false` أو يرمي. Pipes والمعالج والخدمة لا تبدأ. المرشحات تُفحص من المسار إلى العام لأن المسار معروف.
4. Pipe ترمي. الدالة والخدمة لا تُستدعيان. `catchError` في Interceptor الدخول قد يمسك. إن بقي الرمي فالمرشحات من المسار صعودًا.
5. المعالج أو Service يرمي. طريق خروج النجاح لا يحمل قيمة. الأغلفة ترى الخطأ، ثم المرشحات إن بقي غير ممسوك.
6. `try/catch` أو `catchError` الذي يرجع قيمة. المرشحات لا تعمل، والطريق يكمل كنجاح من نقطة الإمساك.
7. `@Res()` أو `@Next()` من غير `passthrough`. أنت تكتب الرد بـ `res.send` أو ما يعادله. من غير إرسال يعلق الطلب. Interceptors والتسلسل القياسي على القيمة المعادة لا يعملان كالمعتاد. `passthrough: true` يعيد القيمة إلى Nest ويكمل الإرسال القياسي.

لا تُضاف حالة «Filter يعمل بعد 200». النجاح لا يدخل البند 9.

## Mental Model

```text
قطع في Middleware     -> لا Guard ولا Pipe ولا دالة
قطع في Guard          -> لا Pipe ولا دالة، ونعم مرشحات المسار
قطع في Pipe أو الدالة -> لا قيمة نجاح، والمرشح إن بقي الخطأ
@Res() بلا passthrough -> الرد من كودك لا من تسلسل Nest
```

## أبسط مثال

```ts
import { Controller, Get, Res } from '@nestjs/common';
import type { Response } from 'express';
import { LoansService } from './loans.service.js';

@Controller('loans')
export class LoanExportController {
  constructor(private readonly loans: LoansService) {}

  @Get('export.csv')
  exportCsv(@Res() res: Response) {
    res.type('text/csv');
    res.send(this.loans.csv());
  }
}
```

## شرح المثال

- `export.csv` لا يسلسل كائنًا عبر طبقة Nest. `res.send` هو النهاية.
- Interceptor ينتظر قيمة `return` لا يرى هذا الجسم بالأسلوب القياسي.
- نسيان `send` يعلق العميل، وهذا قطع ناقص لا استجابة.
- `@Res({ passthrough: true })` مع `return` كان سيبقي التسلسل. المسار هنا اختار الوضع الآخر عمدًا.

## ماذا يحدث داخليًا؟

Nest بعد اكتشاف `@Res()` أو `@Next()` تعطّل الإرسال القياسي لذلك المعالج. مراحل ما قبل الدالة، من Middleware حتى Pipes، تبقى كما هي إن لم تُقطع هي أيضًا. القطع في البند 7 قطع للإرسال لا حذف لـ Guard. حارس فاشل ما زال يمنع الدخول إلى `exportCsv`.

عند الرمي، التوثيق: تُتخطى بقية الدورة ويذهب الطلب إلى المرشح. أغلفة Interceptor جزء من طريق الخطأ عبر `catchError`، لا استثناءً من هذه القاعدة عندما تعيد الرمي.

إنهاء Middleware للرد يعني أن اختيار المسار قد لا يحدث، فيصدق عليها قيد المرشح العام إن كان هناك رمي، أو لا مرشح أصلًا إن كان الرد نجاحًا مبكرًا عبر كائن المنصة.

## مثال عملي

`PATCH /loans/9` بأربع نهايات:

| النهاية | ما لا يعمل |
| --- | --- |
| `MemberGuard` يعيد `false` | Pipe و `update` وخروج النجاح |
| `ParseIntPipe` ترمي | `LoansService.update` |
| الخدمة ترمي والمرشح على الدالة يمسك | المرشح العام لهذا الاستثناء، وقيمة JSON نجاح |
| المعالج `@Res()` بلا `passthrough` ويعمل `send` | تسلسل `return` و Interceptor القيمة |

الرابعة ما زالت تمر على الحارس والـ Pipe إن نجحا. التخطي فيها في طبقة الإرسال لا في رأس القائمة.

## أخطاء شائعة

| الخطأ | الأثر |
| --- | --- |
| تفسير صمت Interceptor الخروج على CSV كخلل ترتيب | `@Res()` أوقف الأسلوب القياسي |
| توقع `LoanPatchFilter` بعد `app.use` | المرشح العام فقط |
| اعتبار `false` من Guard نجاحًا فارغًا | استثناء رفض ثم مرشحات |
| إمساك الخطأ وإعادة `{ ok: false }` ثم البحث في المرشح | الطريق أصبح نجاحًا |
| `next()` مع كتابة الرد من Middleware | خطر نهايتين؛ اختر قطعًا واحدًا |

## متى نستخدمه؟

عند تشخيص «لماذا لم تعمل المرحلة السفلى». ابحث عن أول قطع: `next`، Guard، رمي، `catch`، أو `@Res()`.

## متى لا نستخدمه؟

لا تقطع الطريق بـ `@Res()` لمسار JSON عادي حتى تتجنب Interceptor. أعد القيمة. ولا تبتلع الاستثناء لتفادي مرشح ثم تعِد بناء شكل الخطأ يدويًا في كل Service.

## مقارنة

| القطع | المراحل التي تبقى خارج التنفيذ |
| --- | --- |
| Middleware تنهي الرد | من Guards حتى الاستجابة القياسية |
| Guard يرفض | Pipes والدالة وخروج النجاح |
| Pipe أو خدمة ترمي | ما بعد نقطة الرمي في طريق النجاح |
| إمساك متعمد | مرحلة المرشحات |
| `@Res()` بلا `passthrough` | إرسال Nest و Interceptors القيمة |

## تمارين

### تمرين سهل

لماذا لا تُسلسل Nest كائن `return` في `exportCsv`؟

<details><summary>الحل</summary>

`@Res()` بلا `passthrough` يضع المعالج في وضع المكتبة. `res.send` يكتب الجسم، والأسلوب القياسي متوقف.

</details>

### تمرين متوسط

حارس أعاد `false` و Pipe على `:id` لم تُسجَّل في السجلات. هل الترتيب مكسور؟

<details><summary>الحل</summary>

لا. Pipes بعد Guards. الرفض يتخطاها وينقل استثناء المنع إلى المرشحات من المسار إلى العام.

</details>

### تمرين متقدم

Middleware عام كتب JSON خطأ ورمي. أي مرشح على `LoansController` سيغير ذلك JSON؟

<details><summary>الحل</summary>

لا مرشح على Controller. الاستثناء قبل اختيار المسار فيراه Exception Filter العام فقط. كتابة JSON من Middleware ثم الرمي قد تنتج نهاية مزدوجة؛ القطع الأنظف إما `next()` أو إنهاء من غير رمي يعتمد على مرشح مسار.

</details>

## أسئلة مراجعة

- ماذا يتخطى Guard عند `false`؟
- متى تُتخطى المرشحات رغم وجود خطأ في الخدمة؟
- ماذا يفقد `@Res()` من غير `passthrough`؟

## الخلاصة

باقي المسار يُتخطى عند إنهاء Middleware، أو رفض Guard، أو رمي غير ممسوك ينتقل إلى المرشحات، أو عند إمساك متعمد يكمل نجاحًا. `@Res()` بلا `passthrough` يترك لك الإرسال ويبعد التسلسل و Interceptors القيمة عن السلوك القياسي.
